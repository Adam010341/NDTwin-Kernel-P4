### 3. Diagnosis: (a)

**What the "3505th packet" is: none goes on the wire.**
- In iperf 2.1.9 (`iperf -v`), "Sent 3500" is one more than the datagrams actually sent. OBSERVED in all 8 acked rounds: the client says Sent 3500 and the server reports 0/3499.
- Three independent counters agree on 3499 datagrams:
  - **s1 ingress bytes.** Bytes = 5×98 + 3499×1242 exactly (`table.out`, bytes column = 3499.000). A datagram is 1200 + 8 + 20 + 14 = 1242 bytes; a ping is 98.
  - **s2 egress 100** equals s1.
  - **h2's link.** The netdev delta on s2-eth1 is 4346031 = 3499×1242 + the 273-byte background seen on every idle port (OBSERVED, `$R/2026-09-26T155814Z_p4runtime_solution_ndtwin/link_usage/netdev.*`).
- **INFERRED:** the client counts the FIN (or one extra id) in "Sent". I could not check this against iperf's source.
- There are no pcaps in the round directories.

**Why 081205Z alone reads 3505: one FIN retransmission.**
- s2 ingress 200 = 7 packets / 830 bytes = 5×98 + 2×170, i.e. two server reports instead of one (OBSERVED, `table.out`).
- h2's link got exactly +1242 bytes more than usual (s2-eth1 delta 4347273 vs 4346031).
- h1's link got exactly +170 bytes (s1-eth1 613 vs 443).

It matched "pings + Sent" by coincidence.

**The last block is the read after traffic ended (INFERRED, from timing and counts).**
- The controller reads every 2 s (`~/tutorials/exercises/p4runtime/solution/mycontroller.py:204-210`) and writes unbuffered (`drive_exercise.py:1623`).
- The step between the last two reads is about 234-250 packets, against about 437 per full interval, so traffic stopped inside that interval.
- s1 = pings + the server's Total, and s2e = s1.
- The controller log's last write is about 0.9 s after the iperf files (mtimes in `R/2026-09-26T155814Z…`).
- The controller is stopped right after the link-usage cell, so a repeated block never gets printed.

**Not (b).** Today's final block is byte-identical to the 6 earlier 3504 rounds, from 09-19 to 09-26, which ran on other code and without B. Both trunk-only controls show it too.

**The outliers fit (a) as well:**
- **175425Z is genuinely mid-traffic.** s2e is 3821 while s1 is 3820, and 315 extra 1242-byte frames reached h2's link (+301×1242 bytes in netdev). The source is unexplained (INFERRED).
- **The four 09-19 rounds are failed rounds.** Forwarding broke, the counter stopped at 3, and there is no server report.

### 5. A correct rule (described only, not written into any code)
Derived from the 12 frozen rounds alone. The last block is settled iff:
- (i) it repeats the block before it; **or**
- (ii) the client got the server's ack (a Server Report present, no "did not receive ack"), **and** s2 egress 100 = s1 ingress 100 in that same block (nothing between the two switches), **and** pings + D ≤ s1 ingress 100 ≤ pings + D + 10.
  - D = the server report's Total, which equals Sent − 1 in 8 of 8 acked rounds.
  - The +10 allows FIN retransmissions, which can happen even when acked, as in 081205Z.
  - With no server report, only (i) can settle the block. There is no earlier no-ack round with traffic flowing, so that case rests on no data (stated as such).

**Compared with the current rule: neither tighter nor looser.**
- Looser on the count: it accepts 3504..3514, not exactly 3505.
- Tighter in that it adds s2e = s1, and with no ack it accepts only a repeat.

**On the 12 frozen rounds (`proposed.out`):**
- It settles the 7 rounds that ended after traffic: six at 3504 plus 081205Z.
- It still rejects 175425Z and the four failed 09-19 rounds, which are the ones that really are mid-traffic or have no reading after traffic.

**Today's three logs:** all three would pass the settled check under this rule (s1 3504 in [3504, 3514], s2e = s1, acked). Nothing beyond that was computed or looked at.
