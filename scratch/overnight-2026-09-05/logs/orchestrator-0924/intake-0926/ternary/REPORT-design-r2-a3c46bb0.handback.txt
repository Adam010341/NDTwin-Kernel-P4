## Revised questions for Adam (DESIGN.md §8)

**Q1. How does the proxy tell a proxy restart on a running fabric from a brand-new fabric?**
- (a) [recommended] Pipeline cookie. The proxy sets a cookie on every push and reads it with COOKIE_ONLY before the next push.
  - A0 08 measured that this works: the cookie reads back; a push without a cookie clears it; a fresh bmv2 answers FAILED_PRECONDITION.
  - Gains: proxy-only, no shell or root changes, decided per switch, and it covers both the ndt and stack.sh bring-up paths.
  - Costs: every push must carry the cookie. A switch that was power-cycled but not yet readopted, at the moment the proxy restarts, is treated as a new fabric, so its API entries are quarantined and reported.
- (b) The p4_testbed_topo.py bring_up step writes a fabric_id into the switch manifest.
  - It covers both paths only if stack.sh's script is p4_testbed_topo.py (inferred).
  - Unknown: whether the power helper keeps keys it does not know about.
  - Cannot cover a fabric that has no manifest.
  - Root must not write into .run/.
- (c) `ndt up` quarantines the journal itself.
  - The stack.sh path would not quarantine, so yesterday's rules would come back.
  - Unlike what r1 claimed, this is not a call site for `quarantine()`.
- (d) Record the bmv2 pid per entry. Breaks on power-cycle and when there is no manifest.
- (e) No scoping at all. Not recommended.

**Q2. May the generic writer write tables NDTwin owns?**
- (a) [recommended] No: answer 409 owned_by_ndtwin, enforced in write_table_entry.
  - This fixes the catch-all defect and keeps the journal and kernel routing on disjoint tables.
  - Cost: POSTs that answer 200 today (baseline ipv4_lpm, empty-match flow_5tuple) would answer 409. Every success-path test in test_table_entry_route.py that posts AN_LPM_ENTRY flips, and so do the test doubles in test_p4_client_writes.py.
  - Sub-choice (a-i) [recommended]: keep the 8-1 exception for default actions. Without it, bring-up C comes up with `failed = 1`.
  - Sub-choice (a-ii): no exception.
  - Sub-choice (a-iii): does the roles ticket's "do not edit existing fixtures" rule (p4_client.py:255-257) still hold? Recommended: lift it for those test doubles only, so they can call `bind_routes` explicitly.
- (b) Block only flow_5tuple.
  - Still a behaviour change.
  - API entries in ipv4_lpm would be overwritten by the next link change.
  - A baseline readopt replay must be added before main.py:1743.
- (c) Allow everything and only disclose.
  - The defect stays.
  - insert_5tuple_rule's MODIFY fallback silently overwrites operator entries with the same key.
  - Also needs the baseline readopt replay.

**Q3. The second spelling of don't-care (mask 0, full range, lpm /0)?**
- (a) [recommended] Refuse with 400 and "omit the field".
  - bmv2 itself already refuses all three (A0 04/05). This only moves the refusal from 502 UNKNOWN to a clear local 400.
  - As far as the evidence shows, no existing file needs changing.
- (b) Normalise to omission.
  - NDTwin would then accept what bmv2 refuses, and be looser than the tutorials' own controller.

**Q4. What should the response be when the journal write fails?**
- (a) [recommended] 200 with `journaled: false`, increment `failures`, and report the switch as `journaled: false` for the rest of the boot.
  - Consequence: a missing line can make a later fold wrong, and the entry it covered would be lost.
- (b) Roll back and answer 507. Infeasible: modify and delete cannot be rolled back.

**Q5. Journal PRE/multicast writes too?**
- (a) [recommended] Not in this cut.
- (b) If done, a replay would silently overwrite a package group with the same id: the MODIFY fallback is at p4_client.py:932-946 and :1026-1046, and package PRE entries are applied on every switch. Needs that fixed first, about 150 extra lines.
