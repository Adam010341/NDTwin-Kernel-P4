**2026-08-20 mainDev v2 自陳（未 commit 時發現）。** `7eb54d5` 的 clone A/B：`noclone` 控制組
在 warm fabric 上重跑，量到 kernel 67.7% / proxy 26.6% / bmv2 161.6%——與 1/64 **開著取樣**
那格（67.9% / 26.6%）不可區分，twin 仍有 2352 筆非零讀值、峰值 296.8 Mbit/s。
**控制路徑跑對了**（proxy log 10 次 `DELETED (A/B control)`、0 次 `installed`、env var 在），
**是刪除本身無效**。

**機制寫在它呼叫的那個函式的 docstring 裡**（`p4_proxy/proxy_agent/p4_client.py:294-324`，
2026-08-16 就實測寫下）：pipeline commit 清空 P4Runtime 的 clone-session 簿記，target PRE 的
孤兒 mgroup 存活 → **打在空簿記上的裸 DELETE 是 no-op，碰不到那個 group**。
正解就是 `79e4f69` 已經加好的 `DELETE → INSERT → settle(DELETE+INSERT)`——
A/B 控制組繞過了修好的路徑，自己送裸 DELETE。見 [[proxy-restart-warm-fabric-multiplies-telemetry]]。

**波及**：`trunc128` 的下一格才是 `noclone`，而 trunc128 本來就沒遙測，所以那格分不出
「session 被刪掉」與「上一格的截斷 session 還在」。**沒有有效的零點**，由零點外推的
「206 µs/樣本」「5,300 樣本/秒天花板」「39 個百分點固定階梯」全部撤回。
**存活的**是取樣率掃描：clone 產生率 16× 變動（34.7→556.1 樣本/秒）、bmv2 CPU 在雜訊內不動、
五個取樣率吞吐都 200.0 Mbit/s——這條不需要任何東西被正確刪掉。

**Why:** 這是「回報成功但沒動作」的**第三個實例**（前兩個：
[[power-on-reports-success-without-acting]]、以及反面的 [[rejected-requests-can-still-act]]）。
更重的一層是：**一個實驗的控制組可以無聲地沒有生效，而所有 log 都說它生效了。**

**How to apply:** ①**控制組必須斷言自己生效**——不是斷言指令送出去了，是斷言被移除的東西
真的不見了（這裡＝讀回 clone session／看 twin 是否歸零），和
[[injections-must-assert-their-own-success]] 完全同一條規矩，只是換到 A/B 的移除端。
②**移除型 A/B 在 warm fabric 上不可信**，除非走已修好的 settle 路徑或重建 fabric。
③ 純讀文件的複審抓不到這種東西：Muse Spark 1.2 把這格評為 PASS、稱它是
「the strongest inference in the suite」、還明寫「不要先攻擊 CPU sweep」，
而它是唯一真正斷掉的一格——[[live-runs-find-what-tests-cannot]] 的再一次印證，
這次的「測試」是一份 62 KB 的證據審查。

## ✅ 2026-08-20 傍晚：已解決，並且量到了原本拿不到的東西

**冷啟重跑（`mzero_poll` / `mzero_nopoll`，各 300 s，16:45:07–16:55:11）拿到有效零點。**
關鍵是加了一步先前沒有的檢查：**在量測開始前先跑流量、確認 twin 讀到 0**。
結果 32 條 inter-switch 邊、**0 筆非零讀值**，而 200 Mbit/s 正在跑 → 控制組確實生效。

| | kernel |
|---|---|
| 零取樣（poll-off） | **2.8%** |
| 1/1024（34.7 樣本/秒） | 49.1% |

🔑 **所以「打開取樣本身要付固定成本」是真的，而且是 46.3 個百分點**（0.46 顆核），
而線性斜率只預測 0.7 點。**線不會延伸到零**（外推 48.5% vs 實測 2.8%）。
內部一致性：零點的輪詢成本 +7.7 點，落在取樣格子的 6.3–8.0 區間內（輪詢是 HTTP 工作，
本來就該與取樣率無關）。

**操作規則（這是留得住的部分）**：
1. **clone session 的控制組必須連 fabric 一起冷啟**。只重啟 proxy 不夠——warm fabric 上
   leading DELETE 打在空簿記，孤兒 PRE group 存活，取樣照跑。
2. **量測前先驗證控制組生效**，不要量完才發現。今天這一步是唯一的差別。
3. 我曾經因為證據無效而**撤回**這個階梯，然後拿到有效證據後**又確認它**。撤回當時是對的
   （證據確實無效）；重點是兩次都要說清楚依據，不要因為怕反覆就不撤。

相關：[[proxy-restart-warm-fabric-multiplies-telemetry]]（同一個孤兒 group 機制的另一面）

## 🔴 2026-08-20 深夜補記：同一輪還有**第二個**失效控制組，而且天花板永久出局

**`mnone` 那對也不是零點。** 矩陣本來設計了第六對當截距：跑在 `NDTWIN_CLONE_DISABLE=1` 底下。
**那個 env var 從來沒生效**——twin trace 有 2,352 筆非零讀值、480,540,662,784 counter-units、
**實測 553.5 樣本/秒**（1/64 那格是 556.1）。它是 **1/64 的複製品戴著零點的標籤**，
CPU 也對得上（67.7/60.0 vs 67.9/60.1）。

所以同一輪裡有**兩個**用不同機制失效的控制組：`noclone`（裸 DELETE 打空簿記）和
`mnone`（env var 沒生效）。前者已寫在上面，後者是新的。
`plot_figures.py` 早就抓到並換成 `mzero`，但 **`analyse_matrix.py` 沒有**——它到今晚為止
還把 `mnone` 印成 `none` 那一列**而且拿它一起做回歸**。兩個 reader 讀同一份證據、
走不同程式碼，就是這個 repo 反覆生產缺陷的形狀（見 [[verify-against-known-good-output]]）。

🔑 **「5,300 樣本/秒天花板」是永久撤回，不是暫時的。**
拿到有效零點**不會**讓它復活——恰恰相反，有效零點**證明**那條線不通過原點：
擬合截距 48.5% vs 實測 2.8%，差 45.6 點 ＝ 65× 雜訊地板。
所以 206 µs/樣本 只是 **34.7–556.1 樣本/秒之間的邊際成本**，
拿一顆核除以它得到的「~4,900 樣本/秒」**不是容量**——它把線外推穿過一個從沒量過、
而且在唯一被檢查的那一端已知錯 46 點的區間。

**Why:** 我差一點犯的錯是「證據補齊了 ⇒ 原本的結論復活」。真正的關係是
**新證據決定舊結論的生死，方向可以是任一邊**：這次它救活了「固定階梯」（46.3 點），
同時**永久殺死**了由同一條線外推出來的天花板。同一份資料，兩個相反的裁決。

**How to apply:** ① 宣告某格是零點之前，**讀它的 twin sum**，不要讀它的標籤或它的 env var。
`analyse_matrix.py` 現在會印 `NOT A ZERO -- do not fit through it`。
② **斜率不可外推到沒量過的區間**，除非零點證明線通過那裡。報告裡任何「N 樣本/秒天花板」
都要先問「這條線在 0 附近被驗證過嗎」。
③ 這格的 poll-off 臂（`netdev_only.py`）**自己沒有 twin 讀值**，零是從 poll-on 臂繼承的——
繼承要驗：兩臂只能差一個輪詢成本，實測差 7.7 點對上矩陣的 6.3–8.0。
