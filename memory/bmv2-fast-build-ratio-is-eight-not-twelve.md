# 12× 有一部分不是 build 的功勞（工單 ①／①b，2026-08-29 收案）

正本 `doc/audit/2026-08-28_single-switch-build-ratio/`（`PREREG.md`／`PREREG-1b.md`／
`FINDINGS.md`／`FINDINGS-1b.md`），commit `52d87ee` `e82ac6f` `eb71e36`，raw `714f98a` `ff9206c`。

## 結果

| | 條件 | 比值 |
|---|---|---|
| 08-15 舊量測 | **三跳生產路徑**、控制平面活著 | **12×**（UDP 零損點，1400 B） |
| **①b（四臂）** | **單跳**、控制平面**仍然活著** | **R = 8.0**（stock 45 M、fast 360 M） |
| 膝蓋內插修正 | 同上 | **≈ 7.8** |
| 梯階量化區間 | | **(5.14, 12.0)** |

**六個 stock 臂全部 45、四個 fast 臂全部 360，兩側零散布。** 落在註冊的 **H2**。

⇒ **論文的口徑（三件不准做）**：不准只報 12×；不准只報 8.0× 而不講它是單跳；
**不准把差額歸因給路徑或控制平面**——這一輪只拆了「三跳→單跳」這一個變數，
**控制平面是刻意保持活著的**（一次動一個變數）。差額歸屬＝**已註冊的另一輪**。

📌 **只對 12×（UDP 零損點）比**，不要對「12–18×」——那是**跨指標的範圍不是信賴區間**，
見 [[benchmark-must-name-the-binary-it-measured]]。

## 🔴 第一次沒量到，而那件事被保留下來當結果

① 第一輪：fast 兩臂在**梯尾 360 仍乾淨、從未觸發飽和停止規則**
⇒ **分子是儀器能吐出的最大值，不是量到的零損點**。R ≥ 8.0，三個註冊結局一個都裁不了。

**根因（mainDev 自己找到的，講得比我好）**：PREREG 把梯子**往下**延伸去涵蓋 stock 預期的 25 M，
**沒有人問過拿掉兩跳之後頂端夠不夠涵蓋 fast**。
> **梯子只對著慢的那一臂檢查過。**

**①b 的判準（為什麼這次可以加梯階，而 ③ 不行）**：

| | ③ 的 n=1 | ① 的 fast |
|---|---|---|
| 存活的宣稱需要那個天花板？ | ❌ 不需要（每流曲線同一把尺量五格） | ✅ 需要（整個問題就是比值） |
| 加梯階是為了 | 救一個已撤回的比值 | 讓儀器構到註冊的量測範圍 |
| **事前知道的話會這樣設計嗎** | ❌ 不會 | ✅ **顯然會** |

⇒ **「儀器構不到註冊的問題」＝修 bug，可以重跑；「答案落得不順眼」＝不准重量。**
①b 之後 8.0 落在 H1/H2 邊界旁邊，**沒有再跑更細的梯子**，因為那屬於後者。

**防呆做法**：①b 的梯子**沒有固定頂端**，×1.5 一直爬到**已註冊的停止規則觸發**為止
⇒ **頂端由規則決定、不由人決定**，所以沒有人能把它選到讓 R 落進想要的區間。
（實跑爬到 810 M 才停，fast 的 360 一動沒動。）

🔑 **而那道防護事後看是沒有承重的——這不代表它是浪費**：
> **它的價值不在於它擋下了什麼，而在於它讓「沒被擋下」變成證據。**
> 沒有它，「加長之後 R 沒變」和「我們選了一個讓 R 不變的頂端」無法區分。

## 🔴 兩條可重用的判準（比 8.0 這個數字重要）

### 1. **複製救不了量化。平均對量化無效。**

我原本接受了 mainDev 的「撐住 8.0 的是複製（十臂零散布）」——**那句話是錯的，已撤回。**
梯子量的是「loss <0.5% 的最高階」⇒ 真值落在**該階與下一階之間**
（stock ∈ [45,70)、fast ∈ [360,540) ⇒ R ∈ (5.14, 12.0)，**而邊界 9 就在裡面**）。

**十臂落在同一階，只證明那一階穩定，對「真值在該階區間裡的哪個位置」零資訊。**
不確定性的來源是**量化不是雜訊** ⇒ 加臂數永遠收窄不了它。

### 2. **有硬邊界的決策規則，必須註冊「區間跨過邊界 ⇒ 報不可分辨」那一支**

①的 H1/H2/H3 對**點估計**是窮盡的，卻沒有這一支——**而 PREREG §4 自己就寫過
「比值繼承兩次 ±20% ⇒ ±45%」**。8.0 ± 45% 跨界。⇒ **缺陷在決策規則不在臂。**
這就是 [[controls-decide-what-you-learn]] 的「判準要留以上皆非」在比值上的形態。

## ✅ 用既有資料收窄（沒有新實驗）

**下一階的 loss 帶有真值位置的資訊**：超標越多 ⇒ 越過交叉點越遠 ⇒ 真值越貼近下界。

| | 乾淨階 loss | 下一階 loss | 線性內插交叉點 | 在區間裡的位置 |
|---|---|---|---|---|
| stock ×4 | 0.0000–0.3174% | **4.44–24.49%**（70 M） | 45.2–47.8 | **底部 0.8–11.3%** |
| fast ×2 | 0.1540 / 0.3275% | **25.80 / 26.62%**（540 M） | 361.2–362.4 | **底部 0.7–1.3%** |

⇒ **R ≈ 7.8**。⚠️ **凸曲線上的線性內插給的是交叉點的下界不是估計值**
（真曲線先平後陡 ⇒ 實際交叉更晚）；兩側同向偏誤、R 是比值 ⇒ 部分抵銷。
**這是佐證不是量測**，文件裡逐字寫明。

📌 **修正方向值得注意：8.0 → 7.8 是往「更深地落進 H2」修，離好講的 H1 更遠。**
加長梯子（①→①b）也一動沒動 fast 的 360。**兩次修正都沒往對我們有利的方向走。**

## ⚠️ 如實揭露的兩條

- **註冊的鏡像（8 臂）兩輪都沒跑**（各 4 臂：交錯、每 build 兩臂、同 build 不相鄰；
  每臂要自己一個 fabric 世代、額度不足）。**沒有寫成註冊設計。**
- **binary 來源比最強形式弱一級**：`/proc/<pid>/exe` 這個 uid 讀不到
  ⇒ 退回 argv ＋ 與 override 檔交叉比對、不一致中止，每臂記 sha256。
  ✅ 但 **build 簽章是雙向驗過的**（`EventLogger` fast=0／stock=24，**錯標籤實測 exit**），
  而 §3 註冊的負面對照 `3367d0e9` 是 kernel binary、**分不出兩顆 bmv2**——那個缺口是 mainDev 自己抓到並補的。
