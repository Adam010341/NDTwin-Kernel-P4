2026-08-27 夜。B 段(p4-guide 工具鏈安裝)失敗,而我把**唯一的診斷資料刪掉了**。

## 發生了什麼

交接腳本的結尾寫死了兩件事:**寫完成標記 → 關掉 VM**。它跑完就做,**沒有分支**。
所以一次 `rc=1` 的失敗跑完之後,它照樣:

1. 寫 `.test_run/bsegment.done`(下游的 chaos 等待器在等這個檔)
2. 關掉 VM —— **而 log 在 VM 的 `/tmp/p4guide.log`**

再開機時 log 不存在,`find /` 全機零命中。

## 機制(查證過,不是推測)

```
/usr/lib/tmpfiles.d/tmp.conf:   D /tmp 1777 root root 30d
```

🔑 **大寫 `D` 的語意是「開機時清空這個目錄的內容」,與後面的 `30d` 年齡參數無關。**
(小寫 `d` 才是只按年齡清。)⇒ **Ubuntu 每次開機 `/tmp` 全滅,檔案多新都一樣。**

## 🔴 兩個錯誤單獨都不致命,合起來才刪掉資料

- **錯誤一**:交接動作(不可恢復)排在證據保存之前。
- **錯誤二**:證據放在一個**活不過那個交接動作**的位置。

⇒ **只要其中一個對,資料就還在。** 這種「兩個小缺陷相乘」的形狀特別難在 review 時看見,
因為分開看每一個都像是可接受的取捨。

## 🔑 最貴的一句是我說出口的那句

我跟審查員說:**「證據在磁碟上不會跑掉,先交接沒關係。」** 我當時很有把握。
我用它說服了他**和我自己**,把「先交接、log 之後再拿」正當化。**它是錯的。**

⚠️ 諷刺的地方:同一晚我在**每一個驗收步**上都問了「它有沒有辦法失敗」——
**唯獨沒問「存放證據的地方會不會消失」。** 我把儀器查了一遍,沒查存放櫃。

## 規則

1. **交接動作不能早於證據保存。** 交接會讓下一個人開始改變現場(claim、開機、重灌、跑 chaos)。
2. **「已保存」要驗證到「這個位置能活過我接下來要做的那個動作」為止。**
   不是「檔案存在」,是「檔案在**關機／重開／release 之後**還存在」。
3. **長時間工作的 log 不要放 `/tmp`。** 放 `$HOME` 或直接 copy 出機器。
   🔴 **08-28 找到第二個機制,而且比開機那個更陰險——它在跑的當下就刪。**
   `mininet/clean.py:69`：
   ```
   sh( 'rm -f /tmp/vconn* /tmp/vlogs* /tmp/*.out /tmp/*.log' )
   ```
   ⇒ **測 mininet／bmv2 的時候,`/tmp/*.log` 會被受測物自己刪掉。**
   我的 shell 建好 `/tmp/t1.log`,topology 腳本啟動時跑 cleanup 把它 unlink,
   **而那個行程還握著 fd 繼續寫**——所以「行程活著、輸出無處可尋」。
   🔑 **重點不是「`/tmp` 會被清」,是「受測系統有權刪除你的儀器」。**
   開機清空至少還可預期;這個是**在測試中途、由你正在測的東西執行的**。
   ⇒ 選 log 位置時要問:**受測物的清理程序涵蓋這個路徑嗎?**
4. **失敗路徑要有自己的分支**:失敗時**先把證據拉出來,再交接**;或延後交接並明說原因。
5. 🔑 **便宜的失敗就重現它,不要哀悼證據。** v10 十分鐘就死 ⇒ 重跑一次比想辦法救舊 log 快得多。
   **先問「重現的成本是多少」,那常常是最短的路。**

## 交接指令本身也可能沒有分支

⚠️ 審查員給我的原話是「**B 段跑完(不論成功失敗)做兩件事**」——
**「不論成功失敗」是他寫進去的**,我照做了。他事後自己指認這是他的缺陷。
⇒ **收到一個沒有失敗分支的指令時,失敗分支要由執行的人補上並回報**,
因為只有執行的人知道失敗時現場長什麼樣。

## 🔑 「與其哀悼證據,不如重新產生它」

v10 十分鐘就死 ⇒ **重跑一次比想辦法救舊 log 便宜一個數量級**,
而且**重現本身就成為對照組的第一臂** —— 它不只補回證據,還升級了實驗設計。
⇒ 可操作:**證據沒了,先問「重造要多久」**,不要先問「能不能救回來」。

## 🔴 2026-08-28 夜：**`/compact` 會 reset shell，背景 job 跟著死**——同一個形狀，這次殺的是**進行中的量測**

P1-3 十臂跑到第 6 臂（`n16_b`）中途停住。因果鏈**完全在工具側，不在受測物側**：

| 時間 | 事件 | 證據 |
|---|---|---|
| 20:38:19 | session `2eda4620` 執行 `/compact` | 該 session transcript |
| 20:38:27 | `Shell cwd was reset to ...` ⇒ **背景 driver 隨 shell 死掉** | 同上，**transcript 最後一行** |
| 20:38:30 | 接手 session 起來（3 秒後） | — |
| 20:38:58 → 23:50:37 | **零筆事件、191.6 分鐘** ⇒ 沒有人接手那個 job | 時間戳掃描 |

⇒ **3.2 小時的獨佔實驗機時間，因為一個看起來只影響 context 的指令而蒸發。**

🔑 **`/compact` 在心智模型裡是「壓縮我的記憶」，在實作上是「換一個 shell」。**
這正是本檔的母題：**一個交接動作（compact／release／關機）讓現場開始改變，而證據
——這次是「還在產生證據的行程」——沒有活過它。**

**兩個獨立的擋法，各自都夠：**

1. **`setsid`／`nohup` 脫離 session** ⇒ 背景 job 不再是那個 shell 的子孫。
2. **開跑前就問「這個 job 的父行程是誰、誰死了它會死」**——跟「log 放哪裡會不會被清掉」
   是同一個問句，受詞從**檔案**換成**行程**。

⚠️ **而半途死掉的臂在磁碟上幾乎跟完整的臂一樣**：`arm.meta` 364 B vs 650 B，
差別只有**一行 `finished=`**。⇒ 「被中斷」與「量到一個失敗」序列化成同一份輸出
（[[instrument-must-not-mimic-its-own-finding]]：部分完成 ≠ 完成但值小）。
⇒ 處理：**整臂作廢、移到 `_discarded/` 而不是原地覆蓋**——
**覆蓋會讓「這一格曾經重跑過」這件事消失。**

📌 附帶：本輪 driver stdout 只存在於
`/tmp/claude-1000/<project>/<session>/tasks/<id>.output`，**而那是 session 私有且 `/tmp` 會被清**。
它是我重建這條時間軸的唯一來源。⇒ 本檔規則 3 的又一個實例：**長跑的 log 不要只留在那裡。**

reviewer 對母版做衍生數字全掃（17 個），auditor 追查落點的**耐久性**：
`role-metrologist.md`（12–20×、14.1×、8/25.5/128×）與 `role-bmv2-maintainer.md`
（~31 kpps、~1.6 kB）——`git log --all` **零筆、從未 commit**，只活在磁碟上，
而且所在目錄是「永不進版控」的投稿包。⚠️ **機制已更正（reviewer 指出、auditor 三點親驗）**：
排除來源是 **`.git/info/exclude:26`**、不是 `.gitignore`，而 **`info/exclude` 自己也不在版控**
⇒ ①純 `git clean -fd` **不會**刪（被視為 ignored，要 `-fdx`；實測 `-nd` 空、`-ndx` 列出）
②**規則不共享 ⇒ 任何全新 clone 從一開始就沒有這些檔，而且不知道為什麼看不到**。
⇒ 真正的形狀不是「一道指令就毀了」，是**「只存在於這一台的工作樹，且連隱藏它的規則都不可攜」**——
更難察覺，因為每次在本機檢查都看得到檔案。結論不動：**母版近三成的衍生數字，其算式不在版控**。
🔑 對照 `plot_deck_903.py` 那個守衛的 docstring（"A `git clean -fd` would have deleted the
evidence behind the headline number while the slide kept asserting it was safe"）——
**守衛擋住了投影片那條路，論文這條路沒有守衛**（守衛的措辭指的是另一種 clean 情境，
但它要防的「頭條數字的證據不在版控」是同一件事）。
⇒ 通則：**「不進版控」的鎖是對*內容*下的（投稿材料、場次名），不是對*算式*下的。**
   算式＝量測 provenance，必須另存進版控檔；鎖與耐久性不衝突，混為一談才會兩頭落空。
⚠️ 判準補充：「raw 未保存」≠「算式不在檔」≠「算式在檔但那個檔不在版控」——**三種不同的洞**，
第三種最陰險，因為它在每一次檢查時都看起來是好的。

## 🆕 08-31：**`git reflog` 的 clone 時戳，活得比 shell history 久**

要問「這個目錄是什麼時候被 clone 進來的」。那顆 guest **根本沒有 `.bash_history`**
（從來只有非互動 ssh，bash 不寫），所以最直覺的那個來源**不存在**。

而 `git reflog show --date=iso` 的第一筆是：

```
e1b22c1 HEAD@{2026-08-31 06:23:43 +0000}: clone: from https://github.com/…
```

⇒ **repo 自己記得它何時被建立**，不依賴任何 shell、任何登記、任何人記得。

🔑 **通則：問「這件事有沒有在某個工具的內部帳本裡留下副本」**——
`git reflog`／packfile mtime／`cloud-init` marker／`dpkg` 的 `/var/log/dpkg.log`
都是這一族。**它們不是為了稽核而存在的，所以也不會因為沒人想到要稽核而消失。**

⚠️ 但要配對照組：同法讀一個**已知時間**的目標（我讀 `p4c/.git`＝12:08，
落在已知的建置窗 11:53–12:31 內）⇒ **證明這個時戳讀得對，才敢拿它推翻帳上的數字。**
