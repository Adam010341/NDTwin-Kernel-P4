2026-08-25 夜到 08-26 凌晨，我與 `8/25 mainDev` 在一輪實驗裡撞到**七個彼此無關的機制**，
形狀完全相同：**指令回 rc=0、輸出看起來合理、而結論是錯的**。
這不是「要更小心」，是一個**可辨識的族**，值得先假設它存在。

## 七個實例（都實際發生過，不是推想）

| # | 機制 | 它「成功」的樣子 |
|---|---|---|
| 1 | `ss` filter 用錯 port＋`sport`（proxy 走 IPv6） | 回 **0 bytes**——而 0 正是那個閘門要判定的「遙測全滅」 |
| 2 | `pgrep -f 'X' \| head -1` | 匹配到了，但 `head -1` 取 **pid 最小**的，不是這一輪起的 |
| 3 | `pgrep -a simple_switch_grpc`（18 字元 > `comm` 上限 15） | 零匹配，警告丟 stderr，**指令成功、欄位留白** |

| 5 | `git checkout <ref> -- <file>` | **會寫進 index** ⇒ 後續 `git add 別的檔 && git commit` 把它一起帶走，訊息沒提、`git status` 乾淨 |

## 🔴 第 11 條升級成一條沒有例外的規則（08-27，`開機手冊` 一晚四次之後自己下的）

> **任何 `cmd | filter` 之後接 `&&` / `||` 都是錯的，沒有例外。**
> 用 `PIPESTATUS[0]`，或**乾脆分兩行**——分兩行連 `PIPESTATUS` 都不用想。

「小心」是失敗的對策（他已經知道這個陷阱、當晚還踩了三次）；**「沒有例外」才可執行。**

## 🔑 12 的一般形式：**檔案不是傳輸**

同一族今天出現三次：**路徑不是位元組**（`sha256 /proc/<pid>/exe` 才是 binary 身分）、
**還原的原始碼不是還原的建置產物**（`cp -p` 保留 mtime ⇒ ninja 不重建）、
**result 檔不是結果**。
⇒ 守衛要斷言的是**被測物產生的效果**，不是**跑完留下的東西**。見 [[verify-the-purpose-not-the-mechanism]]。

## 三個有效的解法（都當晚實際擋下過東西）

1. **先餵已知非空／已知正確的輸入**。#1 是這樣抓到的：對著活的十台 fabric 先跑一次，
   回 0 ⇒ 讀取器壞了，不是系統壞了。**若沒先驗，我會把自己壞掉的讀取器發表成
   「truncate 殺死了遙測」。**
2. **拿新算的數字去對已發表的舊數字**。#7 是這樣抓到的：換算成單核百分比之後
   `calFlowPathByQueried` 讀 46.31%，正好落在既有報告的 45.0/46.6 之間。
   mainDev 也用同一招抓到自己讀錯欄位（拿舊資料用現在的 `analyze.py` 重跑，
   逐字複製出他報的數字、落在 `min` 欄而不是 `ratio` 欄）。
3. **讓斷言擋在推論前面，而不是事後檢查**。同一晚有一個**反例**值得記成正面範例：
   proxy 重啟失敗時腳本寫了「等不到 `:8081` 就 ABORT」，所以它**大聲地停下來**，
   而不是繼續跑出一組沒有 proxy 的數字。代價只有一次重跑。

## 一個特別陰險的變體：荒謬值是免費的警報

批次化之後 `λ` 讀到 **1.258e+06**（每秒 126 萬樣本）、`quantum` 塌到 128。
機制是 `quantum = gcd(相異 twin 讀值)`，批次化打散取值集合 ⇒ gcd 崩 ⇒ λ 爆。
🔑 **它之所以被抓到，只是因為它荒謬到不可能。** 換一個估計器故障若落在「合理」區間，
同樣的錯誤會安靜通過。⇒ **對每個推導量先問「它的物理上限是多少」**，那個上限就是免費的斷言。

**Why:** 這一族的代價不是浪費時間，是**把錯結論寫進報告**——七個實例裡有四個
差一步就進了投影片或 commit 訊息。
**How to apply:** 任何回 0／回「找不到」／回一個沒對過帳的數字的量測，
在拿它下任何結論之前先做上面第 1 或第 2 條。
相關：[[verify-against-known-good-output]]、[[process-liveness-checks-lie-in-two-ways]]、

## 第九式(2026-08-27):`grep -c` 計數為 0 時 exit status 是 1

```bash
n=$($SSH 'ps -eo comm= | grep -cE "^(ninja|cc1plus)$"' 2>/dev/null || echo 1)
[[ "$n" == "0" ]] && break
```

`grep -c` **有計到才回 0,沒計到回 1**。所以「零個編譯行程」觸發了 `|| echo 1`,
等待迴圈**永遠不 break**。代價:白等 20 分鐘,而它要等的那件事
(P4 工具鏈安裝)**一步都沒開始跑**,同時我還對外宣稱它在跑。

⚠️ **08-27 修正:機制比我原本寫的更糟。** 我本來寫「0 被翻譯成 1」——
餵已知輸入實測後發現不是。`$(cmd || echo 1)` 會**同時**收下 grep 印出的 `0`
**和** fallback 的 `1`,`$n` 變成兩行字串 `"0\n1"`。所以它不是「數錯」,
是**產出一個根本不是數字的東西**,而 `[[ "$n" == "0" ]]` 只是安靜地不成立。
🔑 這一條本身就是「算術說得通不等於機制對」的實例:「0 變成 1」完全解釋得了觀察到的
行為(迴圈不 break),但它是錯的。**是拿已知輸入去餵才炸出真相,不是重讀程式碼。**

「照一般寫法看 create 的 rc **會**看到 rc=0」——**我標了是推論,他讀成量測並寫進記憶。**

**實測結果推翻了我的推論。** 用 iptables 在 create 進行中砍掉 outbound 443/80(ssh 走 inbound 22,不受影響),
跑兩次(第 8 秒切、第 30 秒切):

| | 我推論的 | 實測 |
|---|---|---|
| `conda create` 的 rc | 0 | **1** |
| 有沒有 ` done` | 有 | **沒有,是 Traceback** |

⇒ **conda 在這條路徑上老老實實回報失敗。** 而且我**沒能重現**原本那個
「印錯誤 → 印 ` done` → 環境不存在」的形狀 —— 硬砍網路和 IncompleteRead 是**不同的失敗路徑**。

🔑 **所以真正成立的教訓換了一個**,而且是我的錯不是工具的錯:

```bash
conda create ... ; conda activate ryu-env ; python --version     # rc=127
```
**`;` 串接會丟掉除了最後一個以外每一個指令的 rc。** 我記到的 127 是 `python --version` 的,
create 自己的 rc **從來沒有被捕捉過**。要它就得 `cmd; rc=$?` 或分成獨立 step。

⚠️ **這一條的元教訓比內容更值錢**:我把一個**沒量過的環節**寫進因果鏈,只因為它讓故事完整;
而下游(審查員)把標好的推論升格成事實,**因為驗收這一關本來就會被信任**。
兩邊都沒有捏造,結論還是錯的。**去量它只花了四分鐘。**

🔑 **`|| <fallback>` 用在「輸出就是要判的那個數」上面,一定會把 0 和失敗混為一談。**
`grep -c`、`pgrep -c`、`wc -l` 接 `grep` 都是這個形狀。
🔑 **`8/27 auditor` 給的分類比我準,採用他的措辭**:這一族不是「把失敗回報成成功」,
是**把「條件不成立」翻譯成「條件成立」——方向相反**。凡是**用 exit status 表達語意**
(而不是表達錯誤)的指令都有:`grep`、`diff`、`test`、`cmp`。
解法:把 rc 和輸出分開處理(rc>1 才算真失敗,rc=1 是合法答案),
或用不會因為零而失敗的形式
(`ps -eo comm= | awk '$1=="ninja"||$1=="cc1plus"{c++} END{print c+0}'`)。

同族:本檔第一式(讀取器回 0 ＝ 閘門要判的結論)。**這是同一句話的第二次記錄。**

## 🔴 2026-08-28 新的一族（三個實例，同一天）：**保護的失效時機與它要防的事件重合**

不是「保護沒寫」，也不是「保護寫錯」，是**保護在它最需要生效的那一刻剛好不生效**：

| # | 保護 | 它要防的事件 | 為什麼那一刻剛好失效 |
|---|---|---|---|
| 1 | `trap EXIT` 清理背景 burner | 驅動腳本被 `timeout` 殺掉後留下孤兒 | **`timeout` 的手段是 SIGKILL，而 SIGKILL 不可捕捉** ⇒ trap 必然不跑 |
| 2 | `vm.sh` 的 claim 守衛（讀 `exclusive_cpu`） | 別人在量測時開 VM | **claim 的內容是舊的**——寫著 `CPU free again`，而寫的人正在跑 10 個 burner |
| 3 | 「驗證守衛會放行」的測試 | 守衛誤擋 | **驗放行路徑＝真的執行那個動作** ⇒ 測試本身刪掉了暫停中 VM 的 monitor socket |

🔑 **共同形狀：** 正常情況下保護會生效（但那時也不需要它）；
**異常情況正是它不生效的情況。** ⇒ **「我測過保護有效」幾乎總是在測不需要它的那一半。**

## ⇒ 三條可操作的（分別對應上面三個）

1. **不要讓清理依賴父行程存活。** 給子行程自己的期限：`timeout N bash -c '…'`。
   > **依賴父行程活著的清理不是清理。**
2. **狀態檔要在狀態改變時更新，不是在階段結束時。** 一個過期的 claim
   比沒有 claim 更糟——**它讓讀的人以為自己查過了。**
3. **被守衛保護的動作要有 dry-run**，讓放行路徑可以在不觸發後果的情況下被驗。

📌 與本檔既有那些的差別：既有的是**工具騙你**（rc 說成功而其實失敗）；
這一族是**保護騙你**（它存在、它被測過、而它在真實故障時不會啟動）。
**兩者都會發綠燈，但第二種更難抓，因為綠燈是真的——只是綠在錯的情境上。**

## 🆕 08-31 第十三個機制：**把錯誤轉譯成一個有自信的否定事實**

```bash
qemu-img snapshot -l "$IMG" 2>/dev/null | sed 's/^/  /' || say "  (no disk or no snapshots)"
```

`qemu-img snapshot -l` 在 qemu 持有 image 鎖時**會讀失敗**。`2>/dev/null` 吃掉錯誤、
`||` 把失敗翻譯成「**沒有快照**」。另一條線讀到它、相信磁碟是空的、建了一個同名快照
（`qemu-img` 允許重複 tag 且完全不報錯）⇒ 那顆磁碟上現在有兩個內容不同的 `fresh`。

🔑 **這比「回報成功」更難抓**：它沒有宣稱成功，它宣稱了一個**具體的、看起來很有用的
負面事實**。而照著它做是完全合理的——**錯的是工具，不是使用者**。

⇒ 規矩：**「讀不到」與「沒有」永遠是兩種輸出。** 任何 `X || echo "沒有 X"` 都要先問
「X 失敗的時候，這句話會不會變成謊話？」同一形狀在同一支腳本裡有第二個實例
（`restore` 把讀失敗吞成 `n=0` 然後放行）⇒ **找到一個就要搜同檔的其他 `||`**。

⚠️ 反向的那個也一起修了：`snap` 末尾 `[ "$was_running" = 1 ] && {…}` 是分支最後一句
⇒ **快照成功卻 exit 1**。危害小得多，但 `snap && <下一步>` 會永遠不執行下一步。

### 🔑 第 2 例值得單獨記：**它只在你 force「紅」那一邊時才現形**

兩個 force-**green** 呼叫點完全正常，**因為 GREEN 恰好映射到 0**。
⇒ 一個**只躲在「大家通常只確認綠」這個習慣後面**的缺陷。
本檔 08-30 那條「每個閘門要 force-red 也要 force-green」**這次反過來救了規則自己**。
⇒ 通則：**exit code 一旦同時表達「判定」與「這次檢查有沒有做對」，兩個語意會在某個分支上打架。**
凡是 `--expect` 這種「我預期它是壞的」模式，成功條件是**預期相符**，與被測量的值無關。

### 🔑 診斷句指錯方向，一晚**五例**（F-2 是正本）

五句 abort/提示，每一句都在紅燈亮起時把讀的人送去錯的元件：說 reader 壞（錯在 parser）／
說 reader 壞（其實 fabric 本來就該安靜）／說「沒有變紅」（它上兩行剛記錄它變紅）／
說「THRESHOLD 錯了」（錯在允許清單，而同檔 docstring 寫對了）／
註解說「太長的名字會靜默不匹配」（防了太長，漏了**太短**）。
⇒ **共同結構：每一句都是在「缺陷不可能在讀取／記錄這個量的方式裡」這個假設下寫的。**
⇒ 可操作：**寫 abort 訊息時問「如果壞掉的是我讀取／記錄這個量的方式，這句話還成立嗎」。** 五句全部失守。
🔴 **一個會失敗、但把人帶去錯誤元件的閘門，比沉默的閘門更貴。**
