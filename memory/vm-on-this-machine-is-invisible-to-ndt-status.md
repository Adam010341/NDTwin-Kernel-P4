2026-08-27。為了測官網安裝手冊,我在這台機器上跑了一個 QEMU VM
([[install-manual-clean-room-test]])。它產生了一整類**實驗室簿記看不到的負載**。

## 撞什麼、不撞什麼

| | 會撞嗎 |
|---|---|
| netns / veth / `s1-eth1` / OVS 實例 / `mn -c` | ❌ **完全不會**。VM 有自己的核心 |
| Port 8000 / 8080 / 8081 / 6653 / 50051-60 | ❌ 不會。只轉發 host `:2222` → guest `:22` |
| `.test_run/` 與 claim | ❌ 不碰,也不 claim |
| **CPU / RAM / 磁碟 I/O** | ✅ **會,而且沒有任何機制會告訴別人** |

🔑 **這正是我堅持用 VM 而不是容器的理由**:容器共用主機核心,同名介面、同一個 OVS、
`mn -c` 會掃到對方 —— 那才會真的撞。**但也因為隔離得好,它在簿記上完全隱形。**

## 一天內發生的三件事

1. **`8/27 sampling` 的工單 H**:三個臂全落在我的負載內 ⇒ **臂間比較仍成立**,
   但跟 11:37 跑的工單 G **不可逐值比較**(loadavg 本輪 7.03–20.07、G 那輪約 11)。
   他們自己抓到並寫進 PREREG 增補。
2. 我的 VM **打到他們正在測的候選假設**:工單 H 的候選之一是 direct reclaim,
   而我造成的記憶體壓力讓它看起來很可信。他們是靠讀 `wchan` 判掉的 ——
   🔑 **「沒有執行緒停在 reclaim 裡」≠「機器沒在 reclaim」,兩句都真,合併就錯**。
   只看 loadavg 的話他們會誤判成立。
3. **`8/27 auditor` 把三小時前的 handoff 當成當下讀數**:13:24 的 note 寫「VM 已關」
   (寫的當下是對的),我 16:14 又起來,他就跟兩個 session 說「環境乾淨」。
   是 `8/27 mainDev` 去實際查 `/proc` 才發現。

## 規則

- **起 VM 之前先 `ndt status`** 看有沒有人在跑,有的話先告知並把重的編譯延後。
- **重的編譯(ninja、p4-guide 工具鏈)一定要避開別人的量測**;輕的(下載、apt)影響小。
- 🔑 **他們要的不是「你停」,是「你別在我跑到一半改變」**(`8/27 sampling` 原話)。
  恆定的背景負載三個臂平均分攤,讀得出來;**跑到一半從輕變重才是真正會毀掉一輪的東西**。
- **handoff / 文件不是當下讀數。** 要知道 VM 在不在,自己查 `/proc`(用 pid,別用 pattern)。
- 停掉之後**要驗證真的停了**:`kill -0 $(cat vm.pid)`。

## 🔑 把「歷史累積」讀成「當下狀態」——同一個陷阱,三種面貌

1. **`ps -o pcpu` 是生命期平均,不是當下負載。** `8/27 auditor` 用它量我的 VM,報出
   147%／163%,並據此跟三個 session 說「環境很忙」。實際上 VM 那時**已經閒置**,
   數字裡一大半是四分鐘前那段 kernel 建置的殘留。要當下值就讀兩次
   `/proc/<pid>/stat` 的 utime/stime 做差分。⚠️ **他當天早上才剛因為同一件事糾正過別的
   session,然後自己踩了** —— 知道陷阱不等於用得出來,量測手法要寫進腳本而不是靠記得。
2. **VM 關掉後 swap 不會自己還回去。** 「9 GB swap 已用」可能是**殘留**而不是**當下壓力**。
3. **handoff note 是寫的當下為真,不是讀的當下為真**(下面第 3 件事)。

⇒ 驗收問句:**這個數字描述的是「現在」還是「從開機到現在」?**

Adam 有一個 post-commit hook（`agy`），**每一個 commit 都會在背景跑一次 LLM code review**
（`--model gemini-3.1-pro-high --print-timeout 900s`）。實測一個瞬間吃 **26.7% 的一顆核**，
而且**會重疊**（編號 0659 比 0660 早取號、晚 11 分鐘完成 ⇒ 單次可跑 10 分鐘以上）。

🔴🔴 **以下數字經 `mainDev` 實測修正，我原本的推論在幅度與方向上都錯。**

**實測方法值得記：不建新儀器，用 hook 自己的產物**——`.git/agy-reviews/<seq>-<sha>.md`
一個 commit 一個檔 ⇒ **`commit 時間 → 檔案 mtime` 就是那次 review 的實際時長。**

| | 我的推論 | **實測** |
|---|---|---|
| 每次 review 時長 | 「上限 900 s」 | **35–43 s**（中位數 ~38 s） |
| 會不會重疊 | 「大部分時間有一個以上在燒」 | 🔴 **窗內從來沒有兩個重疊**（最近的兩個 commit 相隔 38 s、review 36 s，差 2 秒錯開） |
| 佔空比 | — | 區塊 1 **16.2%**、區塊 2 **12.9%** |
| 哪個區塊比較髒 | 「區塊 2 比較多 ⇒ 乾淨框架是錯的」 | 🔴 **反了**：區塊 1 比較多，**區塊 2 在這個軸上仍然比較乾淨** |

📌 我確實觀察到 review 重疊（1688 s 與 1427 s 兩個）——**但那發生在 10:56–11:24，兩個區塊都結束之後**，
commit 變密才開始排隊。**觀察是真的，時間點在窗外，而我沒有查時間點就拿它推窗內。**

⚠️ ~~**仍是推論**：每次 review 的 **CPU 幅度**~~ ⇒ **幅度已於 08-28 19:4x 實測補上，見下節。**

### 🔴 08-28 傍晚：幅度實測，比登記值高一個數量級，而且是**爆發式的**

`8/28 mainDev` 報 219%，我**用差分法獨立複驗**（`/proc/<pid>/stat` 的 utime+stime 差分 / 間隔，
不是 `ps -o pcpu`）：

| pid | **當下（差分）** | ps 生命期平均 | 已跑 |
|---|---|---|---|
| 2481134 | **207.3%** | 222% | 13:35 |
| 2502920 | **2.0%** | 1.1% | 10:36 |

⇒ **登記的「26.7% 一顆核」低估約 8 倍**：單一實例可吃 **2.1 顆核**，且**多實例會疊加**
（19:2x–19:3x 四顆 commit ⇒ 四個實例同時在跑）。

🔑 **但真正該記的是「單一常數」這個框架錯了**：同一時刻兩個實例差 100 倍（207% vs 2%）。
review 的 wall-clock 大部分在**等 LLM API**（幾乎不吃 CPU），CPU 集中在少數幾段爆發。
⇒ **取樣一次拿到的是你碰巧撞上的那個相位**，26.7% 和 207% 可以都是真的。
**這與本檔第 50 行「生命期平均 vs 當下」同族，但方向相反**：那條講「歷史殘留混進當下」，
這條講「**當下的單次取樣代表不了分布**」。要定價就要取樣一段時間的分布，不是一個點。

📌 **這次 `ps` 的生命期平均碰巧接近當下值（222% vs 207.3%）**——因為那個實例全程都在燒。
**那是運氣不是方法**：同一份輸出裡另一個實例是 1.1% vs 2.0%，也吻合，
但兩者吻合的原因都是「負載剛好穩定」，**換一個正在相位切換的實例就會分岔**。

### 🔴 連帶：`load1` 在這台 14 核機器上不是「CPU 忙不忙」的直接量

同一次量測：**當下 CPU 合計 209.3%（≒2.1／14 核，約 15% 使用率），而 `load1 = 6.11`。**

`load1` 計入不可中斷睡眠（D 狀態）且是**一分鐘衰減平均**⇒ 它同時是**落後指標**與**複合指標**。
`load1 = 6.11` 在這裡主要是幾分鐘前那四個實例的**衰減殘留**，不是當下有 6 顆核在搶。

⇒ **拿 `load1 > 3.0` 當「機器忙、臂作廢」的門檻，在 14 核機器上會**：
①**擋住其實可以開跑的時候**（12 顆核閒著）②**用一個落後量去判斷當下污染**。
要判斷「這一臂有沒有被搶 CPU」，直接量是 `/proc/stat` 的 busy fraction 差分（per-core），
`load1` 只適合當「剛才有沒有發生過事情」的粗篩。

🔑 **這個干擾源的來源是「記錄實驗」這個動作**——
**你越勤於把結果寫下來，你越污染正在跑的那個量測。**
而它與 [[proxy-restart-warm-fabric-multiplies-telemetry]] 同族：**正常運維動作產生的負載。**

⚠️ **不對稱性不是隨機的**：commit 發生在「有東西可寫」的時候，
而那與臂的邊界、有趣的結果、剛跑完的那一臂都相關 ⇒ **系統性地偏向某些臂。**

## ⇒ 兩條可操作的

1. **量變異數的實驗（jitter 這種），量測窗內禁止任何 session commit。** 窗前寫完、窗後再繼續。
   🔑 **但一般情況要修的是時機不是規則**（`mainDev` 指出）：窗內 15 個 commit 有 12 個是他的，
   而它們正是「**發現隨時落盤**」那條規則的產物——**那條規則是我要求他遵守的。**
   > **一個為了不遺失證據而設的規則，在量測窗裡製造了干擾。**
   **規則沒錯**（用量中斷／context 壓縮吃掉的東西遠比 1/4 核貴），**改時機**：
   **窗內累積、窗與窗之間落盤**——臂間本來就有 20 秒靜置，那就是安全窗口。
2. **不要用「乾淨機器」描述任何有人在工作的窗**。正確的描述是**列出窗內發生過什麼**。

⚠️ **標記**：12 個 commit、每 commit 一個 review 檔、瞬間 26.7%、review 重疊 ＝ **實測**；
每次 review 的**持續** CPU 與總貢獻 ＝ **推論**（只量了一個瞬間，沒量曲線）。
⇒ **在補上 per-process 取樣之前，只用它修正「乾淨」這個措辭，不要用它解釋具體的臂間差異。**

## 🔑 08-29：判斷污染要問「**這個發現靠不靠時間**」，不是「窗有沒有重疊」

我的九輪裡只有 `controls-01` 與一個背景 agy 重疊（13:16–13:22）。我沒有停下來重跑，
理由不是「重疊很短」，而是：

> **那一輪的三個發現全是結構性的**（發 GET 打 POST 路由、`dpid` 打讀 `ip` 的 handler、
> 對照根本沒實作）——**是讀 `HttpSession.cpp:177`／`:653` 的路由表確認的，不是量時間確認的**。
> 唯一的時間數字 0.0069 s 只是佐證，而且我引用的每個結論都來自 13:30 之後的輪次。

`8/29 auditor` 接受並說要拿去用。⇒ **可轉移的判準**：
**先問「這個結論的證據是時間性的還是結構性的」，再問「窗有沒有重疊」。**
結構性證據（讀碼、比對 schema、數行程）對 CPU 污染免疫，
**重疊本身不構成重跑的理由**；反過來，任何延遲／吞吐／變異數的宣稱只要窗內有事就要重驗。
⚠️ 但這條**不能拿來事後合理化**：判準要在看到結果之前就知道自己量的是哪一種。

## 🆕 08-30 第四個隱形源的機制被釘死：post-commit hook 自動起 agy（T-7b agent 實證）

`.git/hooks/post-commit` 會 `nohup agy --effort high --print-timeout 900s`——**任何 worktree 的
commit 都觸發**（worktree 共用 .git）、最長 15 分鐘、實測 ~207% CPU、`ndt status` 的 measuring
欄看不到、**沒有 opt-out 環境變數**。「lab note 寫 do not commit」不是客氣話。
⇒ 操作規矩：**量測窗內全 repo 禁 commit**；量測 claim 的 note 要載明；其他 session 拉式
（commit 前看 claim）。merge／證據 commit 一律排到量測結束、release 之後。
- 🔧 過帳工具：**`.git/agy-reviews/NNNN-<sha>.md` 的建檔時間＝commit 時刻、mtime＝agy 實際結束**
  （stdout 直灌該檔）⇒ 隱形負載的精確起訖不用猜 900s 上限，ls --time-style=full-iso 直接讀。
  linked worktree 的 commit 寫到各自 git-dir 的 agy-reviews（`git rev-parse --git-path agy-reviews`）。
  hooks-nopost 配方（只留 pre-commit）的 commit 不觸發＝窗內不得不 commit 時的合法通道，但用完必還原。

### 🔴 08-30 傍晚：**這個載體已經退場**——Adam 下令關掉 agy hook
