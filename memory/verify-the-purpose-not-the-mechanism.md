## ✅ 可操作的判準（唯一要記的那一句）

> **每個驗收步都要能回答：「如果這個改動完全沒效，這一步會變紅嗎？」**

答不出來，就是在驗機制不是驗目的。
`開機手冊` 另外給了一句可引用的短版，已寫進官網文件：

> **A script declaring support is not evidence that it installs.**

## 判準要釘在**產物**上，不是釘在被測物自己的宣稱上

- ❌ 腳本說它支援 24.04 → ✅ **裝完之後 `simple_switch_grpc` 與 `p4c-bm2-ss` 存不存在**
- ❌ 有幾個 result 檔 → ✅ **總共搬了幾 MB**
- ❌ 安裝器的 rc → ✅ **binary 在不在**（rc 是關於最後一個指令的，不是關於你關心的那件事）

## 🔴 08-29：**兩個分支都拼成「通過」的判準**——而且它的時序把有訊息的那支藏起來

使用者手冊的 Generating Traffic 驗收句逐字是：

> "The API returns a JSON response containing the currently detected flow records
> (**or an empty list if no flows have been captured yet**)."

**空陣列滿足這句話。** ⇒ 偵測完全死掉也會過。實測 baseline 就是 `200 / 2 bytes / []`。
（我自己的 COVERAGE 原本寫「只驗到 200，那不是那個宣稱」——**說得太輕**，
問題不是「驗得不夠」而是**這個判準不存在紅燈**。）

🔑 **比「判準太弱」更陰險的一格：判準的時序被設成讓讀者最不可能走到有訊息的那一支。**
`FLOW_IDLE_TIMEOUT` ＝ 15 s；而文件叫讀者**前景**跑 `iperf3 -t 300`（卡住 prompt 五分鐘），
**然後**才換終端機打 curl。實測掃「client 結束→curl」的間隔：5 s 兩筆、**20 s 與 30 s 都是零**。
⇒ **健康的系統照著做，最可能看到的就是那個被祝福的空結果。**

⇒ 判準的第三個問題（接前一節的兩個）：**「這個判準的兩支各自長什麼樣？如果它們長得一樣，它不是判準。」**
以及 **「照文件的順序做，讀者會走到哪一支？」**——**能不能失敗**和**實際上會不會走到那一支**是兩件事。

📌 同一輪的鏡像：我自己的比對器搜字串 `"10.0.0.2"` 而 API 回裸 uint32，
450 秒全報 0 命中；**因為每個 response body 都存了下來**才救得回來。
只存判準的布林值，這份報告會寫 FAIL。⇒ [[instrument-must-not-mimic-its-own-finding]]、
[[injections-must-assert-their-own-success]]（同一晚第二次：一個**一個 byte 都沒送出去**的
client 也產生 `[]`，長得跟我要找的發現一模一樣）。

## 🔴 08-29：最壞的一格——**判準的命中條件與它要偵測的事件「反向相關」**

交接節（`ndtwin-current-state.md` §14-12）給下一手的驗證指令逐字是：

> `grep -n '梯子先用完\|細階梯頂端仍乾淨' doc/2026-08-29_bmv2-performance-study.md`
> —— **命中「細階梯頂端仍乾淨」就代表我的更正被蓋掉了**

實跑**命中**。但命中的是**更正區塊自己**——更正的寫法是「原句寫『細階梯頂端仍乾淨』——兩句都不對」，
**引用錯句才能更正它**。⇒ **這個 pattern 只在更正還在的時候才會命中；更正真的被蓋掉時反而不命中。**

🔑 **前面幾格是「兩支長得一樣」（無鑑別力）；這一格是「兩支接反了」（負鑑別力）——照做會得到與事實相反的結論。**

**為什麼會寫出這種判準**：寫的人腦中的錯誤事件是「那句錯話出現在文件裡」，
但更正這個動作**本身就會讓錯話出現在文件裡**。⇒ **當你的修法是「引用並駁斥」，
就不能用「被駁斥的字串在不在」當存活判準。** 可用的判準是 grep **更正自己的簽名**
（`08-29 00:45 更正`）——那個字串只在更正存在時出現，且不會被引用進別處。

📌 同一輪的第二例（同一份交接節、同一段）：`git log --oneline main..HEAD | wc -l` 「應為 16」，
實回 **722**——**基準選錯**（本地 `main` 落後 722）。數字 16 本身是對的（12 工作分支 + 4 audit-raw），
**壞的是拿來驗它的指令**。⇒ **交接節裡「預期值 + 指令」這種組合要分開查驗：
預期值可能對而指令錯，照著跑會誤判成災難。** 正確問法是 `git log --all --not --remotes`
（那也才抓得到交接節漏掉的 `rescue/literature-search-round1` 與一個 stash）。

## 🆕 08-31：要分辨「慢慢在跑」與「根本沒跑」，就得**數事件**，不能量**總成本**

E 輪的 blocking：它能證明兩顆 binary 不同（單元測試驗常數值），**但沒有任何執行期觀測
證明那條路徑在跑** ⇒ null 結果有兩個相反的意義（「改動無效」vs「那段碼沒執行」），
而下游行動完全相反。**「常數的值不同」≠「那個常數所在的迴圈會被執行」。**

🔑 **auditor 對補法加的硬條件，比補法本身更可轉移**：
> **那個觀測必須是「數事件」，不能是 CPU%。**
> **1 Hz 與「完全沒跑」在 CPU% 上都四捨五入成零** ⇒ 拿 CPU 當判別器**沒有鑑別力**。
> 300 秒 × 1 Hz ＝ 300 次事件，log 行計數或 counter 分得出來。

⇒ **通則：選觀測量之前，先問「我要分辨的那兩種狀態，在這個量上會不會塌成同一個值？」**
聚合量（CPU%、總吞吐、平均延遲）在「低頻」與「零」之間常常塌陷；
**計數量（事件數、呼叫數）不會**。
＋ **新加的觀測自己也要見過紅**：做一個「發生率為零」的 fixture，
確認它判 UNINTERPRETABLE 而不是靜靜通過。

## 🔴 08-31：**閘門數的是「守衛」，不是「被守的面」**——32/32 全綠而兩個動詞完全沒守衛

`ndtwin-vm.sh` 的變異閘 **32/32**，每個守衛 force-red／force-green 都做過。
然後我為了別的事去讀 dispatch，發現 **`stop` 與 `ssh` 會改動狀態，而它們沒有 `claim_guard`**。

**閘門不可能抓到**：它列舉的是**我寫過的守衛**，所以只能反覆確認那些守衛。

> 🔑 **「每個守衛雙向都對」與「每個該被守的東西都有守衛」是兩個問題**，
> 而我把前者的答案當成後者交出去了。

⇒ 這條與檔頭那句是同一件事往上退一層：檔頭問「這個檢查會不會紅」，
**這裡問的是「這張檢查清單是從哪裡長出來的」**。從**既有實作**長出來的清單，
**它的盲區恰好等於實作的盲區**——兩者共用同一份遺漏。

### 可轉移的技法：**對「面」做結構斷言，不要對「已寫的保護」做斷言**

1. **先把面明列成兩張表**（這裡＝`MUTATING` 與 `READONLY` 兩組動詞），**寫死在測試裡**。
2. **直接對實作斷言**（parse dispatch，檢查每個 MUTATING 的 case arm 有沒有呼叫守衛）。
3. 🔴 **這裡原本寫「下一個被加進來的成員會在這裡紅掉」——那句是假的，08-31 晚實測推翻。**
   兩張表是**手寫的字串常數**，迴圈跑的是它們；dispatch 多一個動詞，**十一格全綠、零紅**。
   ⇒ 正確的第 3 步是：**母體要從受測物導出**（parse case label），
   斷言兩張表**涵蓋**它。手寫的表從此只決定「歸類」，不決定「範圍」。
   **這樣才真的把「有沒有想到」變成一個會失敗的步驟。**（實測加新動詞 → 紅）
4. **綠方向也要斷言**：唯讀的那組**必須維持不受守衛**（否則「查誰佔了什麼」會要求你先佔東西）。
5. 🔴 **解析器自己要有控制組**：若 parser 一個都沒 match，**十一個檢查會全部空過而看起來像通過**
   ⇒ 加一格「證明它讀得到一個已知存在的守衛」。（同 [[injections-must-assert-their-own-success]]）

三個變異都看過紅：拿掉守衛→3 紅、給唯讀的加守衛→2 紅、弄壞 parser→8 紅＋控制組明說「以上全部空過」。

🔑 **順帶一條設計律**：**守衛與取得是兩個權力，不要合成一個。**

## 🆕 08-31 夜：判一個 force 有沒有效，**四步**（auditor＋reviewer 共同定）

1. 🔑 **它有沒有呼叫端？**（純靜態、grep 得出來）——**零呼叫端的 force，連「抵達與否」都還沒進入討論**。
2. **該路徑該不該呼叫它？** 不該呼叫而回 0 是**正確的**，不要為了讓表格全紅而湊
   ——🔑 **一張全紅的 force 表看起來比較完整，那正是它危險的地方**（湊法只有兩種：
   弱化斷言、或在不該呼叫處硬呼叫，兩者都是把儀器改成配合表格）。
3. **強制值會不會被吸收？**（套在會變成基線的那次讀數上 ⇒ 之後永遠沒有東西不同）。
4. **有沒有更早的檢查先中止？** ⇒ **從未抵達**。**這一種讀碼讀不出來，只有跑一次才現形。**

**實例（08-31，同族第三例）**：身分括號（open/close）在兩輪都零 force 覆蓋，
機制 3 與機制 4 同時成立；修補丁 `exedriftmid` 寫進了庫、生產路徑也插了相位標記，
**但閘門腳本沒有呼叫它** ⇒ 第 1 步就擋下來了。

🔴 **而違反的正是該輪自己寫進註冊的那條**（「預註冊寫幾項檢查，腳本就要有幾個對應呼叫」）：
> **把教訓寫進註冊，與註冊被執行，中間還有一步；而那一步目前只有第二個讀者補得上。**

📌 **連帶的處置形式**（auditor 08-31）：章與證據要分開，且**證據那半要是閘門不是註記**——
「本輪不得開跑，直到證據基礎欄為完整」寫在**可執行的前置條件**上，
不要寫在修訂記錄裡（同「驗收要寫在狀態上不是 rc 上」）。
📌 **派審時要給判準不只給範圍**：審查員能不能問對問題，取決於派審的人有沒有把問題定義好。

**實例（08-31，同族第四例，而且對照組是「有效的」）**：`.ova` 用 ovftool 重打包後，
`The manifest validates` → `Completed successfully`，而且**陰性對照真的會紅**
（翻一個 byte ⇒ exit 1）。但那顆檔案宣告 `<vssd:VirtualSystemType>vmx-99`——
一個不存在的硬體版本——而且 VM 名字叫 `x`（中繼 `.vmx` 的檔名）。

🔴 **對照有效，但它變動的是「磁碟雜湊」這個維度，缺陷在「硬體宣告」那個維度。**
成因是重打包時帶了 `--lax`，工具印了 *"Hardware compatibility check is disabled"*
然後寫下 `virtualhw.version = "99"`——**我叫它不要看，然後拿它說「看過了」**。

🔑 **可執行形式：一個對照只覆蓋它變動的那個維度。** 問「我這個對照改了什麼？
缺陷如果出現在我沒改的那些欄位上，它會紅嗎？」⇒ 這一輪的補法是把「機制」換成「目的」：
不是問「ovftool 收不收這個檔」，而是問「使用者的 VMware 匯得進去嗎」，
所以最後的驗收是**不加 `--lax` 的完整轉換**＋**在 OVF 宣告的硬體上（AHCI）重跑 T-2**。
