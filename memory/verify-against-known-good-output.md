一個純粹的體積優化，在同一小時內產生兩個靜默錯誤的圖。**

## 兩次都不報錯，而且圖看起來完全正常

| # | 機制 | 症狀 |
|---|---|---|
| 1 | glob patch 針對 `os.path.join` 形式，但檔案裡兩處都是**字串串接** → patch 什麼都沒改到 | box plot **四個 cell 全空**照樣畫出來 |
| 2 | `failover_key()` 有 `== "ping_p4_4host.log"` 的**精確比對**，加 `.gz` 就失配、掉進 OVS fallback | cell 數變 **9/11**，而已發表的圖是 **10/10** |

第 2 個特別危險：**兩個 cell 都有資料、分布也合理、圖完全正常。**
第 1 個是隔壁 raster 崩了才被發現 —— **崩潰是比「畫得出來的錯圖」好的失敗模式**。

**Why:** 壓縮改變的是**檔名**，而分類邏輯常常在比對檔名。這種耦合在讀程式碼時看不出來，
因為兩處程式碼各自都是對的。

**How to apply:**

1. **改完之後，把輸出跟已 commit 的已知正確版本逐項對帳。** 今天救回來的是
   `{'P4 / 4 hosts': n=10, ...}` 這組計數 —— 我有先前 commit 的輸出可以比。**沒有基準就先產一份再改。**
2. **精確比對 (`==`) 是最脆的**。有 `endswith` / `startswith` / `==` 對檔名的地方，
   任何改檔名的操作都要當成 breaking change。
3. **同一份證據被兩個 caller 用不同程式碼讀 = 遲早不一致。** 今天把兩個 glob 點收成一個
   `ping_logs()` helper，這正是 08-19 那輪對 `failover_key()` 做過的同一種修法
   （見 [[cited-line-numbers-are-not-evidence]] 家族）。

⚠️ **順帶：優化本身是對的**（51k 行是沒人 diff 的追蹤資料），錯的是把它當成
「不會改變行為的改動」而沒有驗收。

## 同一次壓縮打壞的第四個 reader（2026-08-20 深夜）

`doc/audit/2026-08-20_sampling-rate-and-cpu/plot_figures.py` 的 `_open()` **只處理「呼叫端傳未壓縮檔名」**，沒有「路徑本身就以 `.gz` 結尾」的分支：

```python
if os.path.exists(path): return open(path)      # 傳 foo.jsonl.gz 且它存在 → 文字模式開 gzip
return gzip.open(path + ".gz", "rt")
```

拿真實檔名載入 08-18 的 trace → `UnicodeDecodeError: 'utf-8' codec can't decode byte 0x8b`。

**四個實例的完整名單**（同一次 `ae9f12a` 壓縮引發，兩天內）：
1. `failover_key()` 的 exact-match arm（`== "ping_p4_4host.log"`）→ cell 數 9/11 而非 10/10，**靜默**
2. glob patch 打在不存在的 `os.path.join` 形式 → 四格全空，**靜默**
3. `analyse_matrix.py` presence check 裸 `os.path.exists` → `no cells found`，**半靜默**
4. `_open()` 缺 `.gz` 後綴分支 → `UnicodeDecodeError`，**大聲**

🔑 **只有第 4 個是大聲失敗的，而它是唯一一個修起來零風險的。** 前三個都需要「拿已知正確的輸出對帳」才抓得到。壓縮這種純體積優化**沒有語意改變、沒有測試會紅**，所以它的爆炸半徑等於「所有讀那些檔的程式碼」，而那個集合永遠比你 grep 到的大。

**How to apply:** 改變檔案的**表示方式**（壓縮、改副檔名、換序列化格式）時，不要只找「開檔的地方」——要找**所有形式的路徑處理**：`exists`、`glob`、字串比對副檔名、`endswith`、`os.path.join` 拼接。修在 loader 裡（讓它同時接受兩種形式），不要在每個呼叫端補。

## 第五個實例，新形狀：**我挑了一個「不可能失敗」的樣本來驗證 parser**（2026-08-22）

載流 FP 研究要斷言「fabric 真的有流量」，我寫了

```awk
awk -F'[: ]+' '/^ *s[0-9]+-eth/ {rx+=$3; tx+=$11}' /proc/net/dev
```

回報 **0 MiB**，而 NTG 的 iperf3 log 同時顯示每條流 11 MB、112 條全成功零錯誤。

**機制：`/proc/net/dev` 把介面名**右對齊**在固定寬度欄位裡。**
- `    lo: 706581997 …` → 前面有空白 ⇒ `$1=""`、`$2="lo"`、`$3=rx bytes` ✅
- `s10-eth3: 151812359 …` → 名字夠長、**從第 0 欄開始** ⇒ `$1="s10-eth3"`、`$2=rx bytes`

所以**欄位編號會隨介面名長度整體位移一格**，我加總的是 packet count 不是 bytes。

🔴 **真正的教訓不是 awk。是我怎麼「驗證」的**：我跑了
`awk … /^ *(lo|en|wl)/ {print $2, $3, $11}`，看到 `iface=lo rx=706581997 tx=706581997`
跟原始行吻合，就宣告 parser 正確 —— **而 `lo` 正好是唯一有 padding 的那一類，
是這個 bug 唯一碰不到的樣本**。用一個結構上不可能失敗的案例去驗證，等於沒驗證。

**How to apply:** 驗 parser 要**拿它實際要處理的那些輸入**去驗，特別是
①最長／最短的 key、②有無前導空白、③欄位對齊會變的格式。
`/proc/net/dev`、`ps`、`df`、`netstat` 這種**人類可讀的對齊輸出**全是這個形狀 ——
能改用「先 split 分隔符、再 split 空白」就別用固定欄號：

```awk
awk '/s[0-9]+-eth/ {split($0,a,":"); split(a[2],f," "); rx+=f[1]; tx+=f[9]}'
```

⚠️ 這個 bug 的爆炸半徑是**整份研究**：它會回報「載流下 0 false positive」，
而實際上量的是一個它以為有載流的閒置 fabric —— 正是這份研究存在的目的要排除的那種結論。
救回來的是「**斷言要放在被測系統外面**」：NTG 說它送了流量不算證據，
就像 config 檔說跑哪個 binary 不算證據（[[benchmark-must-name-the-binary-it-measured]]）。

## 🆕 2026-08-31：「空格永遠可接受、猜的格永遠不可接受」會回頭稽核派工單自己

抄錄型派工（把既有編碼整併成一張帶錨點的表）給了一條硬規則：**不准湊表，來源沒有就寫
「—」，兩來源不一致就並列標記、不裁定**。結果它**當場咬到派工單的規格錯誤**——我在
prompt 裡把「10/12 報吞吐」列成統計段的分數之一，而統計段根本沒有那一項（10/12 是漏斗

🔑 **禁止湊表 ＝ 反向稽核。** 一般寫法是「請對帳，不符就報」；差別在於**明示不符時該
偏向誰**——不寫，代理會偏向讓數字對上（那正是要防的）；寫死「偏向來源、標記差異」，
它就會把差異一路報回到規格上。派工時值得多這一句。

**同一輪的第二個收穫**：轉錄紀律逼出「印了數字、鏈上沒有算法」的洞——母版的 `1,500×`
全 repo 查無算式（值本身複算正確）。**抄錄一遍是找 provenance 洞最便宜的方法**，
比重讀原文有效，因為它強迫每一格指名出處。
