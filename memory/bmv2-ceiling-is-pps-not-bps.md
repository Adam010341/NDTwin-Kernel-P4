# 天花板是 pps 不是 bps（工單 ②，2026-08-29 收案）

正本 `doc/audit/2026-08-28_packet-size-sweep/`（PREREG ＋ AMENDMENT-1），
commit `c3bfe50`＋`28dd860`(audit-raw, 168 檔)。註冊 → 開跑 → 收案，**結局落在註冊的 H1**。

軸是**別人的**（64/256/1024 B **frame**，NetSoft '19／CompNet 2021 的 RFC 2544 慣例），
刻意不自創——**自創軸會讓結果對不上它想切進去的那批文獻**。
⚠️ `iperf3 -l` 是 **payload**，frame = payload + 42 ⇒ `-l 22 / 214 / 982`。

## 結果

| frame | arm a | arm b | 平均 kpps | **同一批資料的 Mbit/s** |
|---|---|---|---|---|
| 64 B | 20 | 12 | 16.0 | **8.2** |
| 256 B | 20 | 20 | 20.0 | **41.0** |
| 1024 B | 12 | 20 | 16.0 | **131.1** |

**P(256)/P(64) = 1.25、P(1024)/P(64) = 1.00**（H1 區間 0.75–1.30／0.65–1.30；
H2「頻寬受限」預測 0.15–0.40／0.03–0.12 ⇒ **差非常遠**）。

🔑 **這就是給文獻的那一刀**：17–18 篇報 bmv2 吞吐的論文全部用 Mbps 且**沒有一篇載明封包大小**。
⇒ 那不是「精度不足」，是**一個 16 倍的歧義**，而且是可以用他們自己的軸示範出來的。

## 三條不在註冊測試裡、但獨立同意的支持（比兩個比值更有說服力）

1. 🔑 **六臂全部在同一階（110 kpps）截斷。** 截斷規則**只看 loss、對 frame size 全盲**，
   而三個尺寸在該階的 bit rate 差 16 倍 ⇒ **若天花板是 bps，1024 B 那臂會在低得多的 pps 截斷。**
2. **bmv2 自身 CPU 佔用橫跨整條軸近乎常數**（0.1456–0.1660，逐行程 `/proc/<pid>/stat`）
   ⇒ **在乾淨階上，封包多大都花一樣的 CPU**——正是 H1 主張的機制。
3. **跨輪對帳（開跑前註冊，不是事後補的）**：③ 的 n=1 兩臂 160/240 Mbit @ 1442 B frame
   ⇒ 14.3／21.4 kpps、平均 **17.9**，對 ② 的 1024 B **16.0** ⇒ 比值 **1.12**。
   🔑 **③ 的梯子是用 Mbit/s 刻的，所以那個點不可能被 ② 的 pps 軸塑形。**

## ⚠️ 誠實的解析度聲明（這是結果的一部分，不是但書）

六臂只落在**兩個相鄰刻度**（12 和 20）上，而拿到 12 的兩臂分別在 64 B 和 1024 B
——**對 frame size 是隨機的**。⇒ 正確講法：

> **在 ±1 階（<1.5×）的解析度內，pps 不隨封包大小改變；同一批資料的 bit rate 變 16 倍。
> 本輪排除 H2 的餘裕極大，但排除不了小於一階的真效應。**

📌 ×1.5 對數梯子上的中心值用**幾何平均**比算術平均自然（√(12×20)=15.5 vs 16.0）；
比值變 1.29／1.00，**結論一字不改**。
📌 **一格坐在門檻腰上**：1024 B pass B 複驗中位數 **0.4969%** 對 0.5% 門檻。
若讀成 0.5001 ⇒ 該格 14.0、比值 0.88，**仍在 H1** ⇒ **裁決不繫於它，格值繫於它，兩句都要寫**。
**不准為它補第四個 rep**——註冊規則是三 rep 取中位數，補到跨過門檻為止就是採樣作弊。

## 🔴 那個混淆（會偽造頭條的那個）真的被擋住了

**「pps 恆定」正是發送端受限會產生的結果** ⇒ 頭條與假象在資料裡無法區分。
註冊的閘門：64 B frame loopback 必須撐到 bmv2 最高 pps 的 **5×**。
**實測產生器天花板 770.7 kpps 對要求的 80.0 ⇒ 過關 9.6 倍。**
⚠️ 08-15 那組 loopback（42.4/63.5 Gbit/s）**不能當對照**——它是 **1400 B** 量的，
而小封包產生受限於 per-packet 成本，1400 B 的結果對 64 B 的 pps 天花板零資訊。

## 🔑 最值得記的一條：**陽性對照抓到的是修法自己的 bug**

新的負載閘門是 `external = 總 busy − Σbmv2(utime+stime) − Σiperf3(utime+stime)`
（取代 ③ 那個被證明沒有鑑別力的總量閘門，見 [[bmv2-and-ovs-capacity-do-not-compose]]）。

**第一版 sampler 對「當下活著的 iperf3」加總。每個 rep 生新行程再死掉 ⇒ rep 之間掉回 0
⇒ `last−first` 讀成 0.0000 ⇒ 產生器的成本整包掉進 `external`——而它在 64 B 最大，
也就是處理效應本身。**

> **我要拆掉的那個 bug，在拆除動作裡把自己重建了一次。**

改成逐 PID 累加後：`iperf3_share` 0.0000 → **0.0572**、`external` 0.1052 → **0.0178**（同一個工作負載）。

🔑 **抓到它的是陽性對照，不是程式審查**（4 個 burner ⇒ external 0.2959 對 0.0178）。
⇒ **判準：先證明閘門會發火，才有資格拿它的沉默當證據。**
③ 的舊閘門從頭到尾沒有人看過它偵測到真的外來負載——**那正是它壞了卻沒人發現的原因**。
