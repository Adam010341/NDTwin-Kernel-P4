# WHAT THIS FILE DESCRIBES: the P4 proxy's venv, p4_proxy/venv. It takes THREE commands to
# build, not two; the third is part of the install:
#
#     python3 -m venv p4_proxy/venv
#     p4_proxy/venv/bin/pip install -r p4_proxy/requirements.txt
#     p4_proxy/venv/bin/python p4_proxy/regen_p4runtime_pb2.py
#
# protobuf is 5.29.6 (CVE-2025-4565, CVE-2026-0994; see its line), and p4runtime 1.5.0, the newest
# release, ships generated modules that protobuf >= 4.21 refuses on its default backend: without
# the third command the proxy cannot import p4_client. regen_p4runtime_pb2.py rebuilds those
# modules from the descriptors they embed and replaces them only when every descriptor comes out
# byte-for-byte the same. It is idempotent, and it has to be run again after any reinstall of
# p4runtime.
#
# An EXISTING venv made from this file before protobuf moved to 5.29.6 (it has 3.20.3) is NOT
# brought up to date by `pip install -r`. Build a new one and swap it in: the procedure and its
# rollback are at the end of this file, "UPGRADING AN EXISTING VENV". Until that is done on a
# machine, that machine's p4_proxy/venv is the older set and this file does not describe it.
#
# HOW THIS FILE HAS BEEN RUN. As three different sets: what pip resolves from this file depends on
# the day, because what its packages pull in is not pinned (fifteen packages in set C).
#   A. The candidate's set, 2026-09-25: this file before starlette was pinned, which resolved
#      starlette 1.7.0. Offline, fresh venvs by the three commands on Python 3.13.13 (miniconda,
#      the development machine's) and 3.12.3 ran both suites; on 3.13.13 every test id got the
#      verdict it gets under the protobuf-3.20.3 venv, on one commit:
#        p4_proxy/tests, all 41 test_*.py files        1557 tests, OK, 1 skip (the test that
#                                                      declares it needs a live switch)
#        tools/p4_exercise/tests (unittest discover)   187 tests, OK
#      Without the third command the p4_proxy suite does not load at all and tools/p4_exercise
#      fails 49 of 187.
#   B. Set A again, LIVE, 2026-09-26, on trunk 580767a8, as the proxy's interpreter through
#      P4_PROXY_PY (3.13.13): doc/audit/2026-09-04_p4-tutorial-exercise-prep/live-p1/01_baseline.sh
#      passed with the same switch state and graph as on the 3.20.3 venv (time fields masked,
#      every line equal); 06_thirteen.sh's 26 arms gave the verdicts of the 3.20.3 venv's run of
#      2026-09-24 (the rows that differed were injected-packet counts, every one above its
#      threshold, like the rows two 3.20.3 runs differ in); and the one test that drives a real
#      bmv2, tests/test_p4_client.py with NDTWIN_LIVE_SWITCH_OPT_IN=1, passed. The proxy ran on the
#      upb backend (google/_upb was mapped into it).
#      NOT covered: 128 hosts, long runs, telemetry under traffic, OVS; the exercise driver's own
#      convert and preflight steps, which call p4_proxy/venv by path and so still ran on 3.20.3; a
#      switch REFUSING a table entry under 5.29.6 (the two exercises that would have sent one were
#      stopped earlier by that 3.20.3 preflight); whether ndt's app pre-flight ran on the 5.29.6
#      venv (it reads P4_PROXY_PY, so it should have, but its output does not name the
#      interpreter: inferred, not observed); regen_p4runtime_pb2.py's refusal paths; CI on GitHub.
#      And it tried a SET, not protobuf alone: set A differed from the 3.20.3 venv in fifteen
#      packages -- protobuf, grpcio-tools, setuptools, and twelve unpinned then, starlette 1.7.0
#      among them -- and in the backend (python -> upb).
#   C. This file as pip resolved it on 2026-09-26: set A with starlette 1.3.1, the version the
#      3.20.3 venv has. OFFLINE ONLY: fresh venvs by the three commands on 3.13.13 and 3.12.3 gave
#      every test id the verdict it gets under the 3.20.3 venv, in both suites; l1's P4 lane, run
#      locally in CI's shape (3.12.3 and no other interpreter with p4runtime; not on GitHub), had
#      22 of its 41 files fail without the third command -- 21 dying at import, one whose proxy
#      subprocess did -- and none with it; the procedure at the end of this file was rehearsed on
#      stand-ins, its checks made to fail one at a time (which ones: HOW TO RUN IT, below). Set C

# UPGRADING AN EXISTING VENV, AND ROLLING BACK
#
# For a p4_proxy/venv made before this file moved protobuf to 5.x, i.e. one with protobuf 3. Step 1
# checks for exactly that; a later change here to protobuf, p4runtime or grpcio-tools needs this
# text revisited, not just re-run.
#
# Not `pip install -r` into it. pip would move protobuf to 5.29.6 and leave p4runtime (1.5.0 is
# already there) with its old generated modules, and the proxy then dies at import with
# "TypeError: Descriptors cannot be created directly"; and nothing of the old venv is left to go
# back to. (If that has happened: running regen_p4runtime_pb2.py with that venv's python repairs
# it. Do not follow the advice printed with that TypeError, to downgrade protobuf or to set
# PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python.)
#
# Instead: move the old venv out of the way -- a rename, which writes nothing inside it -- build
# the new one in its place, verify it there, and on a failure move the old one back. In its place,
# because that is how everything that uses the venv finds it: components.env defaults P4_PROXY_PY
# to p4_proxy/venv/bin/python (stack.sh starts the proxy with it; l1_unit_tests.sh tries it
# first), ndt's p4_proxy_py() has the same default, and many scripts call p4_proxy/venv/bin/python
# by path -- the tutorial exercise driver, live-p1/_common.sh, most tests/shell/mutate_*.sh, some
# of them naming the main checkout's venv from other checkouts. Pointing P4_PROXY_PY at another
# venv reaches only stack.sh, ndt and l1: that is how the 2026-09-26 trial ran, and why the
# exercise driver's own steps stayed on 3.20.3. It tries a venv; it does not switch to one.
# Out of the way means outside the checkout ($HOME), on the same filesystem so the move is a
# rename: parked inside p4_proxy/ it would not be covered by .gitignore, and tests that walk that
# tree skipping only directories named exactly `venv` would read it
# (tests/python/test_known_issues_references.py reads every text file under p4_proxy/).
#
# HOW TO RUN IT. The commands are the lines below that start with `#   $ `: paste them WITHOUT that

# paste that runs on past a failure is harmless. Nothing rolls back by itself: after a STOP, read
