# WHAT THIS FILE DESCRIBES: the P4 proxy's venv, p4_proxy/venv. It takes THREE commands to
# build, not two; the third is part of the install:
#
#     python3 -m venv p4_proxy/venv
#     p4_proxy/venv/bin/pip install -r p4_proxy/requirements.txt
#     p4_proxy/venv/bin/python p4_proxy/regen_p4runtime_pb2.py
#
# protobuf is 5.29.6 (CVE-2025-4565, CVE-2026-0994; see its line), and p4runtime 1.5.0, the newest
# release, ships generated modules that protobuf >= 4.21 refuses on its default backend: without
# the third command the proxy cannot import p4_client. regen_p4runtime_pb2.py rebuilds those
# modules from the descriptors they embed and replaces them only when every descriptor comes out
# byte-for-byte the same. It is idempotent, and it has to be run again after any reinstall of
# p4runtime.
#
# An EXISTING venv made from this file before protobuf moved to 5.29.6 (it has 3.20.3) is NOT
# brought up to date by `pip install -r`. Build a new one and swap it in: the procedure and its
# rollback are at the end of this file, "UPGRADING AN EXISTING VENV". Until that is done on a
# machine, that machine's p4_proxy/venv is the older set and this file does not describe it.
# The development machine's p4_proxy/venv is still the older set as this is written. (Whoever
# migrates it deletes the previous sentence and this one in the commit that records that.)
#
# HOW THIS SET HAS BEEN RUN
#   Offline, 2026-09-25: a fresh venv built by the three commands, on Python 3.13.13 (miniconda,
#   the development machine's) and on 3.12.3, ran both suites; on 3.13.13 every test id got the
#   same verdict as under the protobuf-3.20.3 venv, on one commit:
#     p4_proxy/tests, all 41 test_*.py files        1557 tests, OK, 1 skip (the test that
#                                                   declares it needs a live switch)
#     tools/p4_exercise/tests (unittest discover)   187 tests, OK
#   Without the third command the p4_proxy suite does not load at all and tools/p4_exercise fails
#   49 of 187.
#   Live, 2026-09-26, on trunk 580767a8, with such a venv (3.13.13) as the proxy's interpreter
#   (P4_PROXY_PY): doc/audit/2026-09-04_p4-tutorial-exercise-prep/live-p1/01_baseline.sh passed
#   with the same switch state and graph as on the 3.20.3 venv (time fields masked, every line
#   equal); 06_thirteen.sh's 26 arms gave the verdicts of the 3.20.3 venv's run of 2026-09-24
#   (the rows that differed were injected-packet counts, every one above its threshold, like the
#   rows two 3.20.3 runs differ in); and the one test that drives a real bmv2,
#   tests/test_p4_client.py with NDTWIN_LIVE_SWITCH_OPT_IN=1, passed.
#   The proxy ran on the upb backend (google/_upb was mapped into it).
#   What that trial did NOT cover: 128 hosts, long runs, telemetry under traffic, OVS; the
#   exercise driver's own convert and preflight steps, which call p4_proxy/venv by path and so
#   still ran on 3.20.3; regen_p4runtime_pb2.py's refusal paths; CI on GitHub. And it tried a SET,
#   not protobuf alone. That venv differed from the 3.20.3 one in fifteen packages -- protobuf,
#   grpcio-tools, setuptools, and twelve that were unpinned then, starlette 1.7.0 among them -- and
#   in the backend (python -> upb). starlette has been pinned here to 1.3.1 since, the version the
#   3.20.3 venv has, so the exact set this file resolves has not been run live.
#
# Every package that p4_proxy/, its tests or tools/p4_exercise/ imports is pinned `==`, not `>=`
# -- starlette included, which is imported directly although it arrives as fastapi's dependency
# (see its line). Apart from protobuf and grpcio-tools, the pins are the versions the development
# machine's p4_proxy/venv had when this file was aligned with it on 2026-09-25. Why pins: until
# then this file named p4runtime 1.4.1 and floors while the venv had 1.5.0, so it described no
# environment anyone had tested. Change a pin here only together with a re-run of both suites.
# What those packages pull in is NOT pinned.
#
# CI installs this file on Python 3.12 (ci.yml), not 3.13, on purpose: 3.12 is what the user
# manual's P4 path gave a tester on a fresh Ubuntu 24.04.4 VM -- its section 6.3,
# `python3 -m venv p4_proxy/venv`, produced Python 3.12.3 (docs at website commit c5262c3;
# doc/audit/2026-09-02_manual-usertest/run-06-opus/CHECKLIST.md:40 and :372, JOURNAL.md:3). That
# is the record of one run of the manual, not the manual's text, which was not re-read for this.
# The development machine's 3.13 is what the local gates run (tools/test_workflow/l1_unit_tests.sh
# tries $P4_PROXY_PY first, and components.env defaults it to p4_proxy/venv).
#
# [Co-developed with claude code -- Adam]

# UPGRADING AN EXISTING VENV, AND ROLLING BACK
#
# For a p4_proxy/venv that predates a change here to protobuf, p4runtime or grpcio-tools -- such
# as one with protobuf 3.20.3, the set before this file moved to 5.29.6.
#
# Not `pip install -r` into it. pip would move protobuf to 5.29.6 and leave p4runtime (1.5.0 is
# already there) with its old generated modules, and the proxy then dies at import with
# "TypeError: Descriptors cannot be created directly"; and nothing of the old venv is left to go
# back to. (If that has happened: running regen_p4runtime_pb2.py with that venv's python repairs
# it. Do not follow the advice printed with that TypeError, to downgrade protobuf or to set
# PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python.)
#
# Instead: move the old venv out of the way -- a rename, which writes nothing inside it -- build
# the new one in its place, verify it there, and on any failure move the old one back. In its
# place, because that is how everything that uses the venv finds it: components.env defaults
# P4_PROXY_PY to p4_proxy/venv/bin/python (stack.sh starts the proxy with it; l1_unit_tests.sh
# tries it first), ndt's p4_proxy_py() has the same default, and many scripts call
# p4_proxy/venv/bin/python by path -- the tutorial exercise driver, live-p1/_common.sh, most
# tests/shell/mutate_*.sh, some of them naming THIS checkout's venv from other checkouts. Pointing
# P4_PROXY_PY at another venv reaches only stack.sh, ndt and l1: that is how the 2026-09-26 trial
# ran, and why the exercise driver's own steps stayed on 3.20.3. It tries a venv; it does not
# switch to one.
#
# Out of the way means outside the checkout ($HOME below), on the same filesystem so the move is a
# rename. Parked inside p4_proxy/ it would not be covered by .gitignore (only p4_proxy/venv/ is),
# and the tests that walk that tree skipping only directories named exactly `venv` would read it:
# tests/python/test_known_issues_references.py reads every text file under p4_proxy/.
#
# When: nothing may use p4_proxy/venv while it is moved. No fabric and nobody measuring
# (`ndt status`); no proxy (`ps -eo pid,args | grep -F p4_proxy/venv/` lists only that grep); no
# gate or test run, here or in another checkout. While the old venv is parked, run nothing from
# it: its bin/pip and other scripts name p4_proxy/venv/bin/python, which is by then the new one.
#
# From the repository root, in one bash shell. The lines that start with `$` are the commands.
# Each command from step 1's third on first checks that the step before it did its part, so a
# paste that runs on past a failure changes nothing it should not.
#
# 1. Record the old venv, then move it aside. Note the OLD this prints: a rollback from another
#    shell needs it.
#   $ V=p4_proxy/venv; PARK=$HOME; OLD=$PARK/p4_proxy-venv.protobuf3-$(date +%Y%m%d-%H%M%S); echo "OLD=$OLD"
#   $ fp() { (cd "$1" && { find . -mindepth 1 -printf '%y %p %l\n'; find . -type f -exec sha256sum {} +; } | LC_ALL=C sort | sha256sum | cut -c1-64); }
#   $ test -d "$V" && test ! -e "$OLD" && test "$(stat -c %d "$PARK")" = "$(stat -c %d "$V")" && PYTHONDONTWRITEBYTECODE=1 "$V/bin/python" -m pip freeze --all > "$OLD.freeze" && fp "$V" > "$OLD.fingerprint" && mv -T "$V" "$OLD" && echo "parked: $OLD"
#
# 2. Build the new venv where the old one was -- the three commands at the top of this file, with
#    the python3 the old venv was made from (its pyvenv.cfg says which). Until the old venv is
#    parked, $V is still the old venv, so each command checks that first.
#   $ test -d "$OLD" && test ! -e "$V" && "$(sed -n 's/^home = //p' "$OLD/pyvenv.cfg")/python3" -m venv "$V"
#   $ test -d "$OLD" && "$V/bin/pip" install -r p4_proxy/requirements.txt
#   $ test -d "$OLD" && "$V/bin/python" p4_proxy/regen_p4runtime_pb2.py
#
# 3. Verify it where it is. Any command failing, or printing other than its note, means: roll
#    back. The two suites need p4_proxy/p4_src/build (tools/test_workflow/l0_build_check.sh p4).
#   $ "$V/bin/python" -m pip check                         # No broken requirements found.
#   $ "$V/bin/python" -c 'import google.protobuf as g, p4.v1.p4runtime_pb2, p4.v1.p4runtime_pb2_grpc; from google.protobuf.internal import api_implementation as a; print(g.__version__, a.Type())'   # 5.29.6 upb
#   $ "$V/bin/python" p4_proxy/regen_p4runtime_pb2.py     # "already current", then "ok: ..."
#   $ PY=$PWD/$V/bin/python
#   $ (cd p4_proxy && PYTHONPATH=. "$PY" -m unittest $(ls tests/test_*.py | sed 's#/#.#; s#\.py$##'))   # OK (skipped=1)
#   $ HOME=$(mktemp -d) "$PY" -m unittest discover -s tools/p4_exercise/tests -t tools/p4_exercise/tests   # OK (skipped=1)
#    On 2026-09-26 that was 1557 tests with one skip, LiveSwitchTest (it needs a live switch), and
#    187 with one skip. The counts grow as tests are added; the verdicts must not change. Two
#    things in these commands are deliberate. The p4_proxy tests are named as modules, not as
#    files: with tests/test_psample_sflow_emitter.py in its argv this process passes
#    link_telemetry's "is this pid the emitter" check, and test_switch_state fails on it
#    (observed 2026-09-26). And HOME is empty, so the one test that compares tools/p4_exercise's
#    fixtures byte-for-byte with ~/tutorials skips: it tests files, not the venv, and it is red
#    whenever a live run has rebuilt a tutorial's build/ (also observed 2026-09-26).
#
# 4. Keep "$OLD", "$OLD.freeze" and "$OLD.fingerprint" until the new venv has passed a live run
#    (live-p1's 01_baseline.sh and 06_thirteen.sh); deleting them after that is the one step here
#    that cannot be undone. On the development machine, also delete the two sentences near the
#    top of this file that say its venv is still the older set.
#
# ROLLBACK, at any point after step 1: the old venv comes back exactly as it was, since it was
# only renamed. In a new shell, first set V, PARK and OLD (the name step 1 printed) and define fp()
# as step 1 does. The failed new venv is parked beside the old one, not deleted.
#   $ test -d "$OLD" && { test ! -e "$V" || mv -T "$V" "$PARK/p4_proxy-venv.failed-$(date +%Y%m%d-%H%M%S)"; } && mv -T "$OLD" "$V"
#   $ test "$(fp "$V")" = "$(cat "$OLD.fingerprint")" && echo "old venv restored unchanged"
#
# ROLLBACK IN PLACE, when there is no old venv left to rename back. Moving protobuf back alone is
# not enough: the regenerated modules need protobuf >= 5.29 (they import runtime_version), so
# p4runtime is reinstalled too, which puts its shipped modules back. This lands on the older set
# except for what it pulled in (setuptools stays; transitive packages keep their versions).
#   $ "$V/bin/pip" uninstall -y grpcio-tools
#   $ "$V/bin/pip" install protobuf==3.20.3 googleapis-common-protos==1.73.0
#   $ "$V/bin/pip" install --force-reinstall --no-deps p4runtime==1.5.0
#   $ "$V/bin/python" -c 'import google.protobuf as g, p4.v1.p4runtime_pb2; from google.protobuf.internal import api_implementation as a; print(g.__version__, a.Type())'   # 3.20.3 python
