# L5 fault catalogue -- one fault type per line, read by faults.sh
#
# Purpose: give the fixed bugs a standing guard. The 2026-08-12 static+live review found
# the same shape three times -- "fix landed, no test CLASS exists" (unidirectional link
# loss, mastership collision, controller kill). A fix with no fault type behind it is
# defended only until the next regression.
#
# Format (three fields separated by a pipe WITH SPACES around it), the same shape as
# tools/contract_test/warning_allowlist.txt and baseline_diff_allowlist.txt:
#
#   ID | ACTION key=value ... | why this fault type exists / what it guards
#
# The separator is " | " (whitespace-pipe-whitespace), not a bare pipe.
#
# ID       short handle, <family>-<n>. L = link, N = node. Used on the command line.
# ACTION   the first word is the injection mechanism; the rest are key=value parameters.
# reason   free text. Say what regression this catches, not what the command does.
#
# WHERE the fault lands is NOT in this file -- it comes from the command line
# (--iface / --peer-iface / --pid), because the same fault type applies to any link or any
# switch. That is what keeps "add a fault type" to "add a line".
#
# Mechanisms (implemented in faults.sh; a new *type* is a line, a new *mechanism* is code):
#
#   link_loss    direction=one|both  loss=<pct>  expect=<verdict>
#                netem loss on one end (asymmetric) or both ends (symmetric).
#                faults.sh decides WHERE to attach netem by reading the live qdisc tree:
#                on a TCLink interface the root is htb and netem must hang under the class,
#                because `... root netem` REPLACES htb silently and the grant cannot put it
#                back (doc/2026-07-29_environment_gotchas.md, 2026-08-13).
#
#   proc_signal  signal=<SIG>  restore=<SIG>  expect=<verdict>
#                signal a switch process by PID. Never pkill: Mininet nodes share a PID
#                namespace, so a pattern kill takes out all ten switches
#                (doc/2026-07-27_p4_bmv2_support_plan.md item 6).
#
# expect=<verdict> is what tools/twin_audit/criteria.py must say WHILE the fault is in
# place: moving | still | any. Every round additionally requires "moving" before the fault
# and "moving" after the revert, and an empty qdisc diff across the whole round -- those
# are not per-entry, they are the price of admission.
#
# [Co-developed with claude code -- Adam]


L-2 | link_loss direction=one loss=100% expect=moving | Unidirectional link failure -- the 2026-08-13 P0's cause. Loss on ONE end kills LLDP in one direction only, so Ryu fires a single EventLinkDelete and the DiGraph stays asymmetric permanently; install_all_pair_paths then crashed on the missing reverse edge, every rule went stale, and the flow blackholed for 291 s while the twin reported it healthy. Fixed in the BFS both-directions check; nothing re-injects the fault, so this line is the guard. NOTE expect=moving, changed 2026-08-13 after the first live P4 round: the two data planes answer this fault differently and the catalogue has to state one of them. P4 reroutes and the canary recovers in 12.5 s, so by the time a settle of any sane length has elapsed traffic is moving again -- expect=still would fail every healthy P4 run. RETIRED 2026-08-17, do not act on the sentence this replaces: it said OVS blackholes for 291 s with zero self-heal, so expect=still was right there and an OVS round reading 'still' meant the bug was back. 23 live runs (doc/audit/2026-08-17_p4-vs-ovs-matched-topology/) show OVS recovering by itself in every one -- 15.7 s mean over n=10 on a 4-host topology, 50.1 s over n=3 on the 128-host one, every run with the netem verified still present at the moment traffic resumed. The 291 s was this entry's own defect before the BFS both-directions fix, not a property of OVS, so expect=moving is now correct for BOTH data planes and a 'still' on either is a regression. The old note would have had a reader treat a healthy OVS round as the bug reappearing. Same round measured P4 at 13.7 s over n=10 on the matched topology: P4 is 2.0 s faster (p=0.0098, 95% CI 0.55-3.50 s), so the data planes do differ here, by 13% -- not by the 291-vs-12.5 the retired sentence implied.

L-3 | link_loss direction=both loss=30% expect=moving | Gray failure. 30 % loss is under every detector's threshold -- beacons still get through, so link-failure detection never fires and the twin keeps advertising the link as healthy, while rate estimation and failover decisions run on badly skewed data. expect=moving is the FINDING, not a weak assertion: it is an executable statement that connectivity checks are blind here. Catching the damage itself needs rate reconciliation, which twin_audit deliberately does not do (sFlow's 1/256 error floor); revisit when a per-flow loss signal exists.

N-4 | proc_signal signal=STOP restore=CONT expect=moving | Switch process alive but not responding. SIGSTOP leaves the process in the table, so pgrep finds it and os.kill(pid, 0) succeeds -- both liveness checks this repo relies on report healthy (memory: "process liveness checks lie in two ways"). Evidence-based liveness should land on the third state, stalled, rather than up or down. LIVE ANSWER (2026-08-16, this entry's first real round, P4): expect changed still -> moving, same mode convention as L-2. A frozen switch stops beaconing and stops forwarding its neighbours' beacons, so the LLDP watchdog declares every directed link around it down at the 15s mark ("no beacon for 15s", all 8 of s5's links in the log), routes reinstall around it, and by any sane settle the pair is moving again -- the audited route flipped to the sibling aggregation switch and flipped back after CONT. The process-table lies are real but immaterial here: the beacon watchdog never asks the process table. An OVS round reading still here is the old blind spot, not a regression of this guard.
