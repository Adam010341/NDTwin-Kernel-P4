usage: ndt <command>

  up [what]     bring the whole lab up and verify it
                  ndt up            Ryu + OVS, 128 hosts  (the default plane is OVS)
                  ndt up 4          Ryu + OVS on the P4 test bed's 4-host layout
                  ndt up ovs        the same as a bare 'ndt up'
                  ndt up ovs4       the same as 'ndt up 4'
                  ndt up p4         p4 at the current host count
                  ndt up p4 4       p4 at 4 hosts   (rewrites host_count_override)
                  ndt up p4 128     p4 at 128 hosts
                  ndt up p4 --app <dir>   p4 on an APP PACKAGE
                OVS builds only 128 or 4 -- each is a different ndtwin-lab verb, not a
                parameter. For any other size, name the plane: 'ndt up p4 N'.
                NDT_TOPO=<file> forces a specific kernel model.

                --app <dir> brings the P4 plane up on an app package -- a directory
                  with package.json and ndtwin/topology.json, as written by
                  tools/p4_exercise/convert.py from a p4lang-tutorials exercise. The
                  package names every host, its address and the switch port it hangs
                  off, so it SIZES the fabric: no host count may be given with it, and
                  host_count_override is rewritten to the model's count.
                  what it does, in order: runs tools/p4_exercise/preflight.py and
                  prints its table verbatim (a red row means nothing is built and
                  nothing is written); writes p4_proxy/mininet/app_package_override;
                  rewrites host_count_override; points NDT_TOPO, the kernel's
                  --topology and the proxy's NDTWIN_TOPO_FILE at the package's model.
                  --app is a P4 flag: on any other plane it is a usage error (2), not
                  an ignored argument.
                  🔴 THE KNOB IS PERSISTENT AND IS CLEARED AGAIN BY: an 'ndt up' of
                  any plane WITHOUT --app, 'ndt down', 'ndt clean', and a rolled-back
                  bring-up. Each of those prints 'app package cleared: <dir>'. Nothing
                  ever leaves it present-but-empty: that state makes the proxy refuse
                  to start, and 'ndt status' reports it as a problem.
                  an external-control-plane package (mode external) brings the fabric
                  up EMPTY on purpose -- the proxy installs no routes -- so [3/3]
                  names the destination-path count and the forwarding test as NOT
                  CHECKED rather than failing or passing them, and still checks the
                  switches, the graph, the model and the host namespaces.
                  exit 0 the fabric came up and verified; 1 something was MEASURED and
                  it was dirty -- a port held by a stray, a Mininet already running, a
                  fabric older than the compiled pipeline, a bring-up that could not
                  finish or could not verify; 5 a GUARD REFUSED and nothing was built:
                  the lab is claimed by somebody else, a measurement is in flight, an
                  'ndt down' from this checkout is still running, or NDT_TOPO names a
                  model of a different network (H4). An --app package that did not
                  pass tools/p4_exercise/preflight.py is 5 for the same reason: the
                  table is printed and nothing is built. 2 is a usage error.
                  🔴 1 AND 5 ARE DIFFERENT QUESTIONS. 1 says this command looked at the
                  machine and did not like what it found; 5 says it never looked. When
                  both are true at once -- a teardown in flight AND a port held -- the
                  answer is 5, because the one action that helps is waiting for that
                  teardown, and the port is very likely one that teardown is releasing.
                  Both are still printed. 'down' and 'clean' answer with the same three
                  words. 3, "there was nothing to measure", cannot arise here: a
                  bring-up has asked for something whatever it found. (Adam, 09-12)

                  🔴 rc 1 CAN BE AN ENDING FROM AN EARLIER ROUND. stack.sh reports a

  status [--check]     what is running, who has the lab, and the state that
                decides every number. --check also exits non-zero on anything
                that would make a measurement untrustworthy.
                  it compares the live lab against what the last 'ndt up' asked
                  for, recorded in .test_run/up.target -- data plane kind, host
                  count, kernel graph, and the model file's sha256.
                  exit 0 all compared fields match; 1 one of them does not (the
                  message names it); 3 nothing was compared, because there is
                  no baseline RIGHT NOW -- .test_run/up.target is absent (every
                  ordinary up->down clears it) or unreadable.
                  3 is never "checked and matched", and it is NOT "no 'ndt up'
                  has ever run here": that sentence was taken out of the output
                  on 09-05 (W12/I-1) as false after every teardown, and when
                  .test_run/pids/kernel.exit is there the report says what the
                  last run was.
                  --check also prints a 'rules-in-window' row: rules left inside an
                  app's window and locks still held. what could not be checked is
                  printed as NOT CHECKED and never as clean. (G-12 / W16-2)
                  🔴 that row was called 'residue' until 2026-09-12. One word named
                  two findings: this one, and the line 'clean' prints as
                  'XX residue: <proc> holding :<port>', which is a PROCESS and which
                  'ndt down' removes. A rule in a window is deleted by nothing here,
                  and its only remedy is a delete_flow_entry by hand.
                  (Adam, RESIDUE-1 §7-5)
                  rules-in-window FOUND is a problem, and it is rc 1 ONLY while there is a

  check         telemetry double-count tripwire
                  exit 0 the ratio is inside the +/-50% band, or there was too
                  little traffic to compute one at all; 1 the kernel is not up, a
                  DECLARED measurement was refused, or the twin could not be read;
                  4 DOUBLE-COUNTING was printed. 🔴 READ THE CAUSE LINES under it:
                  over the band is NOT the same statement as 'clone replicas'.
                  One netem link failure read 1.60 with no replicas anywhere on

                  2026-09-11). rc 4 is new on 09-11; 'under-counting' (ratio

                  🔴 rc 0 ALSO MEANS "nothing was compared". With
                  under 1 Mbit/s of ground truth crossing the fabric this command
                  prints no ratio and no verdict at all -- it says so -- and exits
                  0, which to a script is the same byte as "inside the band".
                  That 0 is NOT the fabric being healthy: a lab with no traffic
                  generator answers it every time it is asked, for as long as it
                  is asked. So read the ratio block,
                  not the exit code; a run with no traffic has no ratio block. The 0

  .test_run/pids/ is shared, so 'down' kills whoever is registered there.
  Declare yourself before a long run -- any script can just write .test_run/lab.claim:
      owner=<name>   expires=<unix seconds>   note=<optional>

  WHAT A CLAIM DOES NOT COVER, measured 2026-09-11 (ROLE-4 T4):
    a claim only blocks the 'ndt' verbs. It is not the northbound API and it is not
    a lock. A loop calling /ndt/install_flow_entry and /ndt/delete_flow_entry every
    2 s kept getting http 200 through its own claim's expiry, and kept getting 200
    after another owner had taken the claim; it stopped only when that owner's
    'ndt down' killed the kernel. There is no signal at all when a claim lapses or
    changes hands -- not to the API caller, not to the previous holder. Re-read
    'ndt status'; nothing will tell you.

  On P4, 'ndt up' derives the kernel's topology model from
  p4_proxy/mininet/host_count_override, so model and fabric cannot disagree
  because an environment variable was forgotten -- and since 09-10 the
  two-checkout form of that mistake is refused before anything is built ('sudo
  ndtwin-lab' acts in ONE tree, and 'ndt up' checks it is this one).
  It does NOT make the 4-host-model-against-a-128-host-fabric mistake
  impossible: inside one tree the host count is whatever that file says, 'ndt up
  p4 N' rewrites it, and on 09-05 setting it built exactly that pair (R3-3).
  OVS has no such knob -- there the size is the verb.
