# sender-gate 校準結果（PREREG-B v1.0 §3；凍結後、正式臂前）

> 附兩條必須隨 G 一起引用的註記，見同節。

**跑法**：`sender_gate_calibration.sh`（腳本檔，非 inline）於 nslab guest VM 內；
路徑＝veth pair＋network namespace 的 sender→sink 直連，**不經過任何受測 build 的 binary**。
用 veth 而非 `lo` 是刻意的：臂本身跑在 veth 上，用 `lo` 校準會**高估** G，
而高估正是會讓「發送端受限」偽裝成「交換機受限」的方向。

**原始三 rep（收端 Mbit/s）**：8781.8 ／ 8331.3 ／ 8693.0（loss 0 ／ 0.022% ／ 0.0003%）

## G ＝ **8331.3 Mbit/s**（取三 rep 最小值＝保守端）

## 套用凍結的判定式：`G < 5×X ⇒ rung X 及以上標 sender-limited`

⇒ 安全上界＝`G/5` = **1666.3 Mbit/s**。逐階檢查：

| rung (Mbit/s) | 5×rung | vs G | 判 |
|---|---|---|---|
| 360（註冊梯頂） | 1800 | < 8331 | ✅ 安全 |
| 540（規則延伸） | 2700 | < 8331 | ✅ 安全 |
| 810（規則延伸） | 4050 | < 8331 | ✅ 安全 |
| 1215（再一階 ×1.5） | 6075 | < 8331 | ✅ 安全 |
| **1822** | 9110 | **> 8331** | 🔴 **此階及以上標 sender-limited** |

🔑 **結論**：整條註冊梯階（到 360）**以及規則可能產生的前三個延伸階**（540／810／1215）
全部落在發送端能力的五分之一以內 ⇒ **本輪任何讀值都不會是發送端的極限**，
除非 saturation stop 一路沒發火而爬到 1822 以上（那種情況本身就要另外報）。

⚠️ **這個數字只餵判定式，不入 primary、不與任何臂的讀值並列**（PREREG-B §3 防火牆條款）。
⚠️ G 是**這顆 VM 上的**發送端能力，不轉移到機器 1。

## ✅ 歸屬：已由第三方逐字紀錄釐清＝**16 vCPU / 16384 MiB**

**「遠端機器測試」線 08-31 更正**：14:41:41 那次重啟**是他們的**——
`ndtwin-vm.sh` 的 **`snap` 動詞內建自動重啟**（stop→快照→若原本在跑就 start），
而他們 14:41:35 下的是 `VM_CPUS=16 VM_MEM=16384 … snap p4-toolchain-v8`。
其輸出逐字含：`--- booting: 16 vCPU, 16384MiB ---` 與 **`cpus: 16   mem: 15Gi`**，
而**最後那行是 guest 自己的 `nproc`／`free`**（不是意圖陳述）。
三件事對上：**pid 25269**、**pidfile mtime 14:41:41**、我的 **`up 23 min` @15:05 ⇒ 開機約 14:42**。
⇒ 校準（~15:0x）跑在該次開機上 ⇒ **工作點＝16/16384，三 rep 的歸屬成立。**
🔑 **沒有第三個寫者**（我先前的「未解不一致」到此關閉）。

### 🔴 註記一：他們只替**開機組態**背書，不替**校準期間宿主有多忙**背書

同一時段宿主有一筆 **2.6 GB `.ova` 傳輸**（`ROUND-LOG.md` 的重疊事件）。
⇒ 校準可能在宿主有負載時跑。**方向論證（我方）**：宿主忙 ⇒ 產生器**變慢** ⇒ G **被低估**；
而判定式是 `G < 5×X ⇒ 標 sender-limited`，**G 低估 ⇒ 門檻更嚴、更多階被標** ⇒ **保守方向**。
⚠️ **這是方向論證不是量測**：我沒有在無負載下重量比對。若解封後有空窗，重跑 40 秒即可消除
這條註記；在那之前 **G 只能當下界用**（「產生器至少有 8331」），不可當精確值引用。

### 🔴 註記二：我自己的 prereg 有洞，且已由本例證實

PREREG-B v0.3a 的 manifest 時效條款寫「**臂** runner 開頭 dump manifest 並對帳」——
**校準不是臂，所以我沒 dump**，因此當下手上沒有能判定工作點的資料；
**能判定的資料在別人的 transcript 裡**。
🔑 **可轉移的形式（遠端線要求逐字收進他們的規定）**：
**時效條款要跟著「被判定式讀到的值」走，不是跟著「跑判定式的那個東西」走。**
⇒ 本輪處置：解封後開跑前，**校準與臂一樣要 dump 一份當下 manifest**（見 PREREG-B v1.2）。

## 舊記錄（保留：我當時確實判不出來，不因結論翻轉而刪）

「遠端機器測試」線問我：校準是在我顯式復原 16/16384 **之後**跑的，還是在無聲降級的
12/8192 狀態下跑的？我查了自己的紀錄，**答案是「不知道」**，理由如下：

| 事實 | 憑據 |
|---|---|
| ~14:02 我以顯式 `VM_CPUS=16 VM_MEM=16384` 啟動，輸出印 `cpus: 16 mem: 15Gi` | 我的指令輸出 |
| manifest 讀到 `nproc=16`、`free -g`＝15 | 我的指令輸出，**但我無法把它的時刻釘在 14:42 的哪一側** |
| **15:05 guest 自報 `up 23 min` ⇒ 開機時間約 14:42** | kill 指令的 `uptime` 輸出 |
| **14:42 那次重啟不是我下的**（我的啟停只有 ~13:59 與 ~14:02） | 我的全部指令紀錄 |

⇒ 校準（~15:0x）**確定跑在 14:42 那次開機上**（與 15:05 同一次），
而**那次開機的 vCPU/RAM 我沒有在校準當下量過**。若它落回腳本內建預設，
G 就屬於 **12/8192** 那台。

🔑 **這正是我自己在 PREREG-B v0.3a 寫的 manifest 時效條款要防的事**——
條款寫「臂 runner 開頭自動 dump manifest 並與 bootstrap 版對帳」，
而**校準不是臂，所以我沒有 dump**。但 G **餵的是臂的判定式** ⇒ 它需要同一級的歸屬。
**條款有洞：涵蓋「臂」，沒涵蓋「餵給臂的常數」。**

**處置（保守）**：解封後**重跑校準**，前置＝先 dump 並確認組態；成本 40 秒。
舊值三 rep（8781.8／8331.3／8693.0）保留為**歷史讀數**、不作判定用。
