## 3. 🔴 相交的**原因**比判定本身重要——而它是一個獨立的發現

判定是「相交」，但兩個點估計差很多：`360/70 = 5.14` vs `360/110 = 3.27`。
差異全部來自**分母**。看分子：

| offered | D × ndtwin（recv Mbit） | D × firewall（recv Mbit） | 差 |
|---|---|---|---|
| 540 | 482.5 / 458.4 | 478.1 / 451.3 | **0.9% / 1.6%** |
| 810 | 526.0 / 575.4 | 549.3 / 575.9 | 4.4% / 0.1% |

**fast build 在兩支程式上送出的量幾乎相同。**
而 stock build 在兩支程式上差 **1.57×**（70 vs 110）。

⇒ **在 fast build 上，P4 程式已經不是瓶頸了；在 stock build 上它還是。**

> 🔴 **08-31 §E 之後收緊**（[`FINDINGS-E-fine-ladder.md`](FINDINGS-E-fine-ladder.md)）：
> 這句話的可主張版本是「**在 20 Mbit 解析度、±1 階重複性下，兩支程式的 fast 臂
> 分不出來**」，**不是**「fast build 對 P4 程式不敏感」。
> §E 用 20 Mbit 細梯階重測 D 臂，讀到 ndtwin {360,360}／firewall {400,360}
> ——**不嚴格分離，所以本節的推論通過了檢定**；但 firewall 自己兩臂就跨一階，
> ⇒ **任何小於 20 Mbit 的真實差異，那一輪都分不出來**。
> 「分不出來」大部分是解析度的陳述，不是等價的陳述。
兩支程式的 pipeline 工作量差異（508 行含每包取樣 vs 284 行）
**只有 stock build 看得見**。fast build 撞到的是別的東西——
封包 I/O 路徑（veth、raw socket、bmv2 框架本身），那個對 P4 程式不敏感。

### 3.1 這對 ① 的主張是什麼意思

**`R` 不是「這個 build 的性質」。它是一個比值，分母隨 P4 程式移動、分子不太動。**

⇒ 換一支**更重**的 P4 程式，stock 臂會更慢，而 fast 臂大致不動 ⇒ **`R` 會變大**。
換一支更輕的，`R` 變小——這正是本輪量到的（5.14 → 3.27）。

🔑 **這比「比值不可移轉」講得更精確，而且它讓論文的核心主張更強**：
一篇論文報「我的機制比 bmv2 快 N 倍」而不講它跑的是哪支 P4 程式時，
**不確定的不只是 baseline 的絕對值——是 baseline 會隨程式移動而優化後的那一端不會**，
所以 N 本身是程式的函數。

### 3.2 這個推論的強度（照實標）

- 證據＝**四個 rung 讀值 ＋ 兩階的實收速率**，每格兩個複本。
- 「fast build 撞到 I/O 路徑」是**機制假說，不是量到的**——我沒有量 veth／softirq／
  bmv2 內部分層。可否證它的實驗（換 I/O 路徑而不換程式）**沒有做**。
- 支持它的是：兩支差異很大的程式在 fast build 上落在 **540 階 1% 以內**，
  而同樣兩支在 stock build 上差 57%。**這是一致的，但不是唯一的解釋。**
- 🔴 **不得寫成「fast build 的瓶頸是 I/O」**。可以寫的是：
  「在這台機器上，fast build 的讀值對這兩支程式的差異不敏感，而 stock build 敏感。」

## 4. 🔴 這一輪**沒有**量到的東西（§C.3b 的資料前更正，重述以免被引錯）

- **`firewall.p4` 的 register（兩個 Bloom filter）一個封包都沒有執行過。**
  它們被 `if (hdr.tcp.isValid())` 守住，而本輪梯子是 **UDP**。
  ⇒ **本輪對「有狀態記憶體存取的成本」零證據**，不得引用 ICNCC 的 register 論述。
- **P_complex 不比 P_simple 複雜。** 我們自己那支才是大的（508 vs 284 行）。
  註冊判準改寫後是「**夠不一樣**，且更小的方向更嚴」——更小的程式給最佳化器的碼更少，
  若比值仍相容，結論更強。**本輪確實是那個方向。**
- 選擇 `firewall.p4` 的原始理由（「唯一使用 register 的候選」）**在被量到的路徑上不成立**，
  已於資料前作廢並記錄。
