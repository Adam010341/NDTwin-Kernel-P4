## §1 為什麼這張表比本機那張「強」

本機有 `ndtwin-lab` claim 工具當真實來源，所以那張表可以是「意圖」，動手當下再去重讀 claim。

**nslab 上沒有任何 claim 工具**（`rlab` 的機器表原本不認得它；`~/RLAB-CLAIM` 從來沒有存在過）。
⇒ **這張表就是唯一的佔用紀錄，沒有第二個東西可以重讀。**

由此推出本規定最硬的一條：

> ### R1 登記＝事實，不是意圖 ⇒ **開跑前寫、release 後改，不准事後補登**
>
> 事後補登在本機只是遲到；在這裡是**製造一段假的空窗**。下一個人看到「表上沒人」，
> 而那段時間的資料是髒的。

⚠️ **仍然要分清楚**：本表記錄「誰在佔用」，**不代表那一輪已被批准開跑**。每輪仍需自己的
prereg 蓋章＋Adam 的排程裁決（08-30「登記＝授權」被資源主人否決的先例，見
`remote-testbed-parallel-dev` 記憶）。**登記是事實陳述，授權是另一回事**——兩者都要。

## §3 規則

### R2 要登記的不只量測窗，是**任何吃宿主資源的動作**

檔案傳輸、build、容器建置、VM 開關、apt——**全部要登記**。

本機那張表可以只記量測窗，因為 claim 工具會抓到其他佔用；**這裡沒有那個後備**。
H-10 那筆 2.6 GB 傳輸不是量測，但它會污染量測。

### R3 可平行的是**準備**，不是**量測**

- ✅ 可重疊：build 編譯、容器建置、寫作、下載、prereg 起草
- 🔴 必須排隊：**任何兩輪的量測窗**

理由要寫成可驗證的形式，不能只寫「互相干擾」：

> 兩輪的量測跑在**同一顆實體 host** 上，而 PREREG-B 有一道宿主外來負載閘
> ⇒ **一個正確運作的閘門會把兩輪一起判成 suspect**。
> **給第二輪另開一顆 VM 也救不了——競爭發生在宿主層。**

⇒ 平行開 VM 的意義是**隔離 kernel 全域狀態**（Mininet netns／OVS datapath），
**不是**取得獨立的效能量測環境。這兩件事必須分開講。

### R4 共用帳號的暴露條款

所有 session 共用同一個 unix 帳號 `nslab`。放在 `/home/nslab` 的東西，**同帳號的人都看得到**。
H-10 那顆 `.ova` 裡是 **PRIVATE repo 的完整原始碼**。

放敏感 artifact 上去必須四件事都寫進本表：

1. **放什麼**（內容與來源）
2. **權限**：`chmod 600`（目錄 `chmod 700`）
3. **多久內刪**：明確日期，不是「用完就刪」
4. **誰確認刪掉了**：**驗狀態不驗 rc**——`ls -l` 看不到才算刪掉，`rm` 回 0 不算

### R5 指令衝突時，收件人**不自己選**

開機手冊今天同時收到 Adam 的「傳」與 auditor 的「停」，它**把衝突原樣丟回給發話者**
而不是自己挑一句。**這是對的，寫進規定。**

理由：**跨 session 訊息是排隊的**，收件人永遠沒有足夠資訊判斷先後
（見 `rescinded-orders-invalidate-damage-assessment`）。

### R6 一個 session 一顆 VM（工具已強制）

共用**主機**安全（28 核塞得下好幾顆，而 Mininet/OVS 的衝突是 per-kernel）；
共用**同一顆 VM** 不安全（qcow2 快照是那顆磁碟上的全域可變狀態，沒有擁有者概念，
一次 `restore` 無聲蓋掉所有人）。08-31 實際發生過。

```bash
NDT_OWNER=<session> VM_DIR=$HOME/ndtwin-vm-<session> SSH_PORT=<沒被占的> \
VM_NOTE="<用途>" ndtwin-vm.sh create
```

`ndtwin-vm.sh` 已內建守衛：缺 `NDT_OWNER` refuse；別人的 `VM_DIR` refuse (`rc=3`)；
`SSH_PORT` 被占 refuse (`rc=4`)。**`ndtwin-vm.sh vms` 唯讀且不需要 `NDT_OWNER`**——
查「誰占了什麼」不該以「你已經占了東西」為前提。

**平行度上限**：瓶頸是 **RAM 不是 CPU 也不是磁碟**。28 核／31.1 GiB／**swap 只有 8 GiB**／
磁碟空 833 G。

🔴 **這個數字要現場讀，不能抄。** 同一台機器、同一顆 VM、同一天兩次讀數：

| 時間 | `mem available` | 狀況 |
|---|---|---|
| ~15:0x | **27 GiB** | 那顆 16 GiB 的 VM 剛開不久——**qemu 記憶體是 lazy 配置的**，大部分頁還沒被碰過 |
| 15:44 | **15 GiB** | 同一顆 VM，跑了幾小時之後 |

⇒ **宣告值沒變，可用記憶體差了 12 GiB。** 拿早上的數字排下午的平行度會直接超賣。
**開新 VM 前跑 `ndtwin-vm.sh vms`**（最後三行就是現場預算），不要引用本表的數字。

依 15:44 的讀數：host 留 4 GiB 後約 11 GiB ⇒ **再開一顆 8 GiB，或兩顆 5 GiB**。
⚠️ swap 只有 8 GiB，數顆同時進建置尖峰會集體變慢——**「不量效能」是這個數字的前提，不是附註**。

### R7 🔴 工作點必須跟著 VM 走，不是跟著誰的 shell

H-4 的實例：`stop`→`snap`→`start` 沒有重帶 `VM_CPUS`/`VM_MEM`，
**16 vCPU/16 GiB 的 lab 無聲地以 12/8192 開回來**。什麼都沒失敗、什麼都沒警告、guest 開得好好的。
**那之後量到的每個數字，都來自跟之前不同的一台機器，而系統裡沒有任何地方會說出這件事。**

⇒ 已修進 `ndtwin-vm.sh`：`$VM_DIR/CONFIG` 記工作點，優先序＝
**環境變數（顯式意圖）＞ CONFIG（這顆 VM 上次跑的）＞ built-in default**；
落到 built-in 而磁碟已存在時**大聲警告**；`status`／`vms` 都印工作點與它的來源。

### R8 快照命名：**用途＋日期**，禁用通用字

`qemu-img` **允許重複 tag 而且完全不報錯**。現在磁碟上有**兩個都叫 `fresh` 且內容不同**的
快照，reviewer 另建了 `p4-bootstrapped-nodocker` 當不歧義入口。

🔴 **但通用名只是症狀，病因在更上游**：`ndtwin-vm.sh` 舊版的 `snaps` 是

```bash
qemu-img snapshot -l "$IMG" 2>/dev/null | sed 's/^/  /' || say "  (no disk or no snapshots)"
```

而 **`qemu-img snapshot -l` 在 qemu 持有 image 鎖時會讀失敗**。`2>/dev/null` 吃掉錯誤、
`||` 把失敗翻譯成「沒有快照」——**這不是報錯，是一個有自信的錯誤答案**。
讀到它的人相信磁碟是空的，於是建了第二個 `fresh`。**照著它做是完全合理的。**

⇒ 已修五處，而第二條比第一條重要：
1. `-U`（force-share）真的讀得到；
2. **「讀不到」與「沒有」印成兩種不同的字**——把兩者收斂成同一句話，正是鎖變成事實的那一步；
3. `snap` **先讀再寫**，讀不到就拒絕盲建，tag 已存在也拒絕；
4. `restore` 的重複檢查原本把讀失敗吞成 `n=0` 然後放行（**同一形狀的第二個實例**）⇒ fail-closed；
5. 讀到重複 tag 當場印 `🔴 DUPLICATE TAG`。

⚠️ 順帶修掉一個相反方向的：`snap` 在 VM 沒開時，末尾 `[ "$was_running" = 1 ] && {…}` 是
分支最後一句 ⇒ **快照成功卻 exit 1**，`snap && <下一步>` 會永遠不執行下一步。

### R8a 🔴 兩個 session 落在同一顆 qcow2——機制逐字紀錄

**不是「有人忘了溝通」，是預設值的算術。**

```
VM_DIR="${VM_DIR:-$HOME/ndtwin-vm}"      # 預設 A
SSH_PORT="${SSH_PORT:-2222}"             # 預設 B，與 A 互相獨立
```

第二個 session 只要**不設環境變數**（或只改其中一個），就會落在第一個上面。
而在那之前，**沒有任何一層會報錯**：qemu 開得起來、ssh 連得上、快照存得進去。
唯一的徵兆是**快照列表裡出現沒人建過的快照**——而當時 `snaps` 正好讀不到列表（見 R8）。

三個後果都不是理論：
1. **任何人 `restore`，所有人的狀態一起被換掉**，沒有提示。
2. **重複 tag 合法且不報錯** ⇒ `restore fresh` 指哪一個不明確。
3. **VM 執行中時 `qemu-img snapshot -l` 會失敗**——這是正常的，但被回報成「沒有快照」。

⇒ 這就是 R6（一 session 一顆 VM）與 `OWNER`／port 守衛存在的理由。
🔑 **假想的風險說服不了人，這件事說得了**：那套機制若早兩小時部署，H-6 那格
「誰重啟了 VM」根本不會成為一個問題。

### R9 這台量出來的效能數字，哪些算數

規矩只有一條：**一個效能宣稱必須自足——所有臂在同一台機器、同一顆 binary、
同一個工作點上量完，並指名它量了什麼。**

- ✅ 完全在同一顆 VM 內跑完的 A/B 比值
- ✅ 第二個平台**重現**既有定性結論（是加分項：外部效度）
- ⚠️ 絕對容量／吞吐：量得出來，但那是**另一個工作點**，當新的一組報，不併進舊表
- 🔴 **不能**跟 Adam 筆電那批數字比或替換
- 🔴 **不能假設它安靜**——共用機器、非獨佔（見 §2.2 整欄）

### R11 🔴 這條線在那台上**不能免密碼 `sudo`** ⇒ 任何要 root 的動作都要 Adam 本人

`sudo -n true` → `sudo: a password is required`；`/etc/sudoers.d/` 只有 OS 自帶的 `README`。
**這是刻意的**（`ndtwin-virt-root.sh` 當初就是設計成「唯一一次 root，由人自己輸密碼」）。

⇒ 規劃任何步驟前先問「**這條路上哪幾步要 root**」。踩過一次：p4-guide 整段都在 `sudo apt`，
所以兩小時的建置**不可能靠現有權限自己跑完**——那件事要在開工前發現，不是走到一半。
🔑 **VM 內是另一回事**：guest 的 `ndt` 帳號有 NOPASSWD root，爆炸半徑＝那顆 VM。
**要 root 的工作放進 guest，不要往 host 要權限。**

### R11a 🔴 15:47 的實例：**一個沒登記的動作，讓一格帳變成永久的問號**

我 14:52 讀到 dpkg 是壞狀態、15:47 讀到乾淨——**中間有人清掉了，而沒有任何地方記得是誰、
何時、用什麼指令。** 那是 §2.2 的 `H-?` 那一列。

這不是苛責誰（暫緩期間訊息滿天飛），而是**這張表存在的理由的第二個實例**：
第一個是共用 VM 的快照，第二個是這個。兩次都是**「事情做了、狀態變了、而帳上是空白」**，
兩次都要靠事後拼湊。⇒ **R1 的「開跑前寫」不是形式，它是這種問號的唯一預防。**

### R10 暫緩／停用要機械化，不能只寫在文件裡

只寫在文件裡的停止令，靠「誰剛好讀到那份文件」來執行。
`~/.local/bin/rlab` 已內建 `suspended()` 表：**對暫緩中的機器連都不連就 refuse (`rc=4`)**，
並印出誰說的／何時／解封條件／有沒有替代機器。

**刻意沒有環境變數旁路**——解封要改 script，留得下 diff。看不見的旁路不是停止令。
⇒ **「誰可以編輯那張表」是授權問題**，等同於「誰可以解封」。
