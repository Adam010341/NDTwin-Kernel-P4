### 2.1 探針實測（本機，root netns loopback，無 fabric 在路徑上）

`iperf 3.16`，kernel `7.0.0-30-generic`，Intel Core Ultra 5 125U（14 執行緒），
每格 3 reps 取中位，`-b 0 -t 5`：

| payload | frame | loopback pps | loopback Mbit |
|---|---|---|---|
| 64 B | 106 B | 528,761 | 271 |
| 256 B | 298 B | 535,837 | 1,097 |
| 1024 B | 1066 B | 512,805 | 4,201 |

`R_gate = P(1024)/P(64) = 512805/528761 = **0.970**`

⇒ **發送端自己就是「pps 近乎恆定、bit rate 差 15.5×」**。
那正是 ② 在 bmv2 上量到的現象的簽名。**儀器與待測假說在數值上不可分辨。**

## 3. 為什麼這不是「換一組參數就好」

### 3.1 加流數救不了它——**比值是尺度不變的**

直覺的補救是「多開幾個 iperf3，把發送端的天花板抬高」。這抬高的是**絕對值**，
不是**簽名**：每個 sender 的 per-packet 成本曲線相同，所以

```
R_gate(k senders) = k·P(1024) / k·P(64) = R_gate(1 sender) = 0.970
```

⇒ 平行化把 gate 從 0.53 Mpps 抬到約 k×0.53 Mpps，但 `R_gate` **一個字不變**。
可容許性判準（`achieved ≤ 0.80 × gate`）因此變成唯一的救命條款，而它要求
**OvS 的真實天花板落在被抬高的 gate 之下**。

### 3.2 而在同一台機器上，那個條件不可能乾淨地成立

發送端、交換機、接收端**全部跑在同一顆 CPU 上**，而且三者的成本結構同型
（都是 per-packet 主導）。把 sender 平行化到 k 份，同一批核心也要同時負擔
softirq 與接收端 ⇒ **抬高 gate 的動作同時壓低 OvS 可用的預算**。

⇒ 🔑 **在單機軟體 fabric 上，「發送端的每包成本」與「交換機的每包成本」
不是兩個可分離的量。** 兩者共用同一個資源，且簽名相同。

**要分離它們，發送端必須在另一台機器上**——也就是必須有實體網卡。

## 4. 🏁 這一節產生的東西比它原本要量的更有用

§A 原本要回答的是「近乎恆定 pps 是不是通則」。它答不出來。
但**它答出了一個 corpus 層級的問題**，而那正好是本論文的定位（報告規範）：

> corpus 裡兩端相差 ~2500× 的那兩篇，一篇是純軟體單機、一篇走實體網卡。
> **我們現在有機制上的理由說明那不是巧合**：單機量測的天花板可以是發送端的，
> 而發送端與被測交換機**共用同一條每包成本曲線**，所以那個讀值
> 「看起來像交換機的性質」。**沒有實體網卡的量測，無法把它排除。**

⇒ **這一段寫進論文的 limitations**，並且它是**可操作的報告規範建議**：
凡以單機軟體 fabric 報 pps／Mbps 容量者，應報告其發送端在同樣 frame size 下的
獨立上限（loopback gate），否則讀者無法判斷讀到的是交換機還是產生器。

**我們自己的 ② 也受這一條約束**——見 §5。

## 5. 🔴 對 ② 的回頭檢查：我們自己那一輪有沒有中同一個陷阱？

**必須查，而且結論不能預設對我們有利。**

② 量到的是 **12–20 kpps** 量級（`bmv2-ceiling-is-pps-not-bps` 記憶）。
本探針量到的發送端 gate 是 **513–536 kpps**。

```
20 kpps / 513 kpps = 0.039   ⇒  約 gate 的 3.9%
```

⇒ **② 的工作點離發送端天花板有 25 倍餘裕，遠低於本檔註冊的 0.80 可容許上限。**
**② 沒有中這個陷阱。** bmv2 慢到讓發送端完全不參與競爭——
**bmv2 的慢，正是讓 ② 可讀的那個條件。**

⚠️ 反過來說：**這條餘裕是 bmv2 專屬的**。任何比 bmv2 快一個量級以上的軟體交換機
（OvS 就是），在同一套器材上都會落進不可讀區。**這不是我們的疏忽，是單機器材的界限。**

⚠️ **本節用的 gate 是「本機、root netns、單一 sender」的數字**，而 ② 的工作點在
h1 namespace 內、經過 fabric。兩者不是同一條路徑上的量測 ⇒ **25 倍餘裕是量級估計，
不是精確界定**。要精確界定必須在 ② 的 fabric 內重跑 gate，那尚未做。

## 7. 若之後要真的回答這個問題，正當形式是什麼

**不是**在同一台機器上換參數重跑。是下列之一：

1. **兩台機器、實體網卡**：發送端與 DUT 分離，gate 不再與 DUT 共用 CPU。
   （nslab 有第二台的可能性，但 nslab 是單機、需要兩顆 VM 加 vhost，
   **VM 之間的虛擬網卡仍然共用宿主 CPU** ⇒ 沒有解決問題。）
2. **換測量的量**：不量天花板，量**固定負載下的每包成本**（softirq per packet
   隨 frame size 的變化）。這是**另一個問題**，要有自己的預註冊，
   **不得寫成 §A 的結果**。
3. **接受不可判定並照報**——本檔採用的就是這一條。
