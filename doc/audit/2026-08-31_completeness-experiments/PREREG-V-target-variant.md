# PREREG §V — bmv2 **target 變體**（`simple_switch` vs `simple_switch_grpc`）

**凍結於 2026-09-01 14:5x，任何 `simple_switch` 臂存在之前。**
量測尚未開始；本檔在機器上還有別人（A-3）的時候寫完。

**命名**：叫 **§V** 不叫 §D，因為「D 臂」在 B 輪已經指 full-fast build，
兩個 D 會在讀表時撞在一起。

[Co-developed with claude code -- Adam]

---

## 1. 為什麼跑這一輪（動機必須寫在資料之前）

**不是為了完整性。是因為我們自己犯了正在數的那個漏報。**

- 稿件數著「18 篇裡只有 3 篇載明變體，且三篇同一個實驗室譜系」。
- 而 09-01 查證：**我們八臂跑的全部是 `simple_switch_grpc`**
  （四棵樹的 `arm.meta` 逐臂記著 `targets/simple_switch_grpc/.libs/…`），
  **稿件從頭到尾沒有說**，而且**我們自己那份四行最低限度清單裡也沒有變體那一格**。

⇒ 這一輪的產出有兩種，兩種都有用：
量到差 ⇒ 第四個混淆因子，而且是**沒有人隔離過**的；
量不到差 ⇒ 消掉一條軸。**兩邊都可寫，所以這不是賭。**

🔴 **不可用的旁證，先寫下來免得事後被誘惑**：TOMACS 的 grpc ~170 Mbps 與
「`simple_switch` 可到 1 Gbps」**不是它自己的對照**（我方紀錄寫「另述」，
而 TUM SS21 記著同一個「up to 1 Gbit/s」在**沒有 build 出處**的情況下流傳）
⇒ **本輪不得引它當效應量預期，也不得在事後拿它對帳。**

## 2. 設計

| | |
|---|---|
| 機器 | 機器 2＝nslab guest（16 vCPU/16 GiB，i7-14700 宿主） |
| 固定 | 單跳、UDP、payload 1400 B、n=1、同一組梯階、同一支 P4 程式（`ndtwin_switch.json`，與八臂梯子同一支） |
| **變的** | **target 二值**：`simple_switch` vs `simple_switch_grpc` |
| 併變的 | build 二值：**A_stock** 與 **D_fullfast**（不跑 B、C） |
| 臂數 | 2 變體 × 2 build × **2 複本** ＝ **8 臂**，交錯序 |
| 交錯序 | `A·ss₁ A·grpc₁ D·ss₁ D·grpc₁ A·ss₂ A·grpc₂ D·ss₂ D·grpc₂` |

**為什麼要兩個 build 而不是只跑 D**：§C 教過這件事——`R` 的**分母會動、分子不動**。
若變體只影響其中一臂，`R` 本身就會變，而那比「變體有沒有效應」更值得報。
只跑 D 會看不到這個結構。

## 3. 註冊讀出與**它們各自的意思**（值算出來之前先凍）

主讀值＝**最高乾淨階**（loss ≤0.5%），與 B/C/E 輪同一把尺，1.5× 一格。

| 結果 | 判定 | 稿件後果 |
|---|---|---|
| 至少一個 build 上，**兩個複本都**分離 ≥1 格且**同方向** | ✅ **變體是混淆因子** | 進四行最低限度清單，成為第四個被隔離的變數 |
| 兩個 build、兩個複本**全部同格** | ⚠️ **在 1.5× 解析度下不可分辨** | 🔴 **只准寫「我們測了，這把尺分不出來」，不准寫「沒有效應」**（§E 的教訓：分不出來大部分是解析度的陳述） |
| 一個 build 分離、另一個不分離 | ✅ **§C 形狀**：比值的一端在動 | 兩個變體各報一組 `R` 與量化區間，並報**兩區間是否相交** |
| 兩個複本方向相反 | ❌ **本輪無讀值** | 照實報「臂內散布蓋過臂間差」，不挑一邊 |

**次要（登記為次要，不得升格成頭條）**：`R_grpc = D_grpc/A_grpc` 與
`R_ss = D_ss/A_ss` 的量化區間是否相交。

## 4. 🔴 硬閘門：兩個變體必須是**兩顆不同的 binary**

**本輪唯一會產出「假陰性且看起來很乾淨」的失效模式，就是兩臂跑到同一顆 binary。**
（B 輪的 F1 已經證明過這個風險是真的：`P4Switch.start()` 把真 pid 丟掉，
「有行程在」「argv 對」「`check_switch_started` 回真」三個檢查會一起綠燈。）

開跑前與每臂頭尾，走 `/proc/<pid>/exe` 取 sha256：

1. **`sha(simple_switch) ≠ sha(simple_switch_grpc)`**，同一棵樹內。**不成立 ⇒ 整輪作廢**，
   不准報「無差異」。
2. 八臂掃完後 `sort | uniq -c` 必須恰好 **4 個相異 sha**（2 變體 × 2 build），各 2 臂。
3. 每臂頭尾兩次取值必須相同。

🔑 **這一條是陽性對照不是衛生**：它區分「量到相同」與「量了同一個東西兩次」。

## 5. 放棄判準（先寫死）

- **`simple_switch` 的 ELF 不在樹裡** ⇒ 必須重編。若重編使 `tree_sha` 改變，
  **與既有 A/D 讀值的對照作廢**，本輪降為獨立四臂輪、**不得與八臂梯子拼表**。
- **sender gate 未過**（送不出該階的量）⇒ 該階記 `NO_MEASUREMENT`，不往上爬。
- **宿主上有他人負載** ⇒ 不中止，但改連續記帳（`host_witness`）並逐臂標記重疊秒數；
  **點取樣不算證據**（09-01 H-26 的教訓）。
- **A-3 尚未 release** ⇒ 不開跑。R1：登記在先、通知在先。

## 6. 本輪**不**宣稱什麼

- **不宣稱機制**。就算量到差，本輪分不出那是 gRPC server 執行緒、額外的鎖、
  還是連結進來的程式碼大小。**「量到」與「因為」在本檔是兩件事。**
- **不外推到別的工作點**：單跳、n=1、1400 B、一支程式、一台機器。
- **不與機器 1 比**（機器 1 沒有 `simple_switch` 臂）。

## 7. 預期（先寫，才知道有沒有被結果牽著走）

**我預期兩臂在 D 上不可分辨、在 A 上可能分離。** 理由：§C 量到
**fast build 撞到的是封包 I/O 路徑、對 P4 程式不敏感**，而 stock build 還受
pipeline 工作量影響 ⇒ 若 grpc 的成本是固定的每包或每執行緒開銷，
它在被 `-O0` 拖慢的臂上比較容易被看見。

🔴 **所以本輪的資訊在被否證的那一半**：若 **D 上分離**，我上面那句對 fast build
瓶頸位置的解釋就要修；若**兩個 build 都分離**，那是最乾淨的結果，
但也代表我們八臂梯子的每一個數字都帶著一個沒報的變數。
