## §A（P-1）② 的 OvS 對照：近乎恆定的 pps 是 bmv2 的性質還是通則？

> ## 🔴 §A 狀態＝**開跑前放棄，零筆結果資料**（08-31 22:10）
>
> 正本：[`A-ovs-framesweep/ABANDONED-pre-data.md`](A-ovs-framesweep/ABANDONED-pre-data.md)。
> **不要照下面的設計開跑**——下面保留原樣是因為放棄的理由要對著它讀。
>
> 一句話：**A.2a 的修正（改跑 unshaped）沒有解決問題，只是把綁住的那個帽換了一個。**
> 拿掉 fabric 的 htb 帽之後接手的是**發送端**，而實測
> `R_gate = P_gate(1024)/P_gate(64) = **0.970**`，落在 **H1 的註冊區間 (0.65, 1.30)** 內。
>
> ⇒ 這一輪的**兩個判定都構造得出來**，差別只在我拿掉了哪一個帽：
> 留著 htb ⇒ 假 H2（對我們不利）；拿掉 htb ⇒ 假 H1（**對我們有利**）。
> **儀器與待測假說在數值上不可分辨** ⇒ 依 §A.4 的「不可判定」條款放棄。
>
> 🔑 加流數救不了它：`R_gate` 是**尺度不變**的，平行化抬高絕對值而簽名一字不變。
> 🔑 而 §5 的回頭檢查說明 **② 自己沒有中這個陷阱**——bmv2 的工作點只有 gate 的 3.9%。
> **bmv2 慢到讓發送端不參與競爭，正是讓 ② 可讀的那個條件。**

### A.1 問題

② 已證明：跨 64/256/1024 B，bmv2 的 clean-rate **pps 近乎不變**而同批資料的
bit rate 差 **16.0×**。**我們沒有在任何其他交換機上驗過這件事。**

⇒ 現在論文說得出「不報 frame size ＝ 16 倍歧義」，但說不出這句話的適用範圍是
**bmv2** 還是**所有軟體交換機**。

### A.2 🔴 這一輪有一個會讓它答不出問題的陷阱（設計時就要擋）

**OvS 那座 fabric 戴著 as-configured 的 htb 1 Gbit 帽**（goodput 上限 ≈971 Mbit
@1442 B frame——`2026-08-30_ovs-flowcount-control/FINDINGS.md` 更正框）。

在 1024 B frame 上，**帽會在交換機之前先綁住**：
- 1024 B payload ⇒ frame ≈1066 B ⇒ 971 Mbit ÷ (1066×8) ≈ **114 kpps**
- 而 ② 在 bmv2 上量到的是 **12–20 kpps** 量級

⇒ **OvS 若真的能跑到帽，我們量到的就是 htb 不是 OvS**，而那個讀值**看起來會像
「pps 隨 frame size 下降」**（因為帽是 bit rate 帽）——**恰好是 H2 的簽名**。
**一個被儀器製造出來的假 H2。**

**把帽換算成 pps，就看得出它有多致命**（frame ＝ payload ＋42 B，帽 ≈971 Mbit goodput）：

| payload | frame | 帽對應的 pps |
|---|---|---|
| 64 B | 106 B | **1145 kpps** |
| 256 B | 298 B | **407 kpps** |
| 1024 B | 1066 B | **114 kpps** |

⇒ 🔴 **那三個數字本身就是一條隨 frame size 下降的 pps 曲線，`114/1145 = 0.10`
——正好落在 H2 的註冊區間 (0.03, 0.12) 之內。**

而 OvS 的核心 datapath 跑得過那些值（同 fabric 的 08-28 jitter 輪量到 >1 Mpps 量級）
⇒ **帽會在交換機之前先綁住，至少在 256 與 1024 B 上必然如此。**

### 🔴 A.2a 結論：**這一輪不能跑在 ③ 的那座 fabric 上**

原設計（沿用 ③ 的 as-configured OvS fabric）**幾乎確定會 abandon**，
而且它失敗的方式最糟——**不是無結果，是產生一個看起來像發現的假 H2**。

**修正設計：跑在 unshaped 的 OvS fabric 上。**

判準是「這一輪需要跟誰比較」：
- ③ 需要 OvS 與 bmv2 **同置放同梯階**，所以它必須用那座 as-configured fabric；
- **本輪不與 ③ 交叉比較**——它問的是一個**平面內部**的問題（OvS 自己的 pps 隨不隨
  frame size 變），所以**不需要**繼承 ③ 的 fabric 組態。

⇒ **本輪明文與 ③ 的 OvS 臂不可比，且不得並排**（寫進 §A.5 措辭紅線）。

**殘留閘門（仍然要）**：即使 unshaped，任一格 `agg_sent < 0.95 × offered` ⇒ 該格標
**sender/cap-bounded、不入判定**；≥2 格發火 ⇒ abandon，**不得改用剩下那格作結論**。

🔑 **這個坑是在設計時算出來的，不是跑完才發現的**——而算它只花了三行除法。
**下一次設計任何「換一個平面重做」的對照，第一步都應該是把兩個平面的已知
儀器界限換算到同一個單位上**，而不是先假設「同一套梯階＝可比」。
（同族：[[instrument-must-not-mimic-its-own-finding]]——這裡儀器的簽名
與待測假說的簽名**數值上重疊**。）

### A.3 設計（沿 ② 逐字，只換平面）

| 項 | 值 |
|---|---|
| 平面 | OvS（Ryu 控制面）；🔴 **fabric ＝ unshaped，不是 ③ 的 as-configured 那座**（理由見 A.2a） |
| 置放 | 與 ② 同構：單路徑、`h1→h65`（🔴 **暖機必須打量測對象**——見 `ovs-flowcount-control/FINDINGS.md` 補報二㈠ 的化石缺陷） |
| frame size | 64 / 256 / 1024 B payload（**與 ② 同為 payload，不是 frame**——軸的定義沿 ②，避免 TSSA 那個混用） |
| 臂 | 每個 size 兩臂，交錯序 |
| 梯階 | ② 的註冊 ladder 逐字 |
| clean | loss ≤0.5% on 3-rep medians |
| 讀出 | 每臂最高 clean rung ⇒ 換算 pps |

### A.4 註冊結果（兩向都可發表；不利的那向寫在前）

以 ② 的註冊區間逐字判（**不重新推導**）：

| 判定 | 條件 | 敘述 |
|---|---|---|
| 🔴 **bmv2 特有** | OvS 的 `P(1024)/P(64)` 落在 **H2 區間 0.03–0.12** | 近乎恆定 pps **不是通則** ⇒ ② 的「16× 歧義」**只能對 bmv2 主張**，論文的適用範圍要收窄。**這對我們不利，照報。** |
| **通則** | OvS 落在 **H1 區間 0.65–1.30** | 每包成本主導是**軟體交換機的通性** ⇒ ② 的主張**擴大**到所有以 Mbps 報容量而不講 frame size 的軟體交換機論文 |
| **不可判定** | 兩區間皆不落入，或 A.2 閘門發火 | 照實報「本 fabric 回答不了」，**不得挑一格作結論** |

🔑 **注意兩向的價值不對稱而我們仍然照跑**：「通則」讓論文變強、「bmv2 特有」讓論文變窄。
**先寫下這件事，是為了讓事後的失望無法偽裝成方法問題。**

## §B（P-2）③ 的 TCP 對照：一格

> ## 🔴 §B 狀態＝**已修訂、已備妥、排隊中**（08-31 22:2x）
>
> **修訂（在資料之前，只收緊）**：加一條**強制的 loopback 對照**，且**必須先跑**。
> 理由是 §A 今天死於「儀器的簽名與待測假說的簽名相同」，而 §B 有同型的暴露面——
> **十六條 TCP 連線在單機上塌陷，可以完全不關交換機的事**（發送端排程、
> 接收端 socket 壓力、cwnd 互相作用）。
>
> | loopback `T(16)/T(1)` | 判 |
> |---|---|
> | ≥ 0.9 | 宿主自己不塌 ⇒ 經 fabric 量到的塌陷**可歸因於 fabric** |
> | ≤ 0.5 | 🔴 **沒有交換機也塌** ⇒ §B **不可歸因**，照實報不可解讀 |
> | 之間 | 對照本身模稜 ⇒ fabric 的數字**只能與對照數字並排出現，不得單獨引用** |
>
> 儀器：[`B-tcp-control/run_tcp_cell.sh`](B-tcp-control/run_tcp_cell.sh)（對照跑在**前面**，
> 因為事後才跑的對照是一個你可以決定不看的對照）。
>
> 🔴 **排隊，不是技術阻塞**：本機 lab 由 `e-round-sampling-ceiling` 持有至 08-31 08:18，
> 且 `exclusive_cpu=yes`。依 `LOCAL-FABRIC-QUEUE.md` 我是 #2 ⇒ **不搶**。E 輪 release 即可開跑。

### B.1 問題

③ 全部是 UDP。而 corpus 裡 **Chen 組報的多流症狀是 TCP**
（`2026-08-29_bmv2-performance-study.md` §5-3 逐字）。
⇒ 我們說不出「我們看到的流數塌陷，跟他們報的是不是同一件事」。

### B.2 🔴 先凍一條語意條款（否則這一格會被誤讀）

**TCP goodput 與本研究的「最高乾淨速率」不是同一個量。**
TCP 對丟包有壅塞反應 ⇒ **「clean（loss ≤0.5%）」在 TCP 上沒有意義**，
梯階法整套不適用。

⇒ 本格**不產生 rung 讀值、不入任何 ladder、不與 ③ 的數字並排比較**。
它是**一個對照**，不是第四個軸。

### B.3 設計

| 項 | 值 |
|---|---|
| 量 | **aggregate goodput**（iperf3 TCP，不限速），n=1 與 n=16 各兩臂 |
| 平面 | bmv2（③ 的主平面）；**OvS 同格若窗允許則加**，否則不加 |
| 其餘 | 置放、控制面、fabric 皆沿 ③ |

### B.4 註冊結果

令 `T(n)` ＝ n 條流的 aggregate goodput。

| 判定 | 條件 | 敘述 |
|---|---|---|
| **同型** | `T(16)/T(1) ≤ 0.5` | TCP 下 aggregate 也塌 ⇒ ③ 的現象**不是 UDP 的產物**，與 Chen 組的敘述**方向一致** |
| 🔴 **UDP 特有** | `T(16)/T(1) ≥ 0.9` | 塌陷只在 UDP 出現 ⇒ ③ 的敘述**必須加上「UDP」這個限定詞**，且不得引用 Chen 組作旁證。**對我們不利，照報。** |
| **中間** | 0.5–0.9 | 不可判定；照實報區間，不挑邊 |

⚠️ **門檻 0.5／0.9 是現在憑 ③ 的 UDP 塌陷幅度（~10×）訂的，不是資料後訂的。**
③ 的 UDP aggregate 從 160–240 掉到 16–32 ⇒ 比值 ~0.1。
**0.5 是一個對「同型」寬鬆、對我們有利方向嚴格的門檻。**

## §C（P-3）① 的 P4 程式對照：build 比值會不會隨程式改變？

### C.1 問題與我先前的錯誤論證

Adam：「換不同的 P4 程式測測看，better safe than sorry」。

我原本反對，理由是「ICNCC 顯示 register/clone/recirc 只收 5–30%，推翻不了 8×」。
🔴 **那個論證是錯的**：ICNCC 的 5–30% 界定的是**程式對吞吐量的影響**，
而這裡問的是**程式對「stock vs fast 這個比值」的影響**。**兩者無關**——
更複雜的 pipeline 有更多碼可供最佳化，`-O3` 在它身上買到的可能更多也可能更少，
**我們沒有任何界限**。Adam 的直覺對。

### C.2 為什麼它很便宜（關鍵事實）

**換 P4 程式不需要重編 bmv2。** P4 程式是編成 JSON、由同一顆 `simple_switch_grpc`
在啟動時載入。⇒ 成本＝多編一支 `.p4` ＋ 多跑兩條梯子，**不是多一輪 build**。

### C.3 設計（掛在 B 輪的 fabric 上，B 自己的比較完全不動）

| 項 | 值 |
|---|---|
| binary | **B 輪的 A 臂（stock）與 D 臂（full-fast）**，sha256 沿用 B 的身分紀錄 |
| P4 程式 | `P_simple` ＝ B 用的那支（正本沿 B）；`P_complex` ＝ **需指名**【TBD-C1】 |
| 臂 | A×P_complex、D×P_complex 各兩臂（A/D × P_simple 已由 B 提供） |
| 其餘 | 梯階、clean、置放、控制面沿 B 逐字 |

### 🔴 C.3a 【TBD-C1】已落定（08-31，Adam 裁「你選一支」）——**而我註冊的判準沒有一支能滿足**

**我原本寫的判準**：選一支使用 ICNCC 指名的三個特徵（register／clone／recirculate）中
**至少兩個**的程式。**清點手邊全部候選之後，沒有任何一支達得到**：

| 程式 | register | clone | recirc | 行數 |
|---|---|---|---|---|
| **`ndtwin_switch.p4`（＝我們的 P_simple）** | 0 | **10** | 0 | **508** |
| `flowcache.p4` | 0 | 4 | 0 | 330 |
| `link_monitor.p4` | 2 | 0 | 0 | 301 |
| `firewall.p4` | **3** | 0 | 0 | 278 |
| `mri` / `ecn` / `qos` / `multicast` | 0 | 0 | 0 | 151–283 |

🔑 **而清點本身推翻了這一節的前提**：我以為要找「更複雜的一支」，
**但我們自己那支就是最複雜的**——508 行、10 處 clone，比所有 tutorial 候選都大。
⇒ **「換一支更複雜的」在現有素材下做不到。**

**判準因此改寫（改在資料之前、且是收緊）**：問題不是「更複雜」，是「**夠不一樣**」。
一支**更小**的程式是同樣有效的第二點，而且方向上更嚴——
**最佳化器可啃的碼更少，若 `-O3` 仍買到同樣的比值，那個結論更強。**

**選定：`firewall.p4`**（`/home/adam/tutorials/exercises/firewall/firewall.p4`），三個理由：

1. **唯一使用 `register` 的候選**（`:126-127` 兩個 Bloom filter）——
   register 是 ICNCC 唯一有量化成本紀錄的三個特徵之一，也是最可能改變最佳化器行為的那個
   （有狀態記憶體存取）。
2. 🔑 **它保留 `ipv4_lpm` 並且真的 apply**（`:160`、`:192`）⇒
   **我們的控制面（dst-based 裝規則）不必改就能用**。
   這一條是可行性的關鍵——換一支不含 `ipv4_lpm` 的程式，控制面裝不進規則，
   整輪會卡在「控制面活著」那道斷言上。
3. **278 行 vs 508 行**＝碼量的實質差異，方向是「最佳化器可啃的更少」。

⚠️ **與 [[p4lang-tutorials-as-local-control]] 不衝突**：那條記憶說的是
**不要拿 tutorials 的拓樸測 twin**。這裡用的是**它的 `.p4` 當受測程式**，拓樸仍是我們自己的。
**兩件事不同，不要互相套用。**

⚠️ **選擇時我看得到的只有靜態特徵（行數、關鍵字計數），沒有看過任何效能數字。**
這一點必須留在紀錄裡，因為「挑一支剛好讓比值不變的」與「挑一支剛好讓比值改變的」
事後無法分辨——**能分辨的只有「選的時候我知道什麼」**。

### C.4 註冊結果

令 `R_simple`、`R_complex` 為兩支程式各自的 build 比值區間（算法沿 PREREG-B R-B3）。

| 判定 | 條件 | 敘述 |
|---|---|---|
| **程式無關** | 兩區間相交 | build 混淆**不隨 P4 程式改變** ⇒ ① 的主張適用範圍擴大 |
| 🔴 **程式相依** | 兩區間不相交 | **比值是程式的函數** ⇒ ① 必須加上「對這支程式」的限定詞。**對我們不利，照報，且這本身是一個值得報的發現。** |

## §A.5 措辭紅線（若 §A 開跑，這幾條隨數字走）

- 🔴 **本輪的 OvS 數字不得與 ③ 的 OvS 臂並排**——兩者 fabric 組態不同
  （本輪 unshaped、③ as-configured 1 Gbit-shaped）。**並排會製造一個假的「OvS 變快了」。**
- 🔴 **不得寫成「OvS 對照 ②」**，要寫成「**OvS 上的同軸獨立量測**」——
  「對照」隱含同條件，而條件不同。
- 🔴 若判定為「通則」，措辭上限是「**在本輪的兩個平面上，每包成本主導**」——
  **兩個平面不是「所有軟體交換機」**。
