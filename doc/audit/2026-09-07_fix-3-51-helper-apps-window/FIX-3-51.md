### 2.1 兩個裁決沒寫、但不做就會壞掉的

- **`apps stop` 驗證停掉後刪 pidfile。** 不刪的話窗**有起點沒有終點**：sim 昨天停掉，今天的
  `--check` 仍然從昨天窗到現在，把之後裝的每一條規則（含 `ndt up` 自己的 baseline）算成
  SUSPECTED 殘留 ⇒ **永遠紅**。與 `nsr|viz|te` 分支的處置一致（那邊 09-02 就這樣做了）。
- **窗在停之前先讀（`RESIDUE_WINDOW`）。** 上一條會讓「`apps stop` 自己印的殘留報告」失去窗，
  而那正是殘留最重要的一刻（規則還在線上、裝它的行程已經沒了）。所以 `cmd_apps stop` 在
  **停之前**把每個目標的窗讀好，`residue_report` 優先用它。
  🔴 **這一條順手修掉了 `nsr/viz/te` 身上同一個洞**：它們的 `app_stop` 09-02 起就會刪 pidfile，
  所以 `ndt apps stop te` 自己印的殘留報告從來都是「no window」——這在本輪之前沒有人量過，
  是讀碼發現的（**讀過未執行**：沒有為它跑 live）。

### 2.2 `lab_kernel_dir` 是一份**複本**，這件事本身是風險

正本是 `/usr/local/sbin/ndtwin-lab`（09-07 查：與 repo 內 `tools/test_workflow/ndtwin-lab`
**byte-identical**，sha256 `6685d3a90fd94884f8fa…`。**跑過**：`sha256sum` 兩邊）。
`ndt` 現在自己實作了同一條規則，**因為裁決是「不動 helper、不 sudo」**——問 helper 要答案
（`sudo -n ndtwin-lab config` 會印 `KERNEL_DIR:`）就要一個 sudo 呼叫，而
`tools/test_workflow/sudo_surface.sh` 存在的理由就是把那個面積壓小。

複本的失效模式是**漂移**，所以：

- **每一條拒絕都照抄**：目錄先判（可寫目錄＝可換掉檔案）、symlink 拒、非 root 所有拒、
  group/other 可寫拒、未知 key ⇒ **整份不採用**、相對路徑／`..` ⇒ 拒、
  `KERNEL_DIR` 不是目錄或裡面沒有 `p4_proxy/mininet/ntg_bmv2_topo.py` ⇒ 拒。
  **`ndt` 信而 helper 不信的 config 會讓 `ndt` 指到一棵 root 沒在跑的樹**——FINDING-01 反過來，
  一樣安靜。
- **漂移由測試擋**：`tests/shell/test_ndt_helper_apps_window.sh` 群組 1 直接把 `ndt` 的
  `LAB_DEFAULT_KERNEL_DIR=`／`LAB_CONF=` **與 helper 的原始碼文字**對比，並在
  `/usr/local/sbin/ndtwin-lab` 讀得到時比對兩份 sha256（讀不到就印 `note`，**不算成一個通過的檢查**）。
- **沒有複製的**：`NTG_PY`／`ENERGY_DIR`／`SIM_DIR`（這裡用不到）、helper 那套大聲的拒絕訊息

## 3. 為什麼 `energy` 不算紅

E-7 的口徑：**「查不了可以不紅，沒去查不准長得像查了沒事」**。
`energy` 的「在這裡跑過沒」**沒有任何管道**可以問——helper 給它的是一個純 tmux session，
輸出只存在 pane 裡。這件事在**每一台機器、每一次執行**都成立，所以把它折進 rc 會讓
`ndt status --check` 永遠紅，而**一個永遠過不了的閘門會在一天之內被忽略**——那正是 G-12
自己那些綠燈失去意義的方式。

所以：`RESIDUE_UNKNOWABLE` **不進** `residue_verdict`，但

- 殘留報告印 `CANNOT BE ASKED`＋為什麼，且**不再印** `no sign it ever ran here`；
- tally 後面多一行「and N app(s) could not be asked whether they ran here at all: energy」；
- `--check` 的 `residue` 列在 `none` 那一行下面多印一行黃字，並說明
  「'nothing found' above excludes them」。

### 7.1 `apps orphans` 把被追蹤的 sim 當孤兒（rc 1）

```
XX  sim: children with no pidfile and no signature -- Simulation-Platform-Manager
XX      pid 3729217  (process group 3729217)
XX        script -qfa /home/adam/Desktop/NDTwin-Kernel/.test_run/logs/app_sim.log -c ./sim
XX  1 app(s) are running with nothing tracking them
```

pid `3729217` **正是 `.test_run/pids/app_sim.pid` 的內容**，`apps status` 在同一輪印 `running`。

**機制**（讀碼）：helper 起的 sim 是**兩層**——`script -qfa <log> -c ./simulation_platform_manager`
（pgid＝自己）＋它 exec 出來的 `simulation_platform_manager`。
`pid_is_app` 比的是 **argv 元素**，所以**兩層都答得出簽名**，`app_probe` 兩個都收進
`APP_LIVE_PIDS`（`ok sim started (pid(s) 3729217 3729221)` 就是這個）。
`app_survivors` 的三條通道回答的是「**這些通道找到誰**」——`app_recorded_pgid` 從 pidfile 出發、
`app_group_pids` 走 `/proc` 把整個行程組列出來——**而 `apps_orphans` 直接把那份名單當成
「誰都沒在追蹤的」印出來**。`app_stop` 有做這個相減（它的 `extra` 迴圈），`apps_orphans` **從來沒有**。

**修法**（`ndt:5305` 附近）：印之前先減掉 `APP_LIVE_PIDS`（`/proc` 驗過屬於這個 app 的 pid），
剩下的才是「沒人指名」的；剩 0 就不是孤兒。
🔴 **減的是 `APP_LIVE_PIDS`，不是 pidfile 的內容**——pidfile 可能指著死掉或被回收的 pid，
拿它去消音一個同號的存活行程就是把 FINDING #48 反過來做一次。
🔴 **FINDING #48 沒有被放寬**：09-02 那兩個 viz JVM **不帶簽名**，不在任何 `APP_LIVE_PIDS` 裡，
相減之後一個都不會少（本輪為它加了對照格，見 §7.3）。
順帶把標題改成兩句：app 是 `running` 時印「RUNNING as pid(s) …，而這些屬於它、沒人指名」，
因為 lw351 那句「no pidfile」是**事實錯誤**——pidfile 就在那裡。

### 7.2 `apps stop sim` 印 `was: not-running`，而 sim 活到那一刻

helper 的 log 逐字：`[20:28:32.671] Server started at http://localhost:9000` …
`^C[2026-09-07 20:28:51.636] Received signal 2` / `COMMAND_EXIT_CODE="130"` ⇒ **它是被這次 stop 停掉的**。

**機制**（讀碼）：`app_stop` 的 `energy|sim` 分支結尾是 `ok "$name stopped (was: $APP_STATE)"`，
而它上一行的 `app_wait_stopped` 會**輪詢 `app_probe` 直到答案是 `not-running`**——
`APP_STATE` 是全域的，等於在印之前被這次 stop 自己的結果覆蓋掉。
`(was: …)` 是對**停之前**的宣稱，卻讀了**停之後**的變數。

**修法**：`app_probe` 之後立刻 `local was="$APP_STATE"`，最後印 `(was: $was)`。
（lw16pw 在 base 上也印 `was: not-running`，同一個覆蓋——那時剛好也真的沒有 pidfile，
所以看起來像另一個病；是同一個。）

### 7.3 🔴 為什麼原本那 64 格抓不到——這條要記住

**因為每一格的 fixture 都是「一個行程」。**
`( exec -a "$SIM_ARGV" sleep N ) &`：一個 pid、自己就是全部。而 helper 起的 app 是
**wrapper ＋ 被 exec 的程式，兩個 pid、同一個行程組，而 pidfile 記的是 wrapper**。
`app_survivors` 的行程組通道**要有第二個成員才會產出任何東西**——單行程的 fixture 底下
那條通道找到的就是 `APP_LIVE_PIDS` 自己，減不減都一樣，**所以缺陷在單元測試裡不存在**。

新的第 10 群把兩層做出來：`setsid` 起一個 group leader（argv 帶簽名、`pgid == pid`，
就是 `script` 的形狀），它 fork 一個 `exec -a "$SIM_ARGV" sleep` 的子行程，兩個都持有 app log 的
可寫 fd（09-02 找到 JVM 的那條通道）。三件事各一格：
①**通道真的有找到 wrapper**（否則相減是空操作，格子毫無鑑別力）；
②**被追蹤時 orphans rc 0**；③**拿掉 pidfile、蒙住 argv 掃描之後 rc 1 照舊**（FINDING #48 的對照）。
外加 `apps stop` 印 `was: running`、兩層都真的死掉。

〔fixture 的兩個細節是量出來的，不是設計出來的：父行程結尾用 `wait`（builtin）而不是再一個
`sleep`——多一個 `sleep` 就是**第三個**沒有簽名的行程，新碼會（正確地）把它報成沒人指名的，
那一格就變成在量 fixture；而 `reap_fixtures` 只認 `comm == sleep`，所以兩層 fixture 另外用
**行程組**收（收之前先讀 `/proc/<pid>/cmdline` 確認是本 suite 的東西——組 id 也是 pid，會被回收）。〕

## 8. 3-51c（低優先，09-08）：讀一個 log、truncate 它、看進一個行程，是三種權限

裁決原文：`DECISIONS.md`「09-07 20:2x（R3-351 §7 三題）」——`apps trim`／`apps status`／
`app_survivors` 對 helper 起的那份 **root 所有的 log** 仍然盲 ⇒ 開低優先小單，
**先把「讀」跟「truncate」分開**。ndt **不加 verb、不動 sudoers、不碰
`/usr/local/sbin/ndtwin-lab`**（Adam 明裁）。**本節無 live**：全部是讀碼＋單元測試，
下面每一句都標了是哪一種證據。

### 8.1 三個盲點（讀碼確認）

`sudo ndtwin-lab sim-start` 在 tmux 裡以 root 跑
`script -qfa <KERNEL_DIR>/.test_run/logs/app_sim.log -c ./sim` ⇒ 那個檔是 **root 所有的 0644**，
而它所在的目錄是這個使用者的。於是：

| # | 位置 | 問的問題 | 答的問題 |
|---|------|----------|----------|
| a | `apps trim` | `app_log_bytes`＝`stat(2)`（只要目錄權限） | `truncate -s0`（要檔案本身的寫權限） |
| b | `apps status` | 同上，印出大小 | 印出 `'ndt apps trim <app>'`，而那個動詞在這裡跑不動 |
| c | `app_survivors` 第三通道 | `find /proc/[0-9]*/fd -lname <log>` | root 行程的 `fd/` 是 0500，find 進不去 ⇒ **回空** |

(c) 是本檔一直在講的那種錯：**「不准問」與「問了、沒有」輸出一模一樣。**
(a) 的舊行為**沒有把失敗說成成功**（它印 `truncate failed on <path>`、rc 1），
但它是**先寫了 1 MB 的 `<log>.tail` 才發現不能 truncate**——做了做不完的工，
而且那句話既沒說是誰的檔、也沒給唯一能解的那道指令。

### 8.2 修法

- **新的接縫**（`ndt`）：`app_log_owner <path>`（`stat -c %u`，**測試替身就換這一個**）、
  `app_log_blocked_reason <path>`（rc 0＝truncate 得動；rc 1＋**一句**原因＋能解的指令）、
  `proc_uid <pid>`（讀 `/proc/<pid>/status`，**world-readable**——看不進 `fd/` 的時候，
  「誰的」仍然問得到）、`app_fd_readable <pid>`、`app_fd_blindness`。
  🔴 **先問 `-w` 再問 owner，順序是刻意的**：能不能做事是 kernel 的答案，是誰的檔只決定
  要印哪一種解法。以 root 跑 `ndt` 時 `-w` 為真，這一整段都不會觸發。
- `apps trim`：**在寫 tail 之前**問 `app_log_blocked_reason`。擋住就
  `cannot truncate <path>: owned by root (helper wrote it); ask the operator to
  'sudo truncate -s0 <path>'`，rc 1，**不寫 `.tail`、不印 ok**。能寫的照舊。
- `apps status`：root 的 log 那一列多一句（黃）`log is root's (<path>); trim needs sudo`；
  其他寫不動的原因印 `log cannot be trimmed here: <原因>`。**大小照印**——那個讀真的成功了。
- `app_survivors`：所有通道跑完之後問 `app_fd_blindness`，把
  `fd channel: CANNOT READ /proc/<pid>/fd (root process) -- not checked` 併進
  `APP_SURVIVOR_BLIND`。**不增不減任何 survivor。**
- `apps_orphans`：`found > 0` 的那條路也印盲點了（以前只在 `found == 0` 印）——
  `and a channel was blind, so this is a floor and not a count: …`，**rc 不變**。

🔴 **`app_fd_blindness` 只看「別的通道已經指名的 pid」**，這個界限不是裝飾：機器上每一個 root
daemon 的 `fd/` 都讀不到，全列出來就是「一條通道指名半台機器」（見 `APP_SURVIVOR_MAX`），
`ndt apps orphans` 會在每一台機器上永遠回「blind」——**一個永遠不綠的動詞，跟永遠綠的一樣沒人讀。**

### 8.3 rc 口徑：變了什麼、沒變什麼

- `apps trim`：root 的 log 本來就 rc 1，**還是 rc 1**（訊息變了、副作用少了一個 `.tail`）。
- `apps status`：一律 rc 0，**不變**。
- `apps orphans`：**判準沒變**（`found>0`⇒1、`found==0`＋盲⇒2、否則 0）。
  🔴 **但實際碰得到的一個新情形要講明**：在**主 checkout** 上，sim 由 helper 起著、pidfile 在、
  行程組通道找到那個 root wrapper ⇒ 它被相減成「有人追蹤」（found 0），
  而 fd 通道對它是盲的 ⇒ **rc 2（以前是 rc 0）**。
  這正是 E-7 的口徑（查不了不准長得像查過了），但它會讓「helper 起著 sim 時跑 orphans」
  從綠變成 2。**本節沒有 live 驗過這一格**（本單不碰 lab）——`R3-351c-SUMMARY.md` §7 有問這件事。

### 8.4 測試（`test_ndt_helper_apps_window.sh` 第 11 群，28 格）與替身的邊界

🔴 **「root 所有」在這裡只能用替身**：suite 沒有 root，也不准要。替身＝
**真的 `chmod 444` 的檔** ＋ **只對 `*app_te.log` 這一條路徑注入的 `app_log_owner`**。
和真 root 的差別，逐條：

1. 真檔是 **0644／uid 0**；替身是 **0444／我們自己**。⇒ **kernel 真的拒絕了那個 truncate
   （同一個 EACCES）**，但它拒絕的理由是 **mode，不是 owner**。所以那句話的兩半來自兩個證人：
   `cannot truncate` 來自 kernel，`owned by root` 來自 stub。**兩半都各自有真的東西在後面。**
2. 真檔只有 root 能 chmod 回去；替身可以。**沒有任何一格依賴這一點**，且 suite 不留 0444 的檔。
3. 以 root 跑時 `apps trim` 對真檔會成功；碼問的是 `-w` 不是 uid，所以那一格不需要 fixture。
4. **注入只給一條路徑**——其他 app 的列仍然走真的 `stat(2)`。全域回 0 的 stub 什麼也證不了。

**fd 那半不需要替身**：suite 在 `/proc` 裡**現找**一個 `fd/` 讀不到、`status` 說 uid 0 的
**真的 root 行程**（優先挑 userspace 的，kworker 會消失），只做兩件事——`[[ -r ]]` 與讀 `status`，
**跟受測碼讀的完全是同兩樣**。不送訊號、不開檔、不寫任何東西。
找不到（例如以 root 跑 suite）就印兩行 `note` 說**那六格沒有跑**——「沒查」不是「查過沒事」，
而閘門那邊會因此報 SURVIVED，不會安靜地綠掉。

對照格（必須綠）：能讀能寫的 log 照樣被 trim（rc 0、`.tail` 有留、檔案真的變 0）、
可寫的 log 不多印任何一列、**看得進去的行程不會被編造成盲點**。
