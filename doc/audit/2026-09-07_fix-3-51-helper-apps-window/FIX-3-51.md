## 2. 修法（E-8 五點逐條）

| 裁決 | 做了什麼 | 位置 |
|---|---|---|
| ①「起完把 `APP_LIVE_PIDS[0]` 寫進 pidfile」 | `app_wait_started` **驗到活行程之後**才寫，格式與 `app_spawn` 同一個檔同一種內容 | `ndt` `app_start` 的 `energy\|sim` 分支 |
| ②「沒 pidfile 時退到活行程的 `etimes`」 | `app_started_at` 加**第三個來源**：`app_scan_pids` 的活 pid，取 **`etimes` 最大**（＝最舊）的那個 | `ndt` `app_started_at` |
| ③「跑過沒改看 helper 的 KERNEL_DIR」 | 新 `app_evidence_log`：`nsr/viz/te` ⇒ 我們自己的 log；`sim` ⇒ `lab_kernel_dir()` 那棵樹；`energy` ⇒ **rc 1（沒有管道）**。`lab_kernel_dir` **唯讀地**照 helper 自己的規則解析 `/etc/ndtwin-lab.conf` | `ndt` `lab_kernel_dir` / `app_evidence_log` / `residue_report` |
| ④「那句要真的查活行程」 | 沒有窗時先 `app_scan_pids`：有活行程 ⇒ 印 `running as pid(s) N but no pidfile ...` 並計入 `RESIDUE_BLIND`；沒有才印原本那句 | `ndt` `residue_report` |

### 2.1 兩個裁決沒寫、但不做就會壞掉的

- **`apps stop` 驗證停掉後刪 pidfile。** 不刪的話窗**有起點沒有終點**：sim 昨天停掉，今天的
  `--check` 仍然從昨天窗到現在，把之後裝的每一條規則（含 `ndt up` 自己的 baseline）算成
  SUSPECTED 殘留 ⇒ **永遠紅**。與 `nsr|viz|te` 分支的處置一致（那邊 09-02 就這樣做了）。
- **窗在停之前先讀（`RESIDUE_WINDOW`）。** 上一條會讓「`apps stop` 自己印的殘留報告」失去窗，
  而那正是殘留最重要的一刻（規則還在線上、裝它的行程已經沒了）。所以 `cmd_apps stop` 在
  **停之前**把每個目標的窗讀好，`residue_report` 優先用它。
  🔴 **這一條順手修掉了 `nsr/viz/te` 身上同一個洞**：它們的 `app_stop` 09-02 起就會刪 pidfile，
  所以 `ndt apps stop te` 自己印的殘留報告從來都是「no window」——這在本輪之前沒有人量過，
  是讀碼發現的（**讀過未執行**：沒有為它跑 live）。

### 2.2 `lab_kernel_dir` 是一份**複本**，這件事本身是風險

正本是 `/usr/local/sbin/ndtwin-lab`（09-07 查：與 repo 內 `tools/test_workflow/ndtwin-lab`
**byte-identical**，sha256 `6685d3a90fd94884f8fa…`。**跑過**：`sha256sum` 兩邊）。
`ndt` 現在自己實作了同一條規則，**因為裁決是「不動 helper、不 sudo」**——問 helper 要答案
（`sudo -n ndtwin-lab config` 會印 `KERNEL_DIR:`）就要一個 sudo 呼叫，而
`tools/test_workflow/sudo_surface.sh` 存在的理由就是把那個面積壓小。

複本的失效模式是**漂移**，所以：

- **每一條拒絕都照抄**：目錄先判（可寫目錄＝可換掉檔案）、symlink 拒、非 root 所有拒、
  group/other 可寫拒、未知 key ⇒ **整份不採用**、相對路徑／`..` ⇒ 拒、
  `KERNEL_DIR` 不是目錄或裡面沒有 `p4_proxy/mininet/ntg_bmv2_topo.py` ⇒ 拒。
  **`ndt` 信而 helper 不信的 config 會讓 `ndt` 指到一棵 root 沒在跑的樹**——FINDING-01 反過來，
  一樣安靜。
- **漂移由測試擋**：`tests/shell/test_ndt_helper_apps_window.sh` 群組 1 直接把 `ndt` 的
  `LAB_DEFAULT_KERNEL_DIR=`／`LAB_CONF=` **與 helper 的原始碼文字**對比，並在
  `/usr/local/sbin/ndtwin-lab` 讀得到時比對兩份 sha256（讀不到就印 `note`，**不算成一個通過的檢查**）。
- **沒有複製的**：`NTG_PY`／`ENERGY_DIR`／`SIM_DIR`（這裡用不到）、helper 那套大聲的拒絕訊息
  （它要據此**動作**，這裡只是讀一個 log 路徑）。

## 3. 為什麼 `energy` 不算紅

E-7 的口徑：**「查不了可以不紅，沒去查不准長得像查了沒事」**。
`energy` 的「在這裡跑過沒」**沒有任何管道**可以問——helper 給它的是一個純 tmux session，
輸出只存在 pane 裡。這件事在**每一台機器、每一次執行**都成立，所以把它折進 rc 會讓
`ndt status --check` 永遠紅，而**一個永遠過不了的閘門會在一天之內被忽略**——那正是 G-12
自己那些綠燈失去意義的方式。

所以：`RESIDUE_UNKNOWABLE` **不進** `residue_verdict`，但

- 殘留報告印 `CANNOT BE ASKED`＋為什麼，且**不再印** `no sign it ever ran here`；
- tally 後面多一行「and N app(s) could not be asked whether they ran here at all: energy」；
- `--check` 的 `residue` 列在 `none` 那一行下面多印一行黃字，並說明
  「'nothing found' above excludes them」。

### 4.1 為什麼動了 `test_apps_residue.sh` 的 5L

5L 的性質是「**空 log ⇒ 沒跑過（不紅）**／**非空 log ⇒ 跑過、窗掉了（紅）**」，而它拿
**`energy`** 來驗——`energy` 正是那個「log 這個管道根本不存在」的 app。

**精確地說那兩個 check 不是恆真的**（測試自己在 `$REPO` 底下建了 `app_energy.log`，
`-s` 那個分支真的被走過），**但它們驗的是一個在產線上不可能發生的情境**：`energy` 從來不會有
那個檔，因為 helper 不寫。⇒ 判別子對 `energy` 的**真實**行為（永遠回答「沒跑過」）
從來沒有被任何一格看過。**這就是 live 那一句「no sign it ever ran here」的單元測試版本：
測試靠自己捏出那個「它不存在才是重點」的檔案而通過。**
5L 改用 `te`（性質不變、而且對 `te` 在產線上為真），`energy` 自己的行為移到新的 5M 與新套件群組 7。

### 4.2 兩個既有套件為什麼要 stub `lab_kernel_dir`

修法之後 `app_evidence_log sim` 指向**主 checkout**的真實檔案
（`/home/adam/Desktop/NDTwin-Kernel/.test_run/logs/app_sim.log`，144 KB，04:42 留下的）。
不 stub 的話這兩個套件的 rc 會**取決於另一棵樹裡有什麼**——一個報告機器狀態而不是報告碼的套件。
stub 的寫法與它們既有的 `live_dataplane_kind` 同形。**解析規則本身**由新套件群組 1 負責，
沒有被 stub 掉。

## 6. 修完之後仍然為真的兩件事（不要當成已解決）

### 6.1 lw16pw 那一句不只屬於 helper 的兩個 app（**實測**，沙盒 1/1）

把 base（`ee0b399e`）的 `ndt` 原封不動抄到 `/tmp`，餵一個**真的在跑**的 te fixture、
一個 0 秒前裝的 pri-96 規則，跑 `cmd_apps stop te`：

```
  ok  te stopped (was: running) -- no process group, log writer or listener left
    te: no pidfile and no live process -- no window, so no rule can be dated
```

**成因跟 3-51 不同**：`app_stop` 的 `nsr|viz|te` 分支在驗證停掉之後刪 pidfile，而殘留報告在
那之後才跑——所以它問的是一個**兩行前才被自己刪掉**的紀錄。同一個腳本換成本分支的 `ndt`：

```
  te     window 2026-09-07 19:17:45 -> now (0s)
  XX        rule  dpid=2 table=0 pri=96 match={"in_port": 1} actions=["OUTPUT:2"]  installed 0s ago
```

⇒ `RESIDUE_WINDOW` 把兩個都修掉了。**要不要拆單由 Adam 裁**（R3-351 SUMMARY §7-1）。

### 6.2 一個新的「永遠紅」風險

修法之後，**任何** checkout 只要 helper 的 `KERNEL_DIR`（預設主 checkout）裡 `app_sim.log`
非空、而這裡沒有 sim 的 pidfile ⇒ `orphans`／`--check` 的 residue 判定就是「window is LOST」
⇒ **rc 5**。修法前這只在主 checkout 成立（讀碼 ＋ `rounds/08-round2.md` 的判斷），**現在是全域**。
**今天它就成立**：`/home/adam/Desktop/NDTwin-Kernel/.test_run/logs/app_sim.log`，144805 bytes，
root 所有，mtime 09-07 04:42。

報告會印 `(log read: <path>)` 讓人看得出是哪個檔造成的，但**這支工具清不掉它**
（root 所有，而 `apps trim` 走的是 `app_logfile`、不認得那條路徑）。
⇒ 三條路（**待裁**，SUMMARY §7-5）：(a) 現狀＋文件；(b) 收工時人工 `sudo truncate`；
(c) 讓 `ndt` 能請 helper 清掉它——那要動 helper。
