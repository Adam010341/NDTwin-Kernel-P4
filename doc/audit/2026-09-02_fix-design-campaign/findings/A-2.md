## 2. 機制

### 2.1 Ryu 側（item 2）：一個 accept 了不回答的 REST handler

```
kernel poll ──HTTP GET /v1.0/topology/links──► ryu-manager :8080
                                                  │ eventlet.wsgi.server 為每條連線 spawn 一個 greenlet
                                                  ▼
                                    rest_topology.TopologyController._links()
                                                  │
                                                  ▼
                                    topology.api.get_link(app, dpid)
                                                  │
                                                  ▼
                                    app_manager.send_request()
                                       ├─ send_event(dst='switches', EventLinkRequest)
                                       └─ return req.reply_q.get()   ◄── 無 timeout，永遠不回來
```

`ryu.topology.switches` 一卡住，這個 greenlet 就**停在寫出任何一個位元組之前**。
連線已經 accept，但沒有 response ⇒ curl 看到的是 **accept-then-stall**，`%{http_code}` ＝ `000`。

**兩個後果**：

1. **kernel 的 poll 執行緒永遠等下去。** `687de6c` 已經在 client 側加了 `--max-time 5` 把症狀綁住，
   但成因在這裡；一個無界的 server 仍然是一個無界的 server。
2. 🔴 **curl 的 abort 到不了這個 greenlet。** 它卡在 `reply_q.get()`，
   在它 write 之前不會發現 client 走了 ⇒ **它會卡到行程結束**。
   每一輪 poll 打三個端點，就從 eventlet 的 WSGI pool 漏掉最多三個 greenlet：

   ```
   $ grep -n 'DEFAULT_MAX_SIMULTANEOUS_REQUESTS' .../eventlet/wsgi.py
   18:DEFAULT_MAX_SIMULTANEOUS_REQUESTS = 1024
   ```

   ⇒ 夠久的 wedge 會把 1024 個位置耗光，`:8080` 連 accept 都不再被服務。
   **那時故障會換形狀**：從 accept-then-stall（打 `--max-time`）變成 no-accept（打 `--connect-timeout`），
   而 kernel 的恢復 INFO 從此不可能出現。**這是 entry 沒記到的二階效應。**

### 2.2 kernel 側（item 3）：一個沒有人說得出年紀的圖

`pollControlPlaneTopology`（`:508-585`）依序 fetch 三個端點，然後 `updateGraph` 一起套。
`687de6c` 之後，任何一個端點沉默都會走 `:557-574` 的邊沿觸發 WARN——但那條 WARN：

- **一個 outage 只發一次**（`if (m_topologyFetchFailures++ == 0)`）。之後長期半卡的控制平面**什麼都不寫**。
- **分不出「三個都沉默」與「只有一個沉默」**。前者是「控制平面不見了，圖整個凍住」，
  後者是「圖現在由兩個不同年紀的回覆拼起來」——兩種故障、兩種處置，今天長得一模一樣。
- **沒有任何可讀的狀態**。沒有東西能回答「上一輪完整嗎」。

⇒ **壞掉的不是套用政策，是可觀測性。**

## 3. 修法設計（含被否決的方案）

### 3.1 item 3 的裁決：**一輪不該是 all-or-nothing。** 套用拿到的那一半，但要說出來

**理由（按份量排序）**：

1. **三個寫入者單調向上（§1.3 已驗）。** 部分套用製造不出「down」，只可能沒抬起來。
   丟掉 switches 的好回覆，等於丟掉「這些交換機是活的」這件事**唯一可得的證據**。
2. 🔴 **all-or-nothing 會把 A-2 自己的故障方向弄得更糟。**
   A-2 的失效方向是**悲觀＋靜默**（`:120-121`：twin 顯示 40 條 link down、10 台 disabled，
   而 fabric 0% 遺失）。因為 links 沒回答就丟掉 switches 的回答，
   是**往那個悲觀方向再推一步**。而且這正是實測到的那種 wedge 的形狀：
   **`/links` 卡住、`/switches` 健康**（`get_link` 是會 block 的那個）——
   在 all-or-nothing 之下，twin 將**永遠不會再學到任何一台交換機是活的**。
3. **根本沒有 transaction 可以 roll back。** `updateSwitches` 在 `updateLinks` 跑之前
   就已經在 `m_graphMutex` 底下改完圖了。真正的原子性要 shadow graph ＋ swap，
   而那把 mutex 跟 liveness worker 與 REST 層共用 ⇒ 那是設計變更，不是「最小的可觀測改動」。
4. **合法的零連結是存在的。** `/v1.0/topology/links` 對一個還沒被 LLDP 發現完的 OVS fabric
   就是回 `[]`——**每一次開機都是這樣**。

### 3.2 🔴 `""` 與 `[]` 必須保持是兩種不同的答案

這是本題最容易做反、做反了最貴的一格。

`utils::execCommand`（`include/utils/Utils.hpp:543-568`）是裸 `popen(cmd, "r")`，
**只收 stdout，exit status 丟掉**（`:557-566` 只把它印到 `std::cerr`）。所以：

| 情況 | curl stdout | `body.empty()` |
|---|---|---|
| `--max-time` 逾時 | `""` | **true** ⇒ 沉默 |
| fabric 真的沒有 link | `"[]"`（兩個位元組） | **false** ⇒ 有回答 |

⇒ **沉默的判準必須是 `empty()`，不能是「沒有 entry」。**
把它收緊成「links 沒有元素就算沒回答」，會讓**每一次正常開機**都被報成 wedge——
就是 memory 記的那個形狀：**意外的案例被拿去低估故意的案例**。
mutation 5 就是專門盯這一格的。

### 3.3 落地（最小改動，純新增：210 行 insert、0 行 delete）

private 區新增 `PollRoundKind m_lastPollRoundKind = PollRoundKind::NotYetPolled;`

### 3.4 item 2 的落地：patch stock `ryu/app/rest_topology.py`

檔案不在本 repo（site-packages），依指示交付為 **patch 檔**，未在別的 repo commit：

- patch：`A-2_ryu_rest_topology_bounded.patch`（`patch -p1` dry-run 已驗 exit 0）
- patch 過的檔：`A-2_ryu_rest_topology_patched.py`
- 測試：`A-2_test_ryu_rest_topology_bounded.py`（紅綠都跑過，見 §4）

作法：三個 handler 各包一層 `hub.Timeout`（跟 `intelligent_router.py` 用的是同一個原語，
在這個 stack 裡已經驗過），逾時回 **HTTP 503 ＋ 空 body**。

**為什麼是「5xx ＋空 body」而不是別的**——這一格是整個 patch 的關鍵：

| 選項 | kernel 會看到什麼 | 判定 |
|---|---|---|
| 維持 hang | 什麼都沒有，連線被握著 | 現況 |
| **5xx ＋ 有 body**（錯誤頁／`{"error":...}`） | **非空字串** ⇒ 該輪被判成 `Complete` ⇒ 丟給 `json::parse` 或當拓樸迭代 | 🔴 **比 wedge 更糟**：把可偵測的沉默換成偵測不到的「答了垃圾」 |
| **5xx ＋ 空 body** | `""` ⇒ 走 `687de6c` live 驗過的那條路：邊沿 WARN、圖保留上次、我的 partial 行 | ✅ **選這個** |

決定性的理由：**`execCommand` 把 exit status 丟掉，HTTP status code 根本到不了 kernel，
body 是唯一的通道。** 所以 body 必須是空的；status code 設 503 是給 proxy／健康檢查／
`curl -i` 的人看的（也是誠實的那一碼），kernel 看不到它。

**逾時值 3 秒，而且必須 < kernel 的 `--max-time 5`**：先放棄的那一邊才有機會解釋發生了什麼。
若 server 的上限比 client 大，永遠是 client 先 abort ⇒ Ryu 那條 warning 永遠不會寫、
greenlet 也不會被釋放，等於沒修。

**已驗的正確性細節**（`eventlet/timeout.py`）：
`Timeout` 繼承 **`BaseException`**（`:38`），所以 `except Exception` 抓不到它——必須寫 `except hub.Timeout`；
`__exit__`（`:129-132`）只在 `value is self and self.exception is False` 時吞掉例外，
而 patch 沒有傳 `exception=False` ⇒ 例外會正常傳播到 `except hub.Timeout`。**兩點都已按原始碼確認，不是推測。**
