## 3. 修法設計

### 3.1 核心：把兩值輸出換成四值輸出

每支工具原本只有兩個答案（綠／紅），所以**唯一講不出來的話就是「我沒辦法判斷」**。
`spec.py` 加兩個前綴常數，`partition_messages()` 統一拆分（放在 `spec.py` 而不是 runner，
是為了讓 L3 跟未來的呼叫端**用同一套定義**——三支工具對「紅代表什麼」各有見解，正是 A-8
變成三個獨立假警報而不是一個的原因）：

```python
TOOL_PRECONDITION = "TOOL-PRECONDITION-FAILED: "   # 對系統不做任何宣稱
ACCOUNTED_FOR     = "ACCOUNTED-FOR: "              # 說明得出來的偏差，不算失敗
```

**三個答案（`inv_all_switches_up` / `inv_edges_enabled` 各自實作）**：

| 狀況 | 答案 | exit |
|---|---|---|
| down 且 power state 說 **ON** | **失敗，原字串原封不動**（P4 接線失敗偵測完整保留） | 1 |
| down 且 power state 說 **OFF** | `ACCOUNTED-FOR`，**印出來**、不算失敗 | 0 |
| down 且 power state **讀不到** | `TOOL-PRECONDITION-FAILED` | **3** |

🔑 **早退設計**：沒有任何 down／disabled 時**直接回空**，不管 power state 知不知道。
⇒ **健康的 fabric 的輸出跟修改前逐字元相同**，precondition 只在它真的會改變判決時才出現。

🔴 **兩個猜測都不能用**，這是設計的關鍵：
- 猜「全開」⇒ 重現 A-8 假警報。
- 猜「全關」⇒ **蓋掉 P4 接線失敗**，也就是這個不變量存在的理由。
⇒ 所以必須有第三個值。

### 3.2 power state 的讀取：`PowerState` ＋ `classify_power_state`（純函數）

`spec.py` 新增 `PowerState`（`off_dpids` ＋ `error`，`known` 屬性）與
`classify_power_state(payload, ip_to_dpid)`。**任何無法得出「完整且無歧義」dpid 集合的分支都回 unknown**：

| 情況 | 為什麼不能默默當成 ON |
|---|---|
| body 不是 object | 型別不對就不是一個讀數 |
| 值不是 `ON`／`OFF` | 把不認得的狀態當 ON＝取得一個**有自信的錯答案** |
| key 不是本 topology 的交換機 | 那個讀數在描述**別座** fabric |
| topology 有、讀數缺 key | **部分覆蓋會讓已關機的交換機看起來是開的**＝A-8 再現。kernel 有前科：04b8933 之前 CPU／memory map 會**整個省略** down 交換機的 key（F-3） |

`run_contract_test.py` 新增 `probe_power_state()`（唯一做 I/O 的部分），
`Context` 新增 `switch_ip_to_dpid`（**從 topology 檔算，不需要 kernel**），
且 `Context.power_state` 預設是 **`PowerState.unknown(...)`，不是 `all_on()`**——
**建構一個 Context 不構成關於 fabric 的證據**。

### 3.3 `check_logs.py`：有範圍的許可 `WHEN-POWERED-OFF`

新的 rule kind，**不是 allowlist 的第四種寫法**：

| 宣告 | `... read failure for switch 5 ...` | exit |
|---|---|---|
| `--powered-off 5` | **EXPECTED**，另一區印出 | 0 |
| `--powered-off 7` | **PROBLEM**（原樣全額） | 1 |
| `--powered-off none` | **PROBLEM** | 1 |
| （不給旗標） | **TOOL-PRECONDITION-FAILED** | **3** |

- 樣式**必須**含 `(?P<dpid>\d+)`，否則 `load_allowlist` 直接 `SystemExit`——
  沒有它就是**一張空白許可**，正是這個 kind 要避免的東西。
- `--powered-off none` 是**一個真的宣告**（「我斷言沒有任何一台被關」），
  **跟不給旗標不是同一件事**。這是 2026-08-07 wedged-controller 偵測活下來的方式。
- 新增「宣告了關機但 log 裡沒有對應行」的提示——**宣告與 log 不一致本身值得說**
  （可能表示關機根本沒生效）。
- `WHEN-POWERED-OFF` 不列入 stale 檢查（沒觸發代表這輪沒關機，不是規則爛掉）。
- crash 掃描（`check_logs.py` 的 `all_entries` 迴圈）在 rule 迴圈**之前**，
  所以 power 宣告碰不到它——crash 仍然不可 allowlist。
- `--suggest-allowlist` 遇到 undecidable 行時印 `NOT SUGGESTED` 並回 3，
  否則它會在「刻意沒判斷的行」上面印「nothing unmatched」——正是要消掉的沉默零。

### 3.4 字串相容性（🔴 這一條差點把修法本身變成 A-8）

R5 harness 用 **grep 字串**而不是 exit code 判定 A-8 在不在：

（若不釘，修好之後 harness 仍會報「F-2 present」——**儀器在上一層模仿自己的發現**。）

### 3.5 被否決的方案

| 方案 | 為什麼否決 |
|---|---|
| **A. 把 `reported a read failure` 加成普通 `WARNING`** | 🔴 **最危險的一個**，而且是工具自己建議的。它會在**沒有任何交換機被關**時一併消音，那正是 2026-08-07「Ryu wedged、十台全報 0 條規則而 s1 其實有 130 條、每個 liveness 指標都綠」的缺陷。**修 A-8 會換來把 04b8933 那條線弄瞎。** |
| **B. 用 `known_gap`（既有黃燈機制）** | `known_gap` 的語意是「這是 kernel 的缺陷，暫時容忍」，會印 `remove the known_gap marker` 並在修好時報 FIXED。但**被關機的交換機不是缺陷**，是合法運作狀態，永遠不會「修好」⇒ 這條 marker 永遠拿不掉，而且它把一個正常狀態記成待修缺陷。 |
| **C. 用 `admin_disabled` 區分（08-18 的建議）** | 見 §2.2 ⚠️：那是 Intent Translator 的欄位，Energy-App 不寫它，08-18 實測為 false。**照做會得到零效果，而且看起來像修好了。** |
| **D. 不變量預設「猜全開」，只在拿得到讀數時才收斂** | 就是現況。假警報照舊。 |
| **E. 不變量預設「有 down 就當成 power-down」** | 蓋掉 P4 接線失敗——把一個悲觀缺陷換成一個**樂觀**缺陷，方向更糟。 |
| **F. 只加註解／文件說明「紅色可能是正常的」** | [[instrument-must-not-mimic-its-own-finding]] 的 How-to-apply 第一條就否決它：**「不是加註解說明，是改輸出」**。而且讀者訓練成忽略紅色的效果不變。 |
| **G. 讓 L2 把 `get_switches_power_state` 移到 `get_graph_data` 前面** | 只解決順序，不解決「讀不到時怎麼辦」，也不解決 L3 與 check_logs。而且改 `ENDPOINTS` 順序會動到 `--save-json` 的產生順序與既有 baseline 對帳。 |
