## 2. 機制

### 2.0 先更正標題：它不是「永遠不放」，它是「放了 300 秒又立刻搶回去」

KNOWN-ISSUES 的標題寫「永遠不放」，同一條的內文寫「空轉滿 300 秒 TTL」。**內文是對的，標題是誇飾**，
但兩者其實可以合起來——而合起來之後比任何一半都糟，這一點目前沒有被寫下來：

- 租約確實會過期：`acquireLock` 有時間比較（`LockManager.hpp:203`
  `if (state.isLocked && now < state.expiryTime) return false;`）。300 秒後鎖是可取的。
- 但 app 的重試迴圈是 **1 Hz**（`energy_saving_app.cpp:952-956`），而它是唯一一個在等這把鎖的人。
  ⇒ 租約在 T+300 過期，app 在 **T+300±1 秒**就重新取得、重新卡死、再鎖 300 秒。
- ⇒ 對**任何第三方**而言（TE-App、契約測試、chaos harness、operator 的 curl），
  這把鎖的可取用窗口是**每 300 秒一次、寬度 <1 秒、而且被一個 1 Hz 的輪詢者佔走**。
  🔑 **這是 polling livelock，不是死結**；「永遠不放」在可觀測意義上成立，
  而修法不能只靠「反正 TTL 會到期」——**到期救不了它**。

### 2.1 kernel 側

檔案：`include/ndt_core/lock_management/LockManager.hpp`（**header-only，沒有 .cpp**）、
`src/ndt_core/http/HttpSession.cpp`。

#### (a) 有沒有 TTL／到期？——有，但只有一個人在看

| 問題 | 答案 | 位置 |
|---|---|---|
| `LockState` 有到期時間嗎 | 有：`bool isLocked` ＋ `std::chrono::steady_clock::time_point expiryTime`，**沒有 owner、沒有 lease id** | `LockManager.hpp:18-21` |
| acquire 會看到期嗎 | **會**：`if (state.isLocked && now < state.expiryTime) return false;` | `LockManager.hpp:203` |
| renew 會看到期嗎 | **會**（2026-09-01 B-2① 才補上）：`\|\| now >= it->second.expiryTime` | `LockManager.hpp:305` |
| unlock 會看到期嗎 | **不會**：只看 `it->second.isLocked` | `LockManager.hpp:246-248` |
| 到期會清掉 `isLocked` 嗎 | **不會，而且是刻意的** | `LockManager.hpp:285-289` 的註解 |

`LockManager.hpp:285-289` 原文（這段是本題的關鍵，它自己預告了 A-9）：

> An expired entry is deliberately left `isLocked == true` on the refusal path. Clearing it
> would be a state change made by a call that returns false, and it would silently alter what
> unlock() answers for the same lock (unlock currently reports true for an expired-but-flagged
> entry). That is its own decision and it is not smuggled in here.

⇒ **「那個自己的決定」就是 A-9。** 修 B-2① 的人把它記下來留給後面的人，現在輪到它了。

#### (b) 有 renew 端點嗎？持有者不 renew 會怎樣？

有：`POST /ndt/renew_lock` → `HttpSession.cpp:2096`。持有者不 renew ⇒ 租約在 `expiryTime` 到期，
**但系統沒有任何一處觀測到這件事**：

- 沒有清道夫（sweeper）、沒有計時器、沒有背景執行緒。到期只在「下一個人來問」時才被發現。
- 沒有 log。到期不會產生任何一行輸出。
- **沒有任何讀取端點**：kernel 只有 acquire／renew／release 三個 POST，
  **沒有 `lock_status` 之類的東西**（`grep -rn "m_lockManager" src/ include/` 全部命中只有
  `HttpSession.cpp:2043/2096/2160` ＋建構子）。
  ⇒ operator 想知道「誰持有 routing_lock、還剩幾秒」時，**唯一的辦法是去搶它**。
  TR-5 的診斷之所以要撈 app 自己的 tmux buffer，就是因為 kernel 這邊什麼都問不到。

#### (c) 持有者的連線死掉會怎樣？——鎖活下來，實測過

鎖存在於 `main.cpp:392` 建立的**單一 process-wide** `shared_ptr<LockManager>`，
經 `ControllerAndOtherEventHandler.cpp:253` 傳給每個 `HttpSession`。
`LockState` 裡沒有任何東西指向連線或 client。⇒ 連線關閉／client 被殺，鎖原封不動。

**這不是推論，是量過的**：`doc/audit/2026-08-30_live-traffic-round/FINDING-08_energy-app-locks-itself-out.md`
第 6 點：「after `ndtwin-lab energy-stop`, a fresh `acquire_lock` still returns **423**.
Killing the app does not free it.」

#### (d) 🔴 kernel 從來不檢查這把鎖——它是純諮詢鎖

`m_lockManager` 在整個 kernel 只被三個鎖端點碰過（見上）。
**`/ndt/set_switches_power_state`、`/ndt/install_flow_entry`、`/ndt/delete_flow_entry`
沒有任何一個會問「routing_lock 現在被誰持有」。**

⇒ 「持有者在租約過期後還去動網路」這件事，kernel **不會拒絕，也不會發現**。
這正是 memory `rejected-requests-can-still-act` 的鄰居，但更乾淨：這裡連拒絕都沒有。
⚠️ 這一點對第 2.3 節的歸因很關鍵——**0 台被關不是 kernel 擋下來的**。

#### (e) 🔴 過期後的 release 會搶走「現任持有者」的鎖，而且回 200

這是本題在 kernel 側最實質的缺陷，目前沒有被任何一條 KNOWN-ISSUES 精確描述
（B-2② 講的是「任何人可以釋放任何人的鎖」，這是它的一個更陰險的特例——**呼叫端沒有做錯任何事**）：

```
t=0     A: POST /ndt/acquire_lock {"type":"routing_lock","ttl":300}   → 200, isLocked=true, expiry=t+300
t=300   租約到期。沒有人被通知，isLocked 仍然是 true。
t=301   B: POST /ndt/acquire_lock {"type":"routing_lock","ttl":300}   → 200（正確：acquireLock 比了時間）
                                                                        isLocked=true, expiry=t+601
t=302   A: POST /ndt/release_lock {"type":"routing_lock"}             → 200 {"status":"released"}

```

結果：**B 的鎖被 A 放掉了，B 從頭到尾不知道**（`LockManager.hpp:246-250`）。
B 只會在下一次 renew 失敗時發現——而 Energy-App 與 TE-App **都不呼叫 renew**（見 2.4 的呼叫端普查）。
A 這一側收到的是 `200 {"status":"released"}`——**跟正常釋放一個字都不差**。

**這條路是走過的**：FINDING-08 的 "Also observed, out of PREREG scope" 段落記載，
一個從沒 acquire 過的裸 `curl` release 掉了 app 的鎖並得到 200。
那次是刻意用來清場的（也是 KNOWN-ISSUES A-9 寫的繞法），但門是同一扇。

## 3. 修法設計

### 3.0 這一題到底要修什麼——先把它講清楚

指派信說「a lock without expiry is a design defect」。**讀完碼之後這句話要修正：這把鎖有 expiry。**
`acquireLock` 從一開始就比時間，`renew` 在 2026-09-01 補上了同一個比較。
**真正的缺陷不是缺 TTL，是「到期這件事發生了，但系統裡沒有任何一個地方記下它發生過」。**

到期只在「下一個人來問」的那一瞬間被當成一個**條件**檢查，從來不是一個**事件**。
於是三個具體後果，全部是誠實性問題而不是互斥性問題：

| # | 後果 | 舊行為 |
|---|---|---|
| D1 | 過期的 release 與正常 release 無法區分 | 都是 `200 {"status":"released"}` |
| D2 | 過期後的晚到 release 會清掉**現任持有者**的鎖 | 200，現任持有者不被告知 |
| D3 | 到期完全不可觀測 | 無 log、無計數、無讀取端點 |

**這正好對上指派信的三條誠實性要求**（誠實回報到期／到期後不得靜默成功／有 renew 就要強制到期）。

### 3.1 設計

**單一接縫 `reapIfExpired()`**（`include/ndt_core/lock_management/LockManager.hpp:121-152`）：
把「到期」從**條件**升級成**事件**，並且**只有一個地方**做這件事，
acquire／renew／release 三支全部經過它。
（為什麼一定要單一接縫：B-2① 的成因就是 `renew` 與 `acquireLock` 對「held」的定義不一致；
再多一個地方自己判斷到期，就是再造一次 B-2①。）

它做四件事：清 `isLocked`、`expiredLeaseCount += 1`、記下 `expiredLeaseId`、**寫一行 WARN**。

**lease id（不是 owner）**：`LockState::leaseId`，每次成功 acquire 遞增、永不重用，manager 內全域單調。
🔑 **刻意不叫 owner。** owner 需要 kernel 知道「誰在呼叫」，而 kernel 沒有、也不可能有
（線上沒有任何憑證）。lease id 回答的是一個 kernel **答得出來**的較窄問題：
「這把鎖還是你拿到的那一份租約嗎？」

**三個端點的回覆**：

| 端點 | 情況 | 舊 | 新 |
|---|---|---|---|
| acquire | 成功 | `{status,type,ttl}` | ＋`lease`、`reclaimed_expired_lease` |
| acquire | 被持有 | 423「retry after its TTL」 | ＋`held_by_lease`、`retry_after_s` |
| release | 活著的租約 | 200 released | **不變**（`body.size()==2` 的既有斷言保住） |
| release | **過期的租約** | **200 released** | **412 `reason:"expired"`** |
| release | 沒持有 | 412 | 412 ＋`reason:"not_held"` |
| release | lease 不符 | （不存在） | 409 `reason:"lease_mismatch"`，**且不釋放** |
| renew | 過期／沒持有 | 412「expired or not held」 | 412 ＋`reason` 分家 |
| renew | lease 不符 | （不存在） | 409 |

**「持有者在過期後想動作會怎樣」**——指派信要求「必須被拒絕，不能靜默成功」。
分成兩半誠實回答：

1. **對鎖端點本身**：過期後的 release／renew **會被拒絕**（412 `expired`／409 `lease_mismatch`），

```cpp
// [Co-developed with claude code -- Adam]
// The lock is taken by loop_with_fixed_rate() and must be given back by EVERY exit from the
// cycle, not by the two paths that happen to reach a release_lock(). Today the releases live in
// handle_simulation_result() (behind a completed Simulation-Platform-Manager round trip) and in
// easy_disable_switch()'s !sentCase branch; easy_enable_switch() has none at all, and neither
// does any early return or exception inside run_switch_cycle_once().
class RoutingLockGuard
{
  public:
    RoutingLockGuard() = default;
    ~RoutingLockGuard() { if (m_armed) release_lock(); }
    RoutingLockGuard(const RoutingLockGuard&) = delete;
    RoutingLockGuard& operator=(const RoutingLockGuard&) = delete;

    /// Hand the lock over to the in-flight simulation. Call this ONLY where a case was actually
    /// sent -- i.e. exactly where `canSendNextSimulation` is set false and stays false.
    void handOffToSimulation() { m_armed = false; }

  private:
    bool m_armed = true;
};
```

```cpp
void loop_with_fixed_rate(std::chrono::milliseconds period)
{
    auto next = Clock::now();
    while (true)
    {
        next += period;
        if (!acquire_lock()) { std::this_thread::sleep_for(std::chrono::seconds(1)); continue; }

        {
            RoutingLockGuard held;                 // released on EVERY exit below
            if (!run_switch_cycle_once(held)) {
                SPDLOG_LOGGER_WARN(Logger::instance(), "switch cycle failed; routing_lock released");
            }
        }

        auto now = Clock::now();
        if (now < next) std::this_thread::sleep_until(next);
    }
}
```

## C8. auditor 追加的兩條規則（2026-09-02 第二次）

### (1) restore 之後的 mtime —— **字面上本來就對，但已改成明講**

三把閘的 `restore()` 用的是**普通 `cp`**（不是 `cp -p`／`cp -a`），
所以還原後的 mtime 是**現在**，比那顆 mutant 編出來的 .o 新 ⇒ 下一輪 `build()` 會重編。
而且每把閘最後都已經有 `restore` 後的一次 rebuild（`[[ dry ]] || build > /dev/null 2>&1`）。

**仍然加了 `touch` 並把理由寫進碼裡**，因為這個失效**看不見**：
`cp -p`／`cp -a` 會把**原本的** mtime 放回去 ⇒ ninja 判定沒變 ⇒
**下一顆 mutant 是拿上一顆 mutant 的 .o 在測**，之後每一筆結果都被歸到錯的那次修改上，
**而閘看起來仍然在正常運作**。距離「有人順手把它整理成 `cp -a`」只有一步。

批次 runner 也在 byte-identity 檢查之後**再 rebuild 一次**，
當作某把閘提早退出時的兜底。

### (2) 沒跑到的 mutant ＝ SURVIVOR —— **這條本來沒做到，已修**

| 情況 | 舊行為 | 新行為 |
|---|---|---|
| mutant 編不起來 | `BUILD-FAIL`，**自己一欄** | **`SURVIVED`**；`build_failures` 只留作子集計數 |
| anchor 對不上 | `exit 2`，**整把閘中止** | **`SURVIVED`**，閘**繼續跑完**；`anchors_missed` 為子集計數 |

🔑 **舊的分欄讓一把閘可以印出 `survivors=0`，旁邊卻躺著一顆從沒被量到的案例。**
而 `exit 2` 中止整把閘，會把它後面所有結果一起丟掉——
**一個窗口要跑完所有分支的批次時，那是錯的取捨。**

`killed = mutations - survivors`，沒有任何重複計數；
`build_failures` 與 `anchors_missed` 都**印出來但不再加上去**
（讓讀者分得出「測試沒發現」與「測試根本沒跑」）。
`--dry-run` 也一樣：anchor 不見＝那顆變異跑不了＝survivor ⇒ 退出碼 1。
