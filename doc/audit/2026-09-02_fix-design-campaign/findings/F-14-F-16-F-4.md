### 2.5 共同的根 —— 誠實地說是「兩個根、一個位置」

**根 A（F-14 + F-16 共用）：發現路徑是單調的，只會往 up 寫。**
`updateSwitches`（`:637-638`）、`updateHosts`（`:720-721`、`:760-761`、`:796-797`）、
`updateLinks`（`:932-933`）——**六處賦值，全部是 `= true`，全庫沒有一處發現路徑寫 `false`**。
圖是「歷來看過的一切的聯集」，不是「現在被報到的東西的交集」。
而唯一能寫 `false` 的三條路（電源致動、switch liveness 迴圈、`/ndt/link_failed` API）
**沒有一條的定義域包含 host 頂點或 host-facing 邊**。

**根 B（F-4 專屬）：一個 up-writer 的選擇器太寬。**
`updateHosts` 用「IP 相符」當選擇器，而那個述詞在這張圖上不蘊涵「這是一條 host 邊」。
這**不是**根 A 的推論：就算把 poll 改成對帳式的，只要那筆假 host 條目**這一輪有被報到**，
錯的邊還是會被標 up。⇒ **F-4 必須另外修一刀。**

**兩個根共享的設計決定**：發現路徑不區分「這一輪被報到」與「這一輪沒被報到」，
也不區分「這個 IP 是 host」與「這個 IP 只是剛好對上」。兩個都在同一組函式裡。

## 4. 修法設計

### 4.1 一句話

**把「交換機不可用」這件已經有證據的事，傳播到它承載的邊與 host 上（帶遲滯、帶理由），
並且不准 host 條目再去碰非 host 的邊。**

### 4.2 為什麼不是「把 poll 改成對帳式」（被否決的主要替代方案）

最直覺的修法是：poll 時記下控制面這一輪報了哪些東西，沒被報到的往 down 推。
**這個方案在 host 上永遠不會觸發**，理由在 §2.2：兩個控制面的 host 表都是 append-only
（`ryu/topology/switches.py:190-200` 沒有 timeout；`topology_manager.py:539` 逐字說 append-only）。
⇒ 它會編譯、會通過我寫得出來的每一個單元測試（因為測試裡我可以自己餵一份「少了 h1」的回覆），
**而在真機上一次都不會走到**。那是「儀器長得像自己的發現」的典型形狀，明確否決。

其次，它在 link 上**很危險**：控制面回一個合法的空陣列 `[]`（Ryu 剛啟動、或收斂中）
會把整張圖推下去——那正是 A-2（`kTopologyConnectTimeoutSeconds` 那段註解 `:395-420`）
花力氣擋掉的失效模式。

### 4.3 被否決的其他替代方案

| 方案 | 否決理由 |
|---|---|
| 幫 host 加一個 ping/ARP 探針 | 這是**新的量測**，不是修這三條缺陷；而且要跑 Mininet 才能驗，本輪不准。可以是後續工單。 |
| 讓 `handleLinkFailure` 也接受 host IP | 只修 F-16 的一半（要外部有人來 POST），對 F-14 無效，且擴張了一個跨 repo API 的形狀。 |
| 在 `setVertexDown` 裡直接連帶把邊寫 down | 沒有遲滯 ⇒ 1 Hz liveness 的一次抖動就會讓十幾條邊與 host 翻面。而且 `setVertexDown` 也被電源致動路徑呼叫，語意會混（「操作員關機」與「觀測到不可達」共用一條副作用）。 |
| 只修 F-4（維持 08-18 裁定） | 見 §3 第 1 點：三條合起來才是「沒有可信的 down 路徑」，單修 F-4 不改變那個結論。 |

### 4.4 修法（三個部分，都在同一組函式）

**(a) F-4 的守衛 —— `updateHosts` 不准碰非 host 的邊。**
1. 解析出 `ip` 之後、做任何邊查找之前：若 `findSwitchByIp(ip)` 有值，這筆「host」條目**就是**
   一台交換機的管理 IP 被學成 host ⇒ 具名 WARN 之後 `continue`。這一行同時**把 F-4 的成因講出來**。
2. 兩處邊查找各加一個方向守衛：host→switch 邊必須 `srcDpid == 0`；switch→host 邊必須 `dstDpid == 0`。
   （縱深防禦：就算未來有別的路徑製造出 IP 誤判，也搆不到 switch–switch 邊。）

**(b) F-16 + F-14 的傳播 —— 新的 `reconcileDerivedLiveness()`，在 `updateGraph()` 之後跑。**

```
對每一台交換機 s：
    usable(s) = isUsable(vertex(s))            // isUp && isEnabled && !adminDisabled
    if usable(s):  missCount[s] = 0
    else:          missCount[s] += 1
    isolating(s) = missCount[s] >= kMissesBeforeIsolating

對每一條 edge e：
    若 e 的任一端點是「isolating 的交換機」 ⇒ setEdgeDown(e), downReason = SwitchUnreachable
    否則若 e.downReason == SwitchUnreachable ⇒ 清掉 reason（不主動標 up，交還給發現路徑）

對每一個 host 頂點 h：
    若 h 的每一個接取交換機都 isolating ⇒ isUp = false, downReason = SwitchUnreachable
    否則若 h.downReason == SwitchUnreachable ⇒ 清掉 reason（不主動標 up）
```

🔑 **恢復是「清 reason」而不是「標 up」**，這一點是刻意的：
把 up 的權力留給發現路徑（它有證據——控制面報了它），
傳播只負責**它自己造成的那個 down**。否則傳播就會變成第七個「無證據標 up」的地方。

**(c) 可觀測性 —— `downReason` 欄位 + 邊緣觸發的 log。**
- `GraphTypes.hpp` 新增 `enum class DownReason { None, SwitchUnreachable }`，
  `VertexProperties` 與 `EdgeProperties` 各一個欄位，預設 `None`。
- `to_json(VertexProperties)` 與 `HttpSession::handleGetGraphData` 的邊物件各**新增一個 key**
  `down_reason`（`"none"` / `"switch-unreachable"`）。
  **新增 key、不改既有 key 的型別或語意** ⇒ 這是 repo 自己用過的加法式契約變更
  （`GraphTypes.hpp:340-343` 的 `admin_disabled` 就是同一手）。
- log 只在**轉移**時寫（`downReason` 從 `None` 變成 `SwitchUnreachable`，或反向），
  不是每個 poll 一行——與 `m_topologyFetchFailures`（`:553-570`）、`FailureRun`
  （`DeviceConfigurationAndPowerManager.hpp:59-80`）同一個邊緣觸發形狀。
- **不發 event**：`LinkFailureDetected` 在生產碼裡**零個 handler**
  （全庫 grep `registerHandler`，`src/` 下零命中、含 `src/main.cpp`；

### 4.5 遲滯：`kMissesBeforeIsolating = 2`，以及為什麼

- **噪音在哪裡**：不在傳播，在被傳播的那個訊號。switch 的 liveness 已經是三態
  （`ovsLivenessFor` / `p4LivenessFor`，`DeviceConfigurationAndPowerManager.hpp:249-254`），
  **`Unknown` 不寫圖**（`:766-770`、`:743-747`）⇒ 圖上的 `isUp == false` 一定來自
  「查詢成功而且這座橋不在」的**正面觀測**，不是「查不到」。這是強訊號。
- **但仍會有暫態**：power-cycle 期間 `del-br` 與 `add-br` 之間、bmv2 重啟的窗，
  都會產生一次真實但短命的「不在」。
- **兩次連續 poll**：拓撲 poll 收斂期 5 s、之後 30 s（`run()` :2129-2131）
  ⇒ 兩次相隔 ≥5 s，而 liveness 迴圈是 1 Hz ⇒ 中間至少五次獨立觀測都說不在。
  這足以濾掉 power-cycle 的窗，而**不需要**自己再造一套計時器。
- **恢復不設遲滯（1 次 poll）**：恢復方向沒有歧義（交換機答了），而慢在恢復方向
  = 分身報一個不存在的故障（悲觀），那是使用者立刻會抱怨、也立刻會被否證的方向。
- ⚠️ **代價要講明**：收斂之後 poll 是 30 s，兩次 ⇒ **最壞 60 s 之內，被孤立的 host 還是讀成連著的**。
  這是「從不」改成「最多 60 s」，不是「立刻」。要更快就得把常數調小或把傳播搬進 1 Hz 迴圈
  ——後者要自己造遲滯計時器，複雜度不成比例。**數字放成具名常數，改它是一行。**（開放題 Q2）

4. 等 **2 個拓撲 poll**（收斂後 30 s／格 ⇒ 最壞 ~60 s）。
5. **判準（全部成立才算 PASS）**：
   - `10.0.0.1`（掛 s1）：`is_up == false` **且** `down_reason == "switch-unreachable"`
   - `10.0.0.100`（掛 s4）：`is_up == true` **且** `down_reason == "none"`
   - s1→10.0.0.1 的邊：`is_up == false`、`down_reason == "switch-unreachable"`
   - s5→s9 的邊：`is_up == true`
   - kernel.log 有 `... edge(s) and ... host(s) moved to down with down_reason=switch-unreachable`
     **而且只有一行**（驗邊緣觸發，不是每 poll 一行）

**arm 2（負控制，必跑）** — **什麼都不殺**，等同樣長的時間，重跑判準。
128 台 host 必須**全部**維持 `is_up == true`。
**沒有這一 arm，arm 1 的綠對「分身把東西全推下去」零鑑別力。**

**arm 3（遲滯，必跑）** — `sudo ovs-vsctl del-br s1 && sleep 2 && sudo ovs-vsctl add-br s1`（並接回 port）。
在**一個 poll 之內**完成的來回**不得**讓任何 host 翻面。
⇒ 這是 `kMissesBeforeIsolating = 2` 唯一能被否證的地方，而那個數字是我用推理選的、沒有量過。

**arm 4（F-4）** — 要重現「交換機管理 IP 被學成 host」。08-18 的 subagent 是用
「切斷 s10 的 controller」觸發的（18 次）。
先驗觸發條件：
`curl -s localhost:8080/v1.0/topology/hosts | jq '[.[]|select(.ipv4[0]|startswith("192.168.123"))]'`
- 不為空 ⇒ 條件成立。此時 kernel.log 應出現
  `ignoring hosts entries for ...: 192.168.123.x is a switch's management address` **恰好一次**；
  且先 `POST /ndt/link_failed` 把 s1–s5 標 down、等 ≥2 個 poll，那條邊**維持 down**。
- ⚠️ **為空 ⇒ 這一 arm 是 INCONCLUSIVE，不是 PASS。**
  （這正是 08-18 那輪「我 0 次、subagent 18 次」的差別所在。）

**進 audit-raw 的**：`get_graph_data` 的**原始**回應（不是我摘出來的數字）、kernel.log 相關段落、
`ovs-vsctl list-br` 前後、每個 arm 的時間戳。

### 7.4 我知道但沒有處理的

- **兩處方向守衛的 WARN 沒有速率限制。** 前置的 `findSwitchByIp` 拒收有做（一個位址一行），
  那兩處「方向不對」沒有。理由：只要前置守衛還在它們不可能觸發；真觸發代表出現新路徑，
  那時重複警告是正確產出。**但那天到了，它會是每 poll 一行。**
- **`updateHosts` 在 MAC 查不到時不 `continue`** 我沒有改。它是 F-4 鏈條的一環，
  但改它會影響「MAC 對不上、IP 對得上」的合法 host（例如拓撲檔 MAC 過期），是另一個判斷。
- **`m_switchIpsOfferedAsHosts` 永不清空**（刻意）。上界＝拓撲裡的交換機數（10），
  寫在這裡以免被當成洩漏。
- **新的 down 不發 `LinkFailureDetected` 事件**。見 §4.4(c)：生產碼零個 handler。
- **`run()` 的 `graphLivenessSummary` 那行會開始變動**（hosts-up／edges-up 下降）。
  那是本修法在 kernel.log 裡唯一直接可見的差別，也是 live 驗證的抓手。

## 8. 給 Adam 的開放題（每題都寫後果）

**Q1 — F-4 的 08-18「不修」裁定要不要翻案？**
- **(a) 翻案、併入本修法**（建議）：三條一起修，F-4 的守衛已寫好、與 F-14/F-16 同一個函式。
  後果：`/ndt/get_avg_link_usage` 與 `get_top_k_congested_links` 在有交換機死掉時讀值會變
  （往誠實方向），要對帳。
- (b) **維持不修，只取 F-14/F-16**：把三道守衛 revert 掉。
  後果：`reconcileDerivedLiveness` 每 poll 把 s1 的邊標下去、`updateHosts` 又用假 host 條目
  把其中一條標上來——**兩個機制在同一條邊上打架**，只因為 reconcile 跑在後面才看起來沒事。
  **不建議**：那是一個「靠執行順序才正確」的狀態。
- 理由見 §3（兩邊的論證都寫了）。

**Q2 — `kMissesBeforeIsolating = 2` 以及它帶來的 60 秒。**
- **(a) 維持 2**（建議，且留成一行可改）：收斂後最壞 60 s 才把孤立的 host 標 down。
- (b) 改成 1：立刻反應，但一次 power-cycle 會讓 32 台 host ＋ 66 條邊翻面兩次。
- (c) 調短 `run()` 的 `kOnceConverged`（30 s）：全域影響，提高對 Ryu 的請求率。
  §D-2 已經有一張「縮短 LLDP beacon 間隔」的類似待辦，這兩件事可以一起評。
- (d) 把傳播搬進 1 Hz liveness 迴圈、自己造計時器：反應最快，複雜度最高。

**Q3 — 新的 down 要不要發 `LinkFailureDetected` 事件？**
- **(a) 不發**（建議，現在的做法）：生產碼零個 handler。
- (b) 發：把「Ryu 通報的鏈路故障」擴張成「分身自己推論的不可達」，兩者證據強度不同，
  而 payload 只有 edge descriptor、收的人分不出來。要發就該先把 reason 加進 payload。

**Q4 — `is_up == false` 用在 host 上，語意可以接受嗎？**
本修法讓 host 的 `is_up` 意思變成「**經由 fabric 不可達**」，不是「這台機器關機了」。
`LLMAgent.cpp:239` 把 switch 的 `isUp` 譯成 "powered on/off"，**但 host 分支不印 isUp**
（`LLMAgent.cpp:243-245`），所以今天沒有措辭上的謊言；`down_reason` 是給消費端分辨用的。
- **(a) 接受**（建議，現在的做法）。
- (b) 另開一個 `reachable` 欄位、`is_up` 維持不動。
  後果：`/ndt/` 多一個欄位、**既有消費端不會看到孤立的 host 變紅**
  ——也就是 F-14 對現有的 Web-GUI 使用者**等於沒修**。
