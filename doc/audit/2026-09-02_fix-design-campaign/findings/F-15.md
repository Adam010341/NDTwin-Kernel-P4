### 2.3 碰撞怎麼發生（機制），以及**兩條不同的路徑**

ephemeral range 是 kernel 配**本地 port** 給「沒有明講 port 的 socket」時抽號的池子。
落在池子裡的 50051–50060 會被兩種完全不同的東西搶走：

**路徑 A：短命的 client socket（2026-08-18 實際觀測到的那次）**
任何一條對外連線（`connect()` 沒有先 `bind()`）都會被配一個 ephemeral 來源 port。
bring-up 過程本身就製造大量這種連線（`mn -c`、Mininet 建 veth、`ethtool`、proxy 探測…）。
若某條連線在 bmv2 `bind(0.0.0.0:50052)` 的那一瞬間持有 50052，bind 就 `EADDRINUSE` ⇒
**bmv2 直接退出**。Linux 的 bind 衝突判定：綁 wildcard 會與**任何**已綁該 port 的 socket 衝突，
除非兩邊都設了 `SO_REUSEADDR` 且對方不是 LISTEN——一般的 outbound socket 不設，所以衝突成立。

這條路徑的**特徵是自我掩蓋**：連線很短，等你去查的時候 port 已經放掉了。
2026-08-18 的原始觀測（`doc/audit/2026-08-18_live-full-stack-round/subagent-round2-FINDINGS.md:602-640`）
正是這個形狀——s2/s6 死掉，而事後 `ss -ltn` 顯示 **50052 與 50056 是空的**。

**路徑 B：長命的 listener 落在池子裡（今天這台機器就有）**
`bind(port=0); listen()` 拿到的也是 ephemeral 號碼，而它可以活一整天。
2026-09-02 本機 `ss -ltn` 實測（非侵入式讀取，沒有動任何東西）：

```
所有 LISTEN port（去重排序）:
22 53 111 631 1716 2049 3000 3001 5433 8081 9091..9100 50051..50060
34199 36073 37075 37441 38037 39235 43375 44927 50841 55033
```
落在 32768–60999 內的共 **20** 個，其中 10 個是**我們自己的 bmv2**（50051–50060，
表示此刻有一套 P4 stack 正在跑：proxy 在 8081、thrift 9091–9100 也都在），
另外 **10 個是不相干的長命 listener**：34199 / 36073 / 37075 / 37441 / 38037 /
39235 / 43375 / 44927 / **50841** / 55033（擁有者需要權限才看得到，未查）。
**50841 距離我們的區塊只有 781。**

⇒ 「ephemeral 只會被瞬間的 client 搶走」是低估。這台機器**現在**就有十個長命 listener
坐在池子裡，其中一個離 50051–50060 不到 800。

**它們的下場不一樣，而第二種更糟：**

| | bmv2 的下場 | bring-up 看到什麼 | proxy 看到什麼 |
|---|---|---|---|
| A（client socket 搶走） | bind 失敗 ⇒ **process 退出** | `failure_reason()` 抓得到（`is_alive()` 為 False） | 該 dpid 連不上 |
| B（陌生 listener 佔住） | bind 失敗 ⇒ **process 退出** | ⚠️ **可能抓不到**，見下 | ⚠️ **可能連到陌生人的 socket** |

**B 為什麼可能漏判——`verify_switches` 的第一輪存在競態：**

```
p4_testbed_topo.py:308  def failure_reason(self):
p4_testbed_topo.py:320      if self.is_alive() and self.grpc_is_listening():
p4_testbed_topo.py:321          return None
p4_testbed_topo.py:421  while pending and time.time() < deadline:
p4_testbed_topo.py:422      pending = [sw for sw in pending if sw.failure_reason() is not None]
```
`grpc_is_listening()`（`:304`）是**對 127.0.0.1:port 做 connect 探測**——它問的是
「這個 port 上有沒有人接受連線」，**不問那是不是我們的 process**。
於是在「bmv2 剛 spawn、還沒因 bind 失敗而退出」的那個窗內，
`is_alive()` 為 True、陌生 listener 讓 `grpc_is_listening()` 也為 True
⇒ `failure_reason()` 回 `None` ⇒ 該交換機**在第一輪就被移出 `pending`，此後永不再查**
（`:422` 每輪重建 pending，已移出的不會回來）。
接著 `write_manifest()`（`:448`，`:466` 的 `if sw.failure_reason() is None`）
把它寫成「verified-live」，proxy 再依 `main.py:99` 連 `localhost:50051+dpid`——
**連到的是陌生人的 socket**。

⇒ **兩種都會發生：bmv2 綁不上（必然），proxy 連到陌生人（在 B 且踩中競態時）。**
我沒有 live 重現路徑 B——它是**讀碼推得的**，證據等級為「機制推論 + 今天的 listener 普查」，
不是觀測。**這一點請當作推論看待。**

⚠️ 附帶：`tools/p4_power_helper.py:166-171` 的 `port_listening()` 是**同一個 connect 探測**，
所以 `cmd_on` 在 `:263` 的「這個 port 有沒有人佔住」預檢**看不見路徑 A**。
`tests/python/test_p4_power_helper.py:56-58` 自己的註解就講了這件事：
「`port_listening` *connects*，而連到別人的 client port 會被拒絕」。
⇒ 那個預檢擋得住路徑 B，擋不住路徑 A。

## 4. 修復設計：三個選項

先講一件會影響三個選項評分的事：**這個缺陷的「安全」是查不出來的**。
port 沒被搶到的那次，與 port 根本不可能被搶的那次，長得一模一樣。
⇒ **不管選哪一個，都必須有一個「開跑前對著當下 kernel 檢查」的關卡**，
否則下一台機器把 `ip_local_port_range` 的下界調到 20000，我們一樣什麼都不知道。

### 選項 (a)：把 port 區塊移到 ephemeral range 之下 ⭐ **建議**

**哪一段是空的？** 本專案已占用：6343（sFlow UDP）、6633／6653（OpenFlow）、
8000（kernel）、8080（Ryu REST）、8081（proxy）、9091–9100（bmv2 Thrift）。
本機 2026-09-02 的 listener 普查裡，**9101 到 32767 之間一個都沒有**。

⇒ 取 **base 30050 ⇒ 30051–30060**。距 32768 還有 **2717** 個 port 的餘裕
（今天只用 10 個），128 台的假設情境（30051–30178）也遠在界內。

| 好處 | 代價 |
|---|---|
| 缺陷從「隨機」變成「不可能」——kernel 不會從 32768 以下抽 ephemeral | 所有 dial 50051 的呼叫端都要跟著改（清單見 §4.4） |
| 不需要任何 root 動作，clone 下來就是對的 | 文件裡約 20 處「50051 ~ 50060」會變成錯的 |
| 新機器不會忘記做什麼 | ⚠️ 30000–32767 正好是 **Kubernetes NodePort 的預設範圍**；這台機器沒有 k8s，但未來的 container host 會撞 |

### 選項 (b)：用 `net.ipv4.ip_local_reserved_ports` 保留區塊

人類要下的指令（**我不能執行——這是 system setting**）：

```bash
sudo sysctl -w net.ipv4.ip_local_reserved_ports=30051-30060   # 或沿用 50051-50060
echo 'net.ipv4.ip_local_reserved_ports = 30051-30060' | sudo tee /etc/sysctl.d/60-ndtwin-bmv2.conf
```

| 好處 | 代價 |
|---|---|
| 一行就好，不用改任何程式碼、文件、probe | 🔴 **是 per-machine 的 root 設定，跟著機器走不跟著 repo 走** |
| 對「已經公開、port 寫死在文件裡」的產物最省事 | 🔴 **新機器上忘了做，缺陷原封不動回來**，而且症狀跟原本一樣（隨機、事後查不到、訊息指向殘留 process） |
| | 沒放進 `/etc/sysctl.d/` 就撐不過 reboot，而「reboot 後才壞」是最難歸因的形狀 |
| | 這個檔覆寫而非附加——機器上若已有別的保留 port，直接下 `sysctl -w` 會**清掉它們** |

**忘記做會怎樣**：在 (b) 單獨施行的世界裡，什麼都不會提醒你。
⇒ **所以 (b) 不能單獨成立**；它需要一個開跑前的檢查，而那個檢查就是 (a) 也需要的那個。

**安裝手冊在哪裡？** 🔴 **這個 repo 裡沒有安裝手冊。** 查證結果：

| 落點 | 是什麼 | 該寫什麼 |
|---|---|---|
| **repo 外**：P4 官方 `installation-manual` 的 P4 環境節 | `doc/2026-08-15_bmv2-performance-build-public-manual-draft.md` 的內部前言第一行就寫「建議落點：installation-manual 的 P4 環境節」⇒ **真正的安裝手冊是站上的，不在我們手上** | 若走 (b)：port 保留那一段。若走 (a)：不必寫 |
| `doc/2026-07-29_environment_gotchas.md:140` | repo 內最接近「環境前置」的文件，已有 port 對照表 | **一定要改**：port 從 50051-50060 改成 30051-30060，並加一行「為什麼不是 5005x」 |
| `doc/2026-08-16_delivery-package/` | 對外遞交包（errata 走這條路給 patty） | 若走 (b)，這是把 sysctl 送出去的通道 |

### 選項 (c)：配置前先 bind 探測，失敗就換一個

| 好處 | 代價 |
|---|---|
| 不用改 port 數字，也不用 root | 🔴 **TOCTOU 沒有解決**：探測用的 socket 必須先關掉，bmv2 才能綁；那個空隙就是原本的缺陷。除非把 fd 直接交給 bmv2，而 `simple_switch_grpc` 沒有這個介面 |

### 4.3 建議：(a) ＋ 開跑前檢查，並讓檢查同時接受 (b)

## A.0 先講一個比改名重要的發現：**測試在讀過期的 bytecode**

寫 doc 斷言時，紅燈訊息印出「the fabric now uses **50051-50060**」——但磁碟上的
`grpc_ports.py` 寫的是 30050。查證：

```
$ ls -la --time-style=full-iso p4_proxy/mininet/grpc_ports.py .../__pycache__/grpc_ports.cpython-313.pyc
-rw-rw-r-- 8663 2026-09-02 12:58:20.251748018 +0800  grpc_ports.py
-rw-rw-r-- 9671 2026-09-02 12:58:20.225900410 +0800  grpc_ports.cpython-313.pyc   ← 比原始碼早 26 ms
$ python3 -c "...; print(G.GRPC_PORT_BASE)"      → 50050      （過期的 .pyc）
$ rm -rf __pycache__; python3 -c "..."           → 30050      （真正的原始碼）
```

**機制**：CPython 判定 `.pyc` 新舊，用的是原始碼的 **size ＋ mtime（截到「秒」）**。
而 `GRPC_PORT_BASE = 30050` 與 `= 50050` **位元組長度完全一樣**
⇒ size 不變、同一秒內改寫 ⇒ **兩個判準都分辨不出來**，Python 就繼續用舊的 bytecode。

🔑 **為什麼這比改名重要**：這個檔案裡**每一條斷言都是對 `import` 進來的值下的**。
沒有這道防護，整份測試可以綠得很漂亮，而它量的是**一個沒有人 ship 過的模組**。
這正是記憶裡 [[python-tests-need-the-venv-interpreter]] 第三面的同族：
**環境改變的不是「跑不跑得起來」，而是「缺陷存不存在」。**

**修法**：新增 `test_the_imported_constant_matches_the_source_on_disk`——
讀 `G.__file__` 的文字，比對 `import` 到的常數，不一致就紅並指出要刪哪個 `__pycache__`。
**附錄 A 之後所有測試都用 `PYTHONDONTWRITEBYTECODE=1` 且先清 `__pycache__` 重跑過。**
