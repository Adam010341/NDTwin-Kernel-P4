## 4. 修法設計

### 4.1 我建議的作法：**保留 200，但讓 `status` 與新增的 `reason` 有鑑別力，並把謂詞從「模式」擴到「會不會真的有一列」**

理由排序：

1. **B-3 條目自己指認的殘留缺陷就是「看狀態碼或看 `status` 的呼叫端分不出來」。**
   最小、最直接的解法是**讓 `status` 不再是常數**，而不是動狀態碼。
2. **動狀態碼會打破 2026-08-31 才剛對活 kernel 驗過 51/51 的契約。**
   `tools/contract_test/spec.py:789` 與 `:801` 都寫死 `expect_status=[200, 500]`；
   改 501/409 ⇒ 契約測試**在示範當天變紅**，而且是為了說 body 已經說完的話。
   `doc/2026-01-02_ndt_api.md` §39 也把 200 記成三種 shape。
3. **schema 相容**：`tools/contract_test/schema.py:129-141` 的 `Obj` **預設 `strict=False`**
   （註解明講「kernel 多加欄位不算破壞消費端」）⇒ 新增 `reason` **不會**讓契約變紅；
   `status` 只被要求 `Str(nonempty=True)` ⇒ `"not_applicable"` **通過**。
4. **順手治好 TESTBED 那半邊**：`canRecord()` 只問模式。改用 `recordingState()` 後，
   「沒人 start()」與「輸出目錄拒收（本機 OUTPUT_DIR 的實際狀態）」也不會再被報成 `recording:true`。

具體：
- `RecordingState` 五態 + `recordingState()`（優先序：**模式 > 旗標 > 執行緒 > 寫入健康**）
- `reasonCode()` 給穩定 wire token：`recording` / `disabled-by-request` /
  `not-available-in-mininet-mode` / `recorder-not-running` / `writes-failing`
- 非錄製分支 `"status":"not_applicable"`，**message 跟著 reason 走**
  （所有 cause 共用一句話，就是把同一個病往裡再犯一層）
- `start()` 把模式判斷移到 `exchange` 之前，讓 `m_running` 可信；並且**把拒絕寫進 log**
