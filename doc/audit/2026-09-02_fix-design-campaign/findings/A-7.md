(`FlowDispatcher.hpp:132` is private, no reader). The counter can only leave 0 **after** `stop()`

* live dispatcher, nothing dropped — health;
* stopped dispatcher, nothing enqueued since — **every subsequent write will be refused** while

The second is A-7's own failure shape, reappearing one layer up at the surface that was built to

## §2 Mechanism, per item

### 2.1 Item 1 — the ambiguous zero

`FlowDispatcher::stop()` (`FlowDispatcher.cpp:33-45`) sets `running_ = false` under `mtx_` and
moves `workers_` out. After that, both `enqueue` overloads take the `!running_` branch, call
`noteDropped_(n)`, and return — the HTTP layer has already replied `queued`. `noteDropped_`
(`:54-64`) warns **once** and accumulates. The warning is a log line; the counter is the program-
readable half, and it is published. What is not published is which of the two regimes the process
is in, which is exactly what makes the published number readable.

### 2.2 Item 2 — where boot-time programming actually lives

The kernel performs **no** boot-time flow programming. It is done in a **different process** in
both fabrics:

| fabric | where | driven from |
|---|---|---|
| OVS | Ryu app `intelligent_router.py`, `install_all_pair_paths` (BFS, ~128 rules/switch) | `load_static_topology` / `_dynamic_topology_worker` / `_initial_install_watchdog` |
| bmv2 | FastAPI proxy `p4_proxy/proxy_agent/topology_manager.py:1008` `install_initial_routes` | `handle_packet_in` / `readopt_switch` / `run_watchdog_pass` |

Neither has an in-process path to a counter inside the kernel. A `boot_installed` /
`boot_failed` bucket in `DispatchOutcomeLog` would therefore read **0 for the life of the
process** — structurally, not situationally. That is precisely the false affordance
`FlowDispatcher.hpp:47-55` records deleting a `fencePerBurst` parameter over: *dead code is inert,
but a false affordance is load-bearing in someone's head.*

There **is** an in-kernel writer that bypasses the dispatcher, and it is not boot-time:
`IntentTranslator::performTask` calls `FlowRoutingManager` directly at
`src/ndt_core/intent_translator/IntentTranslator.cpp:364` (install), `:394` (modify), `:417`
(delete) and `:733` (BLOCK_HOST install). The fourth is worse than uncounted — it **discards the
`OpResult` entirely** and returns `{"status": "success"}` unconditionally
(`IntentTranslator.cpp:733-739`). That is a B-1/A-7-family defect in its own right, not a counter
gap, and it is not in this ticket.

### 2.3 Item 3 — FINDING-07, traced hop by hop at base

| # | hop | file:line at `4cbec52d` | does priority survive? |
|---|---|---|---|
| 1 | request body → FlowJob | `src/ndt_core/http/HttpSession.cpp:915` `j.priority = entry.value("priority", 0)` | ✅ |
| 2 | dispatcher → sender | `src/ndt_core/routing_management/Controller.cpp:33` passes `job.priority` to `installAnEntry` | ✅ |
| 3 | strategy → southbound body | `src/ndt_core/routing_management/HttpRoutingStrategyBase.cpp:176` `body["priority"] = priority` | ✅ |
| 3b | P4 override? | `src/ndt_core/routing_management/P4RoutingStrategy.cpp` overrides **only** the six group/meter refusals — no `installAnEntry` override, so P4 and OVS send the identical body | ✅ |
| 4 | proxy route → manager | `p4_proxy/proxy_agent/api_routes.py:230-231` forwards `data.get("priority")` into `route_flow` | ✅ |
| 5a | manager → **ternary** table | `p4_proxy/proxy_agent/topology_manager.py:870` `if needs_five_tuple(...)`, `:872` `prio = p4_priority(priority)` | ✅ |
| 5b | client → P4Runtime | `p4_proxy/proxy_agent/p4_client.py:708` `entry.priority = int(priority)` | ✅ **honoured verbatim** |
| 6 | manager → **LPM** table | `p4_proxy/proxy_agent/topology_manager.py:880-897` → `insert_ipv4_route(ipv4_dst, 32, ...)` | ❌ **no priority parameter exists** |

**Verdict: the priority is not dropped by any layer. It is unrepresentable at the destination.**
A destination-only match compiles to `ipv4_lpm`, a P4 LPM table whose tiebreak is the prefix
length and which has no priority column at all (`p4_proxy/p4_src/ndtwin_switch.p4:350-352`, per
FINDING-07's own re-read). FINDING-07's seventeen rules were all destination-only, so all
seventeen went there and read back `0`. The `0` is the field's absence rendered as a default, not
a discarded `915`.

**Not the kernel. Not Ryu. Not a probe artefact.** (It was *nearly* a probe artefact — FINDING-07
§"this finding began as its own opposite" records `tr3_f5_window.py` keying rule identity on the
one field that does not survive the trip, which pinned its count at zero and manufactured a
confident FAIL. That instrument defect is real and already recorded; it is not what the priority-0
observation rests on.)

**What remains, and is in-repo and fixable:** the endpoint accepts a `priority`, routes the rule
to a table that cannot use it, and answers `{"status": "success"}` saying nothing. The answer was
true about the request and false about the consequence. FINDING-07 line 153-155 explicitly leaves
this open: *"Still open: what the endpoint should do instead… That is a design call, not a
measurement, and it is not made here."*

## §3 Fix design, and what was rejected

### 3.1 Item 1 → `FlowDispatcher::running()`, published as `dispatcher_running`

`include/ndt_core/routing_management/FlowDispatcher.hpp:137` (branch), an inline accessor beside
`droppedAfterStop()`, relaxed load for the same reason; `src/ndt_core/http/HttpSession.cpp:678`
publishes it. Now `running=true, dropped=0` is health and `running=false, dropped=0` is "delivery
has ended and nobody has noticed yet".

*Rejected:* making `enqueue` return a status (the header's own note at `:110-112` explains why —
two void overloads, several call sites, contract change); inferring liveness from a heartbeat
timestamp (adds state to answer a question an existing member already answers); putting the flag
inside `counters` (it is not a count).

### 3.2 Item 2 → publish the denominator; do **not** invent a bucket

`src/ndt_core/http/HttpSession.cpp:700-707` adds `counters_cover` = the four dispatch routes plus
`includes_boot_time_programming: false` and `includes_intent_translator: false`. Structured, so a
contract test can assert on it rather than parse prose.

**This item is designed-only as literally specified, and the reason is named:** boot-time installs
cannot be counted here without the refactor below.

*Rejected — `boot_installed`/`boot_failed` counters:* they would be structurally pinned at 0
(§2.2). A counter that can never move is worse than no counter.

*Named refactor, not attempted:* to count the reachable half (IntentTranslator's four sites),
`IntentTranslator` must be handed the `DispatchOutcomeLog` — a constructor-signature and
ownership-graph change (`include/ndt_core/intent_translator/IntentTranslator.hpp:19-23` takes four
`shared_ptr`s, none of them `Controller`), plus a decision about what `record()` means for a
synchronous call that never went through a dispatcher, plus fixing `IntentTranslator.cpp:733`'s
discarded `OpResult` first. To count the **boot-time** half at all, the kernel would have to poll
the Ryu app / the proxy for their install outcomes — a new southbound read, a new cross-process
contract, and a decision about staleness. Both belong in their own tickets.

### 3.3 Item 3 → disclose the table, do not refuse the request

`p4_proxy/proxy_agent/api_routes.py:258-267`: the success body now carries `table`
(`ipv4_lpm`/`flow_5tuple`) and `priority_honoured`, plus a `priority_note` **only when the caller
actually sent a priority**. Derived from the match by `needs_five_tuple` — the same predicate
`route_flow` branches on — so it cannot drift from where the rule actually went.

*Rejected — a `400`:* T-15 Option 0 (`doc/audit/2026-08-30_a7-dispatch-visibility/
T-15_p4-flow-entry-expressiveness.md:106-110`) records the collision explicitly: *stricter
validation is a breaking change for a caller that does not read status codes, and this project has
one of those.* The 2026-08-30 §1.2 ruling stands. Additive fields cost that caller nothing: the
kernel's only check on this body is `status == "error"`
(`src/ndt_core/routing_management/HttpRoutingStrategyBase.cpp:123-125`), verified by reading.

*Rejected — routing dst-only matches to `flow_5tuple` so priority works:* that changes forwarding
semantics for every rule the kernel writes, and T-15:157-166 already withdrew the option.

*Not attempted — making `ipv4_lpm` honour priority:* impossible; LPM tables have no such column.

**One pre-existing test had to change.** `p4_proxy/tests/test_flow_stats_route.py:197` asserted
the **whole** response dict while that test's subject is *which thread the southbound call ran
on*. It went red on a neighbouring concern — a change detector, not a specification. Narrowed to
`resp["status"]` with the reason in-line; the body's shape is pinned in
`test_flowentry_endpoints.py`, where it is the subject. Flagged here because editing someone
else's assertion to make my change pass is exactly the move that deserves a second reader.

### 3.4 Contract coverage (supporting all three)

`tools/contract_test/spec.py` gains `DISPATCH_FAILURE`, `DISPATCH_STATUS`, two invariants and an
`ENDPOINTS` row; `selftest_fixtures.py` gains two fixtures and eight invariant cases. **Every
