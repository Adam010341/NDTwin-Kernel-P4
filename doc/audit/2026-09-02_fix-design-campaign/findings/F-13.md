## 3. 修復設計

### 3.1 修在哪一層

修在 **strategy 層（`HttpRoutingStrategyBase`）**。理由：
- `FlowRoutingManager` 與 `HttpSession` 已經正確傳遞 `OpResult`（`7856efc` 做完了），
  它們沒有壞；
- 只有 strategy 層握有 Ryu 的位址，能去問 stats 路由。

### 3.2 三個動作

**① 先問，再決定，才寫**（`guardedMod`，`HttpRoutingStrategyBase.cpp:430-494`）

| op | 目標存在 | 目標不存在 | 問不到 |
|---|---|---|---|
| add | **409** `no_change_group_exists`／`no_change_meter_exists`，**不送 mod** | 送出 ⇒ 200 `outcome:"installed"` | 送出 ⇒ 200 `outcome:"unverified"` |
| modify | 送出 ⇒ 200 `outcome:"modified"` | **404** `no_such_group`／`no_such_meter`，**不送 mod** | 送出 ⇒ 200 `outcome:"unverified"` |
| delete | 送出 ⇒ 200 `outcome:"deleted"` | **404** 同上，**不送 mod** | 送出 ⇒ 200 `outcome:"unverified"` |

409 而不是 400：請求本身是良構的，錯的是狀態；呼叫端先 delete 再原樣重送就會成功。

**② 存在性是三態，不是兩態**（`Existence{Present, Absent, Unknown}`，
`HttpRoutingStrategyBase.hpp:104-109`）

`entryExists`（`.cpp:371-428`）裡**每一個提早 return 都是 `Unknown`，沒有一個是 `Absent`**：
- GET 失敗（Ryu 不通、非 2xx）⇒ Unknown
- body 不是 JSON（例如 `ofctl_rest` 沒載入時回的 404 HTML，本 repo 有紀錄的已知故障）⇒ Unknown
- body 是 JSON 但不是 `{"<dpid>": [...]}` 的形狀 ⇒ Unknown
- `group_id` 不是整數（Ryu 接受 `"ALL"` 這種名字，而這裡查不了）⇒ 連問都不問，Unknown

> 🔑 **`Absent` 是唯一會變成 404 的答案**。如果讓「問不到」塌成「不存在」，
> Ryu 一掛掉，kernel 就會把整個 fabric 的 group 全報成不存在——
> **儀器把自己的故障當成發現發表**（memory `instrument-must-not-mimic-its-own-finding`）。
> 這是本次設計裡最重要的一條，也是測試裡最該保留的幾個 case。

**③ body 帶 `outcome`**（`OpResult::outcome`，`OpResult.hpp`；
`HttpSession::respondToOpResult` 兩處發出）

`status` 那句英文**一個字都沒動**（跨 repo 契約）。新增的 `outcome` 回答
「已知發生了什麼」，因為 Ryu 的 200 只代表「轉送出去了」：

- `installed` / `modified` / `deleted` — 前置條件查過且成立
- `unverified` — **轉送了，但沒查成功；這不是「改成功了」的宣稱**
- `no_such_group` / `no_such_meter` / `no_change_group_exists` / `no_change_meter_exists`
- `no_such_switch`（dpid 不在 topology）／`no_dpid`／`bad_dpid`／`unsupported_on_p4`

**`outcome` 只在下層真的有話說的時候才出現**（`HttpSession.cpp` 兩處都是
`if (!result.outcome.empty())`）。多一個 key 對嚴格數欄位的 client 也是破壞，
所以 502 那種沒有 outcome 的路徑仍然回原本的三欄 body。

**404 現在有兩個意思**（switch 不存在 vs entry 不存在），
狀態碼分不出來 ⇒ **body 的 `outcome` 是唯一的判別器**，API 文件已標注。

### 3.3 pre-check 引進的 race（**這一段是本設計的但書，不要跳過**）

pre-check 是 TOCTOU。GET 與 POST 之間，另一個寫者（另一個 app、Ryu 自己的
`intelligent_router`、或第二個 NDTwin 請求）可以建立或刪除同一個 id：

| 順序 | 結果 | 嚴重度 |
|---|---|---|
| delete：查到「在」→ 別人先刪了 → 我們的 delete 在交換機端 no-op | 回 200 `deleted`，**其實不是我們刪的** | 低（結果狀態相同） |
| delete：查到「不在」→ 別人建了 | 回 404，**而它其實存在** | 低（假 404，重送即成功） |
| **add：查到「不在」→ 別人先 add 了** | 交換機回 `GROUP_EXISTS` 保留別人那筆，我們回 200 `installed` | 🔴 **高——與今天的缺陷同形**，只是變罕見 |
| modify：查到「在」→ 別人先刪了 | 交換機回 `UNKNOWN_GROUP`，我們回 200 `modified` | 中 |

⇒ **pre-check 把「這個輸入永遠是錯的」變成「只有別人在一個 RTT 內寫同一個 id 才錯」。
它縮小窗口，不關窗。** 這句話同時寫進了 `HttpRoutingStrategyBase.cpp:316-321` 的註解與
commit message，因為下一個讀這段碼的人最容易把它當成已經修好。

**真正關窗要 post-check**：mod 之後再讀一次，斷言目標狀態。
但 post-check 單獨用不行——delete 之後「不在」無法分辨「刪掉了」與「本來就沒有」，
所以要 **pre + post 兩次**，每個請求三個 round trip。
這六個端點不是 hot path（不像 flow entry 一次批 2000），三個 RTT 可以接受，
但它是一個要 Adam 拍板的取捨 ⇒ 列進 §7 開放問題，本次**沒有**實作。

### 3.4 被否掉的替代方案

| 方案 | 為什麼不採用 |
|---|---|
| **在 kernel 內維護一份 group/meter 影子表** | 影子表與交換機真值會漂（本 repo 已有同形前科：`DeviceConfigurationAndPowerManager` 的 flow table 快取，10.7 s 週期 + 幻影列，見 memory `rejected-requests-can-still-act.md` 08-30 那段）。用快取回答「存在嗎」＝**拿讀取器的狀態冒充交換機的狀態** |
| **讀 Ryu 的 `OFPT_ERROR` 事件** | `ofctl_rest` 不做關聯，要另寫一支 Ryu app 才辦得到（跨 repo）；**而且對 delete 沒用**——交換機根本不發那個錯誤 |
| **在 mod 之後補一個 barrier** | Ryu 的 REST 介面沒有暴露 barrier；同樣要改 Ryu |
| **查不到就直接 502／拒絕（fail closed）** | 會把「Ryu 還活著但 stats 讀不到」變成這六個端點全面停擺。而且真的不通的話，接著的 POST 本來就會回 502 ⇒ 誠實的答案還是會到。選 **fail open + 標記 `unverified`** |
| **把 `outcome` 無條件放進 body** | 對數欄位的嚴格 client 是破壞。改成有話才說 |
| **`GET /stats/groupdesc/<dpid>/<group_id>`（讓 Ryu 過濾）** | 🔴 **OF1.3 上 Ryu 會忽略那個 id**（`ofctl_rest.py:400-401` 只在 OF1.5 以上才轉送；`ofctl_v1_3.get_group_desc` `:968` 根本沒有 id 參數）⇒ 會拿回整張表，**每一個 id 都看起來存在**，等於 guard 永遠說 Present。這條有測試釘住 |
