## 起點：Adam 的觀察

> 「大流量的時候，連 iperf 本身在 mininet 顯示的流量都會抖」

## 為什麼今天早上那批資料回答不了它（已證，不要重跑）

區塊 1 的 iperf per-interval 已經算過：名目除數 CV **0.31%**、實際除數 CV **0.35%**。
**兩個都不抖**，所以無從分辨。

🔑 **原因不是分析錯，是那批臂裡沒有那個現象**：
UDP 定速、且**遠低於容量** ⇒ 穩定的送端在任何除數下都給出穩定的序列。
**歸因需要現象存在。** 這批資料叫不起「抖動」這個名字。

⚠️ **`mainDev` 的腳本第一版直接跳到判決分支印出「H1：抖動在線路上」，那是錯的，已改成拒絕。**
這個陷阱要留著：**一個判別器在現象不存在時仍然會輸出一個判決。**

## 一、假設（先寫，因為兩者在一般的圖上長得一模一樣）

| | 宣稱 | 若成立，意義 |
|---|---|---|
| **H1** | **資料面真的在抖**：bmv2 轉發速率隨時間變動 | 是被測系統的性質，要報 |
| **H2** | **「每秒」不是每秒**：量測區間邊界在負載下漂移，位元組除以名目 1.0 秒就會抖 | **是儀器的性質**，與工單 Q 同形狀 |
| **H3** | 🔴 **以上皆非——現象在這個工作點不存在** | 今早那批就是這個。**必須留這一支** |

**H2 不是憑空的**：同一台機器上今天量到 kernel 的 `sleep_for(1s)` 迴圈實際跑 **1141 ms**。
**軟體的「一秒」在這個專案裡已經被證明會長 14%。**

## 二、🔴 先排除「本來就會抖」的來源，否則量到抖動也不算發現

這是這份設計的核心。**下面兩種抖動是預期行為，量到它們什麼都沒證明：**

1. **TCP 壅塞控制**：cwnd 動態本來就讓吞吐上下跑。
   ⇒ **一律用 UDP**。用 TCP 看到抖動是重現教科書，不是發現。
2. **UDP 超過容量**：送端定速、收端丟包 ⇒ 收端數字當然抖。
   ⇒ **工作點必須在容量以下**，而且要**先量出容量**再選工作點。

⇒ **唯一有資訊量的組合：UDP、剛好在容量以下、機器飽和。**
在這個組合裡送端速率是固定的，所以**回報值的任何抖動只能來自 H1 或 H2**。

📌 **要分開記送端與收端**。Adam 說「iperf 顯示的流量」——送端顯示的是它**送出**的，
收端顯示的是它**收到**的，兩者抖的原因不同。**兩邊都記，分開報。**

## 四、判別法（資料在同一份 iperf3 JSON 裡，不必另外量）

每個 interval 都帶 `start`／`end`／`bytes`。算兩條序列：

```
A = bytes / 1.0                (名目)
B = bytes / (end - start)      (實際)
```

| 觀察 | 判定 |
|---|---|
| A 抖、**B 平** | **H2**：抖動是區間邊界漂移造成的，**是儀器** |
| A 抖、**B 也抖** | **H1**：抖動在線路上 |
| 🔴 **A 本來就平**（CV < 1%） | **H3**：現象不存在 ⇒ **不得宣告 H1 或 H2** |

**H3 的門檻要先寫死**：**名目序列 CV < 1% ⇒ 這個工作點沒有現象，重選工作點，不要報結論。**

## 五、預註冊的「不宣稱」

1. **不宣稱這是缺陷。** 就算是 H1，資料面在飽和下有變異可能完全正常。
   **要變成缺陷，得再證明它超出某個規格**——而我們沒有規格。
2. **不宣稱它與分身讀到的數字有關。** 這一輪量的是 **iperf 自己**回報的東西。
   分身讀到的抖動是**另一個問題**（那條路徑還多經過 sFlow 取樣與 API 輪詢）。
   ⚠️ Adam 最初問的是**分身讀的**，後來補了這個 iperf 的觀察——**這是兩張圖，不要合併。**
3. **不宣稱「數十 GB」這個量本身有意義。** 它是 Adam 描述現象的條件，不是判準。
   **若在 5 GB 就出現，就用 5 GB**，並說明為什麼不需要更多。
