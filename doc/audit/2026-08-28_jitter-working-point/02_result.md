# jitter 輪的結果：**H3——現象在這個工作點不存在**，而工作點本身可能不存在

**2026-08-28，`8/28 mainDev`。** lab `exclusive_cpu=yes`、鄰居 VM 已停、窗內無 commit。

---

## 1. 工作點：PREREG 的「容量的 70–80%」**不可用**，而且不是門檻訂錯

單流 ladder 給 160 Mbit 乾淨。**但臂跑 16 條流，而那個數字不可組合**：

| 每流 rate | 總 offered | 每流 loss（中位數） | |
|---|---|---|---|
| 30 M | 480 M | **67.4%** | 🔴 |
| 10 M | 160 M | **9.1%** | 🔴 |
| 5 M | 80 M | 0.325%（6/16 超過 0.5%） | ⚠️ |
| **3 M** | **48 M** | **0.000%（max 0.019%）** | ✅ |

🔴 **單流 160 Mbit 乾淨，16 流合計只到 ~48 Mbit** ——**加流會讓總吞吐下降**。
⇒ **瓶頸不是鏈路頻寬，是 bmv2 的每封包 CPU，而那個資源是整台交換機共享的。**
⇒ **「每流」與「每鏈路」兩種讀法我都問過審查員——實測答案是「兩個都不對」。**
單流量測**在任何除數下都無法外推到多流**。

## 2. 🔴 而 PREREG 要求的兩個條件在 bmv2 上**互相衝突**

PREREG §二要求：**UDP、剛好在容量以下、而且機器飽和**。

我用 **10 個 CPU burner** 去飽和機器而**不增加任何封包**——設計上這應該解耦兩者。**沒有解耦**：

| | 每流 loss 中位數 |
|---|---|
| 3 M/流，**無 burner** | **0.000%**（max 0.019%） |
| 3 M/流，**10 burner**（load1 ~30） | **2.192%**（16/16 全部超過 0.5%） |

⇒ **非網路負載一樣把 loss 推過噪聲底線**，因為 **bmv2 的轉發本身就是一個 CPU 行程**，
burner 直接跟它搶。
🔑 **「機器飽和」與「鏈路在容量以下」在這座 fabric 上是同一個資源的兩端，不能同時滿足。**
⇒ **PREREG 指定的工作點可能不存在。這不是量測失敗，是關於這個系統的結構性事實。**

## 3. ✅ 判定：**H3**（照 PREREG 的門檻，資料之前寫死）

飽和臂（16 流 × 3 Mbit、120 s、10 burner、load1 ~30、1888 個 interval）：

| | |
|---|---|
| 名目 1.000 s 除數的 CV | **0.45%** |
| 實際 `end−start` 除數的 CV | **0.45%** |
| **H3 門檻（名目 CV < 1%）** | 🔴 **TRIPPED** |

⇒ **不得宣告 H1，也不得宣告 H2。** Adam 描述的那個抖動**在這個工作點沒有出現**——
即使機器飽和、即使有 2.2% 丟包。

## 4. 🔑 但同一份資料把另一個結論推到最強

| | iperf3 的 1 秒計時器 |
|---|---|
| 區塊 1（load1 27–31，**偶然**的負載） | mean 1.0000 s、sd **1.5 ms** |
| **本臂（load1 ~30，10 個 burner，刻意飽和）** | mean 1.0000 s、sd **0.3 ms**、max 1.0027 |
| **kernel 速率迴圈（同機器、同量級負載）** | **1141 ms ＝ 長 141 ms** |

⇒ **在刻意飽和的機器上，一個行程的一秒準到 0.3 ms，另一個長 141 ms。**
🔴 **工單 Q 的 141 ms 確定不是 CPU 飢餓**——先前是偶然對照，**這次是設計出來的對照**。
**`sleep_for(1s) + 迴圈本體` 對上 `sleep_until` 語意，這是唯一剩下的解釋。**

## 6. ⚠️ 我這一輪的儀器缺陷（兩個，都自己抓到）

1. **`end.sum` 不是收端**：UDP 的 `sum` 是「送端速率 ＋ 收端 loss」的混合物。
   初版印出「delivered 159.98、loss 1.49%」——**算術上不可能而我沒發現**。
   正確是 `sum_sent` / `sum_received`。**與 `pushedAt` 同形狀：欄位名看起來就是答案。**
2. 🔴 **burner 的清理依賴父行程活著**：驅動被 timeout 殺掉時 **EXIT trap 沒有跑**，
   **10 個 burner 存活**，我在下一個指令才發現並手動清掉（已驗證 0 存活）。
   🔑 **依賴父行程存活的清理不是清理。** 正確做法是給子行程一個**自己的期限**
   （`timeout 180 bash -c 'while :; do :; done'`），**這樣父行程怎麼死都不會留下殘骸。**
