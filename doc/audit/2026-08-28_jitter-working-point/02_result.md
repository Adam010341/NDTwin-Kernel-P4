# jitter 輪的結果：**H3——現象在這個工作點不存在**，而工作點本身可能不存在

**2026-08-28，`8/28 mainDev`。** lab `exclusive_cpu=yes`、鄰居 VM 已停、窗內無 commit。

---

## 1. 工作點：PREREG 的「容量的 70–80%」**不可用**，而且不是門檻訂錯

單流 ladder 給 160 Mbit 乾淨。**但臂跑 16 條流，而那個數字不可組合**：

| 每流 rate | 總 offered | 每流 loss（中位數） | |
|---|---|---|---|
| 30 M | 480 M | **67.4%** | 🔴 |
| 10 M | 160 M | **9.1%** | 🔴 |
| 5 M | 80 M | 0.325%（6/16 超過 0.5%） | ⚠️ |
| **3 M** | **48 M** | **0.000%（max 0.019%）** | ✅ |

🔴 **單流 160 Mbit 乾淨，16 流合計只到 ~48 Mbit** ——**加流會讓總吞吐下降**。
⇒ **瓶頸不是鏈路頻寬，是 bmv2 的每封包 CPU，而那個資源是整台交換機共享的。**

> ### 🔴 2026-08-29 撤回：**上面那兩個數字不得相除**
> （`8/28 mainDev` 量測、`8/28 auditor` 裁決；正本 `doc/audit/2026-08-28_flow-count-capacity/`）
>
> **仍然成立**：加流會讓總吞吐下降；瓶頸是整台交換機共享的每封包 CPU。**本節的結論不變。**
>
> **撤回的是把 160 和 48 相除得到的任何倍數**（本檔 §4 的「3.3 倍」）：
> **160 是「無損門檻」，坐在平台上**（下一階 loss 只跳 3.5×）；
> **48 是「膝蓋」，真的撞到牆**（下一階跳 45×）。**兩端不是同一種量。**
> P1-3 實測：n=1 在梯子最高階 240 M/flow **收到 238.12 Mbit、loss 0.6091%**
> ⇒ **單流交出的比 16 流合計還高**；160 是**無損門檻**，不是交換機的天花板
> （240 那階是真的失敗，所以「最高乾淨階」五格同一把尺、內部一致；答不了的只有飽和天花板）。
> 另外 48 那格的 16 條流**散在四個 path class**，擺法與 160 那格不同（PREREG §2）。
⇒ **「每流」與「每鏈路」兩種讀法我都問過審查員——實測答案是「兩個都不對」。**
單流量測**在任何除數下都無法外推到多流**。

## 2. 🔴 而 PREREG 要求的兩個條件在 bmv2 上**互相衝突**

PREREG §二要求：**UDP、剛好在容量以下、而且機器飽和**。

我用 **10 個 CPU burner** 去飽和機器而**不增加任何封包**——設計上這應該解耦兩者。**沒有解耦**：

| | 每流 loss 中位數 |
|---|---|
| 3 M/流，**無 burner** | **0.000%**（max 0.019%） |
| 3 M/流，**10 burner**（load1 ~30） | **2.192%**（16/16 全部超過 0.5%） |

⇒ **非網路負載一樣把 loss 推過噪聲底線**，因為 **bmv2 的轉發本身就是一個 CPU 行程**，
burner 直接跟它搶。
🔑 **「機器飽和」與「鏈路在容量以下」在這座 fabric 上是同一個資源的兩端，不能同時滿足。**
⇒ **PREREG 指定的工作點可能不存在。這不是量測失敗，是關於這個系統的結構性事實。**

## 3. ✅ 判定：**H3**（照 PREREG 的門檻，資料之前寫死）

飽和臂（16 流 × 3 Mbit、120 s、10 burner、load1 ~30、1888 個 interval）：

| | |
|---|---|
| 名目 1.000 s 除數的 CV | **0.45%** |
| 實際 `end−start` 除數的 CV | **0.45%** |
| **H3 門檻（名目 CV < 1%）** | 🔴 **TRIPPED** |

⇒ **不得宣告 H1，也不得宣告 H2。** Adam 描述的那個抖動**在這個工作點沒有出現**——
即使機器飽和、即使有 2.2% 丟包。

## 4. 🔑 但同一份資料把另一個結論推到最強

| | iperf3 的 1 秒計時器 |
|---|---|
| 區塊 1（load1 27–31，**偶然**的負載） | mean 1.0000 s、sd **1.5 ms** |
| **本臂（load1 ~30，10 個 burner，刻意飽和）** | mean 1.0000 s、sd **0.3 ms**、max 1.0027 |
| **kernel 速率迴圈（同機器、同量級負載）** | **1141 ms ＝ 長 141 ms** |

⇒ **在刻意飽和的機器上，一個行程的一秒準到 0.3 ms，另一個長 141 ms。**
🔴 **工單 Q 的 141 ms 確定不是 CPU 飢餓**——先前是偶然對照，**這次是設計出來的對照**。
**`sleep_for(1s) + 迴圈本體` 對上 `sleep_until` 語意，這是唯一剩下的解釋。**

## 6. ⚠️ 我這一輪的儀器缺陷（兩個，都自己抓到）

1. **`end.sum` 不是收端**：UDP 的 `sum` 是「送端速率 ＋ 收端 loss」的混合物。
   初版印出「delivered 159.98、loss 1.49%」——**算術上不可能而我沒發現**。
   正確是 `sum_sent` / `sum_received`。**與 `pushedAt` 同形狀：欄位名看起來就是答案。**
2. 🔴 **burner 的清理依賴父行程活著**：驅動被 timeout 殺掉時 **EXIT trap 沒有跑**，
   **10 個 burner 存活**，我在下一個指令才發現並手動清掉（已驗證 0 存活）。
   🔑 **依賴父行程存活的清理不是清理。** 正確做法是給子行程一個**自己的期限**
   （`timeout 180 bash -c 'while :; do :; done'`），**這樣父行程怎麼死都不會留下殘骸。**

# 結論段（審查員裁決後，2026-08-28）

## 1. ✅ 本輪成立的結論（限定 bmv2）

> **在 bmv2 能承載的所有工作點上，iperf 的回報值不抖（名目 CV 0.45%，門檻 1%）。**
> **而「機器飽和」這個條件，無法在不引入 loss 的情況下達成。**

**這是關於系統的結構性結論，不是一次沒量到東西的量測。**
H3 在 PREREG 裡就是一等公民，判定照事前門檻做出，**兩個假說都不宣告。**

## 2. 🔴 但它只是 **bmv2** 的答案——**平面未定，這一輪不能結案**

我先前寫「換 OVS 不是 P4 的答案」。**審查員否決了那個理由，而他是對的。**

Adam 的原話是「**大流量的時候連 iperf 本身在 mininet 顯示的流量都會抖**」——
**沒有指定轉發平面，而兩個平面都跑在 Mininet 下。**

| 平面 | 天花板 | 兩條件可否同時成立 |
|---|---|---|
| **bmv2** | **48 Mbit**（16 流） | 🔴 **不可**（飽和與無損爭同一顆 CPU） |
| **OVS** | **53.1 Gbit/s** | ✅ 可，「數十 GB」也構得到 |

⇒ **若他看到的是 OVS，H3 完全沒有回答他的問題**，而換平面不是離題，**是正題**。

🔑 **我的錯在於用「我們現在在做 P4」取代了「他問的是什麼」。**
**這是替提問者選了他沒有選的範圍。**

⇒ **審查員去問他在哪個平面看到的。在他回答之前不開新一輪。**

## 3. 🔑 升級：飽和臂是工單 Q 的**主要證據之一**，不是附註

| 條件 | iperf3 的一秒 | kernel 迴圈的一秒 |
|---|---|---|
| 區塊 1（load1 27–31，**偶然**負載） | sd 1.5 ms | **1141 ms** |
| **本臂（load1 ~30、10 burner、刻意飽和）** | **sd 0.3 ms**、max 1.0027 | **1141 ms** |

**先前那個是撿到的對照，這次是設計出來的。**
而且**刻意飽和之下 iperf3 反而更準**（0.3 對 1.5 ms）。

> 🔴 **「141 ms 是 CPU 飢餓造成的」不是「證據較弱」，是被否證。**
> 同一台機器、同一量級負載下，一個行程的一秒準到 0.3 ms。

📌 **這是「方向剛好對的解釋最貴」的正面版本**：
「機器很忙所以迴圈變慢」是最便宜、方向最順的解釋，
**而它被一個刻意製造飽和的對照殺掉了**——不是被論證殺掉的。

## 4. 🔴 「每鏈路」那個裁決被資料推翻（審查員自己更正）

他裁「每鏈路」，理由是「飽和發生在鏈路上」。**實測：飽和發生在交換機的 CPU 上。**
單流 160 Mbit 乾淨、16 流合計只到 48 Mbit ⇒ ~~**加流讓總吞吐掉 3.3 倍。**~~
🔴 **「3.3 倍」2026-08-29 撤回（不重算）——見 §1 的撤回區塊。**
**加流讓總吞吐下降這件事沒有被推翻**，被推翻的是那個倍數：160 是無損門檻（平台）、
48 是膝蓋，兩端不是同一種量。**這個裁決不影響本節「正確的單位是整台交換機」的結論。**

⇒ **「每流」與「每鏈路」都錯，因為兩者都假設瓶頸在鏈路。正確的單位是整台交換機。**
⇒ 這也**解釋了**為什麼 PREREG 的兩個條件矛盾：**它們爭的是同一顆 CPU。**

## 5. 📌 本輪的兩個儀器教訓（合併成一條）

| | |
|---|---|
| `end.sum` 混合送端速率與收端 loss | **有代數關係的欄位自帶一個免費的一致性檢查，而我們從沒用過** |
| `trap EXIT` 對 SIGKILL 盲，而 SIGKILL 正是 timeout 的手段 | **保護機制在它唯一被需要的情境下必然失效** |

🔑 **合起來**：
> **保護機制的失效模式，與它要防的事件是相關的——不是獨立的隨機故障。**

正常結束時 trap 會跑，**但那時也不需要它**；異常結束才需要，**而異常結束正是它不跑的情況**。
**修法：給子行程自己的期限（`timeout N …`），不要讓它的存活取決於別人。**
