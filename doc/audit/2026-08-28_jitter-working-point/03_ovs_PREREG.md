## A. 測試床狀態：**有 shaping 的那一種**（跑之前查的，不是事後）

`testbed_topo.py:72` 接取層 **`bw=1000` 存在**；核心層 `bw=1000` / `bw=10000`（後者被 Mininet 靜默忽略）。

⇒ **單鏈路約 1.015 G，不是 53.1 G。** 53.1 G 是**拿掉接取層 `bw=` 之後**量到的。

🔴 **本輪在 as-configured 狀態量，不先拿掉 `bw=`。**
**理由**：Adam 看到的就是這個狀態。**為了拿到大數字而改成他沒看過的系統，是換掉被測物。**

## B. 🔴 新增假說 H1a / H1b（**加假說，不改門檻**）

`bw=1000` ＝ TCLink ⇒ **htb qdisc**，而 **htb 的 token bucket 本身就會製造突發與週期性抖動**。
⇒ 原本的 H1「資料面在抖」在 OVS 上混了兩件事：

| | 宣稱 | 若成立 |
|---|---|---|
| **H1a** | **OVS datapath 本身**在抖 | 受測系統的性質 |
| **H1b** | **我們自己配的 htb shaper** 在抖 | **測試床配置的性質，不是系統的** |

🔑 **兩者結論天差地別**，而 **H1b 對 Adam 的問題仍然有意義**——因為**他看到的就是有 shaping 的那一種**。
**要分辨的是「這是 NDTwin 的性質」還是「這是我們限速器的性質」。**

**分離法（只在第一臂量到抖動時才跑）**：
- 第二臂**拿掉接取層 `bw=`**。**shaping 在 ⇒ 抖、不在 ⇒ 不抖 ⇒ H1b。兩臂都抖 ⇒ H1a。**

## C. 不變的（沿用，不重寫）

- 判別法：每 interval 算 `bytes/1.0`（名目）與 `bytes/(end−start)`（實際）
- **H2**：抖動在實際除數下塌掉 ⇒ 儀器
- **H3 門檻不變**：名目 CV **< 1%** ⇒ 現象不存在，**H1/H2 都不宣告**
- **送端收端分開記**：`sum_sent` / `sum_received`，**不是 `end.sum`**（bmv2 那輪咬過）

## D. 帶過來的四條（審查員列的）

1. **不假設多流＝單流** ⇒ **先量 OVS 的「單流 vs 16 流總吞吐」**。
   bmv2 上 16 流合計比單流低 **3.3 倍**，而我們是先假設再被打臉的。
   **若 OVS 沒有那個塌陷，那個對比本身就值得記。**
2. **工作點的單位跟著實測到的瓶頸走** ——不沿用「每流」「每鏈路」「每台交換機」任何一個。
3. **`timeout N bash -c …`**，不用 `trap EXIT`（本輪已示範它在最需要時不跑）。
4. **量測窗內禁止 commit**（含我自己）。
