# 丟包發生在哪一層：**不是 shaper、不是 datapath，是收端的 socket buffer**

**2026-08-28，`8/28 mainDev`。** 審查員提議改讀 htb 自己的計數器（不改配置、不重建），
比「拿掉 `bw=` 的第二臂」更決定性——**因為拿掉 htb 同時也拿掉了一個 CPU 消費者，
而本輪的結論正是「CPU 競爭決定一切」，那個混淆在這裡特別致命。**

---

## 1. 量到的（單流 800 Mbit ＋ 10 burner，前後讀 cumulative 計數）

| 層 | 讀數 |
|---|---|
| **iperf 回報** | loss **9.769%**（401,103 / 4,105,852 pkt），名目 CV **13.54%** |
| **送端 htb**（`h1-eth1`） | 送出 4,105,869 pkt、**dropped 0**、overlimits 2,520,381 |
| **收端側 htb**（`s3-eth3` → h65） | 送出 4,969,683 pkt、**dropped 0**、overlimits 3,374,751 |
| **h65 介面**（`/proc/net/dev`） | rx **errs 0**、rx **drop 261**（4.97 M 中的 0.005%） |
| 🔴 **h65 的 UDP socket** | **`RcvbufErrors` = 406,299**、`InErrors` = **406,299** |

## 2. 🔑 判定：**三個候選層全部清白，第四層才是兇手**

| 候選 | 判定 |
|---|---|
| **H1b：我們自己配的 htb** | ❌ **路徑上每一個 htb 都 dropped 0**，而且 overlimits 有數百萬 ⇒ **它在積極調速卻一個都沒丟** |
| **H1a：OVS datapath / 介面** | ❌ 介面 rx errs **0**、rx drop **261**（0.005%）⇒ **封包送到了 h65** |
| **H2：iperf 的區間時鐘** | ❌ 四格全部否證（實際除數拿掉的抖動為零、interval sd 0.4–0.6 ms） |
| 🔴 **收端行程來不及讀 socket** | ✅ **`RcvbufErrors` 406,299 ≈ 觀察到的 401,103** |

> **`InErrors` 與 `RcvbufErrors` 完全相等 ⇒ 100% 的 UDP 輸入錯誤都是接收緩衝區滿。**

## 3. ⇒ 機制（完整鏈）

```
10 個 CPU burner  →  iperf3 收端行程搶不到 CPU  →  socket 接收佇列來不及排空
                  →  kernel 在 socket 層丟包    →  每秒回報的吞吐上下跳（CV 13.5%）
```

🔴 **「資料面在抖」是錯的。** 網路把封包**送到了**，是**收端的應用程式沒讀走**。

## 4. 📌 這改變了要給 Adam 的答案

| 先前的說法 | 更正後 |
|---|---|
| 抖動在線路上（H1） | **抖動在送達的位元組數上，但丟包發生在收端 socket，不在網路裡** |
| 由 CPU 競爭造成的丟包驅動 | ✅ **成立**，而且現在知道是**收端行程**被搶 CPU |

> **不是 NDTwin 的缺陷，也不是 OVS 的缺陷，是量測主機的資源問題。**
> **同樣的流量、機器不忙時完全不抖（CV 0.01%）。**

⇒ **可行動的結論**：看到 iperf 數字在抖時，**先看收端主機忙不忙**，
而不是先懷疑轉發平面或分身。**`RcvbufErrors` 一條指令就分得出來。**

## 5. ✅ 為什麼 16 流那一臂沒有出現

16 流 × 30 Mbit：**每個收端行程只要處理 30 Mbit**，即使 CPU 被搶也排得空
⇒ loss 0.037%、CV 0.64%。**單流 800 Mbit 才會讓單一收端行程來不及。**
⇒ **決定性的是「單一接收行程的速率」，不是總流量。** **18 GB 分散在 16 流上完全沒事。**

## 6. ⚠️ 仍然不宣稱

- **不**宣稱這是缺陷。**收端來不及是量測配置的性質**，要定成缺陷得先有規格。
- **不**宣稱 Adam 看到的就是這個。他說「或很可能是 OVS」，**也從未說當時機器在做什麼**。
- **不**宣稱 OVS datapath 在高負載下永遠不丟。**本輪只證明在這個工作點它不是主因**（0.005%）。
- 🔴 **`RcvbufErrors` 是 cumulative**，406,299 含少量先前的跑；**與 401,103 的吻合是量級吻合，不是逐位**。

## 8. ⚠️ 一條對既有記憶的具名質疑（已回報審查員）

記憶 `ovs-bandwidth-ceiling-measured` 寫「拿掉接取層 `bw=` ⇒ 單鏈路 **53.1 Gbit/s**」。

**本輪的觀察**：核心鏈路（`s1-s5` 等）**也是 `bw=1000`**，
而 h1→h65 **會經過核心** ⇒ **拿掉接取層不會解除跨核心路徑的 1 G 上限。**

⇒ **那條記憶的適用範圍可能只到「單一鏈路」，不到「跨核心的端到端路徑」。**
**待證，不是已否證。** 審查員已將該條標為**範圍待證**。
