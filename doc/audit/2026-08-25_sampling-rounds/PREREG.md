⇒ 兩道檢查**不獨立**。必須另外拿接收端實收當第三個量，否則「取樣傷了資料面」這個情況
會從兩道檢查中間漏掉。**這是本檔對 brief 的實質補強。**

🔸 **第三個量的出處（經審查員更正）**：**不是** `*_server.log`——`measure.sh:49` 確實寫了

## 3. 工單 A：指認執行緒（附掛，不單獨排一輪）

**做法**：任何一輪 live 跑，同時保留 `kernel.log` 與 cpu trace 的 `thread` 欄，
比對開機時印的 `[calFlowPathByQueried] pid=… tid=…`。

**先驗條件**：開跑前先確認今日 build **真的會印**那一行（`grep` 原始碼的發射行，不靠記憶）。
🔑 **同時記下該 build 的全部具名執行緒**（`run` / `calAvgFlowSendingRatesPeriodically` / 其他），
不只 `calFlowPathByQueried` 一條。理由（審查員的行為指紋，已從既有 raw 算出）：1/1024→1/64
逐執行緒比對顯示 **+9 那條 ×10 放大（＝ingest）**、worker pool 十餘條各 0.03→0.47、而
**那條大的 45.09→46.48 完全不放大**。⇒ 拿到名字就能一次判定「不放大的那條是不是
`calFlowPathByQueried`」**以及**「ingest 是不是 `run`」——兩個結論一次收。
🔴 若印不出來，A 這一格記 **INCONCLUSIVE，不得記 PASS**，也不得用 tid−pid 偏移去猜
（偏移 trace=+13 vs build=+11，跨版本不穩＝已知不可靠）。

**判準（先定死）**：
- 該 tid 的 CPU ≥ 40 點 ⇒ **機制確認**。
- 該 tid 的 CPU < 10 點，而另有一條 ≥ 40 點 ⇒ **候選被推翻**，改讀那條的名字。
- 兩者皆非（例如最高只有 25 點）⇒ **INCONCLUSIVE**，記錄分佈，不下歸屬。

## 5. 工單 C：λ 塌縮測試（Adam 裁定，6 格）

**假設**：精度只取決於 λ，與「取樣率 × 送流率」如何組合無關。

**λ 的母體必須寫明（原始版本的指控已撤回，見下）**：
這一輪存在兩個都叫 λ 的量，差約 2 倍：
- **全邊加總**：`analyse_matrix.py:102-105` 的 `total_sample_rate`，docstring 逐字寫
  "summed over every edge -- not one edge's lambda"。1/1024→34.7、1/64→556 樣本/秒。
- **單邊單窗**：`panel_stats` 的 `lam`（`s5-eth2`）。

🔸 **撤回：我原本指控 brief 的「(1/256, 200) → λ≈70」混用了這兩個母體。那是錯的。**
`cell_verdict.py --selftest` 實測 `m256_poll` 的 `lam = 69.73` ⇒ **70 就是正確的單邊值**，
brief 用的一直是單邊母體。全邊加總才是 ~139。我在沒有實際算過 `lam` 之前就下了指控，
證據方向剛好相反。**保留的只有紀律部分**：報告必須寫明是哪個母體，且配對格以**實測 `lam`**
對齊而非理論值——這一條仍然成立，但它是補強，不是更正。

**設計**：三組 (取樣率, 送流率) 讓實測 λ 相同、來源不同，各做兩個 λ 水準（共 6 格）。
初始候選（送流率上限待 §5-bis 校準後定案）：

| λ 水準 | 組合 1 | 組合 2 | 組合 3 |
|---|---|---|---|
| 低 | (1/256, 200) | (1/512, 400) | (1/128, 100) |
| 高 | (1/64, 200) | (1/128, 400) | (1/256, 800) |

**判準（先定死）**：同 λ 的三格，`sd_mean/floor` 三者兩兩相差 **< 0.1** ⇒ **塌縮成立**，
一條曲線取代整個矩陣。任一對 ≥ 0.1 ⇒ **有第二個變因**，記錄它，不宣稱塌縮。

### 5-bis. 🔴 送流率必須先校準（沿用 mainDev 今天的做法）
400 / 800 Mbit/s **單流**在 bmv2-fast 上沒人量過。直接排 300 s cell ＝ 可能量到 fabric 天花板
而不是 λ。**先跑一個短負載梯**（100/200/400/800 Mbit/s，每階 20 s，只看 `gt` 與 receiver 實收），
把達不到 offered 95% 的送流率**從設計裡刪掉**，再定案 6 格。
校準結果以增補寫入本檔，**不改 §5 判準**。

🔴 **CPU 那一軸不會塌縮**（既有資料：CPU 由「有沒有流記錄」決定、不由樣本數決定），
所以 C 不對 CPU 下任何結論；CPU 要用「流數量」當自變數，那是大規模並發輪的資料。

## D-2. 先驗閘門（不過就不准往上爬）

`truncate(128)` 已加在 egress clone 分支（`ndtwin_switch.p4`，`truncate` op 已在編譯後 JSON 中，值 `0x80`）。

🔴 **理由**：08-20 實測 bmv2 runtime knob `packet_length_bytes=128` ＝**無聲全滅**（全邊讀 0、零錯誤）。
`truncate()` extern 是**不同機制但同一種失效模式**。不先驗就往上爬，會把「全滅」讀成「天花板消失」。

**閘門（三項全過才准繼續）**：
1. 1/256 跑一格：`ratio` 仍 ≈1.00（≥0.95）且樣本數非零。
2. **注入自證**：獨立證據證明截短真的發生了——CPU port veth 的 **bytes/樣本** 應從 ~1442 掉到 ~128。
   **只看「有沒有編譯進去」不算**（編譯進去而 runtime 無效正是舊 knob 的失效形狀）。
3. 對照已知非空輸入：`cell_verdict.py --selftest` 仍 PASS。

任一項不過 ⇒ **停止工單 D，回報，不要調門檻**。

## D-3. 預先寫下的預測（跑完不得修改）

- **D-P1（審查員）**：若 proxy 成本是**每 byte** ⇒ 牆上移約一個數量級，**1/8 與 1/4 變健康**，proxy 平台線上移。

# 增補 G-1：結果——**H-GIL 被推翻**，而卡住 proxy 的東西被指認出來了

跑於 2026-08-27 11:37–11:43，一代 fabric、三臂、同一個 proxy pid 182176。
kernel `3367d0e9`、bmv2 `3ff54b5c`、`SAMPLE_RATE = 8`、`SAMPLE_TRUNC_BYTES = 128`。
**注入落在跑著的 process 的 argv 指的那個檔上**：JSON 編於 11:37:13，
十台 bmv2 起於 11:37:35，argv 指的正是那個 `p4_src/build/ndtwin_switch.json`。

## G-1-1. 主判準：**G = 0.461 ⇒ H-GIL 推翻**

| 臂 | dumps | G（GIL 被持有的比例） | W（事前判準） | proxy 總 CPU |
|---|---|---|---|---|
| I1 閒置（開機殘work） | 40 / 0 failed | 0.000 | 0.20 | 10.6% |
| **L 負載 200 Mbit/s** | **102 / 3 failed** | **0.461** | **1.64** | **144.1%** |
| I2 閒置（漂移基準） | 40 / 0 failed | 0.025 | 0.03 | 8.9% |

事前寫死：**G ≤ 0.60 ⇒ H-GIL 推翻，不論其他指標怎麼說。0.461 ⇒ 推翻。**

🔑 **這句話值得講清楚**：proxy 燒著 **144.1%** 的 CPU——正是那個平台——
而**直譯器有一半以上的時間是空的**。加核心救不了它的理由不成立，
因為**它現在就沒有把手上這一顆核用滿**。

## G-1-2. 兩個指標互相矛盾，而矛盾本身就是答案

W = 1.64（≥1.0）說「有排隊」，G = 0.461 說「GIL 沒飽和」。這兩件事不能同時是
「排隊在 GIL 上」——**等 GIL 的執行緒看到 GIL 是空的就會拿走它**。直接檢定：

| | 有人排隊 | 沒人排隊 |
|---|---|---|
| **GIL 被持有** | 35 | 12 |
| **GIL 是空的** | **46** ← 若排隊在 GIL 上，這格必須是 0 | 9 |

**P(GIL 被持有 │ 有人排隊) = 0.432**，而「排隊在 GIL 上」預測 **1.000**。
⇒ 那些執行緒**不是在等 GIL**。

## G-1-3. 那它們在等什麼——三個 frame，全部指向 proxy 之外

把「排隊」的執行緒按頂層 frame 攤開（原文照登，讓讀的人自己重分類）：

| 次數 | frame | 那一行是什麼 |
|---|---|---|
| 44 | `sflow_emitter.py:363 (emit)` | **`self._sock.sendto(datagram, self.collector)`**——送給 kernel 的 UDP |
| 51 | `grpc/_channel.py:932 (_next)` | `self._call.operate(...)`，cygrpc，**GIL 已放開** |
| 24 | `threading.py:304 (__enter__)` | `Condition.__enter__`＝拿 grpc channel 的鎖，**不是 GIL** |

🔴 **`sendto` 會停住，代表 socket 送出緩衝滿了**——也就是**收端（kernel）沒把它抽乾**。
這是 ③ 回壓因果鏈的**第一環第一次被直接觀察到**，而且方向與假說一致。
（本輪**不宣稱**整條鏈；只宣稱這一環被看到了。）

## G-1-4. 144.1% 花在哪裡（`/proc` 的帳，完全不經過 py-spy）

| 群 | 條數 | 每條 CPU | 小計 |

| `_stream_receiver`（熱的） | **3** | 20.5 / 20.4 / 20.4% | 61.3% |

| **py-spy 看不見的原生執行緒**（無 Python frame） | ~16 | ~2.1% | ~33% |
| | | **合計** | **≈144.8%** ✓ |

⇒ **大約 85% 的 144% 不在直譯器裡。**

## G-1-5. 我的預測：一半對、一半錯，而錯的那半有機制

| 預測 | 實測 | |
|---|---|---|
| G ≥ 0.95 | **0.461** | 🔴 **錯**，而且錯到反方向 |

## G-1-6. 分類器：閘門做了它被設計來做的事

事前寫死：「閒置臂的 W 必須 ≈0；若不是，先修分類器再讀負載臂。」

⇒ 併入 [[instrument-must-not-mimic-its-own-finding]]。

## S-3-2. 三條閘門（全部要過）

| | 判準 | 防什麼 | 常數 |
|---|---|---|---|
| a | **max 間隔 < 5 s** | 單一空洞（**p95 看不到的那個**） | `MAX_LIMIT` |
| b | **p95 < 3 s** | 整體節奏（原本那條，留著） | `P95_LIMIT` |
| c | 🔴 **流量開始後前 30 s 內不得有任何 ≥3 s 的間隔** | **位置**——N 的洞正好落在那裡 | `RAMP_WINDOW` |

🔑 **(c) 是這輪真正的教訓**：同樣大小的洞，落在中段只讓 `analyze.py` 少算一點，
**落在起點整格作廢**。⇒ **位置決定傷害，不只是大小。**

**(c) 只適用於階梯每一階，不適用於本自證**（自證沒有「流量開始」這個時點）。
實作上 `ramp_gate()` 是**獨立函式**、需要傳入 traffic-start 時戳
⇒ **拿不出那個時戳的階不會靜靜通過 (c)，會回報 N/A。**
selftest 兩個方向都驗：洞在流量開始後 5 s ⇒ FAIL；同一個洞在 200 s 後 ⇒ PASS。

## S-3-4. 🔑 審查員對「換儀器算不算移動球門柱」給的四條判準（收進紀律）

1. **門檻一個字沒動**——動的是「能不能分辨」，不是「過不過」。
2. **改動理由是先驗可驗的機制**，與想要的結果無關。
3. 🔴 **新儀器比舊的兇**（每 sweep 多 2 次行程生成）⇒ 通過是**保守方向**的通過。
   **改動若讓量測變寬鬆就該擋。**
4. **舊資料保留**，並指認其角色為「為什麼換儀器的證據」。

⇒ **第 3 條是關鍵：問這個改動讓結論更容易成立還是更難成立。**

## S-3-5. 🔑 門檻紀律的正確形式（審查員改寫，比我的版本強）

我原本寫「註冊門檻時一併註冊儀器的最小可分辨量」。**真正的形式是**：

> **門檻與儀器解析度必須是兩個獨立選擇，而它們今天不是。**
> 門檻 3.0 是從「sweep 間隔 2 s 的 1.5 倍」推的；解析度 1 s 是 `awk systime()` 給的。
> **兩個都是「秒」這個單位的產物 ⇒ 必然對齊。不是巧合，是共同來源。**

⇒ 可操作句：**「如果我的門檻和我的儀器刻度用同一個單位表達，先假設它們會撞。」**
