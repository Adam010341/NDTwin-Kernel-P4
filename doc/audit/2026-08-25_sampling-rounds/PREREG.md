## 1-bis. 🔴 對交接 brief 的三處更正（開跑前必須先解決）

**更正 1：brief 說的 HEAD `23bcd28` 是舊的。** 實際 HEAD＝`8acc3a4`，中間落了 `5965983`
（校準）與 `8acc3a4`（raw gitignore）。**`5965983` 與工單 B 的算術有關係**：

brief 的表格假設 200 Mbit/s ⇒ 17,800 pkt/s。今天實測 64 流 @316 Mbit/s 掉 58–91%、可用點
40.8 Mbit/s。**但兩者的負載形狀不同**：`measure.sh` 是**單一** UDP 流
（`iperf3 -c 10.0.0.33 -u -b 200M -l 1400`，`measure.sh:82`），而 `5965983` 的 cliff 明寫
「limit tracks concurrency, not bandwidth」。既有 ladder 五格的 `gt` 也確實貼著 200。
⇒ **不衝突，B 的基線可用**。但這一段必須寫進報告，否則讀者會以為兩輪互相打臉。

**更正 2：🔴 `twin/truth`、`delivered`、`spread`、`floor` 不是「既有欄位」。**
逐行查過 `analyse_matrix.py` 與 `plot_ladder_rates.py`，實際存在的是：

| brief 的稱呼 | 實際來源 | 定義 |
|---|---|---|
| `twin/truth` | **不存在，要現算** | `mean(vs) / gt`，`plot_ladder_rates.py:64-67` |
| `delivered` | **不存在，要現算** | `gt`＝由 `tx` 計數器差分算出的每秒位元（同上 66-67） |
| `spread` | `sd_mean` | 相對標準差 %（`:75`） |
| `floor` | `floor` | `100/√λ`（`:74`） |
| λ | `lam` | 每個刷新窗的樣本數（`:73`） |
| quantum | `q` | 各相異 twin 讀數的 gcd（`:60`） |

⇒ SATURATED 判準要我**自己寫一個函式算 `mean(vs)/gt`**，不能假設欄位已經在那裡。
**該函式上線前先餵一份已知非空、已知比值的輸入**（用既有 `m256_poll` 那格，它的比值已知 ≈1）。

**更正 3：🔴 `gt` 與 `delivered` 是同一個量，所以 brief 的兩道檢查其實共用一個分母。**
`gt` 讀的是**交換機邊的 tx 計數器**，不是接收端收到多少。因此：
- 樣本在「交換機→kernel」之間掉 ⇒ `twin/gt` 下降 ✅ 抓得到
- 封包在 fabric 裡掉 ⇒ `gt` 自己就跟著下降，`twin/gt` **可能維持 ≈1** ❌ 抓不到

⇒ 兩道檢查**不獨立**。必須另外拿接收端實收當第三個量，否則「取樣傷了資料面」這個情況
會從兩道檢查中間漏掉。**這是本檔對 brief 的實質補強。**

🔸 **第三個量的出處（經審查員更正）**：**不是** `*_server.log`——`measure.sh:49` 確實寫了
server log，但它落在 `$OUT`、**沒有被歸檔，raw/ 裡一個都沒有**。實際來源是 **`*_client.json`
的 `end.sum`**：UDP 模式下該區塊帶的是**伺服端回報**的 `lost_packets` / `lost_percent` /
`jitter_ms`，且 `slim_client_json.sh` 保留的正是這些欄位。⇒ **不需新增採集，只要讀對檔。**

**更正 4：🔴 glob 前綴撞名，而且新工單正好踩中。**
既有 cell 前綴＝`m1024 m512 m256 m128 m64`。工單 B 要新增 `m32 m16 m8 m4 m2 m1`。
`m1*` 會同時吃到 `m1024`、`m128`、`m16`、`m1`；`m2*` 吃到 `m256`、`m2`。
⇒ **新一代 cell 一律用 `r` 前綴＋補零**：`r032 r016 r008 r004 r002 r001`。
任何讀檔一律用**顯式清單**，禁止 glob。

## 3. 工單 A：指認執行緒（附掛，不單獨排一輪）

**做法**：任何一輪 live 跑，同時保留 `kernel.log` 與 cpu trace 的 `thread` 欄，
比對開機時印的 `[calFlowPathByQueried] pid=… tid=…`。

**先驗條件**：開跑前先確認今日 build **真的會印**那一行（`grep` 原始碼的發射行，不靠記憶）。
🔑 **同時記下該 build 的全部具名執行緒**（`run` / `calAvgFlowSendingRatesPeriodically` / 其他），
不只 `calFlowPathByQueried` 一條。理由（審查員的行為指紋，已從既有 raw 算出）：1/1024→1/64
逐執行緒比對顯示 **+9 那條 ×10 放大（＝ingest）**、worker pool 十餘條各 0.03→0.47、而
**那條大的 45.09→46.48 完全不放大**。⇒ 拿到名字就能一次判定「不放大的那條是不是
`calFlowPathByQueried`」**以及**「ingest 是不是 `run`」——兩個結論一次收。
🔴 若印不出來，A 這一格記 **INCONCLUSIVE，不得記 PASS**，也不得用 tid−pid 偏移去猜
（偏移 trace=+13 vs build=+11，跨版本不穩＝已知不可靠）。

**判準（先定死）**：
- 該 tid 的 CPU ≥ 40 點 ⇒ **機制確認**。
- 該 tid 的 CPU < 10 點，而另有一條 ≥ 40 點 ⇒ **候選被推翻**，改讀那條的名字。
- 兩者皆非（例如最高只有 25 點）⇒ **INCONCLUSIVE**，記錄分佈，不下歸屬。

## 4. 工單 B：ladder 延伸到 1/1

**新增六格**：`r032 r016 r008 r004 r002 r001`，poll 臂即可，其餘沿用。
**由低往高跑**（1/32 → 1/1），撞牆就停，這樣中止時已完成的格都是有效資料。

**理論樣本率**（200 Mbit/s、1442 B frame ⇒ ~17,800 pkt/s）：

| rate | 樣本/秒（理論） |
|---|---|
| 1/32 | 1,112 |
| 1/16 | 2,225 |
| 1/8 | 4,450 |
| 1/4 | 8,900 |
| 1/2 | 17,800 |
| 1/1 | 35,600 |

🔴 **預期會撞牆，撞牆點就是結果。** 但「牆」有三種，報告必須分開：
1. **樣本在交換機→kernel 之間掉** ⇒ `mean(vs)/gt` 下降
2. **取樣傷了資料面** ⇒ iperf3 receiver 實收下降（見 §1-bis 更正 3）
3. **clone 路徑自己倒** ⇒ `gt` 下降而 receiver 也下降

### 判準（先定死，不得事後調整）
- `mean(vs)/gt < 0.95` ⇒ 該格標 **SATURATED**，**不進精度曲線**，只進天花板敘事。
- `*_client.json` 的 `end.sum.lost_percent` **> 2.0%** ⇒ 該格標 **DATAPLANE-HURT**，與
  SATURATED 分開記。
  **門檻出處（事前可查，不是憑感覺）**：單流基線 `m256_poll_client.json` 實測
  `lost_percent 0.513`（`bits_per_second 199,999,117`、`lost_packets 27,459`）；
  已知壞的對照是 `5965983` 的梯子（16 流 1.1% / 32 流 24.8% / 64 流 34.1%）。
  2.0% 落在基線之上、遠低於任何已知壞值 ⇒ 既不會被基線噪聲觸發，也不會漏掉真的掉包。
- 兩者皆未觸發 ⇒ 該格進精度曲線。

## 5. 工單 C：λ 塌縮測試（Adam 裁定，6 格）

**假設**：精度只取決於 λ，與「取樣率 × 送流率」如何組合無關。

**λ 的母體必須寫明（原始版本的指控已撤回，見下）**：
這一輪存在兩個都叫 λ 的量，差約 2 倍：
- **全邊加總**：`analyse_matrix.py:102-105` 的 `total_sample_rate`，docstring 逐字寫
  "summed over every edge -- not one edge's lambda"。1/1024→34.7、1/64→556 樣本/秒。
- **單邊單窗**：`panel_stats` 的 `lam`（`s5-eth2`）。

🔸 **撤回：我原本指控 brief 的「(1/256, 200) → λ≈70」混用了這兩個母體。那是錯的。**
`cell_verdict.py --selftest` 實測 `m256_poll` 的 `lam = 69.73` ⇒ **70 就是正確的單邊值**，
brief 用的一直是單邊母體。全邊加總才是 ~139。我在沒有實際算過 `lam` 之前就下了指控，
證據方向剛好相反。**保留的只有紀律部分**：報告必須寫明是哪個母體，且配對格以**實測 `lam`**
對齊而非理論值——這一條仍然成立，但它是補強，不是更正。

**設計**：三組 (取樣率, 送流率) 讓實測 λ 相同、來源不同，各做兩個 λ 水準（共 6 格）。
初始候選（送流率上限待 §5-bis 校準後定案）：

| λ 水準 | 組合 1 | 組合 2 | 組合 3 |
|---|---|---|---|
| 低 | (1/256, 200) | (1/512, 400) | (1/128, 100) |
| 高 | (1/64, 200) | (1/128, 400) | (1/256, 800) |

**判準（先定死）**：同 λ 的三格，`sd_mean/floor` 三者兩兩相差 **< 0.1** ⇒ **塌縮成立**，
一條曲線取代整個矩陣。任一對 ≥ 0.1 ⇒ **有第二個變因**，記錄它，不宣稱塌縮。

### 5-bis. 🔴 送流率必須先校準（沿用 mainDev 今天的做法）
400 / 800 Mbit/s **單流**在 bmv2-fast 上沒人量過。直接排 300 s cell ＝ 可能量到 fabric 天花板
而不是 λ。**先跑一個短負載梯**（100/200/400/800 Mbit/s，每階 20 s，只看 `gt` 與 receiver 實收），
把達不到 offered 95% 的送流率**從設計裡刪掉**，再定案 6 格。
校準結果以增補寫入本檔，**不改 §5 判準**。

🔴 **CPU 那一軸不會塌縮**（既有資料：CPU 由「有沒有流記錄」決定、不由樣本數決定），
所以 C 不對 CPU 下任何結論；CPU 要用「流數量」當自變數，那是大規模並發輪的資料。
