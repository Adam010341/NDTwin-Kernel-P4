## E-1. 這輪為什麼存在，以及它可能不會成功

工單 D 事前寫死「成本若每 byte ⇒ 牆上移一個數量級」，實測截短 5.60× 之後四格**全部略差**
⇒ **per-byte 否證、per-sample 成立**。merge 是被資料指認出來的下一步，不是備選。

🔴 **但先寫下一個限制，免得結果出來才發現問到一半的問題**：

`build_datagram` 的 merge 作用在 **proxy → kernel** 那一跳（N 個樣本包成一個 datagram）。
它**不會減少 bmv2 → proxy 的 packet-in 數量**。而 proxy 每收到一個樣本要做的是：

```
gRPC stream 收 → handle_packet_in → sample_from_packet_in() 解析 → sample_callback → emit() → sendto
```

**merge 只砍掉最後一步。** 前面的 gRPC 收流、Python 解析、per-callback 開銷一個都沒少。

⇒ **merge 很可能也買不到東西。而那本身是有價值的結果**——它會把固定成本進一步定位到**收側**，
把「應用層還能不能救」這題關掉，並指向並行度（proxy 是 Python，14 核只用到 4.4）。

**兩種結果都有結論，事前寫死在 §E-3。**

## E-2. 先驗閘門（三項全過才准往上爬）

沿用 `gate_d.sh` 的結構：**同一格 1/256 跑兩臂，只差 `batch_size` 一個值**（1 vs N，建議 N=8）。

1. **證明它真的 batch**——量 **proxy → kernel 的 datagram 數**（不是位元組）。
   預期：datagram 數下降 ≈N×，**而樣本數不變**。
   🔴 **讀取器必須先餵已知非空輸入自驗**。D 那輪第一版 `grpc_bytes` 對著活 fabric 回 **0**，
   而 0 正是閘門要判定的「全滅」——先驗才抓到 port 猜錯且走 IPv6。
   **同一個坑不要踩第二次：先證明你的計數器在 `batch_size=1` 時讀得到東西。**
2. **證明沒有無聲全滅**——`ratio` ≥0.95、樣本非零、λ 與對照臂同量級、`distinct` 非零。
3. **`cell_verdict.py --selftest` PASS，而且閘門腳本裡要有實際呼叫。**
   🔴 D 那輪這項只寫在預註冊、`gate_d.sh` 沒有對應呼叫，是審查 grep 出來的。
   **預註冊寫了幾項檢查，腳本就要有幾個對應呼叫。**

任一項不過 ⇒ **停止工單 E、回報、不要調門檻。**

## E-3. 預先寫下的預測（跑完不得修改本節）

- **E-P1**：若 proxy 的固定成本主要在**送側**（syscall＋datagram 組裝）
  ⇒ **proxy CPU 平台下降、牆上移、1/8 與 1/4 變健康**。
- **E-P2**：若固定成本主要在**收側**（gRPC 收流＋Python 解析＋per-callback）
  ⇒ **牆不動、proxy 平台幾乎不變** ⇒ 下一把刀不是應用層優化，是**收側並行度**。
- **E-P3（審查員的賭注）**：**我賭 E-P2 偏多。** 理由：D 已經證明每則訊息的**內容**不影響牆。
  若送側是主因，truncate 把位元組砍 5.6× 時 `sendto` 的成本也該跟著降、牆該動——**但牆完全沒動。**
- **E-P4**：**merge 不改變 `ratio`**（樣本的數量與內容都沒變，只是包裝方式變了）。
  🔴 **若 `ratio` 掉了，那代表 batching 實作有 bug，不代表 merge「有效」。**
  最可能的 bug 形狀：run 結束時 `_pending` 裡未滿的那批沒有被 flush ⇒ 尾巴樣本遺失。

## E-5. 附掛（幾乎零成本，但可能是本輪最有價值的一項）

閘門那格 fabric 起著、而且**正在負載下**的時候，**對活的 proxy 跑一次 py-spy dump**。

- 目的：測「proxy 卡在 GIL」這個**讀碼假說**。proxy 平台 ~144% 對一個 Python 程式來說
  正是「一顆核的 bytecode 跑滿＋C 擴充放開 GIL 擠出的零頭」的形狀，而機器有 14 核只用 4.4。
- 🔴 **要透過 `mnexec` 跑**：這台機器 `ptrace_scope=1`，擋同 uid attach。
- 這一項**不影響 E-P1/E-P2 的判讀**，是獨立的加分題。若它證實 GIL 是瓶頸，
  那 E-P2 指向的修法就從「猜的」變成「量過的」。

### 🔴🔴 E-7-bis. 開跑前必讀：現在機器上那顆 kernel 是**嫌疑犯**

`ndt status` 的 handoff 寫著：**Kernel binary is INSTRUMENTED**（每 30 輪記一次迴圈週期，
Debug build）。那顆就是 08-25 23:38 那輪用的——**而那輪把頭號結果從 1.18 翻成 0.92**
（`288813e`）。它多了**兩個 hot mutex 上的 `shared_lock`**，
mainDev 自陳「應該不會碰到位元組記帳，但**沒有驗證過**」。

⇒ **兩條硬規則**：
1. **E 的兩臂必須跑在同一顆 binary 上**，並在 `binaries.txt` 記下 sha256。這是內部效度，
   沒有它整輪作廢。
2. **不要拿 E 的結果去跟 D 的 `t008`/`t004` 逐格比，除非你用的是跟 D 同一顆（未加儀器的）binary。**
   跨 binary 只能比**方向**，不能比數值。

🔑 **建議**：能換回未加儀器的 binary 就換（D 的四格才可逐格對比）；換不了就**明寫用的是哪顆**，
並把比較降級成方向比較。**兩種都可以，但不能不說。**
