J4. Feed the kernel a topology file that doesn't match the running fabric (documented failure mode from the intelligent_router.py comments) — WORKS-BUT, a genuinely useful finding: launched the kernel against `StaticNetworkTopologyOVS_10Switches_4Hosts.json` while the real Mininet fabric (and Ryu) still had all 128 hosts up. Actual network connectivity was **unaffected** (`h1 ping -c3 10.0.0.50` -> 0% loss) since Ryu/OpenFlow forwarding is independent of what the kernel separately models — a real difference from the intelligent_router.py comment's scenario, which was about *Ryu's own* topology file being wrong (breaking forwarding itself), not the kernel's. What I found instead: `curl .../get_graph_data` showed the kernel's model genuinely limited to the 4 hosts in its file (`['h1','h2','h3','h4']`), and the log filled with clear `[warning]` lines — one per unrecognized host/edge, e.g. `Host (00:00:00:00:00:7f) not found in static network topology file` — rather than silently corrupting data or crashing. Undocumented behavior, but a reassuring shape: a wrong `--topology` produces a smaller-but-internally-consistent twin plus loud, specific warnings, not silent wrongness.
