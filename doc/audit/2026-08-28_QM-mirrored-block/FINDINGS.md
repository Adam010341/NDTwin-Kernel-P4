## F-1 🔴 `pgrep -axf` 對任何**帶參數**的 process 一律回「不存在」

**兩個 session 今天都被它騙過**：審查員的現場回報寫「fabric 還活著但 **kernel 死了**，
`pgrep -axf 'ndtwin_kerne[l]'` 空」，我照抄同一條指令，也得到「(no kernel running)」。

**實際上 kernel 一直活著**，是昨晚留下的 `a40e04ce`（pid 1070106，由 `restart_kernel.sh`
在殺掉它之前印出 `running sha256: a40e04ce93b0e226…` 佐證）。

現場示範：

```
$ pgrep -axf 'ndtwin_kerne[l]'      # 空，exit 1
$ pgrep -af  'ndtwin_kerne[l]'      # 1567801 ./bin/ndtwin_kernel --mode mininet --topology …
```

**機制**：`-x` 要求**整條命令列**與 pattern 完全相等。加上 `-f` 之後比對的是 full command
line，而 kernel 的命令列是 `./bin/ndtwin_kernel --mode mininet --topology … --no-ai`，
永遠不可能等於 `ndtwin_kernel`。⇒ **`-x` 與 `-f` 合用，對任何有參數的程式都是恆假。**

🔑 **這是 false negative，而 false negative 比 false positive 貴**：
「它不在」會**驅動動作**（我差點在已經有 kernel 的機器上再起一顆），
「它在」只會讓你多等一下。

📌 與既有記憶的關係：
- `run_plane.sh` 早就記著**同一族**的坑（`pgrep -a simple_switch_grpc` 因 comm 15 字元上限而恆空），
  但那條的解法是「**加** `-f`」；這裡是「**`-f` 加上 `-x` 之後又壞掉**」。**兩條方向相反，要分開記。**
- 這是 [[process-liveness-checks-lie-in-two-ways]] 的**第十種**機制。

**這一輪的實際後果**：沒有。`restart_kernel.sh` 用 pid 檔而不是 pattern 找舊 kernel，
而且在起新的之前斷言 `:8000` 沒被佔住 ⇒ 兩層都擋得住。**是儀器騙人，不是機器壞掉。**

## F-2 ✅ 10 Hz 輪詢在**閒置** fabric 上完全不掉（M-quater (ii-i) 的前置條件，閒置側通過）

M-quater 要求：北向 API 一次只服務一個請求，所以 10 Hz 輪詢**可能自己就是擾動源**，
**這一步不做，整組 M 的數字不可用**。

閒置基線（60 s、無流量、binary `a40e04ce`）：

| 量 | 值 |
|---|---|
| polls | **600**（0 失敗） |
| 達成間隔 median | **0.1001 s** |
| p95 | **0.1001 s** |
| **max** | **0.1002 s** |

⇒ 要求的 10 Hz 拿到了，**最壞的一次也只差 0.2 ms**。

⚠️ **這只證明閒置側**。有負載時 API 會不會慢下來，證據在**每一臂自己的 `poll.jsonl`**
（逐次記 `ms` 與時間戳），read-out 會把兩者並排。**不要拿這一格代替那個比較。**

⚠️ 基線跑在 `a40e04ce` 上，不是三顆 binary 的哪一顆特別選的——它是昨晚留在機器上的那顆（見 F-1）。
對「輪詢器打得動幾 Hz」這個問題不影響，但**要寫出來**，因為 [[benchmark-must-name-the-binary-it-measured]]。

## F-4 ✅ 煙霧臂：**穩定流＋churn 同時跑**成立，而且儀器分得出 M 的效應

這個工作點是**新組合**（先前 Q 只跑穩定流、M 只跑 churn），所以先跑縮時版
（2 臂、`FLOW_S=70`、churn 40 s），**走同一條程式路徑**。原始資料在 `raw/smoke/`。

|---|---|---|

| 分母自證 | ABSENT（如預期） | ✅ **3/3 live, worst 0.0000%** |
| `T` | 1039.6 ms | 1024.2 ms |

| **mean** | **0.0594 s** | **0.5736 s** |

⇒ **效應 ＝ +0.514 s，落在 M-quater 預註冊的 0.4–0.6 s 區間內**，
而且是儀器解析度（輪詢 0.1 s）的 **5 倍**。

📌 **要先寫下的兩件事，免得正式區塊出來之後才「發現」**：

1. **1 kHz 臂的 median 是 0.1001 s，不是 0** ——那正好是**一個輪詢週期**。
   ⇒ 這格量到的是**儀器的下限，不是系統的延遲**。預註冊寫的就是「量不到」，**它確實量不到**。

2. **M 臂的 p95 ＝ 1.081 s，超出預註冊的「p95 < 1.0 s」。** 煙霧臂 n=46，不足以判定，
   但**已經記在這裡**，正式區塊若重現就是一個要處理的區間外事件（PREREG 5-M：
   > 1.0 s ⇒ 重算迴圈的實際週期不是 1 s，與工單 Q 同形狀）。

⚠️ **煙霧臂不是結果。** 它只證明管線會動、儀器分得開。正式的六臂區塊才是要報的東西。

## F-5 10 Hz 輪詢在**有負載**時會退化，但退化量遠小於效應

| | 閒置基線 | `S_B1` 臂內 | `S_M2` 臂內 |
|---|---|---|---|
| gap median | 0.1001 s | 0.1001 s | 0.1001 s |
| gap p95 | 0.1001 s | **0.1178 s** | **0.1177 s** |
| **gap max** | 0.1002 s | **0.2798 s** | **0.4745 s** |
| 失敗輪詢 | 0/600 | 0/678 | 0/670 |

⇒ 中位數完全不動，**尾巴會拖**（最壞 0.47 s）。這正是「北向 API 一次只服務一個請求」的形狀。

🔑 **這就是為什麼每條流各自記 `gap_before_first_seen_s`**：全域「我們用 10 Hz」會把這條尾巴藏起來，
而**單一次 0.47 s 的空洞落在某條流的出生時刻，那條流的延遲就只知道到 ±0.47 s**。
統計量（p95）對它要防的故障是盲的——分析時要逐流看，不是看平均輪詢率。

## F-6 🔴 漂移門檻的校準母體與本區塊的工作點**不同**（**在 B6 跑出來之前寫**）

第一臂 `B1` 的 `T` ＝ **1141.4 ms**，比煙霧臂的 1039.6 高 100 ms——
因為工作點更重（16 條穩定流 **＋ 144 條 churn**，煙霧只有 16 條 churn）。

⚠️ **而 PREREG 3-1 的 90 ms 門檻，是從『安靜臂』推出來的**
（gen 1 的 27.2、gen 2 的 41.6，兩者都是 16 流、**無 churn**）。

⇒ **門檻的校準母體是安靜臂，本區塊不是安靜臂。** 重負載下臂間離散度可能更大。

🔴 **門檻不改。** 預註冊就是預註冊，看到數字之後調門檻就是它存在的意義被取消。
但**這個但書必須現在寫**——寫在 `B6` 之前，否則萬一 `|ΔT|` 落在 90–150 ms，
它就會變成一個**事後找到的藉口**，而不是一個**事前知道的限制**。

📌 **`|ΔT| > 90 ms` 時的正確讀法**：不是「門檻訂錯了」，是
**「這是第一次在重負載下量臂間離散度，而它比安靜臂大」**——那本身就是一個發現，
而且它會改變**未來**每一個區塊的臂數需求。照 PREREG 3-3 執行（重跑一次、新世代）。

## F-9 🔴 我的階梯偵測器**通過了，而它不該通過**——`busy` 在飽和的機器上是瞎的

`開機手冊` 回報（10:0x）：他的 QEMU VM 在**我整個區塊 1 的量測窗內**滿載編譯 p4c／grpc／PI，
4 vCPU，而且**形狀是中間重、兩端輕**：

| 他的作業 | 起訖 | 落在我的第幾臂 |
|---|---|---|
| v10 NOTTY | 09:23–09:36 | 壓到**臂 1 尾巴** |
| v10 TTY | 09:40–**09:56** | **臂 2、3、4、5** |
| v8 乾淨室（VM 10:01:34 開機） | 09:58– | **臂 6** |

⇒ **兩個 base 控制組受影響最小，四個處理臂受影響最大。**
**鏡像抵銷的是漂移，抵銷不了這個形狀。**

### 🔴 我的偵測器為什麼漏掉它

```
arm  cond   busy   busy_max   load1
B1   base  0.867     1.000    27.13   ← 最低
Q2   Q     0.869     1.000    29.96
M3   M     0.878     1.000    31.04
M4   M     0.885     1.000    31.48   ← 最高
Q5   Q     0.879     1.000    28.28
B6   base  0.872     1.000    30.02
```

`Δbusy`：base↔Q **0.005**、Q↔M **0.008**。**乾淨到不可思議——那就是徵兆。**

🔑 **每一臂的 `busy_max` 都是 1.000 ⇒ CPU 早就頂到天花板。**
飽和之後再加負載**不會抬高 `busy`**，只會拉長 run queue、讓所有東西變慢。
⇒ **我把主判準訂在一個有上界的統計量上，而它要防的故障正好發生在上界之上。**

**而 `load1` 有看到**：27.13 → 31.48 → 30.02，**中間重兩端輕，逐字對上他的時間表**。
`ΔL1(Q,M)` = **2.14**，門檻 3.0 ⇒ 過關，**但邊際遠比 `busy` 讓人以為的窄**。

📌 這是 [[instrument-must-not-mimic-its-own-finding]] 的**新一式**：
不是「失敗預設值長得像量測值」，是 **「統計量有天花板，而故障住在天花板之上」**。
與已記的「p95 看不見單一空洞」同族，但機制不同：**那個是分位數不敏感，這個是量本身飽和。**

🔴 **判準不改（區塊 1 的關卡確實是過的），但偵測器要改**：
飽和機器上正確的量是 **run queue 長度／`steal`／每單位工作的完成時間**，不是 CPU 佔用率。
