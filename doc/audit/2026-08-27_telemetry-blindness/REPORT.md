## §0. 結論

**問題的形狀變了。不是「遙測在負載下瞎掉」，是「①用來證明它瞎掉的那個對比，兩邊不是同一個東西」。**

1. ✅ **輪次乾淨**：Q′ 回到 Q，哨兵對每一個有效應的量都判可解讀（①做不到這點）。
2. **`samples/s` 在 28 burners 下掉到 `0.5238`** ⇒ 損失**在 proxy 送出面的上游**。
   ⚠️ **但落在預註冊區間 0.60–0.75 之外** ⇒ 照 P-5 最後一列，**記成獨立結果，不塞進最近的分支**。
3. **P-4 的交叉檢查成立**：per-bmv2 CPU `167.2% → 101.1%`，低於 Q，機制自洽。
4. 🔴 **①的「資料面只掉 5%」是錯的。** 那個 5% 讀的是**唯一一個量在入口的邊類**。
   同一輪的另外兩類，資料面掉到 **0.46 與 0.54**。**資料面掉了一半以上。**
5. 🔑 **少報只發生在 `host→switch` 一類，而且跨兩個 fabric 世代重現。**
   量在轉發面的兩類，分身在負載下**沒有出現少報**。
6. **機制不宣稱**（P-9：本輪只做定位）。最順的「掉包」解釋**被方向否掉**，見 §5。


**與①的對照**：①的 `|Q′−Q|` = 27.2 ms 對 `|B14−Q|/2` = 13.6 ms ⇒ CONFOUNDED。

**而那個紅燈讀起來正好像它要偵測的那個問題。**
⇒ 已改成在 `|B14−Q| < 2%·|Q|` 時明說「**沒有效應可測，哨兵不適用**」。
這是「[[instrument-must-not-mimic-its-own-finding]]」的第五種形式，**出現在哨兵自己身上**。

## §3. 🔑 三個邊類**不是同一種量法**，而整份判讀掛在這件事上

`analyze.py` 的 `reconcile()` 自己的 docstring 就寫著：
**host-sourced 邊記在目的介面的 `rx`，switch-sourced 邊記在來源介面的 `tx`。**

⇒ **`host→switch` 量的是「送進交換機的」（offered in），另外兩類量的是「轉發出去的」（forwarded out）。**

| | veth GB | twin GB | ratio | | veth GB | twin GB | ratio | | veth GB | twin GB | ratio |
|---|---:|---:|---:|---|---:|---:|---:|---|---:|---:|---:|
| | \_\_\_\_ **host→switch**（入口 RX） | | | | \_\_\_\_ **switch→host**（TX） | | | | \_\_\_\_ **switch→switch**（TX） | | |
| **Q** | 4.323 | 4.435 | **1.0257** | | 3.874 | 4.072 | **1.0511** | | 11.951 | 12.362 | **1.0344** |
| **B14** | 3.931 | 3.275 | **0.8332** | | 2.626 | 2.750 | **1.0471** | | 7.943 | 8.086 | **1.0179** |
| **B28** | 3.826 | 2.488 | **0.6502** | | 1.653 | 1.848 | **1.1179** | | 5.972 | 5.653 | **0.9465** |
| **Q′** | 4.465 | 4.502 | **1.0083** | | 4.080 | 4.313 | **1.0571** | | 12.510 | 13.018 | **1.0406** |

**B28/Q，兩邊各自除以自己那一臂的視窗長度：**

| 類別 | veth（資料面） | twin（遙測） | ratio-of-ratios |
|---|---:|---:|---:|
| **host→switch** | **0.9573** | **0.6068** | **0.6339** |
| switch→host | 0.4615 | 0.4908 | 1.0635 |
| switch→switch | 0.5406 | 0.4946 | 0.9150 |

**讀法：**

- **`host→switch`**：主機**照樣把流量送進 fabric**（0.9573），但分身只認到 0.6068。**這一類真的有事。**
- **另外兩類**：veth 和 twin **一起掉到 0.46–0.54**。**分身跟著資料面走。**
  ⇒ **「遙測在 CPU 競爭下瞎掉」對這兩類不成立。**

## §4. 🔴 這撤回了①的頭條，也撤回了本工單自己的 §P-0

①的頭條是：

> veth 4.455 → 4.233 GB = **95.0%** — 資料面幾乎沒事
> twin 4.621 → 3.066 GB = **66.3%** — 少了三分之一

**那個 95% 是 `host→switch` 一格，也就是入口 RX。** 拿①自己的分析器跑①自己的 B28 臂
（`analyze.py --dir raw/L_B28 --auto-window`），各邊類除以自己的視窗：

| 類別 | L_Q | L_B28 | 比 |
|---|---:|---:|---:|
| host→switch | 13.14 MB/s | 12.71 MB/s | **0.9673** ← ①引用的就是這格 |
| **switch→host** | 13.04 MB/s | 5.91 MB/s | **0.4530** |
| **switch→switch** | 39.23 MB/s | 21.47 MB/s | **0.5474** |

🔴 **①的 fabric 在 28 burners 下掉了一半以上的轉發量，不是 5%。**
而那個 5% 被我**原封不動抄進本工單的 §P-0 當成既成事實**，它是這整張工單的動機。

⇒ **「遙測掉 34%、資料面只掉 5%」這個對比，一邊是送進去的、一邊是轉發並取樣到的。**
**這是「[[ratio-sides-must-share-a-population]]」的第四例**，而且這次兩邊連**量測點**都不同（RX 對 TX），
不只是視窗或母體不同。

### 但這是**收窄**，不是全撤

`host→switch` 的少報是真的，而且**跨兩個 fabric 世代重現**：

| | ①（gen 1） | P（gen 2） |
|---|---:|---:|
| h→s ratio，Q | 1.0373 | 1.0257 |
| h→s ratio，B28 | 0.7243 | 0.6502 |
| **B28/Q** | **0.6983** | **0.6339** |

**資料面也重現**（gen 1 的 0.9673 / 0.4530 / 0.5474 對 gen 2 的 0.9573 / 0.4615 / 0.5406）。
⇒ **兩代同形。這不是一次性的量測意外。**

## §5. 本報告**不**宣稱的（含一個被我自己殺掉的解釋）

### 不宣稱機制

P-9 寫明本輪只做定位。**下面這個是候選，不是結論。**

`ndtwin_switch.p4:425` 有一個 per-egress-port counter，註解寫 *"Used for link utilisation"*。
**若 switch-sourced 邊走 counter（精確）而 host-sourced 邊走 sFlow 樣本（統計），上表每一格都能解釋。**
🔴 **我沒有讀 kernel 那一側的兩條路徑，所以這只是候選。** 見 §8。

### 🔴 被方向否掉的解釋：「是掉包」

最順的解釋是 fabric 在丟包，而流量資料支持有丟包：

| 臂 | 回報丟包的流 | 平均丟包率 |
|---|---:|---:|
| P_Q | 8/16 | 12.8% |
| P_B14 | 7/16 | 35.9% |
| **P_B28** | **16/16** | **42.2%** |

**但方向不對。** 讀 `ndtwin_switch.p4:403-412`：取樣在 **ingress 尾端**，唯一的閘門是
`egress_spec != CPU_PORT`。而 `drop()` 是 `mark_to_drop()`（v1model 設 `egress_spec = 511`），
**`511 != CPU_PORT`** ⇒ **連查表就被丟掉的封包都會被取樣**；負載造成的佇列丟包發生在 ingress 之後，**更是照樣被取樣**。

⇒ **若掉包是主因，`host→switch` 的 ratio 應該維持 ~1.0**（樣本仍在，只是封包沒送到），
**而它掉到 0.6502。方向相反，零成本排除。**

📌 順帶一個**沒有追下去**的觀察：既然被丟棄的封包照樣被取樣，
**分身在丟包時應該「高報」轉發量**。這與 `switch→host` 的 B28 ratio `1.1179`（四臂最高）方向一致，
**但我沒有量它，不宣稱。**

### 其他不宣稱

- **不**宣稱天花板或外推。本輪一律限定「**在本工作點**」：P4、1/256、16 流、**已飽和的 14 核機器**（P-6）。
- **不**宣稱這解釋了大規模高報的頭條 —— 那要工單 Q 修完分母之後才完整。
- **不**與工單 N 的「容量之上少報 99.5%」合併（Pb-1 的表仍然適用：**容量之下 vs 之上、精度損失 vs 表示天花板**）。
  本輪四臂**無任何邊 ≥ 0.9 Gbit/s**，表示天花板未發動。
- **不**宣稱 OVS 平面同樣受影響（未測）。

## §6. 儀器揭露

### 分析器第一次 live 跑就找到自己的兩個缺陷

1. 🔴 **拿原始計數跨臂比，而各臂視窗長度不一樣。** B28 短 8%。改成 `samples/s` 後，
   頭條從 **0.4842 → 0.5238**。**視窗長度也是母體的一部分。**
2. 🔴 **還在跑的臂，長得跟「fabric 提早安靜」的臂一模一樣** —— 都是真視窗上的真數字。
   我第一次跑時 Q′ 只有 169 s，**它照樣進了哨兵並印出 CONFOUNDED；那個紅燈是儀器自己造的。**
   現已對各臂 span 比中位數，短的標 `INCOMPLETE` 並**排除在所有裁決之外**。

### `drive_P.log` 含一行已撤回的判讀

四份 arm log 都含 `measure_loop_period.py` 印的
`🔴 the loop DOES hold ~1 Hz -- the hard-coded denominator is not the cause`。
**該行拿新資料對 15:53 的 1.193x 比較，而那個比較已在①的 §0 撤回。本輪未引用它。**
⇒ 工具已於 `5695ce8` 改為只印量測值不下判讀（P 收乾淨之後、Q 開跑之前動的）。

### `T` 的跨世代對帳：**撤回**

我在開跑前報過「新世代 `T` = 1044 ms 與①的 1043.9 逐位吻合 ⇒ 跨重建可重現」。
**那是 `T_REPS=1`、`FLOW_S=30` 的煙霧臂，而且我引的是被 `tail -8` 留下的衍生行。**
同世代的正規安靜臂是 **1001.7 ± 5.8**，與①的 **1043.9 ± 3.4** 差 **42.2 ms（10.9 SE）**。
**負載臂反而複製得漂亮**（B14：1074.0 對 1071.1，0.2 SE）。
詳見 [`compare_T_across_generations.py`](compare_T_across_generations.py) 與工單 Q 的增補 **Q-quater**。
