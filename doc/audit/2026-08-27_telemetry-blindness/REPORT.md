## §3. 🔑 三個邊類**不是同一種量法**，而整份判讀掛在這件事上

`analyze.py` 的 `reconcile()` 自己的 docstring 就寫著：
**host-sourced 邊記在目的介面的 `rx`，switch-sourced 邊記在來源介面的 `tx`。**

⇒ **`host→switch` 量的是「送進交換機的」（offered in），另外兩類量的是「轉發出去的」（forwarded out）。**

|---|---:|---:|---:|---|---:|---:|---:|---|---:|---:|---:|
| | \_\_\_\_ **host→switch**（入口 RX） | | | | \_\_\_\_ **switch→host**（TX） | | | | \_\_\_\_ **switch→switch**（TX） | | |
| **Q** | 4.323 | 4.435 | **1.0257** | | 3.874 | 4.072 | **1.0511** | | 11.951 | 12.362 | **1.0344** |

| **B28** | 3.826 | 2.488 | **0.6502** | | 1.653 | 1.848 | **1.1179** | | 5.972 | 5.653 | **0.9465** |
| **Q′** | 4.465 | 4.502 | **1.0083** | | 4.080 | 4.313 | **1.0571** | | 12.510 | 13.018 | **1.0406** |

**B28/Q，兩邊各自除以自己那一臂的視窗長度：**

| 類別 | veth（資料面） | twin（遙測） | ratio-of-ratios |
|---|---:|---:|---:|

## §5. 本報告**不**宣稱的（含一個被我自己殺掉的解釋）

### 不宣稱機制（但 §5-bis 的讀碼把候選收窄到一個）

P-9 寫明本輪只做定位。**§5-bis 是讀碼的結果，不是量測；它排除了兩個候選、留下一個。**

🔴 **我自己先前寫的候選已被自己的讀碼否掉**：我曾提「`ndtwin_switch.p4:425` 的 per-egress-port
counter 可能供應 switch-sourced 邊」。**錯的。** 見 §5-bis：**三類邊全部由 sFlow 樣本供應，沒有 counter 路徑。**

### 🔴 被方向否掉的解釋：「是掉包」

最順的解釋是 fabric 在丟包，而流量資料支持有丟包：

| 臂 | 回報丟包的流 | 平均丟包率 |
|---|---:|---:|
| P_Q | 8/16 | 12.8% |
| P_B14 | 7/16 | 35.9% |
| **P_B28** | **16/16** | **42.2%** |

**但方向不對。** 讀 `ndtwin_switch.p4:403-412`：取樣在 **ingress 尾端**，唯一的閘門是
`egress_spec != CPU_PORT`。而 `drop()` 是 `mark_to_drop()`（v1model 設 `egress_spec = 511`），
**`511 != CPU_PORT`** ⇒ **連查表就被丟掉的封包都會被取樣**；負載造成的佇列丟包發生在 ingress 之後，**更是照樣被取樣**。

⇒ **若掉包是主因，`host→switch` 的 ratio 應該維持 ~1.0**（樣本仍在，只是封包沒送到），
**而它掉到 0.6502。方向相反，零成本排除。**

📌 順帶一個**沒有追下去**的觀察：既然被丟棄的封包照樣被取樣，
**分身在丟包時應該「高報」轉發量**。這與 `switch→host` 的 B28 ratio `1.1179`（四臂最高）方向一致，
**但我沒有量它，不宣稱。**

## §5-bis. 讀碼結果＋**一個候選機制（決定性測試未做，見 §8）**

`FlowLinkUsageCollector.cpp:1444-1461` —— **同一個樣本被記進兩張表**：

```cpp
m_counterReports[(agentIp, relevantPort)] += frameLength * samplingRate;   // 按 ingress 記
if (isIngress && outputPort != 0)
    m_egressCounterReports[(agentIp, outputPort)] += frameLength * samplingRate;  // 按 egress 記
```

然後：
- **`:1949`（主迴圈）** 付出 `m_counterReports`，寫給 ingress port 的**對面那條邊**
  ⇒ **`host→switch` 與 `switch→switch`**。
- **`:1697`（`creditHostBoundEgressEdges`）** 付出 `m_egressCounterReports`，
  **只付 host-bound 的**（switch far end「歸下游取樣器」）⇒ **`switch→host`**。

⇒ **沒有 counter 路徑。三類全是樣本。** 因此「一類走 counter 所以準」的解釋不成立。

### 🔑 那麼差別在**分母**，而且只有一類的分母含 bmv2 沒吃進去的封包

| 類別 | twin（分子） | veth（分母） | 分母是否含「bmv2 沒吃進去的」 |
|---|---|---|---|
| **host→switch** | 樣本，按 **ingress** port | 該交換機介面的 **RX** | 🔴 **含** |
| switch→switch | 樣本，按下游 **ingress** port | 上游介面的 **TX** | 不含（已通過上游） |
| switch→host | 樣本，按 **egress** port | 該介面的 **TX** | 不含 |

取樣在 P4 的 **ingress 尾端**（`ndtwin_switch.p4:403-412`）⇒ **只有進到管線的封包才會被取樣**。
而 veth 的 **RX 是 Linux 在介面上數的**，**包含 bmv2 來不及讀走的那些**。

⇒ **`host→switch` 是唯一一類，分子量「bmv2 處理了的」、分母量「到達介面的」。**
**CPU 被搶走時 bmv2 讀不贏來包，兩者就分家 —— 而那是真實的資料面丟包，被讀成遙測少報。**

⚠️ **這是讀碼推出的機制候選，不是量測。** 大小方向一致（B28 的 iperf 丟包 42.2%、h→s 缺口 35%），
但**同向不等於同因**。

### 🔑 但現有資料已經能**把「樣本遺失」這個競爭解釋定量排除掉**

`switch→switch` 的分子與分母**都只算「已離開上游交換機」的位元組**
（分子＝下游 ingress 的樣本、分母＝上游介面 TX）⇒ **兩者的差就是純粹的樣本遺失**。

**B28 實測：`switch→switch` = 0.9465 ⇒ 樣本遺失約 5%。**
**同一臂的 `host→switch` = 0.6502 ⇒ 缺口 35%，是前者的 7 倍。**

⇒ **若 35% 是樣本遺失造成的，`switch→switch` 應該也掉 35%。它掉 5%。**
**多出來的 30 個百分點，是「到達了介面但從來沒變成樣本」的封包。**
這與 §5-bis 的結構一致：**只有 `host→switch` 的分母含 bmv2 沒吃進去的那些。**

🔴 **這整段推理依賴一個前提，寫出來讓它可以被攻擊**：
**樣本遺失率與邊類無關** —— 亦即三類邊的樣本走同一條 `P4 clone → CPU port → proxy → kernel` 管線，
沒有哪一類的樣本比較容易掉。**§5-bis 的讀碼支持它**（三類全部出自同一個 `m_counterReports` /
`m_egressCounterReports` 寫入點、同一份樣本），
但**若將來發現某條邊類的樣本有自己的路徑或自己的佇列，這個 5% 的外推就不成立**，
整段要重做。（審查員指出這一點；它是本節唯一的承重前提。）

📌 **為什麼下游交換機不會出現同樣的缺口**：第一跳丟掉之後，
往下游走的就已經是**被削薄過的流**（`edge GB` 20.15 → 11.45，而 h→s 的 veth 只掉到 0.957）
⇒ 下游的 switch-facing 埠負載本來就低得多。**自洽，但仍是推論。**

### 決定性測試（**本輪未做**，需要一個有負載的臂）

比對 **bmv2 自己數到的進入管線封包數**（P4 的 per-port counter，proxy 讀得到）
對**同一個 host-facing 介面的 veth RX**。
相等 ⇒ 沒有 ingest 丟包，機制錯；不等且差 ~35% ⇒ 機制成立。

（本輪的 `veth.tsv` 只採了 `sN-ethN`，沒採 host 側，所以離線也做不了那一版。）

## §8. 這輪留給下一張工單的

§5-bis 已經回答了「為什麼只有 `host→switch`」的**結構**部分（分母含 bmv2 沒吃進去的封包）。
剩下的是**量測**：

1. **P4 ingress-port counter 對 veth RX**。🔴 **前置自證第 1 問當場失敗（17:5x）**：
   `ndtwin_switch.p4` 只有三個 counter（`flow_5tuple_counter`、`ipv4_lpm_counter` 兩個 direct，
   以及 `egress_port_counter` 按 **egress** port），**沒有任何一個按 ingress port 數「進入管線的封包」。**
   我提案時假設它存在而沒有先看。⇒ **這個測試需要一行 P4 change（約三行），因此需要重編 `.p4` ⇒ 換一個 fabric 世代。**

   **160 個 `s*-eth*` 介面的 `rx_dropped` 全部是 0**（`tx_dropped` 合計 3、`rx_errors` 0）。

   而且**丟包發生在 RX 計數之後**（bmv2 的 socket buffer 或管線裡）。
   ⇒ 這正是「veth pair 兩端對帳做不到」的具體理由：**兩端都在丟包點的上游。**
   ⚠️ **與 ingest 假說一致，但沒有檢驗它。**

   ⚠️ **而那個 P4 改動有它自己的風險，寫在跑之前**：每封包多一次 counter 累加，

   **落在兩者之外 ⇒ 儀器有效應，ingest 測試的數字要打折並說出打多少。**

2. 順手記兩個缺陷（都不擋本輪，但會擋那個測試）：
