# 工單 P 預註冊：**遙測在 CPU 競爭下少報 34%，是哪一段少的**

**寫於 2026-08-27 下午，`8/27 mainDev`。實驗室在工單 H 手上，本輪一個位元組的資料都還不存在。**
承接 `doc/audit/2026-08-25_large-scale-concurrent/REPORT.md` §7-ter（工單①）。

## P-0. 問題換了形狀：不是「少了多少」，是「在哪一段少的」

工單①已經量到（同一代 fabric、同一顆 kernel、1/256、16 流、外部 CPU burner）：

| | Q（0 burners） | B28（28 burners） | |
|---|---:|---:|---|
| **veth**（真實轉發位元組） | 4.455 GB | 4.233 GB | **95.0%** — 資料面幾乎沒事 |
| **twin**（遙測回報位元組） | 4.621 GB | 3.066 GB | **66.3%** — **少了三分之一** |

①**排除了兩個**候選、**指不出第三個**，因為缺儀器：

- ❌ **collector 靜默丟包**：`/proc/net/udp:6343` 291 個樣本 `drops` 全 0，`rx_queue` 5/291 非零、max 960 B
- ❌ **burner 餓死 proxy**：proxy CPU% ＝ B14 14.2 / B28 13.1 / Q′ 12.4（**負載下比安靜臂還高**）
- ⚠️ **bmv2 少產生樣本**：最可能，但①**沒有 per-process 資料 ⇒ 拒絕指認**

## P-1. 四段與**決定性切分**

```
bmv2 產生樣本 → proxy 收 packet-in → proxy 送 sFlow datagram → kernel ingest → twin
     ①無資料          ①無資料              🆕 儀器 1              ①已排除
```

🔑 **一刀切在 proxy 的送出面**（`samples_sent`）：

| `samples_sent`(B28/Q) | twin | 結論 |
|---|---|---|
| **跟著掉** | 掉 | **損失在上游**（bmv2 少產生或 proxy 少收）＝**資源限制** |
| **持平** | 掉 | **損失在下游**（kernel 收到了卻沒算進去）＝**bug，不是資源限制** |

**下游那個是更嚴重的發現**，因為它代表在負載下 kernel 會**默默丟掉已經收到的樣本**。

## P-2. 儀器（兩個都已建好並自證，本節記錄它們的極限）

### 儀器 1：`GET /sflow/stats`（`59e7298`）

暴露 `datagrams_sent` / `samples_sent` / `send_errors` / `batch_size` ＋時戳。
**累計計數器原樣回傳**，呼叫端做差分 —— 本專案已經發表過一次「對累計計數器取平均」的數字，而它看起來完全合理。

🔴 **未注入時回 503 不回零。** `samples_sent: 0` 與「沒人接線」序列化成同一份 JSON，
而前者**正是這個端點要偵測的訊號**。**一個儀器唯一不能有的故障，就是長得跟它自己的發現一模一樣的那個。**

⚠️ **狀態：單元已驗（5 測試、突變閘門看著它紅）、live 未驗。**
要 live 必須重啟 proxy 載入新的 `main.py`，而那會動 fabric 世代 ⇒ 排臂時一併做。
**在它真的 live 跑過之前，本輪任何引用都要標「live 未驗」。**
🔴 **live 自證要跑兩面**：接受面（連兩次讀、`t` 前進、三個計數器單調、`batch_size` 讀得到）
**與拒絕面**（未注入 ⇒ 503）。本 repo 有「八條拒絕路徑全綠而 accept path 100% 壞」的前例，
這次方向相反，**不得只驗接受面**。

### 儀器 2：`sample_bmv2_cpu.py`（`049a054`）

十台 `simple_switch_grpc` 各自的 `/proc/<pid>/stat` 原始 jiffies。
**不用 `ps -o pcpu`**（生命期平均，對跑了一小時的交換機做六分鐘臂間差分無意義）。
三問自證通過：間隔 5.0 s、計數器單調、**十台全部標到 s1–s10 零個未標**。
每筆記 `n_switches` —— 一台中途死掉會變成資料裡的階梯，
**而「安靜變小的總和」正好長得跟我們要找的訊號一模一樣**。

### 沿用①的兩個丟包偵測器

`/proc/net/udp:6343` 的 `drops`／`rx_queue`（**累計，取差分不取平均**），
以及 kernel log 的 `sock_ovfl_total`。

## P-4. 預測（**區間，寫死在資料之前**）

| | 預測 |
|---|---|
| **主假說（上游）** | `samples_sent`(B28/Q) 落 **0.60–0.75**（與 twin 的 66.3% 同量級） |
| **對立（下游）** | `samples_sent` **持平 0.95–1.05** 而 twin 掉 ⇒ **更嚴重的發現** |
| **交叉檢查** | 主假說成立 ⇒ **per-bmv2 合計 CPU 應低於 Q**（被 burner 搶走） |
| **矛盾** | 若 per-bmv2 CPU **持平或更高**而 `samples_sent` 仍掉 ⇒ **機制錯了，重想** |
| **丟包面** | `drops` 與 `sock_ovfl_total` 差分應維持 **0**（①已如此）；若非 0 ⇒ ①的排除要重審 |

## P-6. 🔴 範圍限制（**照①寫的，不得外推**）

**這台機器在 16 流下沒有閒置基線** —— ①量到五個臂**全部**是 14 核 100% busy，
量測本身就餵飽了機器。⇒ burner 是**在已飽和機器上加競爭**，不是在閒置機器上加負載。
**本輪結論一律加「在本工作點」，不得外推到閒置機器、其他取樣率、或其他流數。**

## P-7. 中止條件

1. **`samples_sent` 非單調** ⇒ 計數器或端點壞了，不是量測。
2. **`n_switches` ≠ 10** ⇒ 有交換機死了，該臂作廢。
3. **destination paths ≠ 16256 或任何邊 down** ⇒ 模型殘缺。
4. **kernel 或 proxy process 在臂之間重啟** ⇒ 多一個變數，重來。
5. **`/sflow/stats` 回 503** ⇒ 接線失敗，**不是「送出端停了」**（這正是 503 存在的理由）。
6. **負載用 `/proc/stat` 差分量化，不用 `loadavg`** —— ①的中止條件用閒置讀數校準卻在量測中判定，第一個臂就違反。
   🔑 **通則：門檻要在它將被判定的那個狀態下校準。**
