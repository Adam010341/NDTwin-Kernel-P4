**建立 2026-08-31（reviewer 線；auditor 08-31 裁）。**

## 為什麼有這個檔

08-31 對母版做衍生數字全掃（清單＝投稿包 `67_` F 段），發現三種不同的洞：

1. **raw 未保存**（pilot 12×）——原始資料沒了，但算式在檔；
2. **算式不在鏈上**（`1,500×`）——只有結論，沒有算法；
3. 🔴 **算式在檔、但那個檔不在版控**——**最陰險，因為每次檢查它都看起來是好的**。
   08-31 實況：17 個數字追下去「16 個在檔」，其中**五個所在的檔從未 commit**
   （`git log --all` 零筆），且整個目錄由 **`.git/info/exclude`** 排除——
   🔑 **而那個排除檔本身也不進版控**，所以別人連這條規則存在都不知道。
   後果：**一次全新 clone 就完全沒有這些算式，而論文照樣印著那些數字。**
   （更正 auditor 通報的機制一處：純 `git clean -fd` **不會**刪掉被 exclude 的檔，
   `git clean -fdx` 才會；但「只存在於這一台的工作樹、規則不共享」的結論不變。）

**通則（進方法節）**：「不進版控」的鎖是**對內容**下的（投稿材料、場次名、匿名前的識別），
**不是對算式下的**。算式是量測 provenance——鎖與耐久性不衝突，混為一談才兩頭落空。
⇒ 本檔**只搬算術與其輸入來源，不搬任何投稿內容**。

### A5 MDPI 工作點：完整算式（母版現行「3–6 個數量級」為過度宣稱）

輸入：工作點 6.3 Kbps–96 Mbps〔`SEARCH-ROUND-1.md:20`〕；corpus datapath 天花板區間
約 43 Mbps（P4sim）–1400 Mbps（ICNCC）〔census §2-1〕。

```
對「最高天花板」1.4 Gbps：
  6.3 Kbps → log10(1.4e9 / 6.3e3)  = 5.35   個數量級
  96 Mbps  → log10(1.4e9 / 9.6e7)  = 1.16   個數量級
對「最低天花板」43 Mbps：
  6.3 Kbps → log10(4.3e7 / 6.3e3)  = 3.83   個數量級
  96 Mbps  → log10(4.3e7 / 9.6e7)  = −0.35  ⇒ 工作點高端其實**高於**最低天花板
```

⇒ **母版句 "at working points three to six orders of magnitude below _any_ datapath ceiling"
在工作點高端為假**（"any" 要求對所有天花板成立，而 96 Mbps 高於 43 Mbps）。
**誠實形式（auditor 裁：報全距、不藏不方便那端）**：
「工作點距 corpus 最高 datapath 天花板 **1.2–5.3 個數量級**（其最低工作點 3.8–5.3）；
其最高工作點高於 corpus 最低天花板。」低端的論證力不減，高端揭露。
🔴 **改字前先掃引用點**（[[disclosure-is-not-downgrading]]）：08-31 掃得 **6 個檔**——
`doc/2026-08-29_bmv2-performance-study.md`（×2）、`abstract.tex`（×2）、
poster-review 輪的 `role-surveyed-author.md`／`abstract-plaintext.txt`／
`deepseek-v4-pro-round2.md`。**本檔只落算式，不代改任何引用點**（母版改動屬 Adam／擴寫期）。
