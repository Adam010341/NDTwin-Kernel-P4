## ① build 設定值 12–18 倍：有沒有人報告 build？有沒有人做過對照？

**答案：這 14 篇裡沒有人做過對照；build 資訊揭露接近零。**

**證據（9 篇有量 bmv2 的）**：
- flags／optimization level：**0/9**〔O：全文掃描＋逐篇閱讀，關鍵詞清單見 `sweep_keywords.sh`〕。
- 唯一的質性敘述：ICNCC 2023 一句「以不產生 log 的模式編譯以改善效能」〔O，txt 187–190〕——無 flags、無 -O level、無新舊對照。
- 變體載明 2/9（皆 Chen 組）、版本載明 1/9（ICNCC 1.15）。
- **兩篇引了官方 `performance.md`（ICNCC ref[3]、TSSA ref[10]）——那份文件本身就寫著建議 build flags——引用者仍未報自己的 build**〔O〕。TSSA 把自己與官方數字間 ~1000× 的落差全數歸因於 VM 規格（2 vCPU vs c4.2xlarge）〔O，txt 340–354〕；規格差距不足以解釋三個數量級〔I〕。
- Chen 組（PADS '23＝TOMACS）自陳各實作「maximum throughput ranges from 40 Mbps to 1 Gbps」並把差異歸給**變體身分**（simple_switch vs grpc vs psa）〔O〕；他們沒有控制、也沒有報告 build〔O〕。**同一台機器上同一變體僅換 build flags 就差 12–18×（我們的量測，`doc/2026-08-15_bmv2-performance-report.md`）⇒ 在無 build 資訊的前提下，「變體差異」與「build 差異」在這 14 篇裡不可分離**〔I〕。
- 對照組：**CompNet 2021 對它量的 7 個 switch 逐一給 commit/版本、BESS 註明 Haswell 專屬 build、附錄給逐 switch 參數**〔O，txt 520–525〕。⇒ 「報告 build provenance」在隔壁的 NFV benchmark 社群是**現行標準**；缺的只是 bmv2/Mininet 模擬圈〔I〕。
- 淨效果：9 篇合計的 bmv2 吞吐數字橫跨 ~2,500×（0.57 Mbps → 1.4 Gbps），**零篇給出足以重建其 binary 的資訊** ⇒ 這張表上任兩個數字**無法判定是否量了同一個東西**〔I〕。

**⚠️ 精度但書**：我們自己的 12–18× 是單機、單拓樸、n=1–2 的量測（08-15 報告載明）；「12–18×」應以區間引用，不可縮成單值。

**我沒查到的範圍**：未做系統性檢索（無資料庫查詢、無引用網絡追蹤）；PISCES/SIGCOMM 級 P4 論文的 build 揭露習慣未查；p4lang GitHub issues 未掃；「stock（p4-guide／tutorials 式）安裝在使用者間的實際佔比」未查——這影響「已發表數字代表多少真實使用情境」的力度。

## ② 天花板是 pps 不是 bps：有沒有人做過封包大小掃描並下同樣結論？

**答案：這 14 篇裡沒有人對 bmv2 下過這個結論；方法本身在隔壁社群是標配。**

**證據**：
- 對 bmv2 的封包大小掃描：**0/9**。最接近的三件事：
  1. **TSSA 2023 有 64 B／128 B 兩點**〔O〕：574.4–756.7 Kbps vs 1022–1040 Kbps（**08-29 更正**：先前誤植「564」；並把「~1.0–1.1 kpps 近恆定」改成逐情境配對——舊講法挑了最近的一對、高估恆定度）。**逐情境配對換算：64 B 側 ~1.1–1.5 kpps、128 B 側 ~1.0 kpps，pps(128)/pps(64)＝0.69–0.90；頻寬受限假說預測 0.5、每包成本假說預測 1.0 ⇒ 三情境全數偏 pps 恆定端**〔I：我們的換算，論文未計算、未陳述 pps〕；論文把 128 B 的改善歸因「datagram 較少→較不會丟」〔O，txt 371–378〕，全篇 Kbps 敘事。**資料裡有、結論裡沒有。** ⚠️ 另 08-29 讀出：TSSA 自述 64/128 B 是 iperf「buffer length」〔O〕＝ payload 不是 frame〔I〕——在 NFV frame 軸上是 106/170 B 兩點。
  2. **P4CEP '18 是唯一 pps 本位的 bmv2 數字**（min-size ≈12 kpps＝線速 0.08%）〔O〕——單點，無大小掃描，無「與包長無關」宣稱。
  3. **NFV benchmark 圈（NetSoft '19、CompNet 2021）**：64/256/1024 B 掃描＋Mpps 本位＋「testpmd 10 Gbps regardless of the packet size」這類分析是標準做法〔O〕——**但受測清單無 bmv2**。
- ⇒ 我們的貢獻形狀是「**把隔壁社群的標準軸第一次補到 bmv2 身上**，並給出 fidelity 語境下的後果（Mbps 天花板是 pps×包長的假象，直接影響模擬器使用者換算頻寬）」，而不是「發明新方法」〔I〕。

**我沒查到的範圍**：p4lang `docs/performance.md` 自身有沒有做過大小掃描（它報 80 kpps 中位、是 pps 本位單點——但它是文件不是論文，且不在這 14 篇裡）；bmv2 GitHub issues（如 #823）裡有沒有人貼過大小掃描。

## ③ 多流讓總吞吐下降、只有 bmv2 會：有沒有人量化過？

**答案：這 14 篇裡沒有等價的量測；Chen 組量化了「症狀」但從未把流數隔離成自變數，該組實驗也沒有對照平面。**

**證據**：
- **Chen 組（PADS '23 txt 215–218；TOMACS txt 370–373）**：256-switch ring，路徑不重疊，其他 host 開傳後四個樣本對從 1000 掉到 **~212 Mbps**〔O——**這是量化，我們先前說「沒量化」是錯的，已更正**〕。但：
  1. 工作點在 **host 超載**的規模（256 switch 容器 ×多執行緒 ≫ 128 核）〔I，機器規格為 O〕，歸因寫的是容器多工與資源競爭〔O〕——**「流數↑」與「活躍 switch 數↑」在該設計裡綁死**〔I〕；
  2. 該實驗**沒有 OVS 臂**（OVS 對照只出現在 16-sw 頻寬掃描與 SYN-flood 實驗）〔O〕；
  3. 報的是 per-pair 值，**沒有「同一路徑總和吞吐」視角**〔O〕。
- **TOMACS ECMP**：16/4/1 流的 per-flow 短收 72.8–87.5%，且觀察到「(c) 單流比 (a)(b) 高、儘管 hop 較多」並歸因流數〔O，txt 928–933〕——但三個場景走**不同層級的路徑**（edge-only vs edge+agg vs 全三層），流數與拓樸層混雜〔O/I〕；仍無 OVS 臂、無總和視角。
- 其餘 7 篇：ICNCC 全程單流〔O〕；其他無多流實驗〔O〕。
- ⇒ 我們的形狀（**08-29 口徑改寫**——原文「同一條 3-hop 路徑、16 流總和塌 3.3×、OVS 不塌反升」兩處已撤：「同路徑」不成立〔舊 16 流點散在四個 path class〕、「3.3×」係無損門檻÷膝蓋的異類相除〔撤回區塊＝`doc/2026-08-28_bmv2-throughput-literature-vs-ours.md` §3-3〕）——**固定 10-sw 拓樸、host 不超載、每格 n 條流同一 path class 下，每流最高乾淨速率隨流數單調下降、OVS 同工作點不降（量測＝工單 ③，收案前不填數字）**——在這 14 篇裡沒有等價物〔I〕。**帶對照平面**這一半（「只有 bmv2 會」）在這 14 篇裡完全沒人做過〔O：無任何一篇在多流條件下同時量 bmv2 與另一個 datapath〕。

**⚠️ 可比性但書**：Chen 組用 TCP、我們用 UDP；他們 256-sw、我們 10-sw。引用他們的 212 當「同現象的另一個工作點」可以，當「同一實驗的另一組」不行。

**我沒查到的範圍**：incast／同佇列多流的一般文獻（那是機制解釋的鄰域，不是 bmv2 量測）；bmv2 上游 issues 有沒有人報過 per-flow scaling。

## ④ Adam 加問：這些文獻的缺漏，哪些可以延伸

（依「我們接得多便宜」排序；🟢＝我們已有部分數據、🟡＝要新實驗、🔵＝定位型缺口）

1. 🟢 **build 軸**（0/14 掃過）：12–18× 已量（n=1–2 要補 n 與單 switch 隔離工作點）。**同時是 ① 的主角。**
2. 🟢 **封包大小×pps 軸**（0/9 對 bmv2 掃過）：stock 已有 1400 B/64 B 兩點＋fast 的 64 B；補一條 64→1400 的完整掃描很便宜。
3. 🟢 **流數軸（固定拓樸、host 不超載）＋對照平面**（0/14）：~~我們已有 bmv2 塌 3.3×／OVS 不塌~~（**08-29 撤回**：3.3× 係異類相除、舊 16 流點擺位不同——見 `doc/2026-08-28_bmv2-throughput-literature-vs-ours.md` §3-3 撤回區塊）→ 現行形狀＝工單 ③ 同置放量測每流無損門檻曲線（n=1–16、每格兩臂）＋OVS 對照；pass A 已示方向，收案待 pass B。
4. 🟡 **變體×build 交叉**：Chen 組的 simple_switch（~1 G）vs grpc（~170 M）差 ~6×，**歸因變體但 build 未控**〔O+I〕——同 build 下量兩變體、同變體下量兩 build 的 2×2，這 14 篇沒人做過；我們有兩顆 build，加變體軸成本低。
5. 🟡 **規模 vs 流數解耦**：Chen 做了「固定單流、掃 switch 數 1–256」〔O〕；**「固定 switch 數、掃流數」沒人做**——正是 3 的推廣。
6. 🟡 **變異數/jitter 軸**：TUM 明列 jitter 為 future work〔O〕；Chen 只說 variance 隨規模上升、未量化〔O〕。⚠️ 我們現有的 CV 判別資料在 **OVS 臂**；bmv2 側因「高 loss 與速率忠實承載互斥」判別法無適用域（`doc/2026-08-28_bmv2-throughput-literature-vs-ours.md` §4）——延伸前要先設計繞過這個結構性互斥的量法。
7. 🔵 **「量測→模型」路線斷代**：HotSDN '13 的路線是「量真 switch、在模擬器內建模型校正」〔O〕；bmv2 時代沒人接（Chen 組走 virtual time＝縮時間，不改行為模型）〔O/I〕。**數位分身本質上就是這條路線的現代形**——對 NDTwin 的定位敘事有用，不是這輪 workshop 的主菜。
8. 🔵 **儀器效度**：P4-NIDS 自述三場景 CPU 恆 0.3%〔O〕（與我們 08-15 抓過的量測假象同型〔I〕）；TSSA 的歸因跳過 build〔O〕。「bmv2 實驗的 CPU 量測方法學」是個小而實的缺口（我們的 per-thread 取樣法可直接寫成 recipe）。
9. 🔵 **VT 與 build 的互補**：TDF 的 runtime 成本與效能缺口成正比（TDF=2 ⇒ 2× 牆鐘時間，PADS '23 txt 562–565〔O〕）——**快 12–18× 的 build 直接把所需 TDF 除以同倍**〔I〕。這 14 篇裡沒人指出「先修 build 再上 VT」這個順序。對 TOMACS 是補充不是對撞——寫進 VERDICT。
