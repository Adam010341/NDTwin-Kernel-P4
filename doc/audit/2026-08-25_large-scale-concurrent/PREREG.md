# 預註冊：128 台 × 並發流 × 兩平面 —— 規模下的遙測還準不準

寫於**開跑之前**、任何數字存在之前。作者 `8/25 mainDev`。
Adam 2026-08-25 直接授權（「開始跑大規模量測，p4 就直接開 fast」）。

## 0. 題目（只有這一個）

> **把 host 數放大 32 倍、把並發流放大 3–5 倍之後，twin 的 per-edge 遙測還對得上 ground truth 嗎？**

**不是**壓力測試（不找吞吐天花板）、**不是** TE 決策品質、**不是**找新缺陷。
是把 08-16 那份對帳表在規模下重跑一次，並讓**十台交換機全部有負載**。

## 1. 為什麼這一格是空的（對帳既有實驗）

照 [[check-against-prior-experiments]]，開跑前先寫清楚本輪與哪些舊結果的關係：

| 舊實驗 | 它做了什麼 | 本輪的關係 |
|---|---|---|
| `2026-08-16_concurrent-flow-reconciliation.md` | 並發 13–21 流、三路獨立取數 | **方法沿用**（量測側逐項照抄），但只有 **4 台 host** |
| `2026-08-20_sampling-rate-and-cpu` | 128 host、兩平面 | **單一 iperf3 流 h1→h33** ⇒ 同檔 §4：**十台 bmv2 只有三台有負載** |
| `2026-08-17_p4-vs-ovs-matched-topology` | 兩平面 matched | 規模與並發都不是它的題目 |
| `api-concurrency-envelope` | 16× 併發 | **北向 API，與資料面無關**（不要拿來當並發證據） |
| `bmv2-scale-ceiling-and-sflow-sample-math` | 誤差地板 196√(1/c) | **本輪的讀判準**（見 §5） |

⇒ **「大規模」與「並發」各做過一半，交集是空的。** 這是 9/03 報告「量測實驗」類最大的空白。

**為什麼舊的單流量測只碰到三台**：拓撲是 4 access（s1–s4，各 32 host）+ 4 agg（s5–s8）
+ 2 spine（s9、s10）。h1→h33 是 s1→{s5|s6}→s2，正好三台。
**跨 pod**（s1/s2 ↔ s3/s4）才會走 spine，一條流經過五台。

## 2. 拓撲（兩平面 matched，逐項查證過）

| | P4 | OVS |
|---|---|---|
| 模型 | `setting/StaticNetworkTopologyP4_10Switches_128Hosts.json` | `setting/StaticNetworkTopologyMininet_10Switches.json` |
| hosts / switches / edges | 128 / 10 / 288 | 128 / 10 / 288 |
| 起法 | `ndt up p4 128` | `ndt up ovs` |

- access：s1=h1–32、s2=h33–64、s3=h65–96、s4=h97–128，host link **1 Gbps ×128**
- core：**16 條 1 Gbps + 16 條宣告 10 Gbps**（有向計）
- 🔴 **那 16 條 10 Gbps 從來沒有被整形**：Mininet 靜默忽略 `bw>1000`
  （[[ovs-testbed-bandwidth-reality]]）。本輪**不修它**，但 §6-3 會量它。

## 3. 方法（量測側逐項沿用 08-16）

三路獨立取數，每 **2 s** 一次、跨全程：

1. **Ground truth**：root ns 全部 `sN-ethM` veth 的 rx/tx bytes（kernel NIC 計數器，
   在 twin/proxy/bmv2 記帳之下）。128 host port + 32 core port。
2. **Twin per-edge**：`/ndt/get_graph_data` 的 `link_bandwidth_usage_bps`，對時間積分成 bytes。
3. **Twin per-flow**：`/ndt/get_detected_flow_data` 全文。

對映：twin 邊 `sN:ifM→X` ↔ `sN-ethM` 的 tx delta；`X→sN:ifM` ↔ rx delta。
**取樣量測走 kernel 量子法/veth，不碰 `Δ[255]/Δ[1]` 比率法**（撤回案白名單）。

### 3-bis. 與 08-16 的一處**故意偏離**，以及它的代價

08-16 用 **NTG** `flow --config` 產流；本輪用**腳本化的 iperf3 fan-out**。理由：
兩平面要 matched，而 NTG 在 OVS 平面沒有驗證過，且 iperf3 能精確指定並發數、
每流速率與時長——那正是本輪的自變數。

🔴 **代價要寫明**：08-16 的**絕對比值**（1.033／1.028／+28.8%）與本輪**不可逐位互比**，
產流器不同。可比的是**形狀**：聚合比值是否仍近 1、per-edge 散佈是否仍與 Poisson 一致。

## 4. 負載設計（讓十台全部有負載）

64 條並發 iperf3 流，128 台 host 全員參與（64 client + 64 server）。配對：

- **32 條跨 pod**（s1/s2 的 host ↔ s3/s4 的 host）⇒ 每條經過 **5 台**，強制走 s9/s10；
- **32 條同 pod 跨 access**（s1↔s2、s3↔s4）⇒ 每條經過 3 台，只走 agg。

速率階梯（**故意**設計成能讓 F-9 現形）：

| 條數 | 每流速率 | 目的 |
|---|---|---|
| 48 | 5 Mbps | 主體 |
| 8 | **1 Mbps** | **低於 F-9 的 ~3 Mbit/s 量化門檻** |
| 8 | 20 Mbps | 重流 |

總 offered ≈ **408 Mbps**，跨 pod 約半數 ⇒ 每台 spine 約 100 Mbps。

**為什麼這個數字**：P4 fast build 實測 460–530 Mbps／switch（stock 只有 ~40，
所以 Adam 裁定用 fast——不然量到的是 binary 的天花板不是系統的）。
100 Mbps／spine 留了 4–5 倍餘裕。⇒ **本輪不應該撞到任何天花板；撞到就是 §7 的中止條件。**

窗長 **300 s**（150 個取樣點）。

## 5. 判讀規則（跑之前定死）

### 先驗條件（不滿足就不是證據）

0. **twin 已收斂**：`edges_down == 0 && hosts_ipv4 == 128`。開機環的教訓
   （[[punt-window-host-learning]]）：settle 窗外 host 邊不會自己好。**不滿足＝重開，不是照跑**。
1. **binary 指認**：記下 `simple_switch_grpc` 的實際路徑與 pid
   （[[benchmark-must-name-the-binary-it-measured]]——同一個 A/B 連兩次量錯 binary）。
2. **注入自證**：iperf3 每條流的 client 端結果必須回報實際 bitrate；
   任何一條回 0 或 error ⇒ 該流不計入母體，且要**在報告裡列出來**，不得靜默丟棄。

### 誤差地板（先算好才不會把噪聲讀成缺陷）

`error_floor = 196 · √(1/c)`，c ＝該邊的取樣數。1/256 取樣、300 s：

| 邊 | 預估流量 | 封包數 | 取樣數 c | 地板 |
|---|---|---|---|---|
| 20 Mbps host 邊 | 750 MB | ~500k | ~1950 | **4.4%** |
| 5 Mbps host 邊 | 187 MB | ~125k | ~488 | **8.9%** |
| 1 Mbps host 邊 | 37 MB | ~25k | ~98 | **19.8%** |
| spine 邊 ~100 Mbps | 3.75 GB | ~2.5M | ~9700 | **2.0%** |

🔑 **低於地板＝在平滑，不是「特別準」**（[[bmv2-scale-ceiling-and-sflow-sample-math]]）。

### 主判準

- **PASS**：有取樣的邊，聚合 twin/veth ∈ **[0.90, 1.10]**，且 per-edge 散佈與各自的地板一致。
- **PARTIAL**：聚合過但某一**類**邊系統性偏移（例如所有 spine 邊同方向偏）⇒ 新缺陷，要指認。
- **FAIL**：聚合超出 [0.90, 1.10]，或某類邊整組讀 0。
- **INCONCLUSIVE**：先驗條件任一不滿足、或撞到 §7 的天花板。**不得讀成 PASS。**

|---|---|---|---|

| P2 | **switch→host 邊不再是 0** | 3c 已於 `e86cb4d` 修好，Round 3 驗到 1.068 | **推論**（未在規模下驗過） |

| P4 | **F-8 會現形**：首次取樣前的邊報 **1 Gbit/s** | 未在規模下量過；128 台放大了「還沒被取樣」的邊數 | **推論** |

## 7. 中止條件（達到就停，不要硬產數字）

1. **撞到天花板**：任一 switch 的 veth 總吞吐持平在 460–530 Mbps 帶（P4）或 access 邊貼 1 Gbps
   ⇒ 量到的是天花板不是遙測，降載重跑。
2. **收斂先驗條件失敗兩次** ⇒ 停，先處理開機，不要在壞 fabric 上量。
3. **iperf3 失敗流 > 10%** ⇒ 母體不可信，停。
4. **kernel 或 proxy 在窗內重啟** ⇒ 該窗作廢（[[proxy-restart-warm-fabric-multiplies-telemetry]]：
   proxy 重啟 × warm fabric = 遙測 ×N）。

# 增補 A：§7 中止條件 1 在第一次煙霧測試就觸發了

寫於校準**之後**、主量測**之前**。**上面的 §0–§9 一字未改**，這裡只加不減。

## A-1. 發生什麼

第一次 64 流煙霧測試（offered 316 Mb/s）：**UDP 掉包 58–91%，而且每一種路徑類型都掉**，
含只經過三台交換機的同 pod 流。⇒ §7 中止條件 1 觸發：**這個負載量到的是天花板不是遙測**。

## A-2. 負載梯（`calibrate.sh`，每階 20 s、64 流、路徑組合不變）

| scale | offered | 成功流 | loss p50 | loss p90 | 全機 CPU | 判定 |
|---|---|---|---|---|---|---|
| 1 | 320.9 Mb/s | 51/64 | 71.8% | 86.3% | 47% | over |
| 0.5 | 166.5 Mb/s | 55/64 | 59.1% | 63.2% | 54% | over |
| 0.25 | 100.5 Mb/s | 62/64 | 41.6% | 56.6% | 53% | over |
| **0.1** | **40.8 Mb/s** | **64/64** | **0.2%** | **0.6%** | 64% | **USABLE** |
| 0.05 | 20.4 Mb/s | 64/64 | 0.0% | 0.2% | 67% | USABLE |

判讀規則（先寫的）：**取 p90 掉包 < 2% 的最高階** ⇒ **scale 0.1**。

🔴 **懸崖很陡**：40.8 → 100.5 Mb/s 之間，掉包從 0.6% 跳到 56.6%。
⚠️ **全機 CPU 從來沒有超過 67%**，而且**負載愈低 CPU 愈高**（因為流真的送達了）
⇒ **不是整機 CPU 飽和**。機制尚未指認，**不得寫成「bmv2 撐不住」**——那是猜測。

## A-3. 🔴 這個工作點與 P5 直接衝突，必須先解決

scale 0.1 下速率階梯是 **2 / 0.5 / 0.1 Mb/s**——**全部低於 F-9 的 ~3 Mb/s 量化門檻**。
後果：**128 條 host 邊與 128 條 switch→host 邊全部會讀 0**，288 條裡有 256 條沒有訊號。
那不是「量到 F-9」，那是**沒有量到任何東西**。

core 邊不受影響（s1 的 32 條流分到 s5/s6，每條 core 邊約 8 Mb/s，**在門檻之上**）。

## A-4. 因此先加做一個判別實驗（`discriminate.sh`）

**天花板是「總位元率」還是「流數」？** 三個點**同樣 offered ≈ 102 Mb/s**、只有並發數不同
（16 / 32 / 64 流），加上梯子已建立的 64 流 @ 41 Mb/s 當對照。

- **掉包隨流數上升 ⇒ 流數限制** ⇒ 主量測可以**用並發換每流速率**（少而肥的流），
  把 host 邊推到門檻之上。
- **掉包持平 ⇒ 位元率限制** ⇒ 換不了，主量測只能在 core 邊上做，
  而「host 邊在可用負載下全部不可見」本身就是要寫進報告的結果。

## A-5. 主量測的條件因此變成兩個（依 A-4 結果二選一或都做）

- **條件 A（全規模）**：64 流 @ scale 0.1。十台交換機全有負載、core 邊有訊號、
  host 邊預期全 0 ⇒ 直接量 P1（core）、P4、P6、P8，並把 P5 量成「有多少邊看不見」。
- **條件 B（host 邊可見）**：僅在 A-4 判為流數限制時成立。少流、每流 ≥5 Mb/s，
  路徑組合不變 ⇒ 量 P1（host 邊）、P2、P3。

🔴 **兩個條件的並發數不同，所以它們的比值不可互比**，只能各自對自己的 ground truth。

## A-6. 掉包在哪一層——本輪的資料自己就能回答，不必另外做實驗

iperf3 的 loss 是**接收端**算的，所以它同時涵蓋兩種可能，而這兩種的修法完全不同：

1. **fabric 丟的**（bmv2／veth／佇列）；
2. **主機丟的**（128 個 iperf3 行程在 14 核上排程不及，UDP socket buffer 溢位）。

判法（**用已經在收的 ground truth，不新增儀器**）：
比對**接收側交換機 port 的 veth RX** 與 iperf3 回報的 received bytes。
- veth RX ≈ offered、iperf3 < offered ⇒ **主機丟的**（封包過了 fabric 才死）；
- veth RX < offered ⇒ **fabric 丟的**。

🔴 在做出這個比對之前，**不得寫「bmv2 撐不住 64 條流」**。目前唯一站得住的說法是
**「掉包隨並發數上升、與總位元率無關」**，那是觀察；歸因是還沒做的事。

# 增補 B：OVS 那半的判讀規則（寫於 OVS fabric 開機中、任何 OVS 數字存在之前）

> 🔴 **這一節的時序保證比 PREREG 與增補 A 弱，要照實說。**
> 本文寫於 **20:23:48**，OVS 那輪的第一個檔建立於 **20:24:54** ⇒ **文字確實早於資料**。
> 但原本要記錄這件事的 commit **因引號錯誤失敗而且我沒發現**，補交時 run 已經在跑。
> ⇒ 時序靠的是**檔案 mtime ＋ 這段自陳**，不是 commit 時間戳。引用時請一併引用這條。

## B-1. 🔑 P7 的價值比原本寫的大：它是**機制的判別實驗**

`PREREG.md` §6 的 P7 原本只寫「兩平面差異小於地板」，那把它當成一致性檢查。
實際上它能回答一個更重要的問題，而且**兩平面的差異結構剛好適合**：

| | P4 平面 | OVS 平面 |
|---|---|---|
| 取樣**產生**路徑 | bmv2 clone-to-CPU → proxy → gRPC | **OVS 自己的 sFlow agent** |
| 取樣**記帳**路徑 | `FlowLinkUsageCollector`（MININET 模式） | **同一份碼** |
| 速率**發布**路徑 | `calAvgFlowSendingRatesPeriodically` → `linkBandwidthUsage` | **同一份碼** |

⇒ **取樣路徑不同、記帳與發布路徑相同。** 所以：

- **若 OVS 也高報、幅度相近** ⇒ 成因在**共用的 kernel 碼**（§1-quater 的分母寫死是其中一個候選），
  **不在 bmv2／clone-to-CPU／proxy**。這會把搜尋範圍砍掉一大半。
- **若 OVS 不高報、或幅度明顯不同** ⇒ 成因（至少一部分）在**取樣產生路徑**，
  而那正是 P4 專屬的部分。

🔴 **先寫死界線**：兩平面的**絕對比值不可互比**（取樣率、每樣本代價、封包路徑都不同）。
可比的是**「有沒有系統性正偏」與「量級」**，判準見 B-3。

## B-2. 條件（與 P4 逐項相同，這是 matched 的意思）

- **條件 A**：64 流、`RATE_SCALE=0.1`（每流 0.1–2 Mb/s）、340 s
- **條件 B**：16 流、`RATE_SCALE=1`（每流 1–20 Mb/s）、340 s
- 同一份配對（32 條跨 pod ＋ 32 條同 pod）、同一個 `run_plane.sh`、同一個 `analyze.py`

🔴 **負載刻意不重新校準。** P4 的工作點是為 bmv2 選的，OVS 幾乎確定能吃更多——
但**改負載就不是 matched 了**。代價是 OVS 會跑在遠低於它能力的地方，
**那是可接受的**，因為本輪題目是遙測精度不是吞吐。
⇒ 但**必須回報 OVS 的實際掉包率**：若掉包顯著不同，兩平面看到的「真實流量」就不同，
per-edge 比值仍有效（各自對自己的 veth），但**跨平面的敘事要標明這一點**。

## B-3. 判讀規則（跑之前定死）

先驗條件與 P4 相同：`edges_down == 0 && hosts_ipv4 == 128`，不滿足就重開、不照跑。

| 觀察 | 判讀 |
|---|---|
| OVS 聚合比值落在 **1.10–1.40**（與 P4 的 1.18–1.34 重疊） | **成因在共用 kernel 碼**——最強的一種結果 |
| OVS 落在 **0.95–1.05**（在誤差地板內） | **成因在 P4 專屬的取樣產生路徑** |
| OVS 明顯高報但幅度差 2 倍以上 | **兩者都有份**，需要拆 |
| OVS **低**報（< 0.90） | 🔴 新現象，本輪未預期，不得硬套上面任何一格 |

**INCONCLUSIVE 的情形**（不得讀成任何一格）：先驗條件失敗、
有負載的邊少於 8 條、或掉包 > 20%（那時量到的是別的東西）。
