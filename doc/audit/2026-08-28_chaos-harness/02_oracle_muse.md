# NDTwin Chaos/Fuzz Oracle — Human-Supervised Adjudication Criteria

**Role:** Oracle designer (Muse). No execution. Deliverable is written criteria a human applies after a chaos run to decide real defect vs harness-induced noise.
**Repo:** /home/adam/Desktop/NDTwin-Kernel at commit observed 2026-08-28.
**Evidence discipline:** OBSERVED = read in file with path:line. INFERRED = conclusion drawn from observed code; not a claim about running behavior. Definition ≠ call site ≠ reached-at-runtime. No run was performed for this report.
**Language discipline:** Chinese audit material searched; report notes where no search was done vs empty result.

**Central difficulty addressed:** This codebase has documented tendency to REPORT SUCCESS WHILE FAILING (A-1 powerOn 200 while dead, B-1 ghost rules, B-2 lock renew beyond expiry, power/testbed relay, etc.). An oracle that trusts status codes is worthless here. Every invariant below checks STATE via an independent code path, never the status code of the operation under test. For each invariant I ask: if the component were completely broken in this respect, would this check go red? If not, invariant is dropped or flagged decorative.

## 1. INVARIANTS (heart of oracle)

For each: statement | how to measure | independent path that confirms | what violation looks like | bounds/saturation flag.

### INV-01 — Power-state agreement (graph vs process & traffic) — ANTI-LYING check

- **Statement:** `OBSERVED` — `GET /ndt/get_graph_data` `nodes[].is_up` for a switch must agree with the ground-truth process and forwarding plane, not just the API's own success code. `OBSERVED` — `DeviceConfigurationAndPowerManager::queryMininet` (queryMininet) derives power state from `getVertexIsUp` (DeviceConfigurationAndPowerManager.cpp:302), and `P4PowerStrategy::powerOn:46-49` returns `OpResult::success()` when `getVertexIsUp(node)==true` even though liveness is stale (KNOWN-ISSUES A-1). So the graph can say UP while bmv2 pid is gone and traffic is blackholed.
- **Measure:** After any `POST /ndt/set_switches_power_state?action=on|off` (even if HTTP 200 `{"Success"}`): (a) read `GET /ndt/get_graph_data` for `is_up` on that dpid; (b) INDEPENDENT: count bmv2/ovs process existence — P4: `pgrep -a simple_switch_grpc` or gRPC port LISTEN + proxy `/p4/switch_state` `probe_ok` ; OVS: `ovs-vsctl list-br` contains bridge + `is_connected:true`. (c) INDEPENDENT data-plane: `GET /ndt/get_detected_flow_data` path and `/proc/net/dev` or direct ping tx bytes must show 100% loss if graph says DOWN, and movement to alternative port if UP and rule installed (A-4d/A-4e validation method: tx-byte delta). A violation is graph==UP while (b) or (c) shows DOWN.
- **Why independent:** Graph `is_up` is written by liveness worker (1 Hz) and by `inform_switch_entered`; both can lie. Process/port and tx bytes are not written by the kernel at all.
- **Violation signature:** POST on returns 200 in ~0.01s (vs ~1.27s honest, A-1), bmv2 pid count unchanged, graph stays `is_up=true`, `is_enabled=true`, edges 8/8 up, 100% loss. Log contains no `probe_ok==false` proof within 15s. **Saturation flag:** NONE — but note `p4LivenessFor` staleness: `probe_ok==true` with stale age is treated as UP even if proxy poller stalled (ndt_api.md L189-199). So check must use fresh probe (age<15s) and beacon age, not verdict alone.
- **Prior shape:** A-1 (`powerOn:45-50` early-return), A-4c proxy restart, KNOWN-ISSUES F-14/F-16 (host never down, edge up).

### INV-02 — Edge liveness conservation (topology graph vs control plane)

- **Statement:** Every edge `is_up` in `get_graph_data` must be explainable by a control-plane poll snapshot at that time. `OBSERVED` — `TopologyAndFlowMonitor::pollControlPlaneTopology` does untimed `utils::execCommand(curl ...)` with empty-body early-return (TopologyAndFlowMonitor.cpp:469-511). On stuck curl, update never runs, graph freezes, and edges can be permanently wrong (A-2: 40 links down while fabric forwards). So count of `edges is_up=true` must be cross-checked.
- **Measure:** Snapshot A: kernel `get_graph_data` edges_up count. Snapshot B (independent, same wall-clock ±1s): directly `curl --max-time 3 http://localhost:8080/v1.0/topology/links` (or proxy `http://<P4_PROXY>/v1.0/topology/links`) raw JSON lengths. If B answers 000 (A-2 fingerprint) while A reports all down, that's chaos-induced stuck poll — harness found real defect. If A reports all UP but B shows fewer links, that's optimistic resurrection (F-4: dead switch's links revived via host-learning `updateHosts`).
- **Violation:** A shows 40/40 or 288/288 edges DOWN with `up=true,enabled=false` split (A-2 fingerprint) but dataplane tx continues. Or A shows UP for a switch-to-switch edge whose either endpoint is `is_up=false` (F-16 via host edge staying up) or whose reverse is missing — use `findEdgeBySrcAndDstDpid` pair check. Log: zero warning despite stuck curl child alive >5s — check `ps aux | grep curl` age (A-2: 733s).
- **Saturation:** Edge counts saturate at topology size (32 or 288) — useless beyond bound. Must also check per-vertex `is_up && isEnabled && !adminDisabled` triple via `isUsable()` (GraphTypes.hpp:267,393). A bare `is_up` or `is_enabled` alone is decorative.

### INV-03 — Flow-table identity (twin cache vs switch truth)

- **Statement:** `GET /ndt/get_switch_openflow_table_entries` and the per-edge `flow_set` / `link_bandwidth_usage_bps` derived from it must equal what the switch actually holds when read via P4Runtime / OVS `ovs-ofctl`, not the kernel's optimistic cache. `OBSERVED` — `HttpSession::processFlowBatch` enqueues and updates local table via `updateOpenFlowTables` before southbound result exists (HttpSession.cpp:1058-1061, comment queued). So 200 queued ≠ installed. `Controller` historically discarded `OpResult`; Group/Meter handlers previously returned 200 unconditionally.
- **Measure:** After any `install/delete/modify_flow_entry|group|meter` (even 400): read kernel `get_switch_openflow_table_entries` AND independently dump real tables: P4: proxy GET `/stats/flow/<dpid>` or gRPC `ReadTableEntries`; OVS: `ovs-ofctl dump-flows <br>`. Compare by (dpid, priority, match key). For flow ↔ edge consistency: every `edge.flow_set` entry must appear in exactly one switch table's match that routes via that edge's `src_dpid/src_interface`, and every installed rule's translated path must appear in `get_detected_flow_data[].path` after `kFlowPathRecomputeInterval` (1s, FlowLinkUsageCollector.hpp:51) + convergence slack (5-30s per kOnceConverged).
- **Violation:** Ghost rule (B-1): kernel 200, log zero error, but real table lacks entry (OVS silent; P4 400 with `Refusing rule`). Or twin reports healthy edge with 0 usage while real table shows no rule for traffic that tx bytes prove moves (A-4d blackhole after delete, modify priority bug B-2c/Adjacent: modify_flow_entry touched wrong priority). `flow_set` keys using mixed vocabulary (`eth_type/ipv4_dst` vs `dl_type/nw_dst`) indicate optimistic-append vs poll divergence.
- **Saturation:** Table sizes unbounded but kernel's `isUp` gating can blank tables on wedged fetch (DeviceConfigurationAndPowerManager.hpp:299 `getOpenFlowTables` respects liveness). Flag: if switch marked down, tables read as empty even if switch holds rules — so gate check must read liveness first.

### INV-04 — Rate conservation (bytes in = bytes out, twin vs wire)

- **Statement:** Sum of `estimated_flow_sending_rate_bps_*` over `get_detected_flow_data` entries whose path traverses a given edge must equal that edge's `link_bandwidth_usage_bps` (and both must equal wire tx bytes / interval within sFlow sampling error). `OBSERVED` — `Link bandwidth clamp` (capacity-clamp FINDING.md): `linkBandwidthUsage` clamped to `linkBandwidth` (1 Gbps declared) on both flow-sample and counter paths (TopologyAndFlowMonitor.cpp:1089-1095, FLUC:1162-1163). So twin saturates at model capacity even when wire does 22 Gbps. Also F-17 `get_average_link_usage` averages only busy links (denominator wrong) → EA-App decision skew.
- **Measure:** INDEPENDENT wire truth: `/proc/net/dev` or `/sys/class/net/<veth>/statistics/tx_bytes` deltas sampled every 1s (ground truth used in round6 E1/E8 validation). Compare to twin's `link_bandwidth_usage_bps * interval/8`. For flow-rate conservation: pick a single-flow iperf, check `estimated_flow_sending_rate_bps_in_the_last_sec` vs `linkBandwidthUsage` on each hop's edge. Must do within sampling error bound ±5% only at high window/load (sFlow 1/256 theory: 95% ≈196·√(1/c)); low-rate (<3 Mbps) quantizes to one quantum (F-9; KNOWN-ISSUES C F-9 corrected). Also cross-check `get_average_link_usage` vs manual mean over `usableEdges` (isUsable) using raw `link_bandwidth_usage_bps` — if they diverge by factor ~4x at 8/32 busy, that's F-17.
- **Violation:** Twin edge `linkBandwidthUsage==1000000000` (or utilization==100%) while wire delta shows >1 Gbps (clamped). Or sum(flowRates)≈0 while edge usage >0 (or vice versa) beyond 1/√c band — indicates sFlow loss (check `rx` vs `addressed` vs kernel drops in FLUC rate loop logs) or host-bound egress not credited (B-17 fix). Before fix B-17, last-hop usage always 0. `rate divisor check` log line (`rate divisor check: measured_interval_s=...`) must match actual interval within 1% (ticket Q).
- **Bound flag:** 🔴 BOUNDED QUANTITY — `link_bandwidth_usage_bps` and `leftBandwidth` are clamped to `linkBandwidth` (model value) and utilization to 100%. Beyond bound they are DECORATIVE. sFlow rate itself is unbounded but saturates at counter wrap (~1.8e19 guard via `counterDelta`); unguarded subtraction still present in old branches. Any invariant using these values beyond 1 Gbps on 1-GbE-declared links is invalid without independent wire check.

### INV-05 — Path consistency (BFS path vs OpenFlow tables)

- **Statement:** For every flow in `get_detected_flow_data`, `path[]` (computed via `bfsAllPathsToDst` / `getAllPathsBetweenTwoHosts` using `isUsable` edges) must be realizable from the union of `get_switch_openflow_table_entries` rules (exact LPM match). `OBSERVED` — TopologyAndFlowMonitor's `getAllPathsBetweenTwoHosts`, `bfsAllPathsToDst` previously used `isUp && isEnabled` not `isUsable`, missing `adminDisabled` (B-26/B-27). So admin-disabled switches could still appear in computed paths. Also `setAllPaths` had clear-then-add vs ever-add bug (m_allPathMap only added).
- **Measure:** Snapshot C: `get_detected_flow_data[].path` expanded to (dpid, interface). Snapshot D (independent): fetch all `get_switch_openflow_table_entries` and reconstruct forwarding: for each flow's (src_ip,dst_ip), walk tables by LPM priority match (highest priority longest prefix) across switches along path; next hop's `OUTPUT` port must equal path's interface, and final `dstDpid==0` edge must be host edge. Cross-check also `get_path_switch_count` / `get_all_destination_paths` map — must agree on `m_allPathMap` vs `switchCountMap`.
- **Violation:** Path contains a hop through vertex/edge where `isUp==false` or `adminDisabled==true` but `isUsable==false` (old check would include it). Or path length mismatched (`get_path_switch_count` returns 404 or stale 5 when path changed — KNOWN-ISSUES A-2/F-6 note). Or path includes 10-Gbps core links declared 1 Gbps that were never shaped (F §F) — indicates model vs wire drift.
- **Saturation:** Path count bounded by topology; `setAllPaths` clears on empty vector — an empty `inform_all_destination_paths` clears nothing (deliberate asymmetry, FLUC::setAllPaths). So empty-path case is not observable.

### INV-06 — Lock mutual-exclusion (state vs HTTP status)

- **Statement:** `OBSERVED` — `LockManager` has no owner field, `unlock` clears any lock (B-2), `renew` does not check `now < expiryTime` (B-2) — so `POST /ndt/acquire_lock` 200, `/renew_lock` 200, `/release_lock` 200 can all lie. Only observable truth is whether concurrent writes interleave.
- **Measure:** Do NOT check HTTP codes. INSTEAD: have two harness clients A,B compete for same `lockName` with TTL=3s. Measure via independent sequence log: after A acquires, B must get false/412 for full TTL window, and A renew after expiry must get 412 (not 200). Violation if B acquires within TTL, or A renews expired lock and then B is blocked (proves expiry not checked), or any `release` from non-owner returns true (now fixed to bool but still check via second acquire). Log-independent check: after A's TTL expires with no renew, B's `acquire` must succeed within 1s; if not, lock is stuck (owner field missing legacy behavior).
- **Violation:** `renew` extends expired lock (B-2#1); `release` by non-owner frees it (B-2#2). In chaos log, look for two `acquire succeeded` within same TTL overlapping and both proceeding to modify flow tables without serialization — then check flow-table diff interleaving.
- **Bound:** TTL 5s default; `steady_clock` vs wall-clock confusion possible (see N-1 below). TTL short implies timing-sensitive; measure with `steady_clock`.

### INV-07 — Simulation/plug telemetry freshness (silent-zero vs idle)

- **Statement:** `GET /ndt/get_detected_flow_data` and `get_detected_top_k_flow_data` must distinguish idle from dead; `GET /ndt/get_switches_power_state` for testbed must not report request as outcome. `OBSERVED` — `FlowLinkUsageCollector::purgeIdleFlows` uses `FLOW_IDLE_TIMEOUT=15000 ms` but with `now <= endTime → continue` (FLUC:2242) using wall-clock `getCurrentTimeMillisSystemClock()` — wall-clock rollback creates unbounded zombie (N-1). Also HistoricalDataManager MININET early-return (B-3) and DisabledSwitch liveness Unknown vs Down confusion.
- **Measure:** After traffic stops, poll `get_detected_flow_data` every 1s for 20s. Expect `latest_sampled_time` to stop advancing, and list size to decay to ~0 after 15s. If list stays at ~63 entries with ~92% duplicates (B-x churn 13.3× inflation) and `estimated_*_in_the_proceeding_1sec_timeslot==0` but still listed, that's disclosed idle-tail (not defect unless spec says active only — spec says active, so it IS defect). Independent path: wire tx bytes flat while list non-empty confirms ghost. For power: testbed relay must check HTTP status 200 AND body contains outlet text; 200 with error string is not ON/OFF (DeviceConfigurationAndPowerManager::interpretRelayResponse now keys on HTTP status).
- **Violation:** `latest_sampled_time` advances while wire flat (N-1 clock jump zombie — needs wall-clock jump to trigger, chaos harness should inject NTP step). Or HistoricalDataManager `historical_logging` state enabled but snapshot file never written (B-3).
- **Saturation:** Flow table unbounded until purge; bounded by 15s window — beyond that, size==0 is correct but indistinct from no traffic. Check `FlowTableSize` trend not single snapshot.

### INV-08 — Telemetry monotonicity & reset safety

- **Statement:** `link_bandwidth_usage_bps`, `estimated_flow_sending_rate_bps_*`, counters (`inputByteCountOnALinkMultiplySampingRate`) must never go backwards except on explicit clear/reset; a backwards counter wrapped to ~1.8e19 must not be published as elephant flow (B-22 `counterDelta` guard). `OBSERVED` — unsigned underflow fix via `counterDelta` exists now but older branches lacked it; `RenewLock` expiry still unchecked; `UpdateLinkInfoLeftLinkBandwidth` divisor bug (B-4) overstated by period/1s.
- **Measure:** During steady 50 Mbps iperf, log twin's per-second `linkBandwidthUsage` and `flowSendingRate`. Assert monotonic byte count over short window within `196·√(1/c)` band, and no single-second spike > 1e12 bps (underflow signature). Independent: `get_average_link_usage` must be non-decreasing as busy links increase; if it drops when busy links increase, denominator bug.
- **Violation:** Single interval shows ~1.8e19 bps (or 10× step), flags `isElephantFlowPeriodically` true on tiny flow. Or flow rate jumps 0→1.8e19 on purge/recreate boundary.

### Anti-oracle usage rule

If log shows AO item alone, dismiss without further analysis. If AO item + one INV violation with independent path confirmation, escalate — AO does not cancel INV when independent measurement disagrees. Especially: AO-03 jitter + INV-04 clamp coincide at high load — but clamp is >capacity ceiling, jitter is <capacity variance — distinguish by wire bytes (AO if within 1/√c, defect if at exactly 1 Gbps ceiling).
