## 0. 開跑前的三個閘門（缺一不可，順序不可換）

| # | 閘門 | 為什麼在這裡 |
|---|---|---|
| **G1** | **每個 invariant 都要有一個「已知會違反它」的陽性對照，而且要看過它發火** | 沒看過它失敗就不算交付。綠燈的 harness 與「根本沒在檢查」的 harness 長得一模一樣 |
| **G2** | **每個注入都要斷言自己成功了** | 否則「沒發現違規」＝「故障從來沒發生」。**刪除留下一個洞（大聲），改名留下一個假答案（安靜）** |
| **G3** | **claim lab、`exclusive_cpu=yes`** | 見 §2：chaos 本身會製造 §2 那個假陽性 |

**G1 的具體做法**：不要另外寫「模擬違規」的測試碼——**用 KNOWN-ISSUES 裡已經在案的真缺陷當陽性對照**。
每個 invariant 至少配一條：

| INV | 陽性對照（真缺陷，現在就會發火） |
|---|---|
| 01 | **A-1** 關機後立刻開機 ⇒ 回 200 且 ~0.01 s（誠實路徑約 1.27 s） |
| 02 | **A-2** 的指紋 `up=true, en=false`（⚠️ 見 §3，**不是**「任何不一致」） |
| 03 | **B-1** 幽靈規則；**A-4e** `modify_flow_entry` 忽略 `priority` |
| 04 | **capacity clamp**：宣告 1 Gbps 的鏈路上跑贏它 ⇒ twin 停在 1e9 |
| 05 | **A-4d** 裝一條規則再刪掉 ⇒ 目的地黑洞 |
| 06 | **B-2** `renew` 不檢查過期；非 owner `release` 成功 |
| 07 | **B-3** `historical_logging` 回 200「已啟用」但一列都不寫 |

## 1. 🔴 兩個必修（正本在 `03`，這裡只留可貼的修法）

```bash
# INV-01 獨立路徑。-a 不含 -f，比對的是 comm，而 comm 上限 15 字元、
# simple_switch_grpc 有 18 個 ⇒ `pgrep -a simple_switch_grpc` 恆不匹配、100% 偽陽性。
pgrep -cf 'simple_switch_g[r]pc'        # ✅ 正解，bracket 防自我匹配
# ⚠️ 不要改成 pgrep -xf ：-x 配 -f 要求整條命令列完全相等，對帶參數的行程恆假
```

**INV-08 的單調性半條刪掉，指向 INV-04。** `get_average_link_usage` 取的是**忙碌鏈路的平均**（F-17）——
在平均值上加入一個低於現值的樣本，平均值就會下降。**那是算術，不是缺陷。**

## 2. 🔴🔴 最重要的一條：**chaos 自己會製造 INV-04 的違規，而那不是缺陷**

**實測（08-28）**：bmv2、16 條流每流 3 M（乾淨工作點）

| 條件 | loss 中位數 |
|---|---|
| 無 burner | **0.000%** |
| **10 個「零封包」的純 CPU burner** | **2.192%**（16/16 都超過 0.5%） |

**那些 burner 一個封包都沒送。** bmv2 的 datapath 是 user-space 行程、**整台交換機共享 per-packet CPU**
⇒ **轉發與任何負載搶同一顆 CPU**。

⇒ **任何吃 CPU 的 chaos 動作，都會讓 INV-04（rate conservation）與 INV-05（path）發火，
而系統完全正確。** 這不是雜訊，是**與處理效應對齊的**假陽性——它只在你注入的時候出現。

**判準（寫進 anti-oracle，必須配量測、不能只寫「注意 CPU」）**：

- 每個 chaos 動作**前後都取 `/proc/stat` 的 busy fraction**（不要用 `load1`——它在 14 核上是
  **落後的複合指標**，還會把 uninterruptible sleep 算進去，當門檻會給出相反的答案）
- **busy fraction 相對於該回合基線 +0.15 以上 ⇒ 該回合的 INV-04／05 判定作廢**，標成
  `INCONCLUSIVE-CPU`，**不要標成 PASS**（標 PASS 等於宣稱「檢查過而且沒事」）
- 🔑 **`INCONCLUSIVE-CPU` 的比例本身是一個要回報的數字。** 如果它很高，代表這個
  invariant 在 bmv2 上結構性地量不到，那是發現，不是失誤

⚠️ **OVS 上不成立**（load1 43、10 burner，loss 仍 0.037%）⇒ **同一份 anti-oracle 不能兩個平面共用。**

## 3. 收窄三條會過度發火的 invariant

| INV | 外部產出寫的 | 環境事實 | 修正後的判準 |
|---|---|---|---|
| **02** | 「兩個旗標不一致 ⇒ 違規」 | **`up=false, en=true` 是關機交換機的正常穩態**（round 6 更正） | 指紋收窄成**特定的 `up=true, en=false`**，不是任何不一致 |
| **04** | 「twin 對 wire 差 >5% ⇒ 違規」 | sFlow 1/256 的**誤差地板是 196·√(1/c)**，跨 430× 窗長與 10× 負載驗證過；低速率（<3 Mbps）**量子化到一個量子** | 容差要**繼承取樣噪聲**，而且**低速率區間不得判定**。GUI 上看得到的 ±40% 擺盪**是解析度不是缺陷** |
| **05** | 用 `get_path_switch_count` 判路徑變化 | **OVS 三個狀態（裝前／裝後／刪後）它都回 5**，零鑑別力 | 改用 `get_detected_flow_data` 的 **`path`** 欄；資料面切換次秒級、twin 的 path 約 **3–5 秒**跟上，容差要涵蓋這個落差 |

## 4. 🔴 動作面：五個會**毀掉測試床**而不是製造故障的動作

`01` 的動作表在程式碼層面是對的，但下列動作在**這台機器上**的後果不是它寫的那個。

| 想做的事 | ❌ 不要用 | 為什麼 | ✅ 改用 |
|---|---|---|---|
| 殺一個元件 | **`pkill -f` / `pgrep -f` 殺東西** | **已自殺七次**，包含今晚兩次。pattern 會匹配到 harness 自己的命令列 | 在**生出行程的當下記下 pid**，只殺那個 pid |
| 斷一條鏈路 | `ifconfig <iface> down` | **會弄壞整台 bmv2 交換機**，不只那條鏈路 | **`tc netem`**（loss 100% 或 delay） |
| 抓封包當獨立證據 | 隨手起 `tcpdump` | **AppArmor 護體，root 送 SIGKILL 都 EPERM** ⇒ 清不掉，污染後續每一回合 | 用 `/proc/net/dev` 計數器差；真的要抓就先確認殺得掉 |
| 任何 shell-out | 不帶 timeout | `popen(curl)` 在 IPv6 黑洞卡 **131 秒**。**「已知會失敗」≠「失敗很便宜」** | 每一個都帶 `--max-time` |
| 重啟 proxy 當作故障注入 | 當成無害的重啟 | **A-4c：會靜默摧毀 bring-up 以來的每一條規則**；且 warm fabric 下遙測會 ×N | 可以做，但**它是破壞性動作**，之後整個 fabric 的狀態要重新建立 |

## 5. harness 自己是第一個受測物

**新工具第一次 live 跑，找到的幾乎都是工具自己的缺陷。** 所以第一輪的產出要這樣讀：

1. **先跑「不注入任何故障」的一整輪**（null round）。**任何違規都是 harness 的缺陷，不是系統的。**
   這一輪的違規數就是 harness 的偽陽性地板，**要寫進報告**。
2. **放行路徑要有 dry-run。** 被守衛擋下的動作可以真跑（拒絕很便宜），
   **放行的動作不行** ⇒ 每個破壞性動作都要有一個「印出我要做什麼但不做」的模式，
   而且**那個模式要被跑過**。否則守衛失效的時機，正好與它要防的事件重合。
3. **驗收寫在狀態上，不是 rc 上。** 這個 codebase 有 12 種「失敗回報成功」的機制。
   harness 自己不准用 HTTP 200 當任何東西的證據——`02` 的 INV-06 已經寫對了
   （**"Do NOT check HTTP codes"**），把那條推廣到全部。

## 6. 覆蓋邊界（誠實聲明，交接時最容易消失的一欄）

- **只涵蓋 P4/bmv2 平面。** §2 的 anti-oracle 在 OVS 上是錯的，兩個平面要分別跑、分別調容差。
- **N-1（wall-clock 殭屍）需要注入 NTP step**，那會影響整台機器上的其他 session。
  **這一條在多 session 的夜裡不要跑**，留給單獨的窗口。
- **`02` 自標**：Chinese term searches 執行了但不完整、213 個 review 未分類。
  ⇒ 這份 oracle 的覆蓋面上限就是那個上限。
- **本檔沒有涵蓋 `01` 的 §8.4 lifecycle abuse**——那類動作與「G2 注入要斷言自己成功」
  最難相容（行程死了誰來斷言），需要單獨設計。
