## 3. 縮減的理由：哪一段站得住，哪一段站不住

你要求縮減的理由必須寫成「前提被推翻」而非「時間不夠」，並說如果站不住就去要更晚的窗。逐段回答：

### ✅ (a) → (b)：**前提驅動，站得住**

- 2×2 的存在理由是 §3 的 Q3（歸屬）：兩個改動同時落地留下糾纏，用 2×2 拆開。
- 前提被推翻之後，**只有一個因子在生產裡真的變過** ⇒ **沒有共同運動可歸屬**，
  2×2 要拆的那個糾纏不存在。
- 剩下的兩個問題證據需求不同：
  - **Q2（recompute 有沒有抬高天花板）** ＝回顧性、關於生產 ⇒ 需要**全梯階**兩臂，(b) 給滿。
  - **「要不要打開 batching」** ＝前瞻性決策 ⇒ 決策點是天花板會不會動，而 §7 的措辭紅線
    只准寫**天花板格語言**，天花板在牆上 ⇒ 牆邊四階就是這個決策需要的全部。
- ⇒ (b) 砍掉的每一格，都是**被推翻的前提才使其必要**的格；
  保留的每一格都是**存活問題所需**的格。這是前提驅動，不是時鐘驅動。
- **誠實的殘留損失**（③列已寫）：若 batching × recompute 只在低取樣率交互，(b) 看不到。
  但那個觀察在 §7 下**本來就不可宣稱**（不是天花板格語言），且 E4 已把 CPU 降為 secondary
  並禁止用它解釋或補強 primary ⇒ 損失的是探索性觀察，不是可發表結論。

### ❌ (b) → (c)：**時鐘驅動，站不住——照你的規矩，不要縮**

- 300→120 沒有任何前提支持它。它付的代價是具體的：
  1. **§6 的逐格對帳死掉**。§6 自己寫「同 fabric、**同 binary** 才逐格比」，而 D 輪四格是
     300 s；DUR 不同，逐格比就不成立，只剩比方向。
  2. **`ratio` 的精度惡化，而且正好惡化在判定線上**。載入器 `TRIM=6.0`、`SPAN=240.0` ⇒
     DUR=300 給 **240 個 1 秒視窗**，DUR=120 只給 **約 114 個**。
     `ratio` 與 `sd_mean` 的標準誤因此差 **√(240/114) ≈ 1.45×**，
     而健康判準就卡在 `ratio ≥ 0.95` 這條線上。
     🔑 **`lam` 與量化 floor 不受 DUR 影響**（它們是每秒量，`step=round(hz)`）——
     損失精確地就是「視窗數」，不是「樣本數」。這一點值得寫清楚，因為直覺會說反了。
- **反面證據（誠實列）**：`gate_e`／`wall_f` 都用 120 s 且在 1/256 與 1/16 拿到健康讀數
  （`ratio` 0.9955–1.016）⇒ 120 s **在牆邊是可用的**。但「可用」≠「可與 D 輪逐格比」，
  而死掉的是後者這個**已註冊的義務**。
- ⇒ **建議：(b) 若排不進 9/03 之前，去要更晚的窗，不要降 DUR。**

### 🟡 (d)：前提驅動但**過度更正**

砍掉 batching 是前提驅動的；但被推翻的前提**同時創造**了一個新問題
（「要不要打開」），(d) 把那個新問題也一起丟了。除非 Adam 明確裁定
「batching 開不開不在這一輪決定」，否則 (d) 丟掉的比前提要求的多。

## 4. CPU 基線：兩種鑑別力的差別（**數字備妥，關不關桌面 Adam 裁**）

實測，本機，**無 fabric**，兩個 4 秒窗：

| 來源 | 核 |
|---|---|
| `claude-desktop`（三個行程） | ≈ 0.37 |
| `claude` CLI session（三個，**含跑這輪的這一個**） | ≈ 0.25 |
| `gnome-shell` | ≈ 0.08–0.11 |
| `chrome` | ≈ 0.03 |
| **合計外來負載** | **0.842**（另一窗 0.656） |

| 方案 | 基線 | 門檻（超出量） | 抓得到 | 🔴 抓不到 |
|---|---|---|---|---|
| **A：桌面照開** | ≈ 0.84 | 0.50 核 | 08-28 那一類污染（4 vCPU 編譯）；單核 burner（實測 excess **1.004**） | 任何 < 0.5 核的併行負載；而且**基線自己的抖動就有 ≈ 0.19 核**（兩窗 0.656 vs 0.842）⇒ 判定線附近很吵 |
| **B：窗內關桌面** | ≈ 0.1–0.2 | 可降到 0.25 核 | 上述全部，**加上**半核級別的干擾 | < 0.25 核 |

**緩解（兩案都適用，已落地）**：基線與每格讀數都用 **60 秒窗**（`BASELINE_WINDOW` 預設 60），
把 0.19 核的短期抖動平均掉。基線是**量進檔案**的，不是打字的；基線檔缺席時閘門回
**UNRUNNABLE，不回綠**。

## 5. 建議

**採 (b) ＠300 s，6 h 56 m。** 若 9/03 之前排不進去，**去要更晚的窗，不要退到 (c)**——
(c) 的縮減在「前提被推翻」這個理由下站不住，而它殺掉的是 §6 已註冊的對帳義務。

**怎麼跑 (b)**（值全在 `round.env`，不手打）：

```bash
. doc/audit/2026-08-31_sampling-ceiling-after-merge/round.env
# 主因子：recompute 全梯階，batching 固定在生產值（關）
LADDER="1024 256 64 32 16 8 4 1" ARM_ORDER="p mp" REPS=3 ./run_e.sh plan   # 註：見下
```

🔴 **注意**：`ARM_ORDER` 的四個代號是 `bl`(off/1kHz) `m`(on/1kHz) `p`(off/1Hz) `mp`(on/1Hz)。
(b) 的**主因子**是 recompute ⇒ 兩臂＝`bl`（1 kHz, batching 關）與 `p`（1 Hz, batching 關），
**兩者都在生產的 batching 設定上**，這正是「生產行為真的變過的那一軸」。
牆邊補的 batching 格＝`m`／`mp`。所以 (b) ＝

```bash
LADDER="1024 256 64 32 16 8 4 1" ARM_ORDER="bl p"  REPS=3 ./run_e.sh ladder   # 48 格，主因子
LADDER="32 16 8 4"               ARM_ORDER="m mp" REPS=3 ./run_e.sh ladder   # 24 格，牆邊 batching
```

兩次都寫進同一個 `raw/cells.tsv`，`run_cell` 的 resume 會跳過已記錄的格。
