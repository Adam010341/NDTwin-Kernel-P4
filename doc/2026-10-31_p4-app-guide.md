# Put your P4 program into NDTwin

[Co-developed with claude code -- Adam]

This guide is for someone who has a P4 program for bmv2 (v1model) and wants to run it inside
NDTwin, then build an application on top of it: traffic engineering, energy saving, or anything
else that watches the network and changes it.

What you get:

- every switch of a Mininet fabric runs **your** program, with **your** table entries;
- NDTwin's kernel reports the fabric's topology, link usage and flows, **with no change to your
  `.p4`**;
- your application reads and writes **your own tables** through the kernel's REST API on port
  8000.

The steps are: lay the program out as a p4lang/tutorials exercise, compile it with `make build`,
and run `ndt up p4 --app <exercise dir>`.

## 1. Before you start

- An NDTwin checkout and a machine that can already bring up NDTwin's own P4 fabric with
  `tools/test_workflow/ndt up p4`. The [README](../README.md#live-fabric) and the
  [testing manual](2026-08-17_testing-manual.md) cover that.
- The P4 proxy's Python environment. `ndt` converts your exercise with it and refuses to
  continue without it. From the checkout's root:

  ```bash
  python3 -m venv p4_proxy/venv
  p4_proxy/venv/bin/pip install -r p4_proxy/requirements.txt
  p4_proxy/venv/bin/python p4_proxy/regen_p4runtime_pb2.py
  ```

- `p4c-bm2-ss`, the P4 compiler for bmv2, to compile your program.

The `ndt` commands below run from the root of the NDTwin checkout.

## 2. Lay your program out as a tutorials exercise

NDTwin reads the directory convention of [p4lang/tutorials](https://github.com/p4lang/tutorials)
exercises. Any `exercises/<name>` directory there is a valid input once it builds, and so is
your own directory laid out the same way:

```text
my-exercise/
├── Makefile             # optional: TOPO = ..., DEFAULT_PROG = ...
├── my_program.p4
├── pod-topo/            # or the files at the top of the directory
│   ├── topology.json
│   ├── s1-runtime.json
│   └── s2-runtime.json ...
└── build/               # written by `make build`
    ├── my_program.json
    └── my_program.p4.p4info.txtpb
```

- **`topology.json`** declares `hosts`, `switches` and `links` in the tutorials format. Each
  switch names its entries file with `runtime_json`.
- **`sN-runtime.json`** holds one switch's `table_entries`, in the tutorials format. When the
  fabric comes up, NDTwin's P4 proxy writes these entries into each switch (unless the exercise
  brings its own controller, section 6). Each `sN-runtime.json` names the `p4info` and
  `bmv2_json` of the program that switch runs; pre-flight checks that the p4info it names is the
  one that switch runs.
- **Switch names** are `s1`, `s2`, ... The number is the switch's datapath id everywhere in
  NDTwin: the `dpid` the API routes take.
- **Host names** are `hN`, where N is the last number of the host's address (`h1` on
  `10.0.1.1/24`, `h2` on `10.0.2.2/24`). Every host address carries a prefix length; one without
  is refused rather than guessed.

How the files are found:

| what | how it is chosen |
|---|---|
| the topology | `--topology <path relative to the exercise>`, else the Makefile's `TOPO`, else the only `topology.json` at the top of the directory or one directory down (`build/`, `logs/`, `pcaps/` and `ndtwin/` are skipped). With several and no `TOPO`, the command stops and lists them |
| the program | `--p4 <path relative to the exercise>`, else the Makefile's `DEFAULT_PROG`, else the only `.p4` at the top of the directory |
| the compiled program | `build/<stem>.json` and `build/<stem>.p4.p4info.txtpb`, where `<stem>` is the program's file name without `.p4`. A switch whose entry in `topology.json` names its own `program` runs that one instead |

Only literal Makefile values are read. A `TOPO` built with `$(...)` is not evaluated; pass
`--topology` instead.

## 3. Compile it yourself

```bash
cd my-exercise
make build
```

NDTwin never builds what the switches run: they run your `build/` files (pre-flight only
test-compiles a throw-away copy). Run `make build` after every change to the `.p4`; nothing
checks that `build/` is current. Use `make build`, not plain `make`: in the tutorials
Makefiles the default target also starts the tutorials' own Mininet, which you do not want
beside NDTwin's fabric. If the compiled files are missing, `ndt` stops and names the `make build`
command to run.

A directory without the tutorials Makefile can produce the same two files directly:

```bash
mkdir -p build
p4c-bm2-ss --p4v 16 --p4runtime-files build/my_program.p4.p4info.txtpb \
    -o build/my_program.json my_program.p4
```

## 4. Bring it up

```bash
tools/test_workflow/ndt up p4 --app path/to/my-exercise
```

The fabric is sized from your topology: give no host count (`ndt up p4 4 --app ...` is
refused). `p4_proxy/mininet/host_count_override` is set to your host count and `ndt down` puts
it back.

This one command:

1. **converts** the exercise into an NDTwin app package and prints what it chose;
2. **checks** the package (pre-flight: the files are present, the entries match the p4info,
   the program compiles where `p4c-bm2-ss` is installed, and more) and prints the check table;
3. **brings up** the bmv2 fabric with your program on every switch, the P4 proxy and the kernel,
   and verifies them.

If the conversion or pre-flight refuses, nothing is started.

A good run prints `up. ready`. With your own program it also warns `destination paths NOT
CHECKED` and, under the default `owner package`, that NDTwin discovered no links and installed
no routes; both are expected.

Under `up. ready`, one line gives the ports and the way into the topology, sometimes with a
second line under it. With NTG as it ships, it reads:

```text
  proxy :8081   kernel :8000   NTG prompt, no mininet>: sudo tmux -L ndtwinlab attach -t topo
    for Mininet's CLI: 'ndt ntg cli', then 'ndt down' and up again
```

The words before the command say what that tmux pane holds, read from NTG's config. Every
label except `Mininet CLI` has a second line under it that says why, or what to do:

- `Mininet CLI`: a `mininet>` prompt.
- `NTG prompt, no mininet>`: NTG's own prompt (its `custom_command` mode). This is what NTG as
  shipped gives.
- `NTG hardware-testbed mode, no mininet>`: NTG leaves Mininet mode for its hardware-testbed
  mode, and stops if no hardware testbed is set up; either way nothing in the pane drives your
  fabric. Either NTG found no Mininet testbed file to read, or its Mininet testbed file also
  lists a `Hardware_Testbed`.
- `topology pane (NTG mode unknown)`: `ndt` cannot tell. Either the config is in a shape `ndt`
  cannot read, or it cannot read the file, or it names a mode NTG does not know (run
  `tools/test_workflow/ndt ntg` to see which). Or this run reused a fabric that was already up,
  which keeps the mode it started with.

Any line without `Mininet CLI` means `ndt` does not promise a `mininet>` there; section 7 says
how to get one.

The conversion part of the output, for the tutorials `basic` exercise (paths shortened):

```text
  exercise      : <tutorials>/exercises/basic
  topology      : pod-topo/topology.json   (the Makefile's TOPO)
  program       : basic.p4   (the only .p4 at the top)
  pipelines     : s1=build/basic.json, s2=build/basic.json, s3=build/basic.json, s4=build/basic.json
  control plane : ndtwin   (no mycontroller.py: NDTwin installs the routes)
  route role    : auto-filled from the p4info -- its one (table, action) candidate shaped like a destination route: MyIngress.ipv4_lpm hdr.ipv4.dstAddr -> MyIngress.ipv4_forward(dstAddr, port)
                  owner package  (NDTwin only reads this table, to compute flow paths); override with --role-ipv4-route, or --no-roles
  package       : <NDTwin checkout>/.test_run/packages/generated/basic-<8 hex digits>   (created)
```

**Where the package goes.** Under `.test_run/packages/generated/` in the NDTwin checkout,
named after the exercise plus 8 hex digits derived from the exercise's path. Nothing is ever
written inside your exercise directory, and `.test_run/` is ignored by git.

**Running it again.** The package is regenerated each time. If nothing changed, the output says
`unchanged`; otherwise the new package replaces the old one (`replaced`). If the package has
changed and the fabric that is up was built from it, the command refuses and asks you to run
`ndt down` first, because the running switches still hold the old program.

**Taking it down.**

```bash
tools/test_workflow/ndt down
```

## 5. The forwarding table

NDTwin works out each flow's path by reading the switches' forwarding tables and walking them
over the topology. For your program it needs to know which table that is: the **route role**.

**Filled in for you.** The conversion looks through your p4info for tables shaped like a
destination route: one 32-bit LPM match field, and an action that takes a 48-bit MAC address
and a port. If exactly one (table, action) pair qualifies on every switch that runs your
program, it becomes the route role and the output says so (the `route role` line above).

**`owner package` (the default): the table stays yours.** NDTwin only reads it, to compute flow
paths. Your entries from `sN-runtime.json` are written at bring-up, and your application can
change them (section 7). NDTwin writes nothing into that table: the destination-route writes
that NDTwin's OpenFlow-shaped API (`install_flow_entry` and the related routes) sends to the
proxy are refused for those switches with `501` and the reason `owned_by_package`.

**When it cannot choose:**

- **No table qualifies:** no route role is set, and the output warns that the twin will show no
  flow paths for this fabric unless the forwarding table uses NDTwin's own names
  (`MyIngress.ipv4_lpm` on `hdr.ipv4.dstAddr`, action `MyIngress.ipv4_forward(dstAddr, port)`).
  Naming a table with `--role-ipv4-route` does not relax the shape: pre-flight checks it the
  same way.
- **Several (table, action) pairs qualify:** none is picked. The output prints one ready-made
  `--role-ipv4-route ...` line per candidate; add the one you mean to the `ndt up` command.

**Choosing it yourself.** `--role-ipv4-route` wins over the automatic choice. It names five
things, all required:

```bash
tools/test_workflow/ndt up p4 --app path/to/my-exercise \
    --role-ipv4-route table=MyIngress.ipv4_lpm,match_field=hdr.ipv4.dstAddr,action=MyIngress.ipv4_forward,dst_mac=dstAddr,port=port
```

`dst_mac` and `port` are the names of the action's two parameters. `--no-roles` declares no
route role at all.

**`--table-owner ndtwin`: let NDTwin write the table.** This is for applications written against
NDTwin's OpenFlow-shaped route API (`install_flow_entry` and the others), such as the existing
traffic-engineering and energy-saving apps. NDTwin then owns the route-role table and installs
routes in it. Your `sN-runtime.json` match entries for that table are left out of the package
(the output counts them, per switch); the table's default action stays. Writes to that table
through `/ndt/p4/table_entry` are refused with `409` (`owned by NDTwin`). With `--table-owner
ndtwin`, the conversion refuses if it cannot settle on exactly one (table, action) pair; name
it with `--role-ipv4-route`.

## 6. Who programs the switches, and telemetry

**Control plane.** By default (`--mode auto`), an exercise **without** a `mycontroller.py` is
brought up with NDTwin programming the switches: the proxy holds the P4Runtime connection and
writes your entries. An exercise **with** a `mycontroller.py` is brought up `external`: the
fabric comes up with empty tables for that controller to program, and the proxy only reads, so
writes through `/ndt/p4/table_entry` are refused with `409` (`external control plane`). No
route role is set in that case, because the controller owns every table. The output says which
mode it chose and why. `--mode ndtwin` or `--mode external` overrides it.

Run that controller with the Python your tutorials controllers already run under, not
`p4_proxy/venv`: it must import `grpc` and the tutorials' `utils/p4runtime_lib`, which needs
`p4.tmp`. Run `<that python> tools/p4_exercise/run_external_controller.py <package>
mycontroller.py`, where `<package>` is the path on the conversion's `package` line, and add
`--tutorials-utils <tutorials>/utils` if the exercise is not inside a tutorials checkout. It
moves the controller's tutorials addresses and device ids to the fabric's. Until it runs, the
switches forward nothing.

The controller keeps running until you stop it with Ctrl-C: the tutorials controllers loop,
reading counters. If you pipe or redirect its output, run it as `<that python> -u ...`;
otherwise Python buffers the output, and it shows up late or, if the controller is killed, not
at all.

**Telemetry: nothing to change in your program.** The kernel learns about flows and link usage
from sFlow samples. For a switch running your program, the default (`auto`) is **link
telemetry**: NDTwin samples packets with `tc` on the switch-side links of the fabric, outside the
switch, and turns the samples into sFlow. Your `.p4` is not modified. The bring-up prints the
source it sets (`telemetry    auto`, or the word you gave), and its verify step prints how many
switches use each (`telemetry: auto -- 0 cooperative, 4 link, 0 none`).

To choose a source explicitly, add `--telemetry <word>` to `ndt up p4`:

| word | meaning |
|---|---|
| `auto` | the default: `link` for a switch running your program, `cooperative` for one running NDTwin's own |
| `link` | sampled on the links, as above |
| `cooperative` | the program samples packets itself (Appendix A) |
| `none` | nothing is sampled |

Without `--telemetry`, each bring-up writes the default again, so an earlier choice does not
carry over.

## 7. Write your application against the kernel

Your application talks to **the kernel only**, at `http://localhost:8000`. The P4 proxy's own
port (8081) is for tests, tools and debugging.

**Observe** with the kernel's general API, for example:

- `GET /ndt/get_graph_data`: topology, link state and link usage (API reference §3);
- `GET /ndt/get_detected_flow_data`: the flows seen, with their rates and paths (§4).

**Read and change your own tables** with the P4 routes (§43). The kernel relays them to the
proxy unchanged:

| route | what it does |
|---|---|
| `GET /ndt/p4/table_entry?dpid=<n>&table=<name>` | read every entry of a table on one switch |
| `POST /ndt/p4/table_entry` | insert, modify or delete one entry |
| `GET /ndt/p4/counter/{name}?dpid=<n>&index=<i>` | read an indexed counter |
| `GET /ndt/p4/direct_counter/{name}?dpid=<n>` | read a direct counter |
| `GET /ndt/p4/register/{name}?dpid=<n>[&index=<i> \| &start=<s>&count=<c>]` | read a register |

An example with the tutorials `basic` exercise (solution in place: `cp solution/basic.p4
basic.p4` before `make build`; brought up as in section 4). On `s1`, traffic for `10.0.3.3`
leaves on port 3, towards `s3`. Move it to port 4, towards `s4`.

Read the table first:

```bash
curl -s 'http://localhost:8000/ndt/p4/table_entry?dpid=1&table=MyIngress.ipv4_lpm'
```

Each entry comes back in the shape `POST` takes, without `op`. The one for `10.0.3.3` looks like
this (an example built from `basic`'s `s1-runtime.json`):

```json
{"dpid": 1, "table": "MyIngress.ipv4_lpm",
 "match": {"hdr.ipv4.dstAddr": ["10.0.3.3", 32]},
 "action_name": "MyIngress.ipv4_forward",
 "action_params": {"dstAddr": "08:00:00:00:03:00", "port": 3},
 "priority": null, "default_action": false}
```

Send it back as a modify, with the new port:

```bash
curl -s -X POST http://localhost:8000/ndt/p4/table_entry \
     -H 'Content-Type: application/json' \
     -d '{"dpid": 1, "op": "modify", "table": "MyIngress.ipv4_lpm",
          "match": {"hdr.ipv4.dstAddr": ["10.0.3.3", 32]},
          "action_name": "MyIngress.ipv4_forward",
          "action_params": {"dstAddr": "08:00:00:00:03:00", "port": 4}}'
```

Then read the table again to see the entry as the switch holds it. NDTwin computes flow paths
from this table (it is the route role), so the paths it reports follow the change once it has
read the table again.

To watch it, send traffic fast enough to be sampled (NDTwin samples 1 packet in 256). You need
a `mininet>` prompt, and the line under `up. ready` (section 4) says whether the topology pane
holds one. With NTG as it ships it does not. To get one:

1. Run `tools/test_workflow/ndt ntg`. It shows the mode NTG will start in and the file it reads
   it from. With NTG as it ships, that is `setting/Mininet.yaml` in your NTG checkout, in mode
   `custom_command`: NTG's `NTG.yaml` names `setting/Hardware.yaml`, which has no Mininet
   testbed entry, so the P4 bridge hands NTG `setting/Mininet.yaml` instead. NTG's own files
   are not edited for that.
2. Run `tools/test_workflow/ndt ntg cli`. It changes the `mode:` line in that file to
   `mode: "cli"` and says which file it edited.
3. Take the fabric down with `tools/test_workflow/ndt down` and bring it up again as in
   section 4. The mode is read when the topology starts, and `ndt up p4` on a fabric that is
   still up reuses it.

If step 2 refuses because it cannot read the mode line, fix that line by hand in the file it
names. An older `ndt` could leave `mode: "cli"_command"` there; change that line to
`    mode: "cli"` (the same indentation as the lines around it). An older `ndt` could also leave
`mode: "prompt"`, which NTG does not accept; `tools/test_workflow/ndt ntg cli` replaces it.

Attach with `sudo tmux -L ndtwinlab attach -t topo`. Then run `h1 ping -c 1000 -i 0.01 h3`
(about 100 packets a second for 10 seconds; a plain `ping` is mostly not seen), and read the
flow's `path` in `GET /ndt/get_detected_flow_data?liveness=retained`. This view lags the switch
by several seconds ([timing](2026-01-02_ndt_api.md#closed-loop-timing)).

Do not press Ctrl-C in that pane. It does not only stop the ping: it takes the whole Mininet
fabric down (the proxy and the kernel keep running). `-c` ends the ping by itself. To leave the
pane, detach from tmux (Ctrl-b d with tmux's default keys). If you pressed Ctrl-C there anyway,
run `tools/test_workflow/ndt down`, then bring everything up again as in section 4.

**Whose answer is it.** Every reply on these routes carries the header `X-NDTwin-Origin` (use
`curl -i` to see it).
`proxy` means the status and body are the proxy's, passed through unchanged. `kernel` means the
kernel answered itself; its body has `"origin": "kernel"`, an `error` and a `message` (for
example `502 P4 proxy unreachable`, or `501 not a P4 fabric` when the kernel runs an OVS
topology).

## Appendix A. Cooperative telemetry

Link telemetry (section 6) is the recommended path because it needs nothing from your program.
The other source, `cooperative`, is how NDTwin's own pipeline samples: the program itself clones
1 in 256 packets to the CPU port with a small `packet_in` header, and the proxy turns each copy
into an sFlow sample.

To use it with your own program:

1. Copy `p4_proxy/p4_src/ndtwin_telemetry.p4` into a subdirectory of your exercise, e.g.
   `include/`, and include it as `#include "include/ndtwin_telemetry.p4"`. Not next to your
   program: `make build` compiles every `.p4` at the top of the exercise, and the conversion
   expects your program to be the only one there. The package carries only files inside the
   exercise.
2. Make the edits listed in the comment at the top of that file, writing the `#include` as in
   step 1 (the comment and the fixture write `"ndtwin_telemetry.p4"` because they are compiled
   with `-I p4_proxy/p4_src`): the `#include` after `v1model.p4`, two headers and one metadata
   field, a parser state for packets from the CPU port, one `emit` in the deparser, one `apply`
   call at the end of ingress and one at the start of egress, and the two instantiations they
   call.
   `tools/p4_exercise/tests/fixtures/basic_telemetry/basic_telemetry.p4` is the tutorials
   `basic` solution with exactly these edits, each marked `NDTWIN <n>:`.
3. Rebuild with `make build`.
4. Bring it up with the source named:

   ```bash
   tools/test_workflow/ndt up p4 --app path/to/my-exercise --telemetry cooperative
   ```

If a switch's p4info lacks any of the five `packet_in` fields the proxy reads (`reason`,
`ingress_port`, `egress_port`, `frame_length`, `sampling_rate`), the proxy refuses to start and
names the switch and the missing fields; `ndt` prints the end of the proxy log and takes the
bring-up back down, so a program that would report no samples is never left running.
