# 預註冊的繼承檢查清單 — 起草新一輪之前的必經步驟

[Co-developed with claude code -- Adam]

**地位：現役。** 起草任何新的量測輪預註冊時走這一份。

## 這份存在的理由，一句話

> **不繼承可以，靜默地不繼承不行。**

2026-08-31 的實測：D 輪（`doc/audit/2026-08-25_sampling-rounds/`）13 支**實際執行過**的腳本
拆出 **15 條**儀器條款；六天後起草的兩張預註冊，一張繼承了 **3.5 條**，另一張 **1 條**。
掉的三條裡有「**收工還原生產組態，還原失敗要大聲**」——D 輪六支驅動腳本全都有，
而且 `run_c.sh:46` 的註解記著它**真的發生過**。

🔴 **為什麼沒有人發現**：因為**每一張新註冊自己讀起來都很完整**。缺口不在任何一張檔案「之內」，
它在兩張檔案「之間」。單看一張永遠看不出來。

---

## 步驟

### 第 1 步 — 母體是**上一輪實際執行過的腳本**，不是上一輪的預註冊

拿有輸出檔（`.out`／`.log`）的那些腳本，不是整個目錄。

```bash
cd doc/audit/<上一輪>
for f in *.sh; do b="${f%.sh}"; [[ -f "$b.out" || -f "$b.log" ]] && echo "RAN $f"; done
```

🔴 **為什麼不能拿上一輪的預註冊當母體**：註冊本身就可能已經漏了。
上一輪腳本裡有而它自己的註冊裡沒有的條款，**只存在於腳本**——拿註冊當母體會把它一起丟掉，
而且丟得毫無痕跡。**每一代都這樣做，就是幾何級數的流失。**

🔴 **而且母體必須是「條款」，不是「關鍵詞」。** 關鍵詞掃描只在措辭沒被改寫時有效，
而不同輪的預註冊本來就會換措辭——見下面第 4 步的自陷實例。

### 第 2 步 — 逐條拆出儀器條款，寫成表

一條＝一個**可以單獨紅掉**的檢查或紀錄動作。實務上會落在這幾類：

- **身分**：哪一顆 binary（sha256／`ldd`／`readelf -d` RUNPATH／symbol 簽名／`/proc/<pid>/exe`）
- **環境**：`boot_id`、uptime、claim 與獨占、窗內禁止事項
- **注入落地斷言**：改動有沒有真的改到，**而且要對編譯產物斷言，不只對 source**
- **儀器自檢**：`--selftest` 被呼叫、reader 的已知非空前置檢查
- **判定規則與中止條款**
- **收尾**：還原生產組態、還原失敗要大聲、release 前的檢查
- **不變量**：重啟／換裝前後有沒有東西應該不變

### 第 3 步 — 每一條寫「繼承／不繼承」，**不繼承要寫為什麼不**

| 上一輪條款 | 出處 | 繼承？ | 不繼承的理由 |
|---|---|---|---|

「不適用」是完全正當的理由——**但要寫出來**。
🔑 反例（做對的）：PREREG-B 的缺陷是「裸名 → PATH 查找」，而 E 的 kernel 由
`stack.sh:766` 以 `./bin/ndtwin_kernel` ＝**相對路徑** exec ⇒ 該變體不會發生，
所以 E **刻意不整包搬**，只留三條真正殘留的窄路徑。
**把別人的失效模式整包搬過來看起來像謹慎，實際上是把註冊灌水——而假警告會稀釋真警告。**

### 第 4 步 — 🔴 **兩欄分開記：「腳本裡有」與「註冊裡有」是兩回事**

| 條款 | 上一輪腳本 | 新輪**註冊** | 新輪腳本 |
|---|---|---|---|

2026-08-31 的數字：**E 腳本欄 10 個 ✅，註冊欄 4.5 個。**
**差額就是下一個人拿不到的東西。**

為什麼註冊欄才算數：

- 腳本會被改寫、被複製、被另一支取代；註冊不會。
- D 輪的 `gate_d.sh` **只呼叫了預註冊寫的三項中的兩項**，那是 grep 抓出來的
  ——而它之所以**能**被 grep 抓，正因為那三項**寫在預註冊裡**。
  沒寫進註冊的條款，沒有任何東西可以拿來對照。
- 現成的例子：F-5 偵測器的 control 早就在 TR-3 harness 裡，但**未註冊的 control
  可以被下一版腳本刪掉而不留痕跡**。

### 第 5 步 — 新加的條款自己要見過紅

補進註冊的每一條都要有 force-red，**而且「必須大聲」這種條款要連 force-green 一起**
（否則一個永遠紅的檢查也會「通過」force-red）。

🔴 **最容易空洞通過的兩種寫法**：

1. **哨兵值**：用 `UNREADABLE`／`N/A`／`""` 表示讀不到，然後拿它做相等比較
   ⇒ **兩個哨兵彼此相等** ⇒ 完全沒有資料與資料完全一致產生同一個結論。
   比較前先斷言值**長得像一個答案**。
2. **看 exit code**：**`exit 0` 表示「跑完了」，不表示「答案是對的」**——
   而「檢查根本沒跑到」也會 exit 0。判準要看**輸出的 verdict 字串**。

（完整說明：`doc/KNOWN-ISSUES.md` 的「哨兵值會製造空洞的通過」。）

### 🔴 第 5b 步 — **加完 force-red 之後，回頭把接受路徑整條重跑一次**

> **force 的注入本身會改變接受路徑的可達性，而那個改變是靜默的。**

這一步最容易被跳過，因為 **force 紅了會給人「驗完了」的感覺**——紅的那一半確實驗完了，
而綠的那一半剛剛被你動過。2026-08-31 一天之內踩到兩次，**兩次都在寫這條規則的同一份檔案裡**：

| 注入 | 它靜默地做了什麼 |
|---|---|
| 合成的 binary hash 給了一個**常數** | 兩臂中不匹配的那一臂，**接受路徑根本走不到**——梯子在自己第一格就中止。force-red 好好的，正常跑反而壞了 |
| 強制的漂移套在**第一次**讀數上 | 那個值**直接變成基線** ⇒ 永遠沒有東西不同 ⇒ **force 靜靜地什麼都沒測**，而它回報 PASS |

第二個尤其惡毒：它**兩邊都看起來對**——接受路徑綠、force 也「紅」了（其實是根本沒比較）。

**可貼的檢查步驟**：

```bash
# 1. 接受路徑：完整跑一次，必須跑到結尾
DRY_RUN=1 ./<driver> <mode>            # 期望：跑到 "complete"，不是中途 ABORT
# 2. 每一個 force：各跑一次，必須紅
for f in <fail1> <fail2> ...; do DRY_RUN=1 DRY_FAIL=$f ./<driver> <mode>; done
# 3. 🔴 回到 1，再跑一次 —— 因為 2 可能改了 1 的可達性
DRY_RUN=1 ./<driver> <mode>
```

**兩個具體的反面樣式，直接拿去比對自己的 fixture**：

- 合成值是**常數** ⇒ 問「這個常數對**每一個**臂／每一種組態都成立嗎？」
  不成立的話，接受路徑對其中一種永遠走不到。合成值要**跟著被測的狀態走**。
- 注入套在**第一次**讀數 ⇒ 問「第一次讀數是不是拿來當基線的？」
  是的話，注入的值會變成基線，之後什麼都不會不同。**基線型的檢查，注入要套在第二次之後**
  ——而那也才是該失效的真實形狀（漂移，不是一開始就錯）。

🔑 判準一句話：**一個只能產生一種 verdict 的 fixture，就是它自己要抓的那個缺陷。**

🔴 **而且修法自己要被當成有嫌疑的檢查對待。** 2026-08-31：修「fixture 沒有鑑別力」的那段碼，
**第一版錯得跟它要修的東西一模一樣**（用讀取次數當觸發，而不同呼叫端的讀取次數不同
⇒ 在其中一輪靜靜地沒觸發，回報得跟成功一樣）。
⇒ 寫完立刻跑一次，**看它真的變紅，不要看它「應該會變紅」**——
「更早的檢查先中止」與「門檻與呼叫次數耦合」在原始碼裡都長得完全正常，**讀碼讀不出來**。

### 🔴 第 5f 步 — **不是每個 force 都該在每條路徑上紅**

一張**全紅**的 force 表看起來比較完整，**而那正是它危險的地方**：它會誘使人把不該紅的地方
弄紅，**而弄紅的方法通常是讓斷言變弱**。

2026-08-31 的實例：`DRY_FAIL=restore` 在 F-5 的 `arm` 路徑回報 **0 次中止**，而那是**正確的**
——`arm()` 根本不呼叫 `assert_kernel_restored`。正確處置是**去它實際存在的地方驗**
（`selftest` 與 `restore` 兩條路徑各紅一次），**不是**在 `arm()` 裡插一個呼叫讓表變好看。

**判準（四步，第零步先做）**：

| # | 問題 | 若是 |
|---|---|---|
| **0** | 🔴 **這個 force 有沒有呼叫端？**（`grep -rn '<force 名>'`） | **零呼叫端** ⇒ 連「抵達與否」都還沒進入討論。**修法存在 ≠ 修法被執行。** |
| 1 | 這條路徑**有呼叫**那個斷言嗎？ | 沒有 ⇒ **不紅是正確的**，去有呼叫的路徑驗，並記錄「此路徑不適用」 |
| 2 | 有呼叫，但值被**吸收**了嗎？ | 是 ⇒ **fixture 缺陷**（見 5b） |
| 3 | 有呼叫，但**更早的檢查先中止**了嗎？ | 是 ⇒ 這條 force **從未抵達**該斷言 |

🔑 **第零步的價值在於它是純靜態的、`grep` 就查得到。** 第 3 步（更早的中止）**讀碼讀不出來**
——但它有一個**讀碼讀得出來的近親**，就是第零步。
2026-08-31 的實例：`exedriftmid` fixture 寫好了，卻在 `gates_e.sh` **零呼叫端**，
而閘門仍印著 `all reachable`（那是另一個函式的三個 verdict，不是括號的）。
**同一個缺陷第二次發生在同一個腳本家族，而這次發生在「修它的那個補丁」身上。**

🔴 **相關：驗收要寫在可執行的前置條件上，不要寫在修訂記錄裡。**
「證據基礎是否完整」若只是文件裡的一段話，下一個人不會讀到它就開跑
⇒ 做成**欄位＋preflight 讀它**，不完整就拒絕開跑（本輪的 `EVIDENCE-BASIS:` 欄）。

🔑 **零命中要回報「我查了哪些、為什麼這幾條不適用」**，不是回報「沒有問題」——
同一天已有兩次「零命中被誤讀成沒有」。

### 🔴 第 5e 步 — **grep 給的是候選，不是目標**

撤回或更正一個**用詞**時，命中清單要**逐條判定「它講的是不是同一個宣稱」**，判完才動手。
這是「撤回前先清點所有引用點」的**另一半**：**清點 ≠ 全部替換。**

2026-08-31 的實例：一個界限方向寫反要更正，`grep 下界|lower bound` 命中**五處**，
**其中兩處是對的**——`run_e.sh:72` 與 `COST-TABLE.md:24` 講的是**牆鐘時間**在暖機 fabric 上
量到的是下界，**那是另一個宣稱，而且方向正確**。
**整批取代會在修掉一個錯的同時製造一個新的錯**，而新的那個沒有人在找。

**做法**：對每一個命中，先回答「這裡的**主詞**是什麼」——

| 命中處的主詞 | 判定 |
|---|---|
| 與被更正者**同一個量** | 改 |
| **不同的量**，只是用了同一個詞 | **不動**，並在更正記錄裡寫明「已判定不屬於本次更正」 |
| 看不出主詞 | 當成要改的來讀原文，**不確定不能靠猜過關** |

🔑 同一族的還有第 5c／5d 步，共同的形狀是：**不要為了形式一致而動內容。**
一個詞在兩個地方出現，不代表它在兩個地方指同一件事——
而「全部改成一致」看起來像徹底，實際上是把一個正確的陳述改錯。

### 🔴 第 5d 步 — **凡是宣告界限方向的地方，把「靠它的每一條規則」重推一次**

> **一個界限的方向寫反，而下游規則仍然全部保守——這件事是被「檢查」出來的，不是自動成立的。
> 一條規則在某個方向下保守，在相反方向下可以是反保守。**

2026-08-31 的實例：一個執行期觀測寫成「趟數的**下界**」，實際是**上界**（每趟**至少**貢獻一次
讓出，mutex 讓出再往上加 ⇒ S ≥ P）。方向錯了，而靠它的三條判準**碰巧**仍然全部保守
——重推之後才知道，不是寫的時候就知道。

**做法**：對每一條依賴該界限的規則，代入**正確方向**問「失效方向是誤中止還是誤放行」：

| 規則型態 | 要問的 |
|---|---|
| 門檻式（`X ≤ k` ⇒ 中止） | 界限方向讓 X 高估還是低估？高估 ⇒ 這條更嚴；低估 ⇒ **可能漏放** |
| 比值式（`A/B ≥ k`） | 雜訊是**加性**還是**乘性**？加性且兩邊都有 ⇒ 比值被**往 1 拉** ⇒ 觀測值**低估**真值 ⇒ 門檻偏嚴 |
| 絕對頻帶（`lo ≤ X ≤ hi`） | 高估會把健康的樣本推出上界 ⇒ **誤中止**（可接受）；低估會把壞樣本拉進帶內 ⇒ **誤放行**（不可接受） |

🔴 **推導要寫進文件，不是只寫結論。** 「這些判準是保守的」是一個宣稱；
**下一個人要能自己驗，而不是相信我們說它保守**——尤其當方向本身剛被改過。

🔑 **為什麼這條值得單獨列**：方向陳述是**承重的**。同一天內，宿主負載的歸因、
圖表不對稱的解讀、儀器界限的宣稱**都靠方向論證**——寫反一個，下一個人會推出**相反**的保守性，
而且推得完全正確。

### 🔴 第 5c 步 — **抄進註冊的每一個識別值，自己重算一次**

上游給你的表可能只給**截斷過的**值（前 16 碼的 sha、7 碼的 blob）。把它填進一個要求完整值的
欄位時，**缺的那一段只能重算，不能補**。

2026-08-31 的實例：auditor 的表給 `sha256(前 16)`，我要填的是腳本裡的完整 64 碼欄位，
於是我**把後 48 碼編出來**——前 16 碼是真的，尾巴是假的。它通過了所有語法檢查、
`bash -n`、以及肉眼（開頭對得上）。**只有拿 `git cat-file blob … | sha256sum` 重算才會現形。**

- **為什麼特別危險**：這種假值**在正確的一半上是對的**，所以任何「掃一眼開頭」的複查都會放行；
  而它的效果是讓 G0 **永遠紅**（或更糟，若假值恰好被當成期望值而真值被改動，則永遠綠）。
- **規矩**：`git cat-file blob audit-raw:<path> | sha256sum` ——**每一個**識別值，抄完立刻重算，
  並把「已重算」寫進修訂記錄。上游的表是**線索**，不是**來源**。
- 🔴 **更硬的一條：永遠不要把一個識別值「補到」它宣告的長度。**
  欄位要 64 碼而來源只有 16 碼時，**正確動作只有兩個**：
  ①**回去取完整值**（`git cat-file blob … | sha256sum`），或②**把欄位改成 16 碼**並註明是截斷值。
  **把它填滿這個動作本身就是造假**——而它在當下感覺起來像「格式整理」，不像造假，
  這正是它會發生的原因。
- 📌 **給值的一方也有責任**：交遞識別值時**一律給完整值，或給取值指令**。
  給截斷值而對方要填完整欄位，等於把造假的機會遞過去。
- 同族：[[verify-against-known-good-output]] 的「禁止湊表」；差別在那條講的是**遷就派工單的規格**，
  這條講的是**遷就欄位的長度**。

### 第 6 步 — 修訂照三條件記錄

改了什麼／為什麼／誰在什麼時候。並確認四條件：**資料接觸前**／理由是外部發現的缺口
而非結果不好看／**只增不減**（放寬判準是另一回事，要另外論證）／記錄在修訂欄。

## 這份自己踩過的坑（留著，因為它是第 1 步「母體是條款不是關鍵詞」的實例）

2026-08-31 首次執行這份流程時，我用**關鍵字**掃兩張預註冊，得出「E 有註冊收工還原、
有註冊 fabric 完整性；F-5 有註冊已知非空前置檢查」。逐行複查後**三個都是假陽性**：

| 以為命中 | 實際命中的字 |
|---|---|
| production restore | 「**還原** patch」（TBD-1 的用詞，與收尾無關） |
| fabric 完整性 | 「**十台**必須同一顆」（我自己當天早上才加的 bmv2 條款） |
| known-non-empty | 「任一臂**非零**」（併池規則） |

🔴 **三個假陽性全部朝同一個方向——把新輪說得比實際完整。**
如果沒有逐行複查，這份稽核會產出一張讓人放心的表，而它要找的正是「讓人放心但其實有洞」。

⇒ **操作規矩：稽核的母體必須是條款，不是關鍵詞；每一個命中都要看它實際命中的那一行。**

## 🔴 起草／清點前的最後一步：**先寫下你預期會看到什麼**（auditor 2026-08-31 立）

> **即使是例行的清點，也要先寫下預期再去看。**
> 相符 ⇒ 幾乎沒有新資訊；**不符 ⇒ 那裡就是帳錯的地方**。
> **沒有預測的清點，只能確認你已經相信的事。**

這條之所以放進**繼承清單**而不只是量測紀律：繼承的動作**天生就是「照抄上一輪」**，
而照抄的產物**永遠看起來合理**——它跟上一輪長得一樣，這正是它的目的。
⇒ **繼承是「合理」最容易吃掉資訊的地方。**

**08-31 的實例**（`NSLAB-USAGE-RULES` R12／H-19）：盤點一顆快照時預期
「應該少掉某五個 repo」。少 5 那半對了；**另一半錯了，而錯的那半挖出一筆記錯半小時的帳。**
🔑 **資訊在被否證的那一半。** 若沒先寫下預測，那個數字只會被讀成「比較少，合理」。

**怎麼做（要便宜到沒有藉口不做）**：在派工單／註冊草稿旁邊寫**一行**：

```
預期：繼承 N 條，其中 X 條應該因為 <理由> 不適用 ⇒ 實際落地 N-X
```

對不上的時候**不要先改預期**——先問「是我對上一輪的理解錯了，還是這一輪真的不同」。
（同 [prereg-amendment-before-data](../doc/2026-08-31_prereg-inheritance-checklist.md)
的三條件：看到門檻擋住自己才改，是最糟的改法。）

⚠️ **配套**：拿任何時戳／計數去推翻既有紀錄前**要有對照組**——同法讀一個**已知答案**的目標，
證明你的儀器讀得對。**沒有它，你的新數字只是另一個要人相信的東西。**
