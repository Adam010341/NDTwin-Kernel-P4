# NDT RESTful API Documentation
## 1. POST /ndt/link_failure_detected
### Description
Called by Ryu when a link-down event is detected. Marks the edge(s) DOWN and emits internal events.

> 🔧 **B-6 — fixed ON A BRANCH, not on `trunk`.** The fix lives in
> `fix/w8-declared-link-failure-sticky` and has NOT been merged. 🔴 **If the kernel you are calling
> was built from `trunk`, everything in the "what it used to do" box below still applies to it.**
> Ask which ref your binary came from before you rely on either behaviour.
>
> **What it now does.** A failure declared through this endpoint is **sticky**: the topology poll
> may no longer lift the edge, and the edge reports `down_reason: "declared"` in
> `/ndt/get_graph_data` for as long as the declaration stands.
>
> 🔴 **The declaration is PERMANENT until you withdraw it** with `/ndt/link_recovery_detected`
> (or `/ndt/inject_link_recovery`, §2c). It survives Ryu reconverging and a switch restart, by
> design. **This is the new failure mode and it is the mirror of the old one**: B-6 used to be an
> injection that ended early and silently; a forgotten injection now never ends. The reason
> `down_reason` is on the wire rather than an internal flag is precisely so that a forgotten one
> can be found — sweep `/ndt/get_graph_data` for `down_reason == "declared"`.
>
> 🆕 **Calling THIS endpoint also buys exactly one withdrawal** (branch
> `fix/w8b-withdrawal-needs-observed-failure`). A `/ndt/link_recovery_detected` for this link
> withdraws the declaration only because this endpoint reported the link broken first; the report
> is spent by that one recovery. An injection made through §2b reports nothing, so **no**
> `link_recovery_detected` can withdraw it — see §2 for why that rule exists and what it measured.
>
> 🆕 **`src_dpid` and `dst_dpid` must both be non-zero: dpid 0 is refused with 400.** A host vertex
> carries dpid 0, and the edge lookup matches on the two dpids alone, so `{"dst_dpid": 0}` used to
> resolve to whichever host edge of the other switch came first in the graph — a link the caller
> never named, on an edge the host poll raises again anyway. Host edges are not addressed by this
> endpoint family. (Ryu never sends this: `EventLinkAdd`/`EventLinkDelete` are switch-to-switch.)
>
> **Still assert the injection from `/ndt/get_graph_data`, in BOTH directions** — that it holds
> for the whole measurement window, and that it is gone afterwards. The `200` was never the
> evidence and still is not.
>
> **What it used to do (`trunk`, and every kernel built before this branch).** The call set the
> edge's `isUp` to `false`; the next topology poll set it back to `true` — with
> `/ndt/link_recovery_detected` never called and no line in the kernel log. A background thread
> polls Ryu's `/v1.0/topology/links` (5 s for the first 90 s after start, 30 s thereafter) and set
> `isUp = true` unconditionally for every link Ryu still reported. That is safe against a *real*
> failure and only against a real one: Ryu stops listing a severed link, so the poll has nothing
> to restore, while a link that was merely *declared* down is still listed and was resurrected.
>
> **Measured 2026-09-04.** 5 of 5 trials reverted on their own with no recovery call; the three
> reverts timed against `ryu.log` each landed ≈0.6 s after a poll. ⇒ the visible lifetime of a
> declared link failure was uniform on 0–30 s, upper bound 30 s. An earlier round's 0.457 s /
> 9.454 s / 18.453 s are the same 30 s poll struck at three different phases, not three different
> behaviours. **A link that was actually severed was unaffected** — with `tc netem loss 100%` on
> both ends, DOWN 13.3 s after the netem went on, still DOWN at 60 s, back UP 1.0 s after it came
> off. That control is what localised the defect.

### Request
* Method: **POST**
* Content-Type: **application/json**
* Body (the information of failed link)
```json
{
  "src_dpid": 106225808402492,
  "src_interface": 23,
  "dst_dpid": 106225808387660,
  "dst_interface": 23
}
```
### Response
#### Success
* Status: **200 OK**
```json
{
  "status": "link failure processed",
  "down_reason": "declared",
  "until": "/ndt/link_recovery_detected"
}
```
The two extra keys are additive and were added with B-6's fix: they say how long the declaration
lasts, which is the thing that changed. A kernel built from `trunk` answers `{"status": "link
failure processed"}` alone.
#### Error
* Status: **400 Bad Request**
```json
{
  "error": "Invalid link-failure payload"
}
```
Returned when the request body is not valid JSON, or JSON fields have invalid types/format.
* Status: **400 Bad Request**
```json
{
  "error": "JSON parsing error",
  "details": "<exception message>"
}
```
* Status: **400 Bad Request** 🆕 branch `fix/w8b-withdrawal-needs-observed-failure`
```json
{
  "error": "src_dpid and dst_dpid must both name a switch: dpid 0 is the host end of a host edge, and a host edge is not addressed by this endpoint -- it would resolve to whichever host edge of the other switch comes first in the graph"
}
```
Returned when either dpid is `0`. All four link endpoints (§1, §2, §2b, §2c) answer this.
* Status: **404 Not Found**
```json
{
  "error": "edge not found in topology"
}
```
Returned when an unexpected runtime error occurs (e.g., invalid state, missing dependency, system failure).
* Status: **500 Internal Server Error**
```json
{
  "error": "Internal server error",
  "details": "<exception message>"
}
```
Returned when an unknown exception type is thrown.
* Status: **500 Internal Server Error**
```json
{
  "error": "An unknown error occurred"
}
```


## 2. POST /ndt/link_recovery_detected
### Description
Called by Ryu when a failed link becomes UP. Marks the edge(s) UP.

> 🔧 **It withdraws a declared failure — but only one it can PAIR with.** Branch
> `fix/w8b-withdrawal-needs-observed-failure` (which builds on `fix/w8-declared-link-failure-sticky`),
> not on `trunk`.
>
> It does two things, and they are separate: it **withdraws the declaration**, so a topology poll
> may raise this edge again, and it **marks the edge up**, because a caller saying "it recovered"
> is itself evidence and the next poll may be 30 s away. Calling it for a link that is *not*
> actually back therefore still publishes an UP that nothing corrects on its own — the poll only
> ever raises links, so an over-optimistic recovery is not self-healing. Re-read
> `/ndt/get_graph_data` rather than trusting the `200`.
>
> 🆕 🔴 **THE PAIRING RULE.** A recovery report withdraws a declaration **only if
> `/ndt/link_failure_detected` reported this link broken first**, and that report is spent by the
> one recovery that answers it. Three cases:
>
> | what is standing on the edge | what this endpoint does |
> | --- | --- |
> | a failure this endpoint's sibling (§1) reported | withdraws the declaration, marks the edge up, `200 {"status":"link recovery processed"}` |
> | nothing at all | marks the edge up, same `200` |
> | a declaration §2b injected, or one whose report is already spent | **withdraws nothing and leaves the edge DOWN**, `200` with `"declaration_retained": true` |
>
> **Why.** Measured on the live OVS fabric, 2026-09-07 00:08 (arm `lw8b`): kill Ryu, restart it
> with the same argv, and within **one second** the kernel logs a `POST /ndt/link_recovery_detected`
> for **every** link — Ryu's topology module raises `EventLinkAdd` when LLDP *first discovers* a
> link, so a controller restart is indistinguishable from a fabric-wide recovery. Under the old
> unconditional withdrawal the standing declaration was gone in **9 of 9** samples over the next
> 90 s. For an injection made through §2b that is the worse half: the declaration goes and the
> `tc netem loss 100%` stays, so the graph publishes a link that is up and carries no packets.
>
> 🔴 **A retained declaration is withdrawn only by `/ndt/inject_link_recovery` (§2c)**, which is
> what the `declaration_retained` reply points you at.
>
> ⚠️ **Read the body, not the status line.** This endpoint answers `200` even when it declined,
> deliberately: Ryu's `on_link_add` logs *"NDT REJECTED this notification … the kernel's view is
> now stale"* on any 4xx, which would be false here and would fire once per link on every
> controller restart. The honest signal is `declaration_retained` in the body.
>
> 🆕 **dpid 0 is refused with 400**, as in §1.
>
> ⚠️ **On `trunk` this endpoint is not needed to end an injection, because the poll ends it for
> you within 30 s — which is B-6 (§1).**

### Request
* Method: **POST**
* Content-Type: **application/json**
* Body (the information of recovered link)
```json
{
  "src_dpid": 106225808402492,
  "src_interface": 23,
  "dst_dpid": 106225808387660,
  "dst_interface": 23
}
```
### Response
#### Success
* Status: **200 OK**
```json
{
  "status": "link recovery processed"
}
```
#### Success, but nothing was withdrawn 🆕 branch `fix/w8b-withdrawal-needs-observed-failure`
* Status: **200 OK**
```json
{
  "status": "link recovery processed",
  "declaration_retained": true,
  "detail": "a link failure is declared for this link and nothing ever reported it broken, so this recovery report did not withdraw it and the link is still down. That is what an injected failure surviving a control-plane restart looks like. Withdraw it with POST /ndt/inject_link_recovery",
  "until": "/ndt/inject_link_recovery"
}
```
🔴 **The link is still `is_up: false, down_reason: "declared"` after this reply.** `declaration_-
retained` is present only in this case; a kernel built from `trunk` or from
`fix/w8-declared-link-failure-sticky` never emits it, and never declines.

```json
{
  "error": "Missing src_dpid or dst_dpid or src_interface or dst_interface"
}
```
Returned when the request body is not valid JSON, or JSON fields have invalid types/format.

## 2b. POST /ndt/inject_link_failure
### Description
**Declare a link failed AND make it true on the wire, where the twin can.** Added with B-6's fix;
branch `fix/w8-declared-link-failure-sticky`, **not on `trunk`** — a kernel built from `trunk`
answers `404` to this path.

The difference from §1 is who is speaking. `/ndt/link_failure_detected` is a **notification**: Ryu
saw a link go down and is telling the twin. This is an **injection**: the caller wants the link to
BE down. Same body, and it does everything §1 does; on a **MININET** deployment it additionally
attaches `netem loss 100%` to the interfaces at **both** ends.

🆕 🔴 **That difference now has teeth, and it is the reason to prefer this endpoint for fault
injection.** §1 records that the control plane *reported* a break, which buys one
`/ndt/link_recovery_detected` withdrawal. This endpoint records **no** report, so **no
`link_recovery_detected` can end this injection** — including the burst of them Ryu emits for every
link within a second of being restarted (measured, arm `lw8b` 2026-09-07; see §2). Only
`/ndt/inject_link_recovery` (§2c) ends it. Branch
`fix/w8b-withdrawal-needs-observed-failure`.

🆕 **dpid 0 is refused with 400**, as in §1 — and here it matters twice over: this endpoint runs
`tc`, so a dpid-0 payload would have attached netem to whichever host-facing interface the
arbitrarily-chosen edge named.

🆕 **Residue outlives the kernel, and the kernel now says so at startup.** A declaration lives in
the kernel process and is deliberately never restored from a file; the netem lives in the machine's
qdisc tree. So a restarted kernel reports a clean `down_reason` over a link that is still cut. On a
MININET deployment the kernel therefore sweeps `tc qdisc show` for both ends of every
switch-to-switch link once at startup and writes **one WARN naming the interfaces** that already
carry netem. It does **not** clear them (`tools/test_workflow/faults.sh` is entitled to have netem
on an interface) and does **not** declare the link down. Grep the kernel log for
`netem is already attached`.

🔴 **On any deployment that is not MININET the tc half is skipped and the reply says so**
(`"tc": "skipped (not MININET)"`). There is no way for the twin to cut a physical cable, and a
reply that did not say so would let a caller believe the packets had stopped. The physical testbed
gets the declaration and nothing else.

**How the cut is made, and why it is not `tc qdisc add dev X root netem`.** On a Mininet TCLink
interface the root qdisc is `htb`, and attaching netem at `root` **replaces** it — the bandwidth
shaping the experiment depends on is silently gone, and `tc qdisc del dev X root` then restores the
kernel default rather than `htb`. That cost the 2026-08-13 overnight OVS round. The kernel reads
the live qdisc tree and attaches **under** the shaper (`parent <handle><default>`) when the
interface is shaped, at `root` only when it is not, and **refuses** when a netem is already there
(stacking would make the restore ambiguous). Same rule as `tools/test_workflow/faults.sh`.

The tc half needs these NOPASSWD grants, which this machine has:
`tc qdisc {add,del} dev s[0-9]*-eth[0-9]* {root,parent *} netem *` and `tc qdisc show dev ...`.
Interface names are derived as `<bridge_name>-eth<port>` from the topology file and must match
`s<N>-eth<M>`, or the twin refuses rather than running tc against something it cannot have meant.

### Request
Identical to §1.
```json
{ "src_dpid": 1, "src_interface": 1, "dst_dpid": 5, "dst_interface": 1 }
```
### Response
#### Success — MININET
* Status: **200 OK**
```json
{
  "status": "link failure injected",
  "down_reason": "declared",
  "until": "/ndt/inject_link_recovery",
  "tc": [
    { "interface": "s1-eth1", "ok": true, "attached_at": "parent 5:0x1",
      "command": "qdisc add dev s1-eth1 parent 5:0x1 netem loss 100%",
      "qdisc_before": "...", "qdisc_after": "..." },
    { "interface": "s5-eth1", "ok": true, "attached_at": "root", "command": "...",
      "qdisc_before": "...", "qdisc_after": "..." }
  ]
}
```
🔴 **`tc[].ok` is per interface and a `false` there does NOT make the request fail.** The
declaration succeeded; the cut may not have. An entry carries `refused` (the twin declined — netem
already present, unreadable tree, a name outside `s<N>-eth<M>`, no `bridge_name` in the topology)
or `error` (tc itself failed, usually `sudo -n` being denied). **Read the array. A `200` here means
the twin's graph changed, not that packets stopped.**

#### Success — not MININET
```json
{ "status": "link failure injected", "down_reason": "declared",
  "until": "/ndt/inject_link_recovery", "tc": "skipped (not MININET)" }
```
#### Error
* **400** `{"error":"Invalid link-failure payload"}`
* **400** 🆕 either dpid is `0`; body as in §1.
* **404** `{"error":"edge not found in topology"}`
* **500** `{"error":"reverse edge missing from the topology; nothing was injected"}` — unlike §1,
  this endpoint refuses **before changing anything**: a half-applied injection would leave the
  graph and the machine's qdisc tree in a state the caller did not ask for and cannot name.

## 2c. POST /ndt/inject_link_recovery
### Description
The inverse of §2b: withdraws the declaration, marks both directions up, and removes the netem.
Branch-only, as above.

🆕 🔴 **This is the UNCONDITIONAL withdrawal, and since branch
`fix/w8b-withdrawal-needs-observed-failure` it is the only one.** It answers to nobody: an operator
who injected a failure may take it back whether or not the control plane ever agreed the link was
broken. §2 declines exactly the declarations this endpoint exists to end, and its
`declaration_retained` reply names this path.

🆕 **dpid 0 is refused with 400**, as in §1. The ruling named the failure endpoints; this one is
refused with them because a payload this endpoint accepted and §2b refused would be a link nobody
could have injected — and this endpoint would still run `tc qdisc del` against the interface it
resolved to.

**Idempotent on the tc half.** Removing a netem that is not there reports `"noop"` with
`"ok": true` — a caller must be able to bring a fabric back to health without first knowing
exactly what was done to it. The attach point is re-read from the **live** qdisc tree rather than
remembered, so this still works after the kernel process has been restarted; the tree is the state,
not the kernel's memory. If a netem is still present after the delete, the entry reports `error`
rather than success: a restore that leaves the fault in place is how the *next* round's numbers
become about a network nobody described.

### Request
Identical to §2b.
### Response
* **200** `{"status":"link recovery injected","tc":[ ... ]}` (or `"tc": "skipped (not MININET)"`)
* **400 / 404 / 500** as in §2b, including 🆕 the dpid-0 refusal.

## 3. GET /ndt/get_graph_data
### Description
Returns the complete graph topology configured in the file passed to `--topology` (e.g. *setting/StaticNetworkTopologyP4_10Switches_4Hosts.json* for P4, *setting/StaticNetworkTopologyMininet_10Switches.json* for OVS) including nodes and edges, flow information, and edge status.
**vertex_type = 0** means a switch, and **vertex_type = 1** means a host.
**admin_state** / **reachable** / **is_up** — a node carries all three, and the first two are
the two questions the third used to answer at once.

| Field | Type | Written by | Meaning |
| ----- | ---- | ---------- | ------- |
| `admin_state` | `"on"` / `"off"` | the power strategies **only** — `P4PowerStrategy`, `OVSPowerStrategy`, and the TESTBED smart-plug path — on the path where the actuation was confirmed. Topology discovery and liveness probing may never write it | What the twin was **commanded**. `"off"` means a power-off was issued for this device and has not been withdrawn |
| `reachable` | `bool` | liveness probing **only** (the 1 Hz ping worker), plus topology discovery for a device with no standing power-off | Whether the twin can **reach** it now (see [is_up in P4 mode](#is_up-in-p4-mode) below) |
| `is_up` | `bool` | — | 🔴 **DEPRECATED alias of `reachable`.** Always equal to it, never to `admin_state`. **New readers must use `reachable`** |

**Why `is_up` is still there.** Four consumers read it by name — Energy-Saving-App,
Network-Traffic-Visualizer, Web-GUI, Traffic-Engineering-App — and the Energy-Saving-App parses
it with `j.at("is_up")`, which *throws* on a missing key. Removing it is a hard parse failure in
another repository, not a deprecation. It will be removed only once those four have moved to
`reachable`; until then it is emitted on every node and tracks `reachable` exactly.

**The four states, and why the split exists.** One boolean could not express the last two rows:

| `admin_state` | `reachable` | What it means |
| ------------- | ----------- | ------------- |
| `"on"`  | `true`  | Healthy. |
| `"off"` | `false` | The twin powered it off and it is indeed gone. |
| **`"on"`**  | **`false`** | **It died, and nobody asked it to.** A real fault — this is the state the contract suite's A-8 check looks for, and before the split it was indistinguishable from the row above. |
| `"off"` | `true`  | Commanded off, but answering: somebody restarted it out of band. The twin reports the disagreement instead of picking one. |

🔴 **Changed on 2026-09-04.** Before that date a node carried only `is_up`, and it meant both
things at once. Rationale and measurements:
`doc/audit/2026-09-03_fix-is-up-split/FIX-IS-UP-SPLIT.md`.

Hosts carry the two fields too, because the serialiser is shared, but nothing powers a host
through this API: a host's `admin_state` is always `"on"`.

🔴 **Edges are not split and keep `is_up` alone.** There is no such thing as commanding a *link*
off, so an edge has no `admin_state` and no `reachable`; its `is_up` is unchanged in both meaning
and name. An edge incident to a switch whose `admin_state` is `"off"` goes down for that reason,
which is what the contract suite's edge check accounts for.

**is_enabled** – a *folded* value in the JSON: `isEnabled && !adminDisabled`.
The underlying vertex carries four independent flags (an edge carries the first three):

| Flag            | Written by                                          | Meaning                                         |
| --------------- | --------------------------------------------------- | ----------------------------------------------- |
| `isUp`          | Liveness probing (ping worker or P4 proxy poll)     | Powered / reachable. Serialised as `reachable`, and as the `is_up` alias. |
| `isEnabled`     | Topology discovery (`updateSwitches`/`updateLinks`/`updateHosts`) | The control plane can drive this device.        |
| `adminDisabled` | Intent Translator’s `DisableSwitch`/`EnableSwitch`  | Operator asked for this to be out of service.   |
| `adminPoweredOff` | The power strategies, on a confirmed actuation    | A power-off was commanded and carried out. **Vertices only.** Serialised as `admin_state`. |

🔴 `adminDisabled` and `adminPoweredOff` are **different flags with different writers**:
`admin_disabled` is the Intent Translator taking a switch out of service, `admin_state` is the
power API switching it off. A switch the Energy-Saving-App powered down has
`admin_disabled: false` and `admin_state: "off"`.

[Co-developed with claude code -- Adam]


`adminDisabled` is declared on `VertexProperties` in `include/common_types/GraphTypes.hpp`,
with the reasoning in its own doc comment, and folded into the JSON `is_enabled` by the
`VertexProperties` `to_json` in the same header:
`{"is_enabled", v.isEnabled && !v.adminDisabled}`.
The same folding is applied explicitly for edges in
`HttpSession::handleGetGraphData` (`src/ndt_core/http/HttpSession.cpp`):
`{"is_enabled", e.isEnabled && !e.adminDisabled}`.

**Why folded.** The four consumers that read `is_enabled` — Energy-Saving-App,
Network-Traffic-Visualizer, Web-GUI, Traffic-Engineering-App — already treat it as “usable”:
the Energy-Saving simulator’s own walk is `if (!isUp || !isEnabled) continue;`.
Folding `adminDisabled` into `is_enabled` means an operator’s disable takes effect for all
of them with no change on their side.

**Invariant.** Nothing may carry both `admin_disabled: true` and `is_enabled: true`.
A client that only reads `is_enabled` still behaves correctly; `admin_disabled` is there
for a client that needs to tell “operator turned it off” apart from “control plane cannot
reach it.”

**Current default.** The kernel runs with `--no-ai`, so the Intent Translator path that sets
`adminDisabled` is unreachable. In a default run the field is always `false`.
The invariant above is checkable regardless.

### `is_up` in OVS vs. P4 mode

**OVS mode (Ryu).** `is_up` means the switch appears in Ryu’s `/v1.0/topology/switches` poll,
a host appears in `/v1.0/topology/hosts`, and a link appears in `/v1.0/topology/links`.
Discovery sets both `isUp` and `isEnabled` to `true` unconditionally for everything reported
(`TopologyAndFlowMonitor::updateSwitches` / `updateHosts` / `updateLinks`; none of the three has
any path that sets either flag false).
Separately, `pingWorker` runs `ovs-vsctl list-br` once a second and calls `setVertexUp`/`setVertexDown`
for OVS bridges it finds or misses.

**P4 mode (bmv2).** There is no Ryu and no `ovs-vsctl`. The proxy serves Ryu-shaped topology
endpoints (`/v1.0/topology/switches`, `/hosts`, `/links`) so the kernel polls them unchanged,
and discovery marks everything `isUp = true` the same way it does in OVS mode.

Real liveness comes from a *separate* polling path: the kernel’s ping worker calls
`GET /p4/switch_state` on the proxy once a second. The proxy returns evidence, not a verdict —
for each switch it reports:

- `probe_ok`: `true`/`false`/`null` — outcome of the most recent GetForwardingPipelineConfig
  RPC. `null` means no probe has completed yet.
- `probe_age_s`: seconds since that probe; `null` when never probed.
- `last_lldp_age_s`: seconds since the last LLDP beacon arrived from this switch; `null` when none.
- `last_packet_in_age_s`, `stream_alive`, `grpc_addr`.

The kernel’s `p4LivenessFor()` (declared in `DeviceConfigurationAndPowerManager.hpp`, defined in
the matching `.cpp`) applies a three-state policy. The branches are ordered, and the order matters:

| Verdict  | Condition |
| -------- | --------- |
| **Up**   | `probe_ok == true`. **Nothing else is consulted** — not `probe_age_s`, not the beacon. A completed P4Runtime round-trip is taken as proof the process is serving, however old it is |
| **Down** | `probe_ok == false`, `probe_age_s` ≤ 15 s (or absent), and no fresh LLDP beacon (age > 12 s) |
| **Unknown** | Everything else: no payload at all, no entry for this dpid, `probe_ok` is `null` or not a boolean, or — **on the `probe_ok == false` path only** — `probe_age_s` is stale, either age field is malformed, or the failed probe and a fresh beacon disagree |

🔴 **One exception to the Up row, added 2026-09-04.** For a switch with a standing commanded
power-off (`admin_state: "off"`), an **Up** is downgraded to **Unknown** when the probe behind it
was taken *before* the kill — dated from the same `probe_age_s` the Down row uses. The proxy
caches `probe_ok` and a kill does not invalidate the cache, so the first Up after every kill was
routinely a reading of the past: measured on the live 10-switch bmv2 fabric, 18 of 18 trials put
`is_up` back to true within 0.3–1.5 s of the kill and held it for 8–13 s. Unknown is not written
to the graph, so the vertex keeps what it had. A switch nobody has commanded off is untouched by
this, and so is a **Down** verdict — the rule exists to stop a stale reading *lifting* a switch,
not to stop the twin noticing a dead one. `DeviceConfigurationAndPowerManager::p4VerdictFor`.

⚠️ The staleness rule applies to *failures*, not to successes. A proxy poller that stalls after a
successful probe keeps reporting **Up** indefinitely; only a stalled poller whose last probe
*failed* degrades to Unknown. This is deliberate — a stale success is the branch that keeps the
readopt residual described in `doc/2026-08-11_phase7_power_mechanism_design.md` visible — but it is the
opposite of what an “Up means fresh” reading would predict.

**But a hung *switch* does not produce a stale success, because the probe has its own deadline.**
`LIVENESS_PROBE_TIMEOUT_S = 1.5 s` against `LIVENESS_PROBE_INTERVAL_S = 2.0 s`
(`p4_proxy/proxy_agent/topology_manager.py`) — the deadline sits below the interval precisely so
one unresponsive switch cannot make the poller fall behind on the other nine. A switch that stops
answering therefore yields `DEADLINE_EXCEEDED`, which is `probe_ok == false`, not an old `true`.

Measured 2026-08-18 (`27dc65d`), SIGSTOP on one `simple_switch_grpc`, `/proc` state asserted `T`
throughout:

| t | `probe_ok` | `probe_detail` | kernel verdict |
|---|---|---|---|
| +3 s | `true` | answered GetForwardingPipelineConfig | Up (probe had not yet been due) |
| +10 s | **`false`** | `DEADLINE_EXCEEDED` | **Down**, `edges_up 32/40` |
| +20 / +35 / +50 s | `false` | `DEADLINE_EXCEEDED` | Down, unchanged |

So the state the warning above describes needs **the proxy's own poller** to stall — the process
holding the loop — and not the switch it is polling. Two independent reviewers reading only the
table above concluded a frozen switch would be pinned Up forever, which is why this paragraph
exists: the policy was documented and the deadline that bounds it was not.

Note also that `stream_alive` stayed `true` for the whole 50 s while the switch was frozen. It is
a real signal and a misleading one; `p4LivenessFor()` correctly does not consult it.

**Unknown deliberately leaves the graph alone.** The caller `pingWorker` sets `isUp` only on
Up and Down; on Unknown it writes nothing, so the graph keeps its previous state. Conflating
Unknown with Down would take the whole fabric down whenever the proxy is unreachable — the
same mistake that a single failed `ovs-vsctl` call used to make on the OVS side.

The proxy also emits `links` in the same response — the link watchdog’s state, assembled by
`TopologyManager.switch_liveness()` from `link_liveness()` in
`p4_proxy/proxy_agent/topology_manager.py` — but the kernel reads only the `"switches"` key.

At the edge between the switch and host, the dpid and interface on the host side are set to 0.

**Note:** `left_link_bandwidth_source` says where that edge's `left_link_bandwidth_bps` came
from, and a client that treats the headroom figure as an observation **must read it**:

| value | meaning |
|---|---|
| `"measured"` | telemetry produced the figure (an sFlow flow sample under Mininet, an interface counter sample on the testbed) |
| `"declared"` | nothing has been observed on this link yet; the figure is the topology file's `link_bandwidth_bps` |
| `"unknown"` | neither — the edge carries no capacity information at all |

Under Mininet only flow samples drive the update, so **a link that never carries traffic stays
`"declared"` indefinitely**. Before this field existed such a link published a hardcoded
1 Gbit/s, which happened to be right for the access links and wrong by 10× for the core links,
with nothing in the response to tell the two apart. `"declared"` is not a weaker `"measured"`:
Mininet does not enforce link speeds above 1 Gbit/s, so a declared 10 Gbit/s core link has no
shaper behind it and its real ceiling is the software forwarding rate, not the declared speed.

The first two rows and the last two are the same addresses in two encodings — this endpoint

comparison silently never matches:

```python
import socket, struct
def to_dotted(n):            # n is one element of a §3 node/edge `ip` array
    return socket.inet_ntoa(struct.pack("<I", n))

to_dotted(192653504)         # '192.168.123.11'   (switch s1)
to_dotted(16777226)          # '10.0.0.1'         (host h1)
```

⚠️ **Getting this wrong raises no exception.** `str(node["ip"][0])` yields `"192653504"` — a
perfectly good string that will simply never equal the `"10.0.0.1"` that §22 returns, so the bug
shows up as an app that quietly matches nothing.

### Description

**Note:** For ICMP packets, the src_port field represents the ICMP type, and the dst_port field represents the ICMP code.

**Note:** `src_ip`/`dst_ip` are 32-bit integers holding the address in **network byte order** —

🔴 **Corrected 2026-09-06.** A sentence that stood here until this date claimed the node `ip`
array of §3 was dotted-quad text needing no conversion. **It is not** — it carries the same
network-byte-order integers described above. The fields that really are dotted-quad strings are

**Note (2026-09-02, KNOWN-ISSUES B-x): "active" is now enforced, and it used not to be.**
The kernel retains a flow for **15 s** (`FLOW_IDLE_TIMEOUT`) after its last sample, so that a flow
which starts and ends between two polls is still visible. The retention is unchanged. What changed
is that this endpoint no longer presents the retained tail as if it were live traffic: **by default
it returns only flows sampled within the last 3 s** (`kFlowActiveWindowMs`).

Measured before the change, at a churn working point of 1.6 new flows/s: mean 4.7 flows were
actually sending while this endpoint listed mean 63.0 -- a factor of 13.3, so ~92% of the list had
already ended, with no field on any record saying so. That figure is a reading at one working
point, not a constant. The model is `1 + 15 s x new-flow-rate / mean-concurrency`, which
approaches 1 for long-lived flows and diverges under churn.

Every record now carries three fields regardless of the filter:

| field | meaning |
|---|---|
| `liveness` | `"active"` (sampled < 3 s ago), `"idle"` (no recent sample, still retained), `"ended"` (past the 15 s timeout, awaiting the next purge sweep) |
| `last_seen_ms` | epoch **milliseconds** of the most recent sample -- the machine-readable form of `latest_sampled_time` |
| `ended_at_ms` | epoch milliseconds at which this record becomes eligible for removal, i.e. `last_seen_ms + 15000` |

⚠️ `liveness` is a statement about **observation**, not about the world: `active` means a
sample reached the collector within the window. At a low sFlow sampling rate a genuinely sending
flow can miss it, so the error direction is pessimistic (a live flow reported `idle`) rather than
optimistic.

**A fourth per-record field, `telemetry_health`, is also emitted and was undocumented until
2026-09-06.** It is an object describing the collector's own state for the window this record was
computed in — observed keys: `status`, `window_seconds`, `samples_in_window`, `offered_in_window`,
`dropped_in_window`, `loss_fraction`, `rx_total`, `addressed_total`, `app_drop_total`,
`app_drops_in_window`, `sock_ovfl_total`, `socket_drops_in_window`. A healthy window reads
`"status": "ok"` with `"loss_fraction": 0.0`. 🟠 **The key list is a verbatim capture from one
round** (kernel `4c9e0be1`, 2026-09-05,

#### How much traffic a flow needs before the default view sees it — **the unit is packets, not bits**

[Co-developed with claude code -- Adam] Measured 2026-09-03. **A flow that is delivered in full
can be absent from the default view.** The boundary is a *packet* rate. Quoting it in Mbit/s
without the frame size is not transferable: at a fixed 1 Mbit/s, shrinking the frame from 1400 B
to 100 B (14x the packets) moved the 2 s edge count from 0.70 to 1.00 while the offered bandwidth
never changed.

One flow per cell, **0% loss on the wire in every cell** (iperf3's own sender line), 1400-byte
frames, 3 sampling hops, sFlow 1/256. Each figure is how many of 30 one-second polls saw the flow.

| offered @1400 B | pps | *(default)* | `?liveness=all` | `get_num_of_flows_passing_a_switch` |
|---|---:|---:|---:|---:|
| 20 Mbit/s | 1786 | 30/30 | 30/30 | 30/30 |
| 5 Mbit/s | 446 | 30/30 | 30/30 | 30/30 |
| 2 Mbit/s | 179 | 30/30 | 30/30 | 21/30 |
| 1 Mbit/s | 89 | 26/30 | 30/30 | 17/30 |
| 500 kbit/s | 45 | 21/30 | 30/30 | 11/30 |
| 250 kbit/s | 22 | **16/30** | 30/30 | 6/30 |
| 125 kbit/s | 11 | 12/30 | 30/30 | 4/30 |
| 60 kbit/s | 5 | 9/30 | 28/30 | 2/30 |
| 30 kbit/s | 3 | 3/30 | 13/30 | 0/30 |
| 15 kbit/s | 1 | 3/30 | 20/30 | 2/30 |

* **~89 pps** — the default view starts missing polls.
* **~22 pps** — the default view misses **more than half** of one-second polls, while
  `?liveness=all` still returns the flow 30/30. This is the number to design against.
* **~5 pps** — the 15 s retained table starts missing it too; below ~3 pps all three converge on
  "absent". (The 1 pps row reads higher than the 3 pps row on `all`: at that sample rate 30 polls
  is Poisson noise. Do not read a trend into the bottom two rows.)
* `?liveness=retained` was **not** measured. By construction it sits between the two: it returns
  everything `all` does except records already past the 15 s timeout.

The three columns are three different windows, which is why they disagree: the default is
`kFlowActiveWindowMs` (3 s since the last sample), `?liveness=all` is the whole retained table
(`FLOW_IDLE_TIMEOUT`, 15 s), and `get_num_of_flows_passing_a_switch` counts each edge's flow set,
whose entries are expired **2 s** after that edge's last sample — so it is the narrowest of the
three and drops out first.

🔴 **Do not read absence from the default view as "the flow stopped".** For a consumer that infers
idleness in order to act on it (powering a switch down, declaring a path unused), use
`?liveness=all` and the `last_seen_ms` field, or require several consecutive polls.

Controls for the above: 12 quiet cells, one immediately before each load cell with the same
command and no traffic, read 0/8 on all three windows in 12 of 12; a decoy flow key that was never
sent read absent in 100% of 456 polls while the real flow read present. The 1 Mbit/s cell was run

> **Note on the flow-entry endpoints (9, 10, 11 and 23).**
> These enqueue work onto an asynchronous, per-switch dispatcher and return as soon as the
> entries are accepted, before any request reaches the controller. A `200` with
> `"status": "queued"` therefore means *accepted for programming*, not *programmed*.
> Per-entry outcomes -- including a rejected rule or an unreachable controller -- are logged
> with the dpid and the controller's reply. Earlier versions answered
> `"Flow installed"` regardless of what happened, which made a failure
> indistinguishable from a success.

<a id="unknown-dpid-contract"></a>
> **Unknown-dpid contract for the flow-entry endpoints (9, 10, 11 and 23).**
> All four share one code path (`HttpSession::processFlowBatch`), so all four answer the same way.
> Before anything is enqueued, the batch is partitioned into entries whose `dpid` names a switch in
> the loaded topology and entries whose `dpid` does not.
>
> **Every entry unknown → `404 Not Found`, nothing is enqueued.** The body names the offenders in
> `unknown_dpids`:
>
> ```json
> {
>   "status": "error",
>   "error": "unknown dpid",
>   "unknown_dpids": [999999999999],
>   "detail": "these dpids are not switches in the loaded topology; check the dpid, or that the topology file matches the running network"
> }
> ```
>
> **Some entries known → `200 OK`, the known ones are enqueued and the rest are dropped.** The
> success body then carries two *extra* fields, `rejected` (a count) and `rejected_dpids`:
>
> ```json
> {
>   "status": "queued",
>   "accepted": 1,
>   "rejected": 1,
>   "rejected_dpids": [999999999999],
>   "detail": "some entries were dropped because their dpid is not a switch in the loaded topology; the rest were accepted for programming, and per-entry outcomes are reported in the kernel log, not in this response"
> }
> ```
>
> ⚠️ **`rejected`/`rejected_dpids` are present only when something was dropped**, so a client may
> treat their absence as "all of it was taken" — but a client that reads only the status code will
> see `200` and miss the partial acceptance entirely. Check for the keys.
>
> The `404` is a refusal, not an outage: it means the request named no switch this kernel knows
> about. Retrying it unchanged will always produce the same answer.
> Worked examples with live responses are in
> [`doc/audit/2026-08-09_integration-runbook.md`](audit/2026-08-09_integration-runbook.md).

## 24. GET /ndt/get_average_link_usage
### Description
Returns the average link utilization across all **usable** inter-switch links (host-facing links
are excluded). Only links with non-zero `link_bandwidth_usage_bps` are included in the average.

"Usable" is the full `isUsable(edge)` intersection — `isUp && isEnabled && !adminDisabled` — not

<a id="avg-link-usage-unit"></a>
🔴 **Unit: `avg_link_usage` is a 0–1 fraction, not a percentage — stated 2026-09-06.** A fully
loaded fabric reads `1.0`; the `0.12` in the example below means **12%**. **This is not the unit
§3 uses for the same quantity per link:** `link_bandwidth_utilization_percent` there is 0–100. The
two are exactly 100× apart —

```
avg_link_usage == mean(link_bandwidth_utilization_percent) / 100
```

over the usable inter-switch links with non-zero usage. Measured three times in a row on kernel
`4c9e0be1` (2026-09-05, OVS plane, `scratch/overnight-2026-09-05/logs/r6-27-avg-unit.log`), it
agreed to six decimal places every time:

| trial | `avg_link_usage` | `mean(link_bandwidth_utilization_percent)` | links in the mean |
|---|---|---|---|
| 0 | `0.2687655578083333` | `26.876556` | 12 |
| 1 | `0.23094866429230768` | `23.094866` | 13 |
| 2 | `0.31960428104000005` | `31.960428` | 10 |

**never fires** — there is no field in the body and there was no line in this manual to say why.
Nothing about the value changed on 2026-09-06; only this paragraph was added. The per-link unit is
stated at [§3](#utilization-units).

⚠️ Note also the denominators differ: this endpoint averages only links whose

## 27. POST /ndt/acquire_lock
### Description
Acquires a global lock (typed lock) to prevent application conflicts (mutual exclusion).

**`type` is required.** There is no default. Until 2026-08-30 a missing, malformed or unknown
`type` silently acquired `routing_lock` — the lock nominally responsible for serialising writes
to real switches — and answered `200 {"status":"locked","type":"routing_lock"}`, so a caller
could hold that lock without ever having named it. All three now return `400` and acquire nothing.

⚠️ **This lock is advisory, not enforced.** Nothing in the write paths queries it: none of
`install_flow_entry`, `delete_flow_entry`, `modify_flow_entry`, the batch flow endpoint, the
group/meter endpoints, or `set_switches_power_state` call into `LockManager`. The only code that
does is this endpoint and §29's `/ndt/release_lock`, both in `HttpSession.cpp` —
`grep -rn 'acquireLock\|->release(' src/ include/` finds nothing outside those two call sites and
`LockManager.hpp`/`.cpp` themselves. Holding `routing_lock` stops nothing on its own: a second
caller that never acquires it, or that acquires it and ignores a `423`, writes through unimpeded,
and the kernel neither blocks nor records it. Coordination between well-behaved callers that all
acquire before writing is real — that is what makes the lock useful today — but nothing here
would notice, or stop, a caller that does not.

* Body Parameters:

| Field       | Type   | Description                                                             |
| ----------- | ------ | ----------------------------------------------------------------------- |
| `type` | `string` | **Required.** Lock category, one of `routing_lock`, `graph_lock`, `power_lock`. Absent, non-string, or any other value → `400`, and no lock is touched. |
| `ttl`   | `int` | Optional, defaults to `5`. Lock time-to-live in seconds. A `ttl` that is absent or not an integer falls back to the default — unlike `type`, a duration cannot make the request act on something other than what it named. |

**`ttl: 0` and negative values are accepted, and both mean "already expired," not "unlimited."**
`LockManager` compares `now < expiryTime` with `expiryTime = now + seconds(ttl)`, so `ttl: 0`
never holds anyone off — a second `acquire_lock` on the same type succeeds immediately — and a
negative `ttl` puts `expiryTime` in the past the same way (chosen deliberately over the
alternative unsigned-conversion reading, which would produce a lock lasting several million
centuries). Pinned by `tests/test_LockManager.cpp`'s `AZeroTtlLockIsAlreadyExpiredWhenTheNextCallerAsks`
and `ANegativeTtlIsTreatedAsAlreadyExpiredRatherThanAsForever` (lines 178-200). A caller that reads
`ttl: 0` as "hold indefinitely" — a common reading elsewhere — gets the opposite: an acquire that
reports `200 {"status":"locked",...}` and excludes nobody.


### Request
* Method: **POST**
* Content-Type: **application/json**
* Body
```json
{
  "type": "routing_lock",
  "ttl": 30
}
```

### Response
#### Success
* Status: **200 OK**
```json
{
  "status": "locked",
  "type": "routing_lock",
  "ttl": 30,
  "lease": 41,
  "reclaimed_expired_lease": false
}
```

**`lease`** (added 2026-09-02) identifies *this* lease. It is never reused. Pass it back as
`lease` on `/ndt/release_lock` and `/ndt/renew_lock` and the kernel will refuse — rather than act
— if the lock has since moved on to a different lease. Callers that omit it get the pre-2026-09-02
behaviour, which is that the kernel cannot tell one caller from another; see §29.

**`reclaimed_expired_lease`** is `true` when this acquire took over a lease whose holder let it
run out without releasing. It is not an error — that is what a TTL is for — but it means the
previous holder is gone or wedged, and it is worth logging. The kernel also emits one
`WARNING` per reclaim naming the lock and the dead lease.

#### Error
Returned when the body is absent, is not valid JSON, has no `type`, has a non-string `type`, or

Busy — and *only* busy. The type was valid and the lock is held by someone else, so retrying


## 29. POST /ndt/release_lock
### Description
Releases a previously acquired lock, allowing other applications to proceed.

**`type` is required.** This section previously documented the body as optional, with a missing
or malformed body releasing `routing_lock`. That default was removed on 2026-08-30: an
application holding `power_lock` that released without a body released *another application's*
`routing_lock` — the lock nominally responsible for serialising writes to real switches (it is
advisory only; see §27) — was answered
`200 {"status":"released","type":"routing_lock"}` naming a lock it had never mentioned, and still
held its own `power_lock`. No caller was using the default; all senders in this workspace pass an
explicit `type`.

### Request
* Method: **POST**
* Content-Type: **application/json**
* Body (**required**; `type` must be present)
```json
{
  "type": "routing_lock"
}
```

### Response
#### Success
* Status: **200 OK**
```json
{
  "status": "released",
  "type": "routing_lock",
  "lease": 41
}
```
`lease` (added 2026-09-02) names the lease this request actually released. Compare it with the
`lease` your own `acquire_lock` returned: if they differ, **you have just released somebody
else's lock** — see the ⚠️ note at the end of this section. Until every caller sends a `lease`,
this is the only way to find that out.

#### Error
Returned when the body is absent, is not valid JSON, has no `type`, has a non-string `type`, or
names a lock that does not exist. **No lock is released in any of these cases.**

`reason: "lease_required"` is returned only by a kernel configured with
`LockManager::setRequireLeaseId(true)`, which no build does today. It means the lock is held and
the request named no `lease`, so the kernel could not tell this caller from any other and refused
rather than acting.
```json
{
  "error": "Invalid lock request",
  "reason": "lease_required",
  "detail": "this kernel requires a \"lease\" on release; lock 'routing_lock' is held and the request named no lease, so it could not be attributed to a holder. Nothing was released"
}
```
* Status: **400 Bad Request**
```json
{
  "error": "Invalid lock request",
  "detail": "unknown lock type \"alpha\"; expected one of routing_lock, graph_lock, power_lock"
}
```
Not held, or expired. A *state*, kept apart from `400` for the same reason as in §28.

🔴 **`reason: "expired"` is new on 2026-09-02 and it used to be a `200`.** Until then, a release
that arrived after its own lease had run out was answered
`200 {"status":"released","type":"..."}` — byte-identical to a release that actually released
something — because expiry never cleared the held flag. A caller could not tell "I released it"
from "it was taken off me while I was working". It now answers `412` and says which.
* Status: **412 Precondition Failed**
```json
{
  "error": "Release failed",
  "reason": "expired",
  "detail": "Lock 'routing_lock' had a lease that already ran out; it was reclaimed by expiry, not released by this request"
}
```
```json
{
  "error": "Release failed",
  "reason": "not_held",
  "detail": "Lock 'routing_lock' is not held"
}
```
Lease mismatch — only reachable if the request carried a `lease`. The lock is held, on a lease
that is not the one named, and **it was not released**. Refusing is the point: releasing here
would free a lock the caller does not hold.
* Status: **409 Conflict**
```json
{
  "error": "Release failed",
  "reason": "lease_mismatch",
  "detail": "Lock 'routing_lock' is no longer on lease 41; it was NOT released"
}
```
Returned when the handler itself throws.
* Status: **500 Internal Server Error**
```json
{
  "error": "Release lock failed"
}
```

> ⚠️ **A caller that sends no `lease` can still release any other caller's lock.**
> `LockManager` has no owner token: the locks are keyed by type and guarded by a TTL, and nothing
> ties a lock to whoever took it. `release_lock` naming a held lock therefore succeeds no matter
> which application sends it. The `400`/`412` split above only guarantees that a request acts on
> the lock it *named* — not that the caller was entitled to it. Tracked in
> `doc/2026-07-28_test_coverage_gaps.md` §1.1.
>
> **Partial mitigation, 2026-09-02, opt-in:** pass the `lease` value from your own
> `acquire_lock` reply and a release naming a superseded lease is refused with `409` instead of
> freeing the current holder's lock. This is opt-in on purpose — two requests from two different
> applications are otherwise the same bytes, and the kernel has nothing to distinguish them by.
> **No caller in this workspace sends `lease` yet, so the hole above is still open in practice.**
>
> **How it gets closed:** the kernel already has the switch —
> `LockManager::setRequireLeaseId(true)` makes `lease` mandatory on release and renew, answering
> `400 reason:"lease_required"` to a request that names none. **Nothing calls it**, because
> turning it on refuses every release sent by Energy-Saving-App, Traffic-Engineering-App, the
> chaos harness and the contract suite. The order is: apps start sending `lease` → the
> `unattributedActions` counter on each lock reaches zero → flip the switch. The counter exists
> so that the middle step is a measurement rather than a guess.
>
> Two earlier warnings in this section have been overtaken by fixes and are recorded here so the
> history is not read as still-current: that release answered `200` unconditionally (fixed by the
> commit that made `unlock` return `bool` and added the `412` above), and that a malformed or
> absent body released `routing_lock` (fixed on 2026-08-30 by the shared parser).
> `tools/contract_test/README.md` still describes the first of these as an open `known_gap`; the
> marker was already removed from `spec.py` and that README paragraph is stale.

### Description
Returns detailed information about the Top-K active flows observed by the network system (sFlow), including their estimated sending rates, timestamps, protocol type, and the full path taken across the network.

The returned list is sorted in descending order by:
`estimated_packet_rate_in_the_proceeding_1sec_timeslot`.

**Note (2026-09-02, KNOWN-ISSUES B-x):** this endpoint takes the same optional **`liveness`**
parameter as §4, with the same default (`active` only) and the same three fields on every record
(`liveness`, `last_seen_ms`, `ended_at_ms`). See §4 for the values and for what changed.

The filter is applied **before** the sort and before the top-K truncation, so `k` still means "the
K busiest matching flows" rather than "whatever survives a filter applied to K arbitrary rows".
This matters more here than on §4: with the default `k = 50` at the measured churn working point,
roughly 45 of the 50 returned rows were flows that had already ended, and a median of 4 of the top
10 were. They were not outranking live flows — their sort key is 0 — they were filling the list
from the bottom, because fewer than ten flows were alive at once.

**Note:** because the default population is the same, **the low-packet-rate blind spot measured in
§4 applies to this endpoint unchanged**: a fully delivered flow below roughly 22 pps is absent
from more than half of one-second polls in the default view, while `?liveness=all` still returns
it. The boundary is a packet rate, not a bit rate. See §4 for the table and the frame-size
dependence. [Co-developed with claude code -- Adam]

**Note:** For ICMP packets, the src_port field represents the ICMP type, and the dst_port field represents the ICMP code.

**Note:** `src_ip`/`dst_ip` are 32-bit integers holding the address in **network byte order** —
the same value as `struct in_addr::s_addr`, which is what the kernel stores and serialises directly.

Do **not** read the decimal digits as a host-order integer. `16777226` is `10.0.0.1`, not
`1.0.0.10`: its bytes are `0A 00 00 01`, which is the address in order. Convert with `ntohl()`
before formatting (portable, and a no-op on a big-endian host), or read the four bytes in
little-endian order. The host-order integer for `10.0.0.1` would be `167772161`.

🔴 **Corrected 2026-09-06.** A sentence that stood here until this date claimed the node `ip`
array of §3 was dotted-quad text needing no conversion. **It is not** — it carries the same
network-byte-order integers described above. The fields that really are dotted-quad strings are
§22 `get_path_switch_count` and §38 `get_static_topology_json`. Full table and a conversion
snippet: [the IP-encoding table in §3](#ip-encoding).

<a id="path-node-types"></a>
**Reading `path[].node`: the first and last entries are hosts, everything between them is a
switch — documented 2026-09-06.** A `path` array mixes two kinds of identifier and the value
alone does not tell you which is which:

| position | `node` is | `interface` is |
|---|---|---|
| **first** element | the **source host's** IP, as a network-byte-order integer — the same value as this record's `src_ip` | the port on the *first switch* the packet enters through |
| **middle** elements | a **switch dpid** | that switch's egress port for this flow |
| **last** element | the **destination host's** IP, again equal to this record's `dst_ip` | `0` — the host side of a switch-host edge carries dpid 0 and interface 0, as §3 states |

**Check it against the record rather than guessing from the number**: `path[0].node == src_ip` and
`path[-1].node == dst_ip` always hold, which is the reliable discriminator. Magnitude is **not** —
on a small fabric a dpid is a small integer, so `1` is a valid dpid *and* a valid reading of
`1.0.0.0`. Both worked examples below satisfy the rule, as does a live capture on the OVS
10-switch plane (kernel `4c9e0be1`, 2026-09-05,
`scratch/overnight-2026-09-05/logs/r6-14-topk.json`, 2 records, both directions):

### Request

* Method: **POST**
* Content-Type: **application/json**
* Body

The body must include a `"dpid"` field identifying the target switch. All other fields are
those the Ryu `/stats/groupentry/add` route accepts. The kernel does not inspect them.

```json
{
  "dpid": 106225808380928,
  "type": "ALL",
  "group_id": 1,
  "buckets": [
    {
      "actions": [
        {"type": "OUTPUT", "port": 1}
      ]
    },
    {
      "actions": [
        {"type": "OUTPUT", "port": 2}
      ]
    }
  ]
}
```

### Response

#### Success

* Status: **200 OK**

```json
{
  "status": "Group entry installed",
  "outcome": "installed"
}
```

(The shape above is derived from `respondToOpResult` at `HttpSession.cpp` lines 686-727
with `successMessage = "Group entry installed"`. A real 200 from Ryu passes through as-is;
the success body is the kernel’s own acknowledgment, not Ryu’s.)

**`outcome`** — added by F-13. `status` is unchanged and still says what the kernel was asked
to do; `outcome` says what is known to have happened, because Ryu answers 200 as soon as it has
*forwarded* an OpenFlow `*_MOD` to the switch, before the switch has adjudicated it.

| `outcome` | Meaning |
|---|---|
| `installed` / `modified` / `deleted` | The kernel read the switch's group/meter table before the request AND after it, and the table afterwards is what the verb asked for: the entry is there for an install or a modify, and gone for a delete. |
| `unverified` | The request was forwarded, but the kernel could not read the table (controller unreachable, unrecognised reply, or a non-numeric `group_id`/`meter_id` such as `"ALL"`). **This is not a claim that the entry changed.** |
| `absent` | **502.** The install or the modify was forwarded and acknowledged, and the entry is *not* on the switch afterwards — the switch did not take it. (Added 2026-09-04, FINDINGS #87.) |
| `still_present` | **502.** The delete was forwarded and acknowledged, and the entry is *still* on the switch — it was not deleted. |

🔴 **What the read-back after a `modify` does and does not establish.** The check asks whether
the `group_id` / `meter_id` is present in `/stats/groupdesc` / `/stats/meterconfig`. It does
**not** compare buckets or bands. So `"outcome": "modified"` means *the entry still exists after
the modify was forwarded*; it does **not** mean the switch adopted the new definition. A modify
that the switch silently declined while keeping the old entry answers `modified`. If you need
that stronger claim, read the entry back yourself and compare it — the kernel does not, and the
wording here is deliberately no stronger than the evidence.

`installed` and `deleted` do not have that gap: for those two, the presence check is exactly the
question being asked.

The field is present only when the layer below had something to say. A failure that carries no
outcome — an unreachable controller, for instance — answers the same three-key body it always
did, so a strict client counting fields is unaffected on those paths.

#### Error

* Status: **400 Bad Request** – body has no `"dpid"`, or `"dpid"` is unreadable.
  `outcome` is `no_dpid` or `bad_dpid`.

* Status: **404 Not Found** – the named group/meter is not on that switch, so `MODIFY` would be
  rejected by the switch (`OFPGMFC_UNKNOWN_GROUP` / `OFPMMFC_UNKNOWN_METER`) and `DELETE` would
  be a silent no-op. `outcome` is `no_such_group` / `no_such_meter`. **Added by F-13**: these
  requests previously answered 200 with the success sentence and changed nothing.

```json
{
  "status": "error",
  "error": "no such group 9 on dpid 1; nothing was deleted",
  "controller_status": 404,
  "outcome": "no_such_group"
}
```

* Status: **409 Conflict** – `install` only: the id is already in use, so the switch would answer
  `OFPGMFC_GROUP_EXISTS` / `OFPMMFC_METER_EXISTS` and keep the entry it already has. `outcome` is
  `no_change_group_exists` / `no_change_meter_exists`. **Added by F-13**: this too previously
  answered 200 "installed" while the entry carrying the traffic remained somebody else's.

```json
{
  "status": "error",
  "error": "install group entry requires a dpid",
  "controller_status": 400
}
```

* Status: **404 Not Found** – the dpid is not a switch in the loaded topology. ⚠️ **This
  endpoint answers 404 for two different reasons**; `outcome` is what tells them apart —
  `no_such_switch` here, `no_such_group`/`no_such_meter` for the entry-level 404 above.

```json
{
  "status": "error",
  "error": "no routing strategy for dpid <n>",
  "controller_status": 404,
  "outcome": "no_such_switch"
}
```

* Status: **501 Not Implemented** – P4 mode only. All six group/meter operations return
this on a bmv2 data plane. `outcome` is `unsupported_on_p4`.

```json
{
  "status": "error",
  "error": "group entry install is not supported on a P4/bmv2 data plane: …",
  "controller_status": 501,
  "outcome": "unsupported_on_p4"
}
```

* Status: **502 Bad Gateway** – the controller/proxy did not respond within 5 s.

```json
{
  "status": "error",
  "error": "no response from …",
  "controller_status": 0
}
```

* Any other non-2xx from the controller is passed through with its HTTP status and
`controller_status` set to that value.

* Status: **500 Internal Server Error** – unexpected runtime error.

```json
{
  "error": "Internal server error",
  "details": "<exception message>"
}
```

* Status: **500 Internal Server Error** – unknown exception.


## 42. GET /ndt/get_flow_dispatch_status

### Description

[Co-developed with claude code -- Adam]

Reports the state of the asynchronous flow-entry dispatcher — the queue that §9, §10, §11 and §23
hand their entries to and return from before anything reaches the controller.

🔴 **Added to this manual on 2026-09-06. The endpoint is older than this section.** The success
body of §9/§10/§11/§23 names it (`"... are readable afterwards from GET
/ndt/get_flow_dispatch_status"`), and until this revision the name appeared **nowhere else in this
document**. The manual instead told the reader that per-entry outcomes are "reported in the kernel
log" — advice an application running outside this process cannot act on. **This is the only
programmatic outcome channel the flow-entry endpoints have.** Read the limits below before you
build on it: they are severe.

### Request
* Method: **GET**

### Response
#### Success
* Status: **200 OK**

Verbatim from kernel `4c9e0be1`, 2026-09-05, OVS plane
(`scratch/overnight-2026-09-05/logs/r6-18-dispatch-status.json`; reformatted for reading, keys and
values unchanged):

```json
{
  "counters": {
    "dispatched": 5,
    "dropped_after_stop": 0,
    "failed": 0,
    "succeeded": 5
  },
  "counters_cover": {
    "dispatch_routes": [
      "/ndt/install_flow_entry",
      "/ndt/modify_flow_entry",
      "/ndt/delete_flow_entry",
      "/ndt/install_flow_entries_modify_flow_entries_and_delete_flow_entries"
    ],
    "includes_boot_time_programming": false,
    "includes_intent_translator": false
  },
  "dispatcher_running": true,
  "recent_failures": [],
  "recent_failures_capacity": 256,
  "recent_failures_evicted": 0
}
```

| field | meaning |
|---|---|
| `dispatcher_running` | whether the dispatcher thread is up. `false` means nothing queued afterwards will be programmed |
| `counters.dispatched` | entries taken off the queue and sent to the controller |
| `counters.succeeded` | entries the **control plane** answered affirmatively. See the two warnings below — this is not "the switch has the rule" |
| `counters.failed` | entries the control plane rejected, or that could not be sent |
| `counters.dropped_after_stop` | entries discarded because they were queued after the dispatcher stopped |
| `counters_cover.dispatch_routes` | the routes these counters cover, by name — the four flow-entry endpoints |
| `counters_cover.includes_boot_time_programming` | `false`: the rules the controller installs during bring-up are **not** counted |
| `counters_cover.includes_intent_translator` | `false`: writes originating from §41 are **not** counted |
| `recent_failures` | a ring of recent failure records; empty when nothing has failed |
| `recent_failures_capacity` | the ring's size (`256` as measured) |
| `recent_failures_evicted` | how many failure records the ring has overwritten. **Non-zero means you have lost failures** — the capacity is fixed and does not follow the size of a batch |

🟠 **Grade of that table.** The body above is measured; the *meanings* are not all of equal
standing. `counters.succeeded` is backed by the measurements in the next block, and
`counters_cover.*` restates what the body itself says. **The rows for `dropped_after_stop`,
`recent_failures`, `recent_failures_capacity` and `recent_failures_evicted` are read from the
field names** — every one of them was zero or empty throughout the 2026-09-05 round, and this
revision did not open the source to check them. Do not write an assertion against them without
exercising them first.

### Limits — read these before using it as a read-back

🔴 **1. The counters are global and carry no request id.** Nothing in the body identifies which
POST a change belongs to. They are process-wide totals over the four routes named in
`counters_cover.dispatch_routes`, so a concurrent client's write moves the same numbers, and there
is no window or reset marker in the response to bound them. Reading them before and after your own
POST is only meaningful if you are the only writer — which this API does not let you guarantee
(§27's lock is advisory and enforces nothing, as that section states). A per-request identifier is
open as work item **W11**; 🔴 **W11 is written in a nightly session's `scratch/`, which is not
under version control — ask that session for it before citing it.**

🔴 **2. `succeeded` counts dispatch, not programming — and a write that changed nothing still
counts as a success.** Two measurements on the same kernel:

- The same match installed **20 times** moved `succeeded` by **+20** while the switch gained
  **one** row; **15 deletes of a match that never existed** moved `succeeded` by a further **+15**
  with **no** change on the switch and `failed` unchanged. Raw:
  `scratch/overnight-2026-09-05/logs/r0-40-w4.log`,
  `scratch/overnight-2026-09-05/logs/r0-41-w4-vals.txt`
  (`S0=4 S1=24 S2=39 S3=40 R0=0 R1=1 R2=0 R3=0`).
- 🟠 A single delete of a match no switch carried moved `succeeded` from 12 to 13 — transcribed
  from the 2026-09-05 app-developer round (R6 K-4); **console-only, no raw file, not re-run.**

⇒ **`succeeded` cannot answer "did my rule take effect", "did my delete remove anything", or even
"was there anything to remove". §10 has no other channel that can, either.** The kernel log states
the underlying reason on the install side: the control plane "answers before the switch
adjudicates", so its acceptance is not evidence the switch programmed anything
(`doc/KNOWN-ISSUES.md` C-4). Splitting this into a second, switch-side counter is open as **W11**
(same version-control caveat as above).

**3. What it is good for.** `dispatcher_running`, a rising `failed`, and the contents of
`recent_failures` are real signals and have no substitute: they are how an app learns that its
writes are being rejected or that the queue has stopped. Treat `succeeded` as "the request left
the kernel", and confirm effect by reading the network back — with the delays in
[the section below](#closed-loop-timing).

🟠 **Not observed in the 2026-09-05 round:** a non-empty `recent_failures` (its record shape is
therefore undocumented here), any non-zero `recent_failures_evicted` or `dropped_after_stop`, and
this endpoint's error responses. The partial-batch `detail` string quoted in
[the unknown-dpid contract](#unknown-dpid-contract) was likewise not re-checked and may, like the
success strings, have moved on.

## Closed-loop apps: how long until a change is visible

[Co-developed with claude code -- Adam]

**Added 2026-09-06.** Until this revision nothing in this manual said how long it takes for a flow
write to become visible through the reading endpoints. An app that installs a rule and verifies it
on the next poll will read "it did not work", install it again, and oscillate — the failure is in
the polling interval, not in the network.

**Measured** on kernel `4c9e0be1`, 2026-09-05, OVS 10-switch / 4-host plane, one rerouting rule
(`install_flow_entry` then `delete_flow_entry` on the same match), sampled every 0.5 s with
t = 0 at the moment the POST returned 200. Raw:
`scratch/overnight-2026-09-05/logs/r6-17-install-reroute.log`,
`scratch/overnight-2026-09-05/logs/r6-25-delete-reroute.log`,
`scratch/overnight-2026-09-05/logs/r6-28-s5-withhold.log`,
`scratch/overnight-2026-09-05/logs/r6-29-s5-stale-after-delete.log`.

| what you are watching | after `install_flow_entry` | after `delete_flow_entry` |
|---|---|---|
| the switch itself — the rule is in the table (controller REST, not this API) | **0.52 s** | **0.52 s** |
| the traffic actually moves (switch port counters, not this API) | **0.52 s** | **0.52 s** |
| §3 `get_graph_data` — the new link's utilisation | **1.03 s** | **0.00 s** (the next read was already right) |
| §5 `get_switch_openflow_table_entries` — the rule listed / no longer listed | **3.66 s** | **10.12 s** |
| §30 `get_detected_top_k_flow_data` — the flow's `path` swaps to the new route | **6.14 s** | **7.19 s** |

**How to read this table.** The first two rows are the network; the last three are this API. The
data plane has finished in about half a second in both directions — **the delay is entirely in the
views**, and the views do not agree with each other for several seconds afterwards. The probe
sampled every 0.5 s, so the two `0.52 s` figures in a column are **one sample, not two independent
measurements**: all the resolution says is that the rule and the traffic had both moved by the
first sample after the POST.

* 🔴 **§5 is the worst of the three and it fails in both directions.** After an install it withholds
  the rule for ~3.3 s (deliberately — `doc/KNOWN-ISSUES.md` C-4); after a delete it keeps
  reporting a rule the switch has already dropped, for **9.61 s** (`doc/KNOWN-ISSUES.md` C-4b).
  It is the read-back this manual documents, and it is the one not to use for immediate
  verification.
* **§30's `path` is the slowest but it is the one that answers the question an app actually asks**
  — "is this flow taking the new route" — and it settles at 6–7 s.
* **§3's utilisation moves first** but says least: on a link already at its declared capacity both
  the old and the new path read `100.0`, so it can show that *something* changed and not that the
  change was the right one.

**What to do**

1. **Do not poll faster than ~15 s** when the poll is what decides whether to act again. 15 s is
   about twice the slowest kernel-side view measured here, and it is also the retention window §4
   uses. A 5 s loop — the obvious choice, and the one the numbers above were collected against —
   re-reads the old `path` after a successful reroute and mistakes it for a failed one.
2. **Verify through §30's `path`, not through §5.** If an app must confirm within a few seconds,
   §30 is the endpoint whose lag is bounded by something the app can wait out; §5's delete-side
   staleness is longer and is not signposted in its own response.
3. **Never treat a §9/§10/§11 `200` as confirmation.** It means *accepted for programming*.
   §42's counters do not close that gap either — see the limits in §42.
4. **Wait before re-issuing.** A write repeated because a stale view said it failed is not
   harmless: §10 answers 200 for a delete that matches nothing, so the second attempt looks
   exactly like the first.

⚠️ **Scope of these numbers.** One kernel build (`4c9e0be1`), one date (2026-09-05), one plane
(OVS 10-switch / 4-host under saturating iperf3 load), **n = 1 per direction for the §3 and §30
rows and n = 2 for the §5 rows** — the §5 install row was measured twice in the same round, at
3.66 s and 3.25 s after the POST. They are the right order of magnitude to design against, not
constants. Nothing here is a promised latency, and a busier fabric, a larger topology and the P4
plane were not measured at all.
